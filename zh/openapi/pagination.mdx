列表接口分页返回结果。大多数接口使用页码分页；数据量大或变化快的集合还支持游标分页。每个接口支持哪些分页参数、上限和默认值是多少，以该接口页面为准——下文给出的是常见默认值，并非对所有接口都成立。

## 页码分页

### 请求参数

| 参数 | 类型 | 描述 |
| --- | --- | --- |
| `p` | integer | 页码，从 1 开始。不传或传 `0` 视为 1。offset = (p - 1) × limit |
| `limit` | integer | 每页条数。通常最大 100、默认 20；部分接口的范围不同，见接口页面。 |

### 响应字段

| 字段 | 类型 | 描述 |
| --- | --- | --- |
| `total` | integer | 匹配条数（见[关于 total](#关于-total)） |
| `has_next_page` | boolean | 是否还有下一页 |

### 示例

<Tabs>
  <Tab title="请求示例">
```json
{
  "p": 1,
  "limit": 20
}
```
  </Tab>
  <Tab title="响应示例">
```json
{
  "total": 1000,
  "has_next_page": true,
  "items": []
}
```
  </Tab>
</Tabs>

### 深度限制

<Warning>
On-call 的列表接口要求 `p × limit` 不超过 10,000，更深的页返回 `400 InvalidParameter`。如需继续往后取，请在接口支持时改用游标分页，或收窄筛选条件（例如缩短时间范围）。
</Warning>

两次调用之间如有数据新增或删除，偏移量会随之移动，页码分页可能漏掉或重复部分数据。需要完整、稳定地导出时请使用游标分页。

## 游标分页

把上一次响应中的 `search_after_ctx` 传回即可获取下一页。游标是不透明的：不要自行构造或修改，翻页过程中其他请求参数保持不变。传了 `search_after_ctx` 时 `p` 会被忽略。

在查询故障列表和查询告警列表上，可以先用页码分页、随时切换为游标分页：每个非空页都会同时返回 `search_after_ctx`，即该页最后一条之后的游标。

### 请求参数

| 参数 | 类型 | 描述 |
| --- | --- | --- |
| `search_after_ctx` | string | 上一次响应返回的游标，首页不传。 |
| `limit` | integer | 每页条数，范围见接口页面。 |

### 响应字段

| 字段 | 类型 | 描述 |
| --- | --- | --- |
| `has_next_page` | boolean | 是否还有下一页 |
| `search_after_ctx` | string | 下一页的游标。游标模式下仅当 `has_next_page` 为 `true` 时返回。 |

### 示例

<Tabs>
  <Tab title="请求示例">
```json
{
  "search_after_ctx": "658bcbae6ab5a67b3b800230",
  "limit": 20
}
```
  </Tab>
  <Tab title="响应示例">
```json
{
  "total": 1000,
  "has_next_page": true,
  "search_after_ctx": "658ba7f9566077d6090e8d51",
  "items": []
}
```
  </Tab>
</Tabs>

## 关于 total

`total` 不总是精确值。为保证大查询的响应速度，故障、告警、告警事件、复盘报告和映射数据相关的列表最多计数到 1,000：

<Warning>
- 匹配数据少于 1,000 条时，`total` 是精确值。
- 匹配数据达到或超过 1,000 条时，`total` 固定为 1,000，表示"1,000 条及以上"。
</Warning>

<Tip>
请用 `has_next_page` 而不是 `total` 判断是否还有下一页：`has_next_page` 不依赖 `total`，超过 1,000 条后仍然准确。
</Tip>
