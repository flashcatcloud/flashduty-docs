## 上线前准备

在创建或迁移前，建议先确认以下信息。准备越充分，状态页上线后的调整成本越低。

| 准备项 | 说明 | 相关文档 |
| --- | --- | --- |
| 状态页类型 | 公开状态页面向客户和合作伙伴；内部状态页面向组织成员 | [什么是状态页](/zh/on-call/statuspage/statuspage) |
| 管理权限 | 确认谁可以管理状态页、发布事件、管理订阅者 | [权限设计](/zh/platform/permission-design) |
| 品牌素材 | 准备 Logo、暗色 Logo、Favicon、页头、页脚、联系方式和自定义链接 | [创建与管理状态页](/zh/on-call/statuspage/create-manage-page) |
| 自定义域名 | 如果要使用 `status.example.com`，提前确认 DNS 管理人和 CNAME 切换窗口 | [创建与管理状态页](/zh/on-call/statuspage/create-manage-page) |
| 服务结构 | 梳理要展示的产品、区域、模块、依赖服务和可见性要求 | [组件与分组管理](/zh/on-call/statuspage/components-sections) |
| 订阅策略 | 确认是否开放邮件、RSS/Atom 或内部 IM 订阅，以及是否需要导入订阅者 | [订阅管理](/zh/on-call/statuspage/subscriptions) |
| 沟通模板 | 准备故障、维护、恢复、进展更新等标准话术 | [事件模板](/zh/on-call/statuspage/templates) |

<Note>
公开状态页和内部状态页的访问方式、订阅方式和版本要求不同。正式上线前，请先确认当前订阅版本是否满足页面数量和内部状态页需求。详见[版本与价格](/zh/platform/pricing)。
</Note>

## 从零开始上线

如果你的团队还没有正式状态页，建议按以下顺序完成首个页面上线。

<Steps>
  <Step title="确认状态页类型">
    选择创建公开状态页或内部状态页。公开状态页适合向客户、合作伙伴公开服务状态；内部状态页适合让销售、客服、管理层和内部团队统一查看系统状态。

    如果你不确定两者区别，阅读[什么是状态页](/zh/on-call/statuspage/statuspage)中的状态页类型说明。
  </Step>

  <Step title="创建状态页并配置基础信息">
    在 Flashduty 控制台创建状态页，填写名称、URL 标识和类型。创建后配置品牌信息、页面内容、显示设置和订阅开关。

    详细步骤见[创建与管理状态页](/zh/on-call/statuspage/create-manage-page)。
  </Step>

  <Step title="配置自定义域名">
    如果你希望用户访问 `status.example.com` 这类公司自有域名，为目标域名添加 CNAME 记录，并在状态页设置中完成域名配置。

    域名切换通常涉及 DNS 管理权限，建议在正式公开前完成验证。详细配置见[创建与管理状态页](/zh/on-call/statuspage/create-manage-page)。
  </Step>

  <Step title="设计组件和分组">
    将要对外或对内展示的服务拆成组件，并按产品线、区域、服务层级或业务模块分组。只展示读者真正需要感知的服务，不必把内部技术依赖全部暴露出来。

    建模建议见[组件与分组管理](/zh/on-call/statuspage/components-sections)。
  </Step>

  <Step title="配置订阅方式">
    公开状态页可以启用邮件订阅和 RSS/Atom；内部状态页可以通过已绑定的 IM 集成接收推送。你也可以由管理员批量导入订阅者。

    配置说明见[订阅管理](/zh/on-call/statuspage/subscriptions)。
  </Step>

  <Step title="准备事件模板">
    为常见故障和计划维护准备模板，减少故障发生时临时组织语言的成本，并保持每次状态更新的表达一致。

    模板配置见[事件模板](/zh/on-call/statuspage/templates)。
  </Step>

  <Step title="发布一次测试事件">
    在正式推广状态页前，发布一次测试故障或维护事件，确认组件影响、时间线更新、订阅通知和页面展示都符合预期。

    事件发布流程见[发布与管理事件](/zh/on-call/statuspage/publish-events)。
  </Step>
</Steps>

## 从 Atlassian Statuspage 迁移

如果你已经在使用 Atlassian Statuspage，可以使用 Flashduty CLI 将**组件、分组、历史事件和邮件订阅者**迁移到 Flashduty 状态页。迁移分为两个独立步骤：

1. **迁移结构与历史**：导入组件、分组、历史事件、维护记录和通知模板。
2. **迁移邮件订阅者**：导入订阅者列表及其订阅偏好。

两步分离的原因是：迁移结构时**不会**向订阅者发送通知。你可以先检查导入内容是否正确，再决定是否导入订阅者。导入的订阅者会直接变为活跃状态，无需重新邮件验证。

### 准备工作

#### 安装 Flashduty CLI

<Tabs>
<Tab title="macOS / Linux">
```bash
curl -sSL https://raw.githubusercontent.com/flashcatcloud/flashduty-cli/main/install.sh | sh
```
</Tab>
<Tab title="Windows (PowerShell)">
```powershell
irm https://raw.githubusercontent.com/flashcatcloud/flashduty-cli/main/install.ps1 | iex
```
</Tab>
<Tab title="手动下载">
访问 [GitHub Releases](https://github.com/flashcatcloud/flashduty-cli/releases) 下载对应平台的二进制包，解压后放入 `PATH` 即可。
</Tab>
</Tabs>

更多安装方式请参考 [CLI 文档](/zh/developer/cli)。

#### 登录 Flashduty

```bash
flashduty login
```

按提示输入 APP Key。获取方式：登录 [Flashduty 控制台](https://console.flashcat.cloud)，进入 **个人中心 > 个人信息**，复制 APP Key。

#### 获取 Atlassian Statuspage API Key

1. 登录 [Atlassian Statuspage 管理面板](https://manage.statuspage.io/)
2. 进入 **User icon > API info**，复制 API Key
3. 设置环境变量：

```bash
export ATLASSIAN_STATUSPAGE_API_KEY="your_api_key_here"
```

#### 获取 Atlassian Statuspage Page ID

在 Atlassian Statuspage 管理面板中，**Page ID** 显示在页面 URL 或页面设置中。格式类似 `0db0rq26tg1l`。

### 迁移步骤

建议先迁移结构和历史，再迁移订阅者，最后切换域名。这样可以先检查导入结果，再让订阅者开始接收 Flashduty 状态页通知。

<Steps>
  <Step title="迁移结构与历史">
    执行以下命令导入 Atlassian Statuspage 的组件、分组、历史事件、维护记录和通知模板。此步骤会创建或复用 Flashduty 目标状态页，但不会通知订阅者。

    ```bash
    flashduty statuspage migrate structure \
      --from atlassian \
      --source-page-id <your_atlassian_page_id> \
      --api-key "$ATLASSIAN_STATUSPAGE_API_KEY"
    ```

    | 参数 | 必填 | 说明 |
    | --- | --- | --- |
    | `--from` | 是 | 迁移来源，目前仅支持 `atlassian` |
    | `--source-page-id` | 是 | Atlassian Statuspage 的 Page ID |
    | `--api-key` | 是 | Atlassian Statuspage 的 API Key |
    | `--url-name` | 否 | 新创建的 Flashduty 公开状态页的 URL 名称 |

    <Warning>
    `--url-name` 仅在本次迁移**创建新的目标状态页**时生效。如果同一个 `--source-page-id` 已经在历史迁移中映射到一个已存在的目标状态页：

    - 省略 `--url-name`，或传入与已存在目标状态页完全一致的值，迁移会复用该目标页继续执行。
    - 传入与已存在目标页不同的值，迁移会在预检阶段失败。如需更改 URL 名称，请在 Flashduty 控制台直接编辑目标状态页。
    </Warning>

    `--url-name` 的格式与唯一性要求：

    - 经 `MakeSlug` 规范化：转换为小写、用连字符连接、长度不超过 255 个字符；纯符号或规范化后为空的输入会被拒绝，错误信息为 `url_name must not be empty after normalization`。
    - 在账号下的公开状态页范围内全局唯一，重复时会以 `url_name must be unique` 拒绝。
  </Step>

  <Step title="查询迁移进度">
    迁移任务为异步执行，命令会立即返回一个 **Job ID**。使用以下命令查询进度：

    ```bash
    flashduty statuspage migrate status --job-id <job_id>
    ```

    迁移会依次导入 `components`、`sections`、`history` 和 `templates`。任务完成后，输出中会包含 Flashduty 状态页 ID（`target-page-id`），后续迁移订阅者时需要使用。

    如果需要取消正在运行的迁移任务，执行：

    ```bash
    flashduty statuspage migrate cancel --job-id <job_id>
    ```
  </Step>

  <Step title="验证导入内容">
    在进行下一步之前，建议检查导入的内容：

    ```bash
    # 查看新状态页信息
    flashduty statuspage list --id <target_page_id>

    # 查看导入的事件
    flashduty statuspage changes --page-id <target_page_id> --type incident
    ```

    你也可以登录 [Flashduty 控制台](https://console.flashcat.cloud)，在状态页管理界面中检查组件、分组和历史事件是否完整。
  </Step>

  <Step title="迁移邮件订阅者">
    确认结构和历史导入正确后，执行订阅者迁移：

    ```bash
    flashduty statuspage migrate email-subscribers \
      --from atlassian \
      --source-page-id <your_atlassian_page_id> \
      --target-page-id <flashduty_page_id> \
      --api-key "$ATLASSIAN_STATUSPAGE_API_KEY"
    ```

    | 参数 | 必填 | 说明 |
    | --- | --- | --- |
    | `--from` | 是 | 迁移来源，`atlassian` |
    | `--source-page-id` | 是 | Atlassian Statuspage 的 Page ID |
    | `--target-page-id` | 是 | 结构与历史迁移完成后输出的 Flashduty 状态页 ID |
    | `--api-key` | 是 | Atlassian Statuspage 的 API Key |

    导入的订阅者会直接变为活跃状态，无需邮件验证。已在 Atlassian 端被标记为隔离（quarantined）的邮箱地址会被自动跳过。订阅者迁移可以安全地多次执行，已存在的订阅者不会被重复导入。
  </Step>

  <Step title="切换域名和 RSS/Atom">
    如果原 Atlassian Statuspage 使用自定义域名，将 CNAME 记录切换到 Flashduty 提供的状态页地址。Flashduty 兼容 `history.rss` 和 `history.atom` 链接格式，原 RSS/Atom 订阅可继续生效。

    自定义域名配置请参考[创建与管理状态页](/zh/on-call/statuspage/create-manage-page)。RSS/Atom 订阅规则请参考[订阅管理](/zh/on-call/statuspage/subscriptions)。
  </Step>
</Steps>

### 完整迁移示例

```bash
# 设置 Atlassian API Key
export ATLASSIAN_STATUSPAGE_API_KEY="your_api_key_here"

# 1. 迁移结构与历史
flashduty statuspage migrate structure \
  --from atlassian \
  --source-page-id 0db0rq26tg1l \
  --api-key "$ATLASSIAN_STATUSPAGE_API_KEY"
# 输出: Job ID: str_abc

# 2. 查询进度，等待完成
flashduty statuspage migrate status --job-id str_abc
# 重复执行直到 Status: completed
# 记录输出中的 target-page-id

# 3. 验证导入结果
flashduty statuspage list --id <target_page_id>

# 4. 迁移邮件订阅者
flashduty statuspage migrate email-subscribers \
  --from atlassian \
  --source-page-id 0db0rq26tg1l \
  --target-page-id <target_page_id> \
  --api-key "$ATLASSIAN_STATUSPAGE_API_KEY"
# 输出: Job ID: sub_xyz

# 5. 查询进度，等待完成
flashduty statuspage migrate status --job-id sub_xyz
```

## 上线检查清单

正式向客户或内部团队推广状态页前，逐项检查：

- 已确认状态页类型、页面数量和当前订阅版本满足需求
- 已分配状态页管理和状态页事件管理权限
- 已配置状态页名称、URL 标识、Logo、页头、页脚、联系方式和自定义链接
- 已完成自定义域名配置，或确认使用 Flashduty 默认访问地址
- 已创建组件和分组，并确认隐藏策略和可用性展示方式
- 已启用所需订阅方式，并完成订阅者导入或自助订阅验证
- 已准备故障和维护事件模板
- 已发布测试事件，并验证页面展示、时间线更新和订阅通知
- 如果从 Atlassian Statuspage 迁移，已完成结构、历史、订阅者、域名和 RSS/Atom 切换验证
