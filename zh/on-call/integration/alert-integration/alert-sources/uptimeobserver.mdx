通过 UptimeObserver Webhook 将监控故障同步到 Flashduty On-call。每个 UptimeObserver Incident 对应一条 Flashduty 告警；Incident Webhook 触发告警，Resolution Webhook 恢复同一条告警。

<div className="hide">

## 在 Flashduty On-call

您可通过以下两种方式获取集成推送地址，任选其一即可。

### 使用专属集成

1. 进入 Flashduty 控制台，选择 **协作空间**，打开一个协作空间
2. 选择 **配置** → **集成数据** → **专属集成**，点击 **新增一个集成**
3. 选择 **UptimeObserver**，点击 **保存**
4. 打开生成的集成卡片，复制 **推送地址**

### 使用共享集成

1. 进入 Flashduty 控制台，选择 **集成中心 → 告警事件**
2. 选择 **UptimeObserver**，填写集成名称
3. 配置默认路由并选择协作空间；创建后可在 **路由** 中增加更多规则
4. 点击 **保存**，复制生成的 **推送地址**

</div>

## 在 UptimeObserver 中配置

UptimeObserver 没有固定的 Webhook 报文，报文由您填写的模板决定。Flashduty 只解析下面两个模板，需要创建两个 Webhook：一个用于故障，一个用于恢复。

<Steps>
<Step title="在 UptimeObserver 中创建 Incident Webhook（故障）">

**操作路径**：UptimeObserver › Integrations › Webhooks

| 字段 | 填写 |
| :--- | :--- |
| Friendly name（必填） | 自定义名称，例如 `Flashduty Incident` |
| URL（必填） | `{integration_url}` |
| HTTP Method（必填） | `POST` |
| Authentication（必填） | `None`（这些选项默认均未选中；Flashduty 通过地址中的 `integration_key` 认证） |
| HTTP Body Encoding（必填） | `application/json` |
| HTTP Body（必填） | 下方 JSON 模板 |

Webhook 表单本身没有触发时机，触发时机在关联 Monitor 时选择。将下面的 JSON 粘贴到 HTTP Body，点击 **Save Webhook**：

```json
{
  "event_type": "trigger",
  "incident_url": "__INCIDENT_URL__",
  "incident_id": __INCIDENT_ID__,
  "incident_status": "__INCIDENT_STATUS__",
  "monitor_id": __MONITOR_ID__,
  "monitor_name": "__MONITOR_FRIENDLY_NAME__",
  "monitor_url": "__MONITOR_URL__",
  "root_cause": "__INCIDENT_ROOT_CAUSE__"
}
```

</Step>

<Step title="在 UptimeObserver 中创建 Resolution Webhook（恢复）">

**操作路径**：UptimeObserver › Integrations › Webhooks

再新增一个 Webhook，其余字段与上一步相同（URL 同为 `{integration_url}`），名称例如 `Flashduty Resolution`，HTTP Body 粘贴：

```json
{
  "event_type": "resolved",
  "incident_url": "__INCIDENT_URL__",
  "incident_id": __INCIDENT_ID__,
  "incident_status": "__INCIDENT_STATUS__",
  "monitor_id": __MONITOR_ID__,
  "monitor_name": "__MONITOR_FRIENDLY_NAME__",
  "monitor_url": "__MONITOR_URL__"
}
```

<Warning>
`event_type` 必须分别保持 `trigger` 和 `resolved`，`incident_id` 两处都要保留且不加引号。缺少 `incident_id` 或 `event_type` 时 Flashduty 会拒绝请求，因为无法可靠关联故障与恢复。
</Warning>

</Step>

<Step title="在 UptimeObserver 中为 Monitor 添加 Webhook 告警">

**操作路径**：UptimeObserver › Monitor 编辑页 › Add Alert（入口位置未在官方 Webhook 文档中列出，以界面为准）

每个需要通知的 Monitor 添加两条 Alert，**Alert Type** 都选择 **Webhook**：

| Event | Webhook |
| :--- | :--- |
| `Monitor Down` | 上一步创建的 Incident Webhook |
| `Monitor Up` | 上一步创建的 Resolution Webhook |

然后点击 **Save changes**。

</Step>

<Step title="验证生命周期">

**操作路径**：UptimeObserver › Integrations › Webhooks（Webhook 保存后点击测试按钮 🧪）

测试按钮只能验证连通性，不能证明故障与恢复能被关联。请让被监控的地址真实不可达，确认 Flashduty 收到活动告警（接入清单的「收到第一个事件」变绿）；恢复访问后，确认同一条告警自动恢复。

</Step>
</Steps>

## Alert Key

Flashduty 使用 `incident_id`（`__INCIDENT_ID__`）作为 Alert Key。UptimeObserver 文档将其定义为数字型 Incident 标识，并在故障与恢复两个示例模板中都使用它。文档没有明确写出两个 Webhook 对同一 Incident 返回相同的值，这一点属于推断，请在首次接入时按上一节的方法用真实故障验证。

`monitor_id` 只作为标签。监控名称、根因和 `incident_status` 的变化不会改变 Alert Key；同一监控的下一次故障会产生新的 Incident，因此是一条新的告警。

## 状态和告警等级

| `event_type` | Flashduty 状态或等级 |
| :--- | :--- |
| `trigger` | Critical（监控项宕机） |
| `resolved` | 恢复，原等级为 Critical |

`event_type` 为空或其他值会被拒绝。请求体为空对象 `{}` 时返回 200 且不创建告警。

## 排查问题

- **UptimeObserver 返回非 2xx**：确认 URL 完整且包含 `integration_key`
- **Flashduty 返回参数错误**：确认 Body 是有效 JSON。`__INCIDENT_ROOT_CAUSE__` 或监控名称含双引号时，UptimeObserver 直接替换文本，可能破坏 JSON，可删除 `root_cause` 字段或改用不含引号的监控名称
- **告警没有恢复**：确认已创建 Resolution Webhook，其 `event_type` 为 `resolved`，且已关联到同一个 Monitor
- **测试成功但真实告警没收到**：检查 Monitor 是否真正进入 Incident，以及是否关联了两个 Webhook

更多变量说明请参阅 [UptimeObserver Webhooks](https://support.uptimeobserver.com/integrations/webhooks/)。
