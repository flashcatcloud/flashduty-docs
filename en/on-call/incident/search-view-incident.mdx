## Incident list

The incident list has two entry points. The list inside a channel shows only that channel's incidents. The list under **Incident Management** spans channels and can show every incident in the account.

<Frame>
<img src="https://docs-cdn.flashcat.cloud/images/png/988781efcb13781c33c986b6f19ef1f9.png" alt="Incident List Interface" />
</Frame>

| # | Feature | Description |
| :---: | :--- | :--- |
| 1 | Assignment toggle | A three-state control at the head of the filter bar: **All** / **Assigned to Me** (I am a responder) / **My Teams** (in channels I belong to). Selecting **Responders** or **Channels** under **More Filters** resets the toggle to **All** and the manual filter wins; the toggle applies again once both filters are cleared |
| 2 | Time Filter | Supports relative time and custom range filtering |
| 3 | Severity | Filter incidents by severity |
| 4 | Processing Progress | Filter incidents by progress, defaults to **All** |
| 5 | More Filters | Supports rich dimension filtering, including responders, channels, creator, acknowledger, closer, teams, snooze status, ever converged due to flapping, rare incidents, labels, custom fields, and **Unfinished actions / follow-ups** (the only option is **Yes**, which returns only incidents that still have unfinished action items or follow-ups). The **Channels** and **Teams** filters are only visible under the global Incident Management entry, and Teams narrows incidents by the team that owns each channel |
| 6 | Search | Located at the end of the filter bar, supports searching by incident title, ID, labels, and custom fields. After an incident's title, labels, or custom fields are updated, query results may be slightly delayed |
| 7 | View Settings | Supports rich rendering options including **custom display attributes** and even aggregate views |
| 8 | Pagination | Pagination and items per page adjustment |

<Warning>
For query performance, the query time range is limited based on your subscription tier:

- **Free**: up to **30 days**
- **Standard**: up to **180 days**
- **Professional**: up to **366 days**

To query older data, adjust the start and end times, or use the [Incident Query API](/en/api-reference/on-call/incidents/incident-list).
</Warning>

<Note>
To improve performance, when search conditions match more than **1000** incidents, the system only displays 1000+, not the exact number. Therefore, you can only view 1000 incidents through pagination. To see more, adjust your search time range or use the [Incident Query API](/en/api-reference/on-call/incidents/incident-list) to get all data.
</Note>

### Using aggregate view

Aggregate view groups incidents in real time by the dimensions you define (a live Group By), for example by severity.

<Frame>
<img src="https://docs-cdn.flashcat.cloud/images/png/c0b5d9a41a35c47f928da0d44e96f2aa.png" alt="Aggregate View" />
</Frame>

After switching to aggregate view, a **Grouping Rule** selector appears at the top of the list:

- **Pick an existing rule**: Click the dropdown to switch between all saved grouping rules under the current account. Each rule defines a set of Group By attributes (for example, by **Severity** + **Channel** + `labels.service`)
- **Create a rule**: At the bottom of the dropdown, click **New**. Select attributes, labels, and custom fields, then name and save the rule for reuse
- **Edit or delete a rule**: Hover over an existing rule to edit or delete it with the inline icons
- **Share a view**: The selected rule is recorded in the list link, so copying the link shares the same perspective with other members

<Note>
To improve performance, in aggregate view, the system matches at most **100** records for aggregation. Therefore, the list you see may not contain all matching data. If this concerns you, switch to list view.
</Note>

### Using more filters

**More Filters** lets you combine many dimensions. Common uses:

- Search for incidents triggered by the "Host Down" alert policy based on `check` label
- Search for incidents marked as "false positive" based on the false alarm field
- Set **Unfinished actions / follow-ups** to **Yes** to surface incidents that still have open work to wrap up

**Labels** and **Custom fields** match **exactly**; wildcards and regex don't apply:

- A label value must equal the value stored on the incident, case included. A value containing `*` or wrapped in `/…/` is compared literally: the system doesn't expand it into a wildcard or a regex, tells you "Label values match exactly; * and /…/ are not supported. Use the search box for a partial match", and leaves that condition out of the query
- **Custom fields** list single-select, multi-select, and checkbox fields only, and their values also match exactly. Text fields can't be filtered by field; use **Search** instead. Unsupported fields show "Only single-select, multi-select and checkbox fields can be filtered. Use the search box for text fields". Saved filters are cleaned by the same rules when restored
- One label or custom field can hold several values at once: the values chosen under the same item match **any of them** (a multi-select field matches by containment), while different labels and different fields still must all match. A checkbox field only has `true` / `false`, so choosing both says nothing extra and only the first applies
- For a partial match, use **Search** at the end of the filter bar. Wildcard and regex syntax applies only inside [Filter Conditions](/en/on-call/configuration/filter-conditions), which configure rules such as escalation, silence, and inhibit rules

<Tip>
For faster queries, narrow the time range and use conditions such as **Assigned to Me** and **Processing Progress** to reduce the scope.
</Tip>

### Row content

Beyond the title and progress, each incident row surfaces two key counters:

- **Associated alerts**: total number of [alerts](/en/on-call/channel/noise-reduction) grouped into this incident
- **Alert events**: cumulative count of events merged into the incident. When a new event has been merged in the past **5 minutes**, the merge icon turns orange to signal that the incident is still actively aggregating

Hovering over the counters opens a tooltip with the associated alert count, associated event count, and the relative time since the last merge.

### Batch operations

After selecting one or more incidents in the list, use the action bar above the list to perform batch operations:

| Operation | Description |
| :--- | :--- |
| **Acknowledge** | Acknowledge the selected incidents in bulk |
| **Snooze** | Snooze the selected incidents in bulk. For durations and preset settings, see [Snooze](/en/on-call/incident/handle-update-incident#snooze). Only incidents in the Processing state can be snoozed; the button is disabled if your selection contains incidents in other states |
| **Assign** | Assign the selected incidents to specific members in bulk. Closed incidents cannot be assigned; the button is disabled if your selection contains closed incidents |
| **Close** | Close the selected incidents in bulk |
| **Merge** | Merge the selected incidents into a single incident |
| **AI Analysis** | Send the selected incidents as context to the AI SRE Agent for batch analysis. Requires the AI SRE module to be enabled with the corresponding permission; if all selected incidents belong to the same team, that team is automatically used as the conversation scope |

Except for **AI Analysis**, the above batch operations require incident update permission.

### Custom rendering

Click the **Settings** button in the upper right corner of the incident list to customize display content and interaction behavior:

| Option | Description |
| :--- | :--- |
| **Display Type** | Choose **List** or **Aggregate** view mode |
| **Detail Display** | Choose **Page** mode (navigate to a new page) or **Side Panel** mode (view details in the right panel) |
| **Auto Refresh** | Set list auto-refresh interval, or disable auto-refresh |
| **Display Attributes** | Toggle visibility of basic attribute columns such as duration, responders, channel |
| **Custom Fields** | Select platform-defined custom fields as additional display columns; if incident doesn't have this field, displays "-" |
| **Incident Labels** | Select or type label keys as additional display columns; if incident doesn't have this label, displays "-" |

For snooze durations, see [Snooze](/en/on-call/incident/handle-update-incident#snooze) |

### Labels and related links

Incident labels appear in the **Details** area of the details page. Link labels are lifted into a **Links** button bar above the label list. For the button-name mapping, the jump links to RUM issues and alert rules, and how images, ARNs, times, and query expressions are rendered, see [What is an incident · Incident labels](/en/on-call/incident/what-is-incident#related-links-and-label-value-rendering).

To get back to the query as it was when the alert fired, open the Query Workbench from any of these places:

- **The hover card on a system label**: hover over query-type system labels such as `__alert_rule_queries`, `__alert_rule_values`, and `__alert_rule_relate_queries` to see the query and the values at trigger time
- **The comprehensive info panel's investigation entries**: the **Investigation** block in the right-side panel (see **Investigation** below)
- **The "Investigate" popover in the Associated Alerts tab**: every alert row builds its entries from that alert's own labels

### AI summary

<Tip>
**Plan requirement**: This feature requires an On-call Pro or higher subscription. [Learn more](https://flashcat.cloud/flashduty/price/)
</Tip>

Click the **AI Summary** button in the details area to generate a structured summary from the incident's associated alerts (up to 20):

- **Summary**: A one-sentence description of what happened
- **Impacts**: Key affected resources such as services, systems, environments, and instances
- **Actions**: Immediately actionable investigation and remediation steps (up to 3)

The generated summary streams in real time, can be regenerated, and can be saved as the incident description.

<Tip>
AI Summary is only available for incidents automatically triggered by alerts. Manually created incidents do not support this feature.
</Tip>

### Comprehensive info panel

The comprehensive info panel on the right side of the incident details page consolidates auxiliary information around the incident. From top to bottom:

| Section | Description |
| :--- | :--- |
| **Responders** | Lists all responders (individuals or on-call personnel) assigned to the incident along with their acknowledgment status |
| **Attributes** | Basic attributes such as channel, incident trigger time, and alert count |
| **Investigation** | Appears only for incidents aggregated from Monitors alerts. Lists the investigation entries snapshot configured on the alert rule, showing 3 entries by default; below it you also get the alert rule that produced the incident with its main and related queries. See **Investigation** below |
| **Images** | Displayed when alerts associated with the incident include image information reported by API. Click a thumbnail to preview, and hover to view the Alt description and source link |
| **Key Timestamps** | A timeline view of key timestamps in the incident lifecycle, including **trigger time**, **first acknowledgment time**, **close time**, and reopen events, so you can quickly grasp incident progress |
| **Related Links** | Shortcut links preconfigured in the owning channel (such as dashboards, runbooks, knowledge bases). Parameters are dynamically rendered from the current incident's labels or fields, enabling one-click navigation to related systems. Link templates are maintained in channel settings |
| **Custom Fields** | Displays and allows editing of the incident's custom field values; unset fields are shown as `-` |
| **External Tickets** | If you have configured ticket integrations such as Jira, ServiceNow, or ServiceDesk Plus, external tickets created from this incident appear here and can be clicked to open in the external system |

### Investigation

For incidents aggregated from Monitors alerts, the comprehensive info panel gains an **Investigation** block between **Attributes** and **Images**. It does not show live query results: it renders the investigation-entry snapshot that the alert rule produced **at the moment the alert fired**.

Each entry is one row showing the entry-type icon (query or dashboard), the **purpose** configured on the rule, and the data source (name plus type icon). When the rule has no purpose, a query entry shows its query expression instead, and a dashboard entry shows the dashboard title and its location path (the whole dashboard, or `Tab › Panel`). Entries that render with a problem carry an orange dot on the type icon.

- Hovering an entry opens a detail card with the full query expression (copyable), the named **variables** (filled in from the alert's labels; unresolved ones are highlighted in red), and the **time range** — the relative window on one line (for example "60 min before → 10 min after the alert") and the absolute start and end on the next. An **Open** button at the bottom opens the corresponding view in the Query Workbench or dashboard in a new tab
- The number next to the heading is how many entries the snapshot holds; the **N with issues** badge counts the entries that render with a problem (query failed to render, dashboard variable unresolved, data source or dashboard deleted or unauthorized)
- Only the first **3** entries show by default; the rest sit behind **N more**, which expands and collapses
- Below the entries are the **Related alert rule** card (rule name plus data source, clickable through to the rule) and the rule's **Queries**: main queries are listed by `A` / `B` with the **value at trigger time**, hover for the full expression with a copy button, and a no-data alert is marked **No data** on the matching main query; related queries show the **result at trigger time**: a result table for statistical queries, and for a VictoriaLogs / Loki related query whose query mode is **Raw** one log line per row with its fields laid out as `k=v` and the fields that do not fit collapsed into **+N fields**; the hover card shows at most 3 rows, and **View full data** next to its heading opens the query workbench with everything

When the rule has no investigation entries configured, the block says "No investigation entries configured on the rule" and offers a **Configure** link. Other cases where entries cannot be shown:

- The rule's investigation entries are misconfigured: the block says "The rule's investigation entries are misconfigured and were not generated", with **Edit rule**
- The alert rule has been deleted: "The alert rule was deleted, so no investigation entries were generated"
- The alert came from an older Edge: upgrade to v0.75.3 or later and new alerts will include investigation entries
- The snapshot exceeds 8KB: view the entries in the monitoring alert details

Incidents aggregated from non-Monit integrations (Zabbix, RUM, and so on) never show this block; older Monit alerts that carry no investigation-entry snapshot show only the **Related Alert Rule** and **Queries** below it.

In the **Associated Alerts** tab, each alert row also has a magnifier **Investigate** icon. It opens an "investigation entries for this alert" popover: in a multi-alert incident each alert has different labels, and the popover builds entries from **that alert's own labels**, so its entries can differ from the right-side panel.

The right column of the alert details page embeds the same panel; see [Alert management · Alert details](/en/on-call/incident/alert-management#investigation).

### Detail tabs

The incident details page contains 7 tabs; some appear only under certain conditions:

| Tab | Content | Visibility |
| :--- | :--- | :--- |
| **Incident Overview** | A panoramic view including the incident summary, key attributes, recent timeline, responders, and associated events. This is the default tab when the details page opens | Always visible |
| **Associated Alerts** | All [grouped](/en/on-call/channel/noise-reduction) alerts associated with the incident, with filtering by progress and view switching | Visible when the incident has at least one associated alert |
| **Timeline** | The complete lifecycle record of the incident — triggering, assignment, reassignment, responder changes, notifications, acknowledgments, snoozes, closure, comments, and action-item and follow-up operations such as creation, updates, and completion — with a Markdown comment box at the top | Always visible |
| **Change History** | Change events correlated with the current incident in time, helping you pinpoint the relationship between the incident and recent deployments or configuration changes | Always visible |
| **Resolution** | Records the incident's impact, root cause, and resolution | Visible when any of the three has content |
| **Post-Mortem** | A built-in post-mortem editor that lets you create, edit, AI-generate, and publish a post-mortem report without leaving the details page | On-call Pro or higher |
| **Past Incidents** | Shows historical incidents similar to the current one, so you can draw on prior handling experience | Always visible |

### Timeline comments

The top of the Timeline tab provides a Markdown comment box that supports:

- Writing notes, troubleshooting memos, or meeting summaries in Markdown syntax
- Pasting or uploading images directly; screenshots are auto-uploaded and converted into image links
- Clicking an image in a comment opens the original image in a new tab (no in-page preview)
- Mentioning members with @ in a comment. The mentioned member gets a personal notification with the comment and an incident link, by email and Flashduty App push by default. This pulls the right people into the discussion
- Appending the published comment as a record on the incident timeline, interleaved with system-generated events for easy retrospection

<Note>
@mention notifications are dedicated personal notifications and are not affected by notification muting such as snooze or silence rules.
</Note>

<Tip>
Posting a comment requires update permission on the incident; members without it do not see the send controls.
</Tip>

### Comment types

Comments can carry a **comment type** tag to distinguish their nature on the timeline (for example, "root cause analysis" or "handling progress"):

- When posting a comment, pick a type, or **No comment type**, in the **Comment type** selector next to the comment box. The timeline shows the type as a colored tag
- Comment types are configured at the **account level** and apply to all incidents under the current account; renaming or recoloring a type also affects historical comments
- The selector next to the comment box only appears when the account already has comment types, or when you have comment-type management permission

Members with comment-type management permission can open the **Manage comment types** dialog from the selector and perform the following operations:

| Operation | Description |
| :--- | :--- |
| **Create** | Enter a name (up to **40** characters) and pick a color (6 preset colors, plus a custom picker); up to **10** types per account |
| **Rename** | Edit the name in place (up to **40** characters); the change also applies to historical comments |
| **Recolor** | Change the color with the color picker; this also applies to historical comments |
| **Drag to reorder** | Drag types to change their order, which determines how they appear in the selector |
| **Delete** | After deletion, historical comments will no longer show this type |

<Note>
The limits above apply to the **Manage comment types** dialog in the console. In the Flashduty App (mobile), types appear as pills above the comment box. With management permission you can create a type from the **More** panel (name up to **20** characters, one of 30 preset colors, no custom color); rename, recolor, delete, and reorder in the console.
</Note>

### Action item and follow-up events

The timeline records every operation on [action items and follow-ups](/en/on-call/incident/work-items) with an icon, alongside comments, acknowledgments, and other events. These operations are create, update, change assignees, complete, delete, convert an action to a follow-up, and link a follow-up to the post-mortem. When the incident closes, one record summarizes the unfinished actions that Flashduty converted.

When a create or assignee-change record carries assignees, the sentence continues with "assigned to …". Members alone appear one by one as avatar plus name. If AI SRE is among the assignees, the record uses a joint signature: member names joined by ", ", ending with "and AI SRE" (for example, "John, Jane and AI SRE").

### AI SRE action records

AI SRE sometimes acts on behalf of a member, for example when an [automation rule](/en/ai-sre/automations) writes its conclusion back to the incident. The timeline signs these actions **`{{name}} and AI SRE`**, because AI SRE uses that member's identity and permissions.

Each such row has a **Continue conversation** entry that opens the original session in the AI SRE panel (one incident can have several sessions). This requires AI SRE to be enabled for the account and permission to use AI SRE chat; personal sessions (visible only to their creator) and expired sessions cannot be continued.

### Change history

The Change History tab shows change events close in time to the incident, so you can see whether a recent deployment or configuration change caused it.

The change event list displays the following information:

| Column | Description |
| :--- | :--- |
| **Status** | Current status of the change event, including Planned, Ready, Processing, Canceled, Done, Failed |
| **Change Key** | Unique identifier of the change event |
| **Title** | Brief description of the change event |
| **Description** | Detailed information about the change event |
| **Start Time** | When the change event started |
| **End Time** | When the change event ended |
| **Duration** | How long the change event lasted; in-progress events update in real time |
| **Link** | External link to the change event's original source |

You can adjust the query scope through the filter at the top, including time range and change source. Expand any row to view a timeline visualization of that change event, allowing comparison with the incident trigger time.

### Post-mortem

The incident details page has a built-in post-mortem editor, and a shortcut button in the action area jumps straight to the **Post-Mortem** tab. There you can create a post-mortem, AI-generate a first draft, edit the title and rich-text content, publish, re-edit after publishing, delete, and export as Markdown.

See [Post-Mortem](/en/on-call/post-mortem/create-edit-post-mortem) for details.

### War room operations

When an incident has a war room, the **More** menu offers **Invite Followers to War Room** and **Close War Room**. For when these appear, what happens if the IM integration is disabled, and the mobile app, see [War Room](/en/on-call/advanced/war-room).

## FAQ

<AccordionGroup>
<Accordion title="Console error: Due to the large volume of data, we are unable to respond...">
This error often appears on incident/alert list queries, analytics dashboards, and so on. It's mainly because the system matched too much data and the query timed out.

In this case, narrow your query scope, such as time range, or use more precise query conditions. If issues persist, contact us.
</Accordion>
</AccordionGroup>
