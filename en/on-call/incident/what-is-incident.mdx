## Incidents, alerts, and events

When Flashduty On-call receives an alert event (such as a Zabbix notification), the system triggers an alert, which in turn triggers an incident. Multiple similar active alerts may be grouped into the same incident for unified assignment, notification, and handling.

**An incident is a group of similar alerts.** Without noise reduction, an incident equals an alert. Conversely, with noise reduction, an incident equals its associated multiple alerts. For more about alert noise reduction, read [Understanding Noise Reduction](/en/on-call/channel/noise-reduction).

## Incident severity, status, and progress

### Severity

| Level | Description |
| :--- | :--- |
| **Info** | Minor, service is still running normally, just a status reminder, no immediate action needed |
| **Warning** | Warning, service may have errors or problems are imminent, should intervene early to prevent escalation |
| **Critical** | Critical, widespread service errors or outages, users affected, must take immediate action |

Incidents, alerts, and events all use these three severity levels. **Severity is capitalized**, which is important when using APIs. The severity generation rules are:

- **Event Severity**: Alert events from different integration sources (like Zabbix and Nightingale) have different severity enumerations. Flashduty On-call maps them to these three standard severities according to specific rules. For mapping details, refer to the specific integration documentation. To customize severity, see [Alert Processing](/en/on-call/integration/alert-integration/alert-pipelines).
- **Alert Severity**: Equals the highest severity among associated events. As new events keep merging in, the alert severity only escalates to the worst level and never drops because of a lower-severity event.
- **Incident Severity**: Equals the highest severity among associated alerts.

### Processing progress

| Status | Description |
| :--- | :--- |
| **Triggered** (`Triggered`) | After incident triggers, progress defaults to "Triggered", system initiates automatic assignment, sets responders and sends notifications |
| **Processing** (`Processing`) | When anyone clicks **Acknowledge**, progress immediately changes to "Processing". In this state, responders may be **Acknowledged** or **Unacknowledged**, but at least one person is "Acknowledged". When all responders **unacknowledge**, progress reverts to "Triggered" |
| **Closed** (`Closed`) | When anyone clicks **Close** or **incident auto-recovers**, progress immediately changes to "Closed" |

API fields represent progress with the capitalized enum values `Triggered` / `Processing` / `Closed`. Use these raw values when calling APIs or configuring filters.

### Incident status

Alert status represents the incident's state in the original monitoring system, that is, "Recovered" or "Not Recovered". Incident status depends entirely on its associated alerts.

| Status | Description |
| :--- | :--- |
| **Recovered** | All alerts associated with the incident have recovered, incident auto-recovers |
| **Not Recovered** | At least one alert associated with the incident hasn't recovered, incident remains unrecovered |

<Note>
Incident auto-recovery leads to automatic closure (of processing progress); but manually closing an incident has no effect on incident status.
</Note>

## Incident labels

Labels are a fundamental concept in Flashduty On-call. Different labels describe alert and incident information across various dimensions, and are extensively used in filtering, searching, and grouping scenarios.

### Label generation rules

Flashduty extracts alert labels from the event messages that the monitoring system reports. Different sources have different extraction methods, but generally we follow the **capture everything relevant** principle. For example, for Prometheus-sourced alert events, Flashduty On-call extracts Labels and Annotations information from the Payload.

<Tip>
- Labels come only from reported events; you can't edit or add them manually
- Auto-triggered incident labels always equal the labels of the first associated alert
- Manually triggered incident labels are always empty
</Tip>

Flashduty On-call provides label enhancement for automatic label generation. Go to [Configure Label Enhancement](/en/on-call/integration/alert-integration/label-enhancement) to learn more.

### System labels

The label panel on the incident/alert details page collects platform-internal labels into a separate **System labels** section, with a **Hide system labels** / **Show system labels** toggle (with an eye icon) next to the heading. Which labels count as system labels depends on the alert source:

| Alert source | Labels treated as system labels |
| :--- | :--- |
| Monit alerts (`monit.alert`) | Names starting with `__alert_rule_` or `__entity_alert_`, such as `__alert_rule_id` or `__entity_alert_promql`. Internal labels that are not Monit's own — `__name__`, for instance — stay in the regular label list |
| Other sources | Names starting with `__alert_rule_` / `__entity_alert_` / `__flashduty_`, or names that both start and end with `__`, such as `__instance__` or `__name__` |

- The toggle appears only when the labels actually contain system labels. Its tooltip states the rule used for the current alert source: Monit alerts show "Monit system labels start with `__alert_rule_` or `__entity_alert_`", other sources show "System labels are platform labels starting with `__`, such as `__alert_rule_id` and `__name__`"
- System labels are **collapsed by default**. While collapsed, the bottom of the list holds a dashed button reading "N system labels collapsed (first few keys…)"; clicking it expands a separate **System labels** section with a divider, and the toggle next to the heading collapses it again
- Flashduty saves the toggle as a **per-user preference** that persists across sessions and devices; the mobile app and the web console share the same preference
- The count badge next to the heading is the total number of labels (system labels and related links included), not the number of rows currently visible
- While system labels are collapsed, the **JSON view** and the JSON you copy exclude them too; drag-to-reorder applies to regular labels only, and system labels are never reordered
- System labels written by Monit come with a hover card that translates the machine-readable label into a plain-language alias and offers a jump: `__alert_rule_id` → the alert rule, `__alert_rule_folder_*` → the rule's folder, `__alert_rule_data_source_*` → the data source, `__alert_rule_event_kind` → firing / repeating / resolved, `__alert_rule_values` and `__alert_rule_queries` → each main query's value and expression at trigger time, `__alert_rule_relate_*` → related queries and their result at trigger time, `__alert_rule_investigation_context*` → investigation entries

### Related links and label value rendering

The label panel shows a **Links** button bar above the list and renders some label values specially.

**Related links**: labels whose value is an `http(s)://` link and that are not images stop acting as regular, sortable labels — they are lifted above the list, one button per link. The button name comes from the label key:

| Label key | Button name |
| :--- | :--- |
| `generatorURL`, `generator_url`, `detail_url`, `link`, `web_url`, `client_url`, `insight_url` | **View source**; shown as **View in {source}** when the alert's integration has a name |
| `runbook_url` | **Runbook** |
| `silenceURL` | **Silence** |
| `dashboardURL`, `dashboard_url` | **Open dashboard** |
| `panelURL` | **Open panel** |
| `query_url` | **View query** |
| `log_url` | **View logs** |
| `alert_url` | **View alert** |
| `ruleURL`, `rule_url`, `alert_rule_url` | **View rules** |
| `alert_history_url` | **Alert history** |
| Any other key | `key · host` |

Buttons follow the order of the table above; keys not listed come after them in alphabetical order. Hovering a button shows the full key and URL. Image links (a key containing `image`, or a link ending in an image extension) are not related links and stay in the label list. This extraction applies to regular labels only — link labels already in the **System labels** section stay where they are.

**Special label value rendering**: label values are recognized by format and rendered as follows. Recognition looks only at the key name and the value's format; it does not depend on per-integration metadata.

| Form | Recognition | Rendering |
| :--- | :--- | :--- |
| Image thumbnail | The value is an `http(s)` link and the key contains `image` (Grafana's `imageURL`, for example), or the link ends in `.png` / `.jpg` / `.jpeg` / `.gif` / `.webp` / `.svg` | A 160 x 90 thumbnail; clicking opens the original image in a new tab. The request carries no referrer and the image loads lazily as it scrolls into view |
| ARN | The value looks like `arn:partition:service:region:account:resource` | The resource segment on the main line, followed by small **Service** / **Region** chips |
| Time | The key ends in `_time` / `_at` / `timestamp` and the value is a 10-digit (seconds) or 13-digit (milliseconds) timestamp falling between 2000 and 2100; or the value is an ISO 8601 time with a time zone | Formatted as `YYYY-MM-DD HH:mm:ss` in the account's time zone with a relative "x ago"; hover shows the original value |
| Time (no time zone) | The value is a wall-clock string such as `YYYY-MM-DD HH:mm` with no time zone | Shown as-is, with no time-zone conversion |
| Query expression | The key ends in `ql` / `promql` / `logql` / `query` / `expression` / `sql` (preceded by a separator or the start of the string, so `mysql` and `graphql` are not misread) | A monospace code block with a copy button for the whole expression |

Forms that already have a fixed display size — images and query expressions — are not truncated to two lines; other values longer than two lines are collapsed behind a **View all** / **Collapse** toggle.

## Incident lifecycle

<Steps>
<Step title="Trigger New Incident">
You can trigger incidents in the following ways:

- **Auto-trigger**: Flashduty On-call receives an alert event from an integration (like Zabbix notification), event auto-triggers an alert, alert auto-triggers an incident
- **Manual trigger**: Click **Create Incident** button in Flashduty On-call console, fill in title, description, severity, and so on. to trigger a new incident
- **External reporting**: After enabling external reporting, external personnel can submit incident tickets through a dedicated link without logging into a Flashduty account. See [External Incident Submission](/en/on-call/incident/external-submission) for details
</Step>

<Step title="Assignment and Notification">
After a new incident triggers, Flashduty On-call sequentially matches escalation rules under the channel. After matching an escalation rule, the system assigns the incident to individuals, team members, or on-call personnel and sends notifications.

<Warning>
If no escalation rule matches, Flashduty assigns the incident to no one and sends no notifications.
</Warning>

You can set different escalation rules for different time periods or incident types to achieve flexible assignment. The system allows you to set multiple levels within an escalation rule. If current level responders don't acknowledge and resolve the incident within the specified time, the system automatically escalates to the next level.

You can flexibly arrange notification methods in escalation rules. Flashduty On-call supports many group chat and direct message notification channels. Direct messages are one-to-one push channels (like voice, SMS, email), group chats push messages to messaging groups (like Feishu/Lark, Dingtalk, Slack) with additional mentions for assignees.

<Note>
If you assign an incident to a schedule with no one on-call (empty schedule), Flashduty notifies no individuals, but it still posts to any group chat channels you configured.
</Note>
</Step>

<Step title="Acknowledge and Resolve">
On-call personnel can acknowledge immediately upon receiving notification. You can acknowledge incidents by **voice calls** or **instant messages**. After acknowledgment, incident progress changes to **Processing**.

<Tip>
Flashduty On-call currently doesn't restrict incidents to only be acknowledged by "assigned responders". Anyone who sees the incident can acknowledge it.
</Tip>

**Closing an incident** changes progress to **Closed**. If alerts associated with the incident auto-recover, the incident also auto-closes. Conversely, if you manually close an incident, all associated alerts are automatically closed. This means these alerts will no longer merge new events.
</Step>
</Steps>

## Incident timeline

Every incident has a timeline for tracing changes and actions at different historical moments. For example, at what time, through what channel, who was notified, and notification results.

Each timeline record shows the full date and time (`YYYY-MM-DD HH:mm:ss`) by default; hovering switches to a relative time (for example, "3 minutes ago").

## Triggering incidents

### Trigger from an integration

Flashduty On-call supports most common monitoring systems, including Prometheus, Zabbix, Nightingale, and cloud monitoring. Go to [Alert Integration](/en/on-call/integration/alert-integration/alert-sources/prometheus) for specific steps.

<Tip>
Flashduty On-call supports dedicated and shared integration modes:
- **Dedicated Integration**: Deliver alerts to a channel's dedicated integration, incidents trigger within that channel
- **Shared Integration**: Deliver alerts to Integration Center's shared integration, then configure routing to deliver alerts to different channels by rules
</Tip>

### Trigger with the API

Flashduty On-call provides a custom event standard, allowing you to report alerts using the standard protocol, suitable for any non-integrated monitoring system. For details, read [Custom Alert Events](/en/on-call/integration/alert-integration/alert-sources/standard-alert).

<Warning>
To ensure system stability, Flashduty On-call enforces rate limits on alert push APIs (**8000 requests/second** per API, **2000 requests/minute** per account, **2000 requests/minute** per integration). Exceeding these limits returns a `429` status code — wait and retry. See [Integrate Data - Rate Limits](/en/on-call/channel/integrate-data#rate-limits) for details.
</Warning>

<Warning>
Ensure you actively close alerts, or set incident auto-close timeout in the channel. Too many incidents will severely degrade console search performance. The system may close historical incidents without notification.
</Warning>

### Trigger by email

Flashduty On-call provides email integration, allowing you to report alerts by sending emails, suitable for all monitoring systems supporting email alerts. For details, read [Email Integration Guide](/en/on-call/integration/alert-integration/alert-sources/email).

<Tip>
You can set specific email prefixes for each integration. You can also contact us to set a memorable dedicated domain for your account. For example, order-service@tesla.flashcat.cloud.
</Tip>

### Trigger from the console

You can click the **Create** button on the incident list page to manually create an incident. Follow these steps:

<Steps>
<Step title="Enter incident title">
Enter the incident title with a brief description of what happened. This field is required.
</Step>
<Step title="Select severity">
Choose Critical, Warning, or Info.
</Step>
<Step title="Select channel">
Select the channel the incident belongs to. If you create the incident inside a channel, Flashduty fills in this field and you can't change it.
</Step>
<Step title="Select assignment method">
After selecting a channel, the system displays assignment method options:

- **By Policy**: Select an escalation rule from the current channel. If no escalation rules are available in the channel, this option is disabled
- **Direct Assignment**: Manually select responders (individuals or schedules) for direct assignment
</Step>
<Step title="Enter incident description (optional)">
Enter a detailed description of the incident. The editor supports rich text and Markdown syntax.
</Step>
</Steps>
