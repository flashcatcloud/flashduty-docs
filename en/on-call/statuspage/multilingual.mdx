Flashduty Status Pages support **简体中文** (`zh`) and **English** (`en`) with no default language: both languages are equal peers with symmetric fallback. You can enable one language for a single-language audience or enable both for a bilingual status page.

## Enable languages

Open your status page details, go to **Settings → Basic Settings**, select the languages you want in the **Language** multi-select dropdown (**简体中文**, **English**), and select **Save**.

Language settings follow these rules:

- **Keep at least one language**: when only one language remains selected, it is disabled and can't be unchecked.
- **No default language**: when both languages are enabled, you don't need to pick a primary language. The page matches each visitor's preference and falls back symmetrically when a field is blank.
- **New status pages**: creating a status page doesn't ask for a language. Flashduty sets your current console language as the page's sole enabled language.
- **Existing status pages**: status pages created before multilingual support are treated as having both **简体中文** and **English** enabled.
- **Lossless preservation**: unchecking a language keeps all saved translations for that language in the background. Re-enabling the language restores them intact.

## Multilingual fields

Nine **page settings** support separate Chinese and English values across three settings pages (event and maintenance content is covered in [Bilingual event content](#event-bilingual)):

| Settings page | Field | Description |
| --- | --- | --- |
| **Settings → Basic Settings** | **Page Title** | Shown at the top of the status page and in the browser tab; required in at least one enabled language |
| **Settings → Appearance** | **Page Header** | Custom text shown below the page title |
| **Settings → Appearance** | **Page Footer** | Custom text shown at the bottom of the status page |
| **Settings → Appearance** | **Custom Links — Link name** | Each custom link can have a separate display label per language |
| **Settings → Appearance** | **Custom Links — URL** | Each custom link can point to a separate URL per language, such as localized documentation or privacy policies |
| **Settings → Components & Groups** | **Component name** | Required in at least one enabled language; uniqueness is checked per language |
| **Settings → Components & Groups** | **Component description** | Brief description of the component |
| **Settings → Components & Groups** | **Group name** | Required in at least one enabled language; uniqueness is checked per language |
| **Settings → Components & Groups** | **Group description** | Brief description of the group |

The following settings are shared across languages:

- **Addresses**: **Status page URL** and **Custom domain**.
- **Brand assets and contacts**: **Logo**, **Dark Mode Logo**, **Logo Link**, **Favicon**, and **Contacts**.
- **Display and structure**: event history view, uptime display mode, and component and group ordering, hierarchy, and visibility.
- **Incident and maintenance content**: the **title** and **message** you publish with an event or maintenance, and the body of every **timeline update**, are filled in per language too. Visitors see the language they are viewing, and a language left empty falls back to the other one; affected component and group names behave the same way. See [Bilingual event content](#event-bilingual).

## Editing in the console

### Single-language and bilingual inputs

- **Single-language mode** (one language enabled): all inputs stay single-line with no extra language controls.
- **Bilingual mode** (both **简体中文** and **English** enabled): each multilingual field expands into a stacked dual-row input labeled **简体中文** and **English** on the right, so you can edit both versions together. Each custom link row pairs the **Link name** and **URL** for that language.
- **Fallback placeholder**: when one language is empty and the other has text, the empty row shows the other language's text as its placeholder to preview the visitor fallback.

### Validation and preview

- **Required fields**: page title, component name, and group name only need a value in at least one enabled language to save; you don't need to fill in both.
- **Duplicate checks**: component and group name uniqueness is enforced per language. Two items can't share a name in the same language, while the same item can use identical names in Chinese and English (for example, `API` in both).
- **Bilingual preview**: in **Settings → Components & Groups**, the **Preview** section adds **简体中文** and **English** tabs in bilingual mode so you can check component trees and descriptions in both languages.

## Bilingual event content

The **content** of events and maintenances is bilingual too, not just the page settings. On a bilingual page every one of these editors shares the same language tabs:

| Where you edit | What is filled in per language |
| :--- | :--- |
| **Publish an incident / Publish a maintenance** | the **incident name** or **maintenance name**, and the **message** |
| **Add an update** (event or maintenance detail page) | the **message** of that update |
| **Edit an existing update** | the **message** of that update |
| **Retrospective event** (backfilling an event that is already over) | the event name and each historical update's body |
| **Inline event title edit** | both title inputs; saving writes both |

The rules match the page-level fields:

- **One language is enough to publish** — the editor says "Fill in at least one language; the empty side shows the other language automatically."
- The side left empty shows the other language on the public page (symmetric fallback), and the empty input is placeholder-filled with the other language's text.
- **Tab order follows the console language**: Chinese consoles list **简体中文** first, English consoles list **English** first, and the editor opens on the tab matching the console language (or the first enabled one when the console language is not enabled on that page).
- **A single-language page has no tabs** — the editor degrades to a plain input, and there is no translate button.
- Event titles are still limited to 255 characters.

### One-click translation (AI translation)

When the **current tab is empty and the other language already has content**, the editor shows a **Translate** button: one click machine-translates the other language into the current tab instead of retyping it.

- The translation uses the status page's **glossary** — page name, group names and component names in both languages constrain the output, so translated component names match the page; Markdown structure is preserved.
- On success a six-second toast reads **"Translated to English"** or **"Translated to 简体中文"** with an **Undo** action: undoing restores the pre-translation content, and editing manually after a translation retires the Undo entry.
- On failure the toast reads **"Translation failed, please try again later"** and the existing content is untouched.
- **Status description templates** translate as a set: when every status is empty in the current language and the other language is filled in, one click translates the whole set.
- The button appears only on a **bilingual page that has AI translation enabled**; without it (for example a self-hosted deployment with no translation model configured) you fill both languages by hand.

## Visitor language behavior

### Symmetric fallback

When a multilingual field is blank in the visitor's active language, the status page automatically displays the value from the other language instead of leaving it empty. For example, if you only enter an English component name, Chinese visitors see that English name, and vice versa.

### Language detection and switching

<Tabs>
  <Tab title="Single language enabled">
    - Both the status page UI and your content always render in the sole enabled language.
    - The language switcher in the top-right corner is hidden automatically.
    - Passing `?lang=` for the disabled language, or having a different browser language or cookie, still clamps the page to the enabled language.
  </Tab>
  <Tab title="Both languages enabled">
    - The display language is resolved in this order: URL query parameter `?lang=zh` or `?lang=en` > `NEXT_LOCALE` cookie > browser `Accept-Language` header (the first supported language in the browser's preference order; English when none matches).
    - Visitors can switch languages at any time using the language switcher in the top-right corner. Switching updates `?lang=zh` or `?lang=en` in the URL and stores the preference in the `NEXT_LOCALE` cookie (valid for 1 year).
    - You can share direct language-specific links with `?lang=zh` or `?lang=en` (for example, `https://status.example.com?lang=en`). Opening the link renders that language and writes the `NEXT_LOCALE` cookie.
  </Tab>
</Tabs>

## Notifications, widgets, and RSS/Atom

Your status page's language settings apply automatically across notifications, embedded widgets, and feeds with no extra setup:

- **Subscriptions and notifications**: the subscription dialog renders component and group names in the visitor's active page language and saves their locale preference. Email, Slack, Microsoft Teams, and IM notifications render the status page title, affected component and group names, **and the event title and body** (the latest timeline update's body, falling back to the event description when it has none) in the subscriber's locale; an empty locale falls back to the other language, and a disabled locale clamps to the page's sole enabled language. On bilingual pages, detail and unsubscribe links in notifications include `?lang=`. See [Subscription management](/en/on-call/statuspage/subscriptions).
- **Widgets**: `<flashduty-status-widget>` passes `?lang=zh` or `?lang=en` to the summary endpoint based on its `locale` attribute. Calling `GET {status page URL}/api/widget/v1/summary.json?lang=zh|en` directly returns localized values for `page.name`, `affected_components[].name`, `affected_components[].group_name`, **and the event title and timeline-update body** (falling back to the other language when that one is empty), clamped to the page's enabled languages. On bilingual pages, omitting `?lang=` defaults to English. See [Widgets](/en/on-call/statuspage/widgets).
- **RSS/Atom feeds**: `/feed.rss`, `/feed.atom`, and their aliases `/history.rss` and `/history.atom` accept `?lang=zh` or `?lang=en` to return localized status page titles, affected component names, **and event titles and update bodies** (falling back to the other language when that one is empty; when the latest update has no body, the event description is shown instead), and item labels such as Status and Affected components are translated too. Single-language pages always return the enabled language; bilingual pages default to English when `?lang=` is omitted. See [Subscription management](/en/on-call/statuspage/subscriptions).
