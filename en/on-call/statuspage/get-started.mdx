## Prepare before launch

Before creating or migrating a status page, confirm the following information. Better preparation reduces follow-up changes after launch.

| Preparation item | Description | Related docs |
| --- | --- | --- |
| Status page type | Public status pages serve customers and partners; internal status pages serve organization members | [What is a status page](/en/on-call/statuspage/statuspage) |
| Management permissions | Confirm who can manage status pages, publish events, and manage subscribers | [Permission design](/en/platform/permission-design) |
| Brand assets | Prepare logos, dark logos, favicon, page header, page footer, contact information, and custom links | [Create and manage status pages](/en/on-call/statuspage/create-manage-page) |
| Custom domain | If you plan to use `status.example.com`, confirm the DNS owner and CNAME cutover window in advance | [Create and manage status pages](/en/on-call/statuspage/create-manage-page) |
| Service structure | List the products, regions, modules, dependent services, and visibility rules you want to show | [Components and sections](/en/on-call/statuspage/components-sections) |
| Subscription strategy | Decide whether to enable email, RSS/Atom, or internal IM subscriptions, and whether subscribers need to be imported | [Subscription management](/en/on-call/statuspage/subscriptions) |
| Communication templates | Prepare standard messages for incidents, maintenance, recovery, and progress updates | [Event templates](/en/on-call/statuspage/templates) |

<Note>
Public and internal status pages have different access models, subscription methods, and plan requirements. Before launch, confirm that your current plan covers the required page count and internal status page needs. See [Plans and pricing](/en/platform/pricing).
</Note>

## Launch from scratch

If your team does not have a formal status page yet, use the sequence below to launch the first page.

<Steps>
  <Step title="Confirm the status page type">
    Choose whether to create a public or internal status page. Public status pages are suitable for communicating service status to customers and partners. Internal status pages help sales, support, management, and internal teams share one view of system status.

    If you are unsure about the difference, read the status page type section in [What is a status page](/en/on-call/statuspage/statuspage).
  </Step>

  <Step title="Create the status page and configure basic settings">
    Create a status page in the Flashduty console, then fill in the name, URL slug, and type. After creation, configure branding, page content, display settings, and subscription switches.

    See [Create and manage status pages](/en/on-call/statuspage/create-manage-page) for detailed steps.
  </Step>

  <Step title="Configure a custom domain">
    If you want users to visit a company-owned domain such as `status.example.com`, add a CNAME record for the target domain and configure the domain in status page settings.

    Domain cutover usually requires DNS permissions, so complete verification before promoting the page. See [Create and manage status pages](/en/on-call/statuspage/create-manage-page) for configuration details.
  </Step>

  <Step title="Design components and sections">
    Break the services you want to expose into components, then organize them by product line, region, service tier, or business module. Show only the services your audience needs to understand. You do not need to expose every internal technical dependency.

    See [Components and sections](/en/on-call/statuspage/components-sections) for modeling guidance.
  </Step>

  <Step title="Configure subscription methods">
    Public status pages can enable email and RSS/Atom subscriptions. Internal status pages can send updates through linked IM integrations. Administrators can also bulk import subscribers.

    See [Subscription management](/en/on-call/statuspage/subscriptions) for configuration details.
  </Step>

  <Step title="Prepare event templates">
    Create templates for common incidents and planned maintenance so responders do not need to draft messages from scratch during an incident, and every update stays consistent.

    See [Event templates](/en/on-call/statuspage/templates) for template configuration.
  </Step>

  <Step title="Publish a test event">
    Before promoting the status page, publish a test incident or maintenance event and verify component impact, timeline updates, subscription notifications, and page rendering.

    See [Publish and manage events](/en/on-call/statuspage/publish-events) for the event workflow.
  </Step>
</Steps>

## Migrate from Atlassian Statuspage

If you already use Atlassian Statuspage, you can use Flashduty CLI to migrate **components, sections, historical events, and email subscribers** to Flashduty Status Page. Migration is split into two independent steps:

1. **Migrate structure and history**: import components, sections, historical events, maintenance records, and notification templates.
2. **Migrate email subscribers**: import the subscriber list and subscription preferences.

The two-step design is intentional: structure migration does **not** notify subscribers. You can verify the imported content before importing subscribers. Imported subscribers become active immediately and do not need to verify their email again.

### Prerequisites

#### Install Flashduty CLI

<Tabs>
<Tab title="macOS / Linux">
```bash
curl -sSL https://raw.githubusercontent.com/flashcatcloud/flashduty-cli/main/install.sh | sh
```
</Tab>
<Tab title="Windows (PowerShell)">
```powershell
irm https://raw.githubusercontent.com/flashcatcloud/flashduty-cli/main/install.ps1 | iex
```
</Tab>
<Tab title="Manual download">
Download the latest release for your platform from [GitHub Releases](https://github.com/flashcatcloud/flashduty-cli/releases), extract it, and place the binary in your `PATH`.
</Tab>
</Tabs>

For more installation options, see the [CLI documentation](/en/developer/cli).

#### Log in to Flashduty

```bash
flashduty login
```

When prompted, paste your APP Key. To obtain one, sign in to the [Flashduty console](https://console.flashcat.cloud) and copy your APP Key from **Profile > Personal Info**.

#### Get your Atlassian Statuspage API Key

1. Log in to the [Atlassian Statuspage management panel](https://manage.statuspage.io/)
2. Go to **User icon > API info** and copy the API Key
3. Set the environment variable:

```bash
export ATLASSIAN_STATUSPAGE_API_KEY="your_api_key_here"
```

#### Get your Atlassian Statuspage Page ID

In the Atlassian Statuspage management panel, the **Page ID** is displayed in the page URL or page settings. It looks like `0db0rq26tg1l`.

### Migration steps

Migrate structure and history first, then migrate subscribers, and switch the domain last. This lets you verify imported content before subscribers start receiving Flashduty status page notifications.

<Steps>
  <Step title="Migrate structure and history">
    Run the following command to import Atlassian Statuspage components, sections, historical events, maintenance records, and notification templates. This step creates or reuses the target Flashduty status page but does not notify subscribers.

    ```bash
    flashduty statuspage migrate structure \
      --from atlassian \
      --source-page-id <your_atlassian_page_id> \
      --api-key "$ATLASSIAN_STATUSPAGE_API_KEY"
    ```

    | Flag | Required | Description |
    | --- | --- | --- |
    | `--from` | Yes | Migration source, currently only `atlassian` |
    | `--source-page-id` | Yes | Atlassian Statuspage Page ID |
    | `--api-key` | Yes | Atlassian Statuspage API Key |
    | `--url-name` | No | URL name for the newly created Flashduty public status page |

    <Warning>
    `--url-name` is honored **only when this run creates a new target status page.** If the same `--source-page-id` is already mapped to an existing Flashduty status page from a previous migration:

    - Omit `--url-name`, or pass a value that exactly matches the existing target's URL name, and the migration reuses that target.
    - Pass a value that differs from the existing target's URL name, and the migration fails during preflight. To change the URL name, edit the target status page directly in the Flashduty console.
    </Warning>

    Format and uniqueness requirements for `--url-name`:

    - Normalized by `MakeSlug`: lowercased, hyphen-separated, and capped at 255 characters. Pure-symbol input or anything that normalizes to an empty string is rejected with `url_name must not be empty after normalization`.
    - Globally unique across the account's public status pages. Collisions are rejected with `url_name must be unique`.
  </Step>

  <Step title="Check migration progress">
    Migration jobs run asynchronously, and the command returns immediately with a **Job ID**. Check progress with:

    ```bash
    flashduty statuspage migrate status --job-id <job_id>
    ```

    The migration imports `components`, `sections`, `history`, and `templates` in order. When the job completes, the output includes the Flashduty status page ID (`target-page-id`), which you need for subscriber migration.

    To cancel a running migration job, run:

    ```bash
    flashduty statuspage migrate cancel --job-id <job_id>
    ```
  </Step>

  <Step title="Verify imported content">
    Before proceeding, verify the imported data:

    ```bash
    # View the new status page
    flashduty statuspage list --id <target_page_id>

    # View imported incidents
    flashduty statuspage changes --page-id <target_page_id> --type incident
    ```

    You can also log in to the [Flashduty console](https://console.flashcat.cloud) to visually inspect components, sections, and incident history.
  </Step>

  <Step title="Migrate email subscribers">
    After confirming the structure and history are correctly imported, run the subscriber migration:

    ```bash
    flashduty statuspage migrate email-subscribers \
      --from atlassian \
      --source-page-id <your_atlassian_page_id> \
      --target-page-id <flashduty_page_id> \
      --api-key "$ATLASSIAN_STATUSPAGE_API_KEY"
    ```

    | Flag | Required | Description |
    | --- | --- | --- |
    | `--from` | Yes | Migration source, `atlassian` |
    | `--source-page-id` | Yes | Atlassian Statuspage Page ID |
    | `--target-page-id` | Yes | Flashduty status page ID returned by the structure and history migration |
    | `--api-key` | Yes | Atlassian Statuspage API Key |

    Imported subscribers become active immediately without email verification. Email addresses marked as quarantined on the Atlassian side are automatically skipped. Subscriber migration can safely be run multiple times, and existing subscribers will not be duplicated.
  </Step>

  <Step title="Switch domain and RSS/Atom">
    If your original Atlassian Statuspage used a custom domain, point the CNAME record to the Flashduty-provided status page address. Flashduty is compatible with `history.rss` and `history.atom`, so existing RSS/Atom subscriptions can keep working.

    See [Create and manage status pages](/en/on-call/statuspage/create-manage-page) for custom domain configuration. See [Subscription management](/en/on-call/statuspage/subscriptions) for RSS/Atom feed behavior.
  </Step>
</Steps>

### Complete migration example

```bash
# Set Atlassian API Key
export ATLASSIAN_STATUSPAGE_API_KEY="your_api_key_here"

# 1. Migrate structure and history
flashduty statuspage migrate structure \
  --from atlassian \
  --source-page-id 0db0rq26tg1l \
  --api-key "$ATLASSIAN_STATUSPAGE_API_KEY"
# Output: Job ID: str_abc

# 2. Poll until completed
flashduty statuspage migrate status --job-id str_abc
# Repeat until Status: completed
# Record the target-page-id from output

# 3. Verify imported content
flashduty statuspage list --id <target_page_id>

# 4. Migrate email subscribers
flashduty statuspage migrate email-subscribers \
  --from atlassian \
  --source-page-id 0db0rq26tg1l \
  --target-page-id <target_page_id> \
  --api-key "$ATLASSIAN_STATUSPAGE_API_KEY"
# Output: Job ID: sub_xyz

# 5. Poll until completed
flashduty statuspage migrate status --job-id sub_xyz
```

## Launch checklist

Before sharing the status page with customers or internal teams, verify each item:

- Status page type, page count, and current plan meet your requirements
- Status page management and status page event management permissions are assigned
- Status page name, URL slug, logos, page header, page footer, contact information, and custom links are configured
- Custom domain is configured, or you have confirmed that the Flashduty default URL will be used
- Components and sections are created, with visibility rules and uptime display verified
- Required subscription methods are enabled, and subscriber import or self-service subscription has been tested
- Incident and maintenance event templates are prepared
- A test event has been published, and page rendering, timeline updates, and subscription notifications have been verified
- If migrating from Atlassian Statuspage, structure, history, subscribers, domain cutover, and RSS/Atom compatibility have been verified
