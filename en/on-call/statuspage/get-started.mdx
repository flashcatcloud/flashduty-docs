## Prepare before launch

Before creating or migrating a status page, confirm the following information. Better preparation reduces follow-up changes after launch.

| Preparation item | Description | Related docs |
| --- | --- | --- |
| Status page type | Public status pages serve customers and partners; internal status pages serve organization members | [Status Page overview](/en/on-call/statuspage/statuspage) |
| Management permissions | Confirm who can manage status pages, publish events, and manage subscribers | [Permission design](/en/platform/permission-design) |
| Brand assets | Prepare logos, dark logos, favicon, page header, page footer, contact information, and custom links | [Create and manage status pages](/en/on-call/statuspage/create-manage-page) |
| Custom domain | If you plan to use `status.example.com`, confirm the DNS owner and CNAME cutover window in advance | [Create and manage status pages](/en/on-call/statuspage/create-manage-page) |
| Service structure | List the products, regions, modules, dependent services, and visibility rules you want to show | [Components and sections](/en/on-call/statuspage/components-sections) |
| Subscription strategy | Decide whether to enable email, RSS/Atom, or internal IM subscriptions, and whether subscribers need to be imported | [Subscription management](/en/on-call/statuspage/subscriptions) |
| Communication templates | Prepare standard messages for incidents, maintenance, recovery, and progress updates | [Event templates](/en/on-call/statuspage/templates) |

<Note>
Public and internal status pages have different access models, subscription methods, and plan requirements. Before launch, confirm that your current plan covers the required page count and internal status page needs. See [Plans and pricing](/en/platform/pricing).
</Note>

## Launch from scratch

If your team does not have a formal status page yet, use the sequence below to launch the first page.

<Steps>
  <Step title="Confirm the status page type">
    Choose whether to create a public or internal status page. Public status pages are suitable for communicating service status to customers and partners. Internal status pages help sales, support, management, and internal teams share one view of system status.

    If you are unsure about the difference, read the status page type section in [Status Page overview](/en/on-call/statuspage/statuspage).
  </Step>

  <Step title="Create the status page and configure basic settings">
    Create a status page in the Flashduty console, then fill in the name, URL slug, and type. After creation, configure branding, page content, display settings, and subscription switches.

    See [Create and manage status pages](/en/on-call/statuspage/create-manage-page) for detailed steps.
  </Step>

  <Step title="Configure a custom domain">
    If you want users to visit a company-owned domain such as `status.example.com`, add a CNAME record for the target domain and configure the domain in status page settings.

    Domain cutover usually requires DNS permissions, so complete verification before promoting the page. See [Create and manage status pages](/en/on-call/statuspage/create-manage-page) for configuration details.
  </Step>

  <Step title="Design components and sections">
    Break the services you want to expose into components, then organize them by product line, region, service tier, or business module. Show only the services your audience needs to understand. You do not need to expose every internal technical dependency.

    See [Components and sections](/en/on-call/statuspage/components-sections) for modeling guidance.
  </Step>

  <Step title="Configure subscription methods">
    Public status pages can enable email and RSS/Atom subscriptions. Internal status pages can send updates through linked IM integrations. Administrators can also bulk import subscribers.

    See [Subscription management](/en/on-call/statuspage/subscriptions) for configuration details.
  </Step>

  <Step title="Prepare event templates">
    Create templates for common incidents and planned maintenance so responders do not need to draft messages from scratch during an incident, and every update stays consistent.

    See [Event templates](/en/on-call/statuspage/templates) for template configuration.
  </Step>

  <Step title="Publish a test event">
    Before promoting the status page, publish a test incident or maintenance event and verify component impact, timeline updates, subscription notifications, and page rendering.

    See [Publish and manage events](/en/on-call/statuspage/publish-events) for the event workflow.
  </Step>
</Steps>

## Migrate from Atlassian Statuspage

If you already use Atlassian Statuspage, migrate structure and history first, then migrate subscribers, and switch the domain last. This lets you verify imported content before subscribers start receiving Flashduty status page notifications.

<Steps>
  <Step title="Install and log in to Flashduty CLI">
    Migration runs through Flashduty CLI. Install the CLI first, then log in with your Flashduty APP Key.

    See the prerequisites in [Migrate from Atlassian Statuspage](/en/on-call/statuspage/migrate-from-atlassian).
  </Step>

  <Step title="Migrate structure and historical events">
    Use `flashduty statuspage migrate structure` to import Atlassian Statuspage components, sections, historical incidents, maintenance records, and notification templates. This step creates or reuses the target Flashduty status page but does not notify subscribers.

    See the structure and history migration step in [Migrate from Atlassian Statuspage](/en/on-call/statuspage/migrate-from-atlassian).
  </Step>

  <Step title="Verify imported content">
    In the Flashduty console, check components, sections, historical events, templates, and page rendering. Migrate subscribers only after the imported content looks correct.
  </Step>

  <Step title="Migrate email subscribers">
    Use `flashduty statuspage migrate email-subscribers` to import subscribers. Imported subscribers become active immediately and do not need to verify their email again.

    See the email subscriber migration step in [Migrate from Atlassian Statuspage](/en/on-call/statuspage/migrate-from-atlassian).
  </Step>

  <Step title="Switch domain and RSS/Atom">
    If your original Atlassian Statuspage used a custom domain, point the CNAME record to the Flashduty-provided status page address. Flashduty is compatible with `history.rss` and `history.atom`, so existing RSS/Atom subscriptions can keep working.

    See the domain and RSS/Atom cutover section in [Migrate from Atlassian Statuspage](/en/on-call/statuspage/migrate-from-atlassian).
  </Step>
</Steps>

<Tip>
For migration commands, flag descriptions, and a complete example, see [Migrate from Atlassian Statuspage](/en/on-call/statuspage/migrate-from-atlassian).
</Tip>

## Launch checklist

Before sharing the status page with customers or internal teams, verify each item:

- Status page type, page count, and current plan meet your requirements
- Status page management and status page event management permissions are assigned
- Status page name, URL slug, logos, page header, page footer, contact information, and custom links are configured
- Custom domain is configured, or you have confirmed that the Flashduty default URL will be used
- Components and sections are created, with visibility rules and uptime display verified
- Required subscription methods are enabled, and subscriber import or self-service subscription has been tested
- Incident and maintenance event templates are prepared
- A test event has been published, and page rendering, timeline updates, and subscription notifications have been verified
- If migrating from Atlassian Statuspage, structure, history, subscribers, domain cutover, and RSS/Atom compatibility have been verified
