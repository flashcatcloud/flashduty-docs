Status pages use **components** to represent individual services or functional modules, and **sections** to group related components for a clearer structure. This guide covers how to manage components and sections.

## Components

Components are the basic units of a status page. Each component represents a specific service or feature. Events reflect actual service status through their impact on components.

### Create a component

In the status page, go to **Settings → Components & Groups** and click **Add component**. Fill in the following fields:

| Field | Required | Description |
| --- | --- | --- |
| **Name** | Yes | Display name for the component; must be unique within the same language on the status page |
| **Description** | No | Brief description of the component |

<Note>
Drag a component to change its display order, and drag it into a section to assign it. Newly created components begin tracking uptime from the moment of creation.
</Note>

### Edit a component

You can modify a component's name and description at any time, or drag it to change its section and order. When changing the name, ensure it does not conflict with other components on the same status page.

### Delete a component

Deleting a component removes its uptime data and related subscriptions. Impact records in already-published events that reference this component are not affected.

### Component visibility

Each component row has two independent icon switches at the end of the row; hover over an icon to see its name:

| Switch | Effect |
| --- | --- |
| **Hide historical data** | The component is displayed on the status page but uptime statistics are hidden |
| **Hide component** | The component is not displayed on the status page and is excluded from uptime calculations |

The two switches control different effects. When **Hide component** is on, that component's **Hide historical data** switch is disabled.

<Tip>
For internal-only service components that you do not want to expose to status page visitors, turn on **Hide component**. Hidden components can still be referenced in events.
</Tip>

## Sections

Sections group related components together for a clearer status page structure. For example, you can group "Web App", "API Service", and "Database" under a "Core Services" section.

### Create a section

In the status page, go to **Settings → Components & Groups** and click **Add group**. Fill in the following fields:

| Field | Required | Description |
| --- | --- | --- |
| **Name** | Yes | Display name for the section; must be unique within the same language on the status page |
| **Description** | No | Brief description of the section |

### Edit a section

You can modify a section's name and description at any time, and drag it to change its display order.

### Delete a section

Deleting a section does not delete its components. Instead, the components become ungrouped and continue to be displayed independently on the status page.

### Section visibility

Like components, each section row has two independent icon switches:

| Switch | Effect |
| --- | --- |
| **Hide historical data** | The section is displayed on the status page but its uptime statistics are hidden |
| **Hide group** | The section and all its components are hidden from the status page and excluded from uptime calculations |

When **Hide group** is on, that section's **Hide historical data** switch is disabled too.

<Warning>
Turning on "Hide group" also hides all components within it, even if those components are not individually set to hidden.
</Warning>

## Availability display

Below the structure list in **Settings → Components & Groups**, **How should we show historical data for your components?** controls how the status page shows uptime data:

| Option | Effect |
| --- | --- |
| **Colored bars and uptime percentage** | Shows colored bars and percentage values together |
| **Colored bars only** | Shows colored bars only, without percentages |
| **Nothing** | Hides uptime data; the **Hide historical data** switch on each component and section row is hidden as well |

## Multilingual editing and preview

When both **简体中文** and **English** are enabled, each component and group in **Settings → Components & Groups** expands into a stacked dual-row input for separate names and descriptions. In single-language mode, inputs stay single-line.

- **Input and fallback**: component and group names only need a value in at least one enabled language to save. If one language is left blank, visitors see the other language's text automatically.
- **Duplicate checks**: uniqueness is enforced per language. Two items can't share a name within the same language, while the same component or group can use identical names across Chinese and English (for example, `API`).
- **Bilingual preview**: the **Preview** section at the bottom includes **简体中文** and **English** tabs so you can inspect both versions in real time.
- **Preserved translations**: unchecking a language preserves saved component and group translations in the background; re-enabling the language restores them.

For full language rules, see [Multilingual status pages](/en/on-call/statuspage/multilingual).

## Organization tips

- **Define components by business function**: create one component for each user-facing service or functional module, such as "Web Console", "API Gateway", or "Billing System".
- **Create sections by service tier**: group components by service tier or business domain, such as "Core Services", "Monitoring & Alerting", or "Third-party Integrations".
- **Use visibility controls wisely**: for internal dependencies or backend infrastructure components, use hidden options to keep the status page clean.
