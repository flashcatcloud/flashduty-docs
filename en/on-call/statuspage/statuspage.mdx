A Flashduty status page is one place to publish service status: during an incident or maintenance window, you post an update once, and customers and internal staff see the same real-time information and can subscribe to notifications.

<Tip>**Plan requirement**: All plans can create public status pages (Free and Standard: up to 1; Pro and Private deployment: up to 5). Internal status pages are available on Pro and Private deployment only (up to 20). Email notifications for public status pages count toward your plan's email quota, and access traffic is unlimited. [Learn more](https://flashcat.cloud/flashduty/price/)</Tip>

<Note>
You cannot create a new status page in these cases (existing status pages keep working, and you can still edit them and publish events):

- The subscription is expired or disabled: you can create again after renewing.
- Internal status pages: require Pro or higher.

See [What happens when your subscription expires](/en/platform/pricing#what-happens-when-your-subscription-expires).
</Note>

Subscribe to the [Flashduty Official Status Page](https://status.flashcat.cloud/flashduty) to receive Flashduty service status updates first.

## Status page types

Flashduty offers two types of status pages:

<Tabs>
  <Tab title="Public Status Page">
    **For customers and partners**

    - Open to all public internet users, accessible without sign in
    - Visitors can subscribe to event updates by **email** or **RSS/Atom**
  </Tab>
  <Tab title="Internal Status Page">
    **For internal organization employees**

    - Accessible only to internal organization users, requires Flashduty account sign in
    - Users can receive real-time notifications through **IM integration** (Feishu/Lark, Dingtalk, WeCom, Slack)
  </Tab>
</Tabs>

For subscription methods, see [Subscription management](/en/on-call/statuspage/subscriptions).

## Core concepts

### Components and sections

Status pages organize and present different services through **Components**. A component is one functional unit of your system; each event states which components it affects, so the scope of impact is clear. Related components can be grouped into **Sections**.

### Event types

| Type | Description |
| --- | --- |
| **Incident** | Unexpected events that affect service availability |
| **Maintenance** | Planned events to notify users in advance of possible service changes |

### Impact status

<Tabs>
  <Tab title="Incident Impact Status">
    In order of increasing severity:
    - 🟢 Operational
    - 🟡 Degraded Performance
    - 🟠 Partial Outage
    - 🔴 Full Outage
  </Tab>
  <Tab title="Maintenance Impact Status">
    - 🟢 Operational
    - 🔵 Under Maintenance
  </Tab>
</Tabs>

## FAQ

<AccordionGroup>
<Accordion title="What’s the difference between a Status Page and an Uptime Monitor?" defaultClose>
Both a status page (such as Flashduty Status Page) and an uptime monitor (such as Uptime Kuma) provide dashboards that display service availability.

The key differences are as follows:

| | Status Page | Uptime Monitor |
| --- | --- | --- |
| Audience | External customers & cross-functional internal teams | Internal operations / engineering teams |
| Typical deployment | Third-party hosted | Self-hosted |
| Monitoring approach | Does not perform monitoring probes itself; relies on reported events | Performs monitoring probes directly |
| Monitoring capabilities | Rich event information, including affected services, severity, and lifecycle | Basic service checks such as website / API / DNS / port availability |
| Notification model | End users can self-subscribe to updates | Notification channels are configured by operations teams |
| Focus | Enables transparent internal and external communication by publishing events during incident response and maintenance | Generates alerts through simple monitoring mechanisms (for example, periodic Ping) to notify technical teams of failures |

If you only need a simple self-monitoring tool for **service availability checks** (such as domain or port probing), use an uptime monitoring tool instead.  
If you need a **formal service status dashboard and notification system** for external customers or internal organizations, Flashduty Status Page is the better choice.
</Accordion>

<Accordion title="Who can access the status page? Who can manage it?" defaultClose>
**Access Control**
- **Public status pages** are accessible to anyone on the public internet and do not require login.
- **Internal status pages** are restricted to organization members and require authentication with a Flashduty account.

**Management Permissions**
Status page management follows Flashduty’s RBAC permission model. Administrators can assign the following roles:
- **Status Page Management**: Create, edit, and delete status pages; manage subscriptions.
- **Status Page Event Management**: Publish, edit, and delete events on status pages.
</Accordion>

<Accordion title="How is service availability calculated?" defaultClose>
For a component, **Partial Outage** and **Full Outage** durations count as downtime. Although maintenance may impact service behavior, Flashduty excludes maintenance time from service uptime calculations.

Flashduty calculates component availability over a rolling quarterly window, as the ratio of uptime to total available time.

Group availability also uses a quarterly window. It's the sum of uptime across all components in the group divided by the sum of their total available time.

**Maintenance** events follow a separate rule. A component shows Under Maintenance only while the maintenance actually runs, from Ongoing until closure. A scheduled maintenance that hasn't started doesn't affect availability charts or the calendar. Uptime calculations exclude components and sections set to "Hide all". They include those set to "Hide uptime" but don't show their statistics publicly. You can choose the uptime display mode in status page settings: chart and percentage, chart only, or none.
</Accordion>

</AccordionGroup>
