Create BlueKing tickets from Flashduty incidents and synchronize workflow node or completion states back to linked incidents.

## Synchronization scope

| Direction | Create tickets from Flashduty | Apply linked ticket states to Flashduty |
| --- | --- | --- |
| Bidirectional | Manual or automatic creation | Supported |
| Flashduty → BlueKing only | Manual or automatic creation | Does not acknowledge or close incidents |
| BlueKing → Flashduty only | Link an existing ticket number; creation is disabled | Supported |

Inbound synchronization applies only to linked incidents. It does not import other BlueKing tickets as new incidents. Acknowledging, closing, or editing an incident does not perform a BlueKing approval or update arbitrary fields on an existing ticket.

## API version and submission mode

Select the version that matches the API documentation provided by your BlueKing administrator. Existing integrations default to the legacy ESB API.

| Setting | Legacy ESB API | ITSM v4 |
| --- | --- | --- |
| Example endpoint prefix | `https://bk.example.com/api/c/compapi/v2/itsm` | `https://bk.example.com/api/itsmv4/prod/api/v1` |
| Submission mode | By service | By workflow or by service |
| Target selection | Select a service | For service submission, enter the portal code, then select a catalog and service. For workflow submission, select a workflow. |
| Link an existing ticket | Enter its ticket number (`sn`) | Enter its ticket ID (`id`), not its number |
| Node mapping | Numeric `state_id` | `activity_key` |

**Test connection and load services** loads catalogs, services, or workflows for the selected mode. Selecting a catalog loads its services; selecting a service or workflow loads its fields. After changing the API version, submission mode, or target, reload fields and configure mappings again.

Request the following v4 resource permissions for the selected mode:

| Method | Endpoint relative to the v4 prefix | Purpose |
| --- | --- | --- |
| GET | `service_catalog/list/` | Service submission: load catalogs |
| GET | `service_catalog/service_list/` | Service submission: load services and workflow identifiers |
| GET | `workflows/` | Service submission: load the published workflow and form |
| GET | `user_workflow/list/` | Workflow submission: load workflows |
| GET | `user_workflow/detail/` | Workflow submission: load the form |
| POST | `ticket/create/` | Create a ticket; not called in inbound-only mode |
| GET | `ticket/detail/` | Query a linked ticket's state and current steps |

Both versions use `X-Bkapi-Authorization`. Put the application credentials and username in the same JSON object; do not send `bk_username` as a separate header. The portal code defaults to `DEFAULT`; use the value provided by your administrator for other portals.

## Prerequisites

1. Confirm that your Flashduty version includes the BlueKing ITSM integration.
2. Prepare a published BlueKing service and identify its creation fields, required values, and workflow node meanings.
3. Obtain the BlueKing application's `app_code` and `app_secret`, and a username authorized to access the target service and tickets.
4. For the legacy ESB API, request application permissions for the following resources. Confirm that the gateway allows the application to access them using the configured username.
5. Ensure that the Flashduty backend can reach the gateway. For callbacks, BlueKing must also be able to reach the Flashduty callback URL.

| Method | BlueKing operation | Purpose |
| --- | --- | --- |
| GET | `get_services` | Load available services |
| GET | `get_service_detail` | Load creation fields and validation rules |
| POST | `create_ticket` | Create tickets; unused in inbound-only mode |
| GET | `get_ticket_info` | Verify the service when linking an existing ticket |
| GET | `get_ticket_status` | Query actual ticket status and current nodes |
| POST | `ticket_approval_result` | Check approval results when completion-based closure is configured |

Production connections use ESB / API gateway authentication. Flashduty sends the application credentials and username in the `X-Bkapi-Authorization` header as `bk_app_code`, `bk_app_secret`, and `bk_username`. If your gateway requires additional headers, configure the names and values supplied by its administrator. Obtain and refresh interactive user tokens separately.

For SaaS, use a public gateway address reachable by the backend. On-premises deployments can use reachable private addresses. Authentication adapters for standalone test environments are for integration testing; passing those tests does not establish compatibility with production gateway authentication.

## Configure the integration in Flashduty

Open the Integration Center, find BlueKing ITSM, and create an integration. Enter its name, description, and management team.

### Connection settings

| Setting | Value |
| --- | --- |
| ESB / API gateway URL prefix | The shared URL prefix for ITSM resources, such as `https://bk.example.com/api/c/compapi/v2/itsm`. Use the actual prefix supplied by your administrator |
| `app_code` | BlueKing application identifier |
| `app_secret` | Application secret. Leave it empty when editing to retain the saved credential |
| BlueKing user | The authorized username, rather than the user's password |

Do not append an operation such as `get_services`, query parameters, or embedded URL credentials to the prefix. Flashduty appends each operation name and a trailing `/`. A console login URL or a standalone instance's raw OpenAPI URL may differ from the production gateway prefix.

Click **Test connection and load services**, then select a ticket service. This checks service-list access only. Ticket creation, status queries, and callbacks require separate verification.


### Custom headers

Under **Headers** in the connection settings, add or remove name/value pairs such as `Host: bk.example.com` or `Portal: DEFAULT`. They apply to catalog, service, and workflow discovery, ticket creation, and subsequent ticket queries. For `Host`, enter a hostname and optional port without a scheme or path. It does not change DNS resolution or the hostname used for HTTPS certificate verification.

`X-Bkapi-Authorization` is generated from the application credentials and operator. `Content-Type` is fixed to `application/json`. Do not add either header manually. Header names are case-insensitive and must be unique.

Saved header values are masked. Keep a mask unchanged to reuse its saved value, or delete the row to remove the header; renaming a saved header means re-entering its value. After changing the gateway URL, `Host`, `app_code`, or the **BlueKing operator**, re-enter `app_secret` and the saved header values, then test the connection.

### Synchronization settings

Choose a direction and the channels covered by this integration. Each integration uses one BlueKing service or v4 workflow and keeps one ticket association per incident. Create separate integrations for different services.

When outbound creation is enabled, choose a trigger mode:

- **Manual**: In the incident's BlueKing ITSM section, open **Create or link a BlueKing ticket**, select the integration, leave the ticket number (or v4 ticket ID) empty, and create the ticket.
- **Automatic**: Configure matching conditions. Eligible incidents can create tickets when a creation, acknowledgment, closure, or field-update event is processed. Saving the integration does not scan historical incidents. An existing association prevents duplicate creation.

Outbound-only mode does not require callback or status mappings. Inbound-only mode hides creation triggers; link an existing ticket number (or v4 ticket ID) to establish the association.

## Creation field mappings

Select a service before adding mappings. Target fields come from its definition, and each target field can appear only once.

| Incident field source | What to enter in the value / label / custom-field input |
| --- | --- |
| Title, description, severity, resolution, incident ID | Leave empty; Flashduty reads the selected incident property |
| Constant | The literal value to write |
| Label | A label key, such as `service` |
| Custom field | The custom field's Key, rather than its display name |

For the legacy ESB API, Flashduty uses the incident title when `title` has no explicit mapping. In v4, map the title explicitly using the selected workflow's actual key, such as `ticket__title` or `ticket_title`; do not reuse field keys across different workflows. Map other required fields and ensure that their sources contain values when the ticket is created. Missing labels, custom fields, or empty values can cause creation to fail. Inbound-only synchronization does not require creation field mappings.

V4 preserves JSON Schema field types. Enter boolean constants as `true` or `false`, and arrays or objects as valid JSON. Required nested properties must be present. BlueKing validates workflow-specific controls and custom rules.

For the legacy ESB API, values are converted using the BlueKing field type. Integer and number fields require valid numeric values. String values for multiselect, checkbox, or custom-table fields must contain valid JSON, such as `["a","b"]` for a multiselect. Use actual option keys for enumerations. Severity uses the original incident value and is not automatically converted to BlueKing priority.

For example, map a service-name field to **Label / `service`** and an environment field to **Constant / `production`**. Both target fields must exist in the selected service.

Mappings write values at creation only. After republishing service fields or workflows, reload the fields, review the mappings, and verify them using a test incident.

## Synchronize BlueKing states

### Node mappings

Add a mapping using a published workflow node ID and an **Acknowledge incident** or **Close incident** action. For the legacy ESB API, the ID is `current_steps[].state_id`. For v4, use `current_steps[].activity_key` from ticket details, rather than a ticket ID, ticket number, or node name.

| Configuration | Condition | Incident action |
| --- | --- | --- |
| Node ID → acknowledge | Both the ticket and mapped node are `RUNNING` | Acknowledge |
| Node ID → close | Both the ticket and mapped node are `RUNNING` | Close |
| Completion action → close | Ticket is `FINISHED` and a fresh approval query confirms approval | Close |

**A node mapping takes effect when the ticket enters the node, not when that node finishes.** Map a node to closure only if entering it means that the incident is already resolved. Do not map pending approval or work-in-progress nodes to closure. Avoid conflicting actions across parallel nodes.

The completion action is optional. Leaving it empty prevents completion alone from closing the incident. Termination (`TERMINATED`), withdrawal (`REVOKED`), or a completed ticket with a negative approval result does not trigger completion-based closure. Running tickets still follow node mappings; ensure that rejection branches cannot enter nodes mapped to closure.

Inbound updates do not reopen closed incidents or move them back to processing. Flashduty does not automatically approve, transfer, or withdraw BlueKing tickets.

V4 state comparisons ignore case, so `running` and `RUNNING` are equivalent. Unknown states do not automatically resolve an incident. A false `approve_result` on a draft or running ticket alone does not mean rejection; completion-based resolution requires `FINISHED` and an explicitly approved result.

If the deployment returns only node names without `activity_key`, v4 node mappings cannot be used; do not substitute a node name for its identifier.

### Callbacks

1. Complete the connection and synchronization settings, then save the integration. Its callback URL is not available before the first save.
2. Reopen the integration for editing. In the documentation panel, find **Callback URL for this integration** and copy the complete address, including `integration_key`. Do not assemble the address manually or reuse an example key or another integration’s key.
3. To register a completion callback during ticket creation, enter the copied address in the callback setting and save again before creating tickets. The legacy ESB API uses `meta.callback_url`; v4 uses the top-level `callback_url`.
4. For updates during the workflow, configure HTTP triggers for the relevant BlueKing events. Send a `POST` request to the same URL with `Content-Type: application/json`.
5. Put the actual ticket number in the top-level `sn` property. Trigger variable syntax varies by BlueKing version; select the ticket-number variable available in your deployment instead of hardcoding a test number.

```json
{
  "sn": "REQ20261022000001"
}
```

Flashduty identifies the integration using `integration_key` and queries BlueKing for the actual ticket state. Payload status and approval values do not directly acknowledge or close incidents. A callback does not establish an association; link existing tickets first. HTTP 200 alone does not prove that an incident changed state.

To verify the callback chain, use a **test incident and its linked ticket number**:

```sh
curl --request POST '<complete BlueKing callback URL>' \
  --header 'Content-Type: application/json' \
  --data '{"sn":"<linked test ticket number>"}'
```

A background worker also reconciles linked tickets that have not reached an end state, covering missed callbacks. Reconciliation is periodic rather than real-time. Use **Refresh status** in incident details when checking an outcome.

## Link existing tickets and retry failed creation

Open **Create or link a BlueKing ticket** in incident details. Select the integration, enter an existing ticket number, and link it. The ticket must belong to the integration's service, and the incident must belong to one of its channels.

If creation fails or its result is unknown, first search BlueKing using the incident title and creation time:

1. If the previous attempt may still be running, wait at least 60 seconds before checking again. Flashduty rejects retries made too early.
2. If a matching ticket exists, link its number instead of creating another ticket.
3. If no ticket exists, use **Retry after reconciliation** and confirm the warning.

Do not change the integration's service as a retry workaround. Existing associations must retain the same service.

## Verification and troubleshooting

Use test incidents to verify manual creation, linking an existing ticket, entry into an acknowledgment node, approved completion, rejection or withdrawal, reconciliation after callbacks stop, and inbound-only / outbound-only restrictions before connecting business workflows.

| Symptom | Check first |
| --- | --- |
| Connection failure, 401, or 403 | Prefix, credentials, application resource permissions, username policy, and network access |
| Connection passes but the service is unavailable | Whether the service is published and the user has access |
| Required-field, type, or option errors | Current field keys, actual source values, numeric / JSON format, and enumeration keys |
| Existing ticket cannot be linked | Ticket number, matching service, and incident channel scope |
| Callback succeeds but the incident stays unchanged | Existing association, inbound direction, current node ID, and whether the node is running |
| Completion does not close the incident | Configured completion action and a queryable positive approval result; payload claims are insufficient |
| Creation result awaits reconciliation | Check for an existing remote ticket, then link it or explicitly retry after confirming absence |

Ordinary comments, arbitrary post-creation field updates, automated BlueKing approvals, and bulk ticket imports as new incidents are currently unsupported. BlueKing's `comment` API is a completion rating, rather than an ordinary comment.

## Public references

BlueKing publishes its [create-ticket contract](https://github.com/TencentBlueKing/bk-itsm/blob/develop/docs/itsm_bkapi/apidocs/en/create_ticket.md) and [ticket-status contract](https://github.com/TencentBlueKing/bk-itsm/blob/develop/docs/itsm_bkapi/apidocs/en/get_ticket_status.md). Authentication policies and resource paths depend on your BlueKing version and administrator configuration. This page describes the capabilities implemented by the current Flashduty integration.

V4 callbacks may place the number in `ticket.sn`:

```json
{"ticket":{"sn":"SN-EXAMPLE"}}
```

If both `sn` and `ticket.sn` are sent, they must match. Keep the integration's `integration_key` in the callback URL; the application secret cannot replace it. A callback only requests a fresh query of a linked ticket; its state is not trusted directly.

## Call history

Open **Call history** on the BlueKing integration detail page. Filter by time (presets from the last 30 minutes to the last 30 days, defaulting to the last 7 days, spanning at most 30 days), incident ID (a full 24-character ID), channel, or success/failure. The list shows the time, operation, incident, BlueKing ticket, channel, and result. Open a record to see its duration, remote status, and error message.

Creation, reconciled retries, linking, and status refreshes are recorded separately. Refreshes triggered manually, by callbacks, or by periodic reconciliation are included. If creation succeeds but the following refresh fails, the two results remain separate. Connection tests and service/field discovery are excluded.

History records new calls after the feature is enabled, without backfilling older calls, and retains them for 30 days. Background checks record failures and changes to ticket state or linked incident actions; manual refreshes and callback-triggered queries are recorded as usual. Authentication headers, secrets, and raw request or response bodies are never recorded.
