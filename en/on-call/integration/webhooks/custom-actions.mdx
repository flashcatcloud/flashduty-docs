Configure incident custom actions, allowing you to quickly call external interfaces during incident troubleshooting to achieve self-healing, information enrichment, or any custom operations.

## Create action

1. Login to Flashduty console, go to **Integration Center - Webhook**
2. Click to add Custom Action integration
3. Configure Action Name—this name will appear as a button in incident details
4. Configure Managing Team—select the team that manages this integration; only team members can edit the integration configuration
5. Configure Channels—you can configure multiple, but each channel can have at most **5** Custom Actions
6. Configure Endpoint and custom Headers
7. **TLS Verification** is enabled by default. If the target service uses a self-signed or internal-CA certificate, turn off **TLS Verification**, and Flashduty skips validating the server certificate

<Warning>
Disabling TLS certificate verification may expose you to man-in-the-middle attacks. Only disable it in test environments or when using self-signed certificates.
</Warning>
8. Save to complete

<Warning>
Each channel can have a maximum of 5 custom actions. You can't select a channel that has reached this limit when adding a custom action.
</Warning>

## Edit a saved action

Once saved, the Endpoint, the custom Headers values, and the custom request body are treated as secrets and are never shown back: the integration detail page shows a **Saved; hidden for security reasons** hint in place of the Endpoint, and the Headers and custom Payload values read as `******`.

The edit form pre-fills those fields with `******`, and saving follows these rules:

| What you submit | What gets saved |
| --- | --- |
| Leave the `******` mask untouched | The stored value is kept; it is never overwritten with the mask |
| Type a new value | The new value replaces the stored one |

To change the Endpoint, a Header value, or the request body, you therefore have to retype it — the saved content can't be read back from the console. If you change the Endpoint while another secret field still holds `******`, the save is rejected and asks you to enter the saved secrets again, because those secrets would otherwise be sent to the new address.

## Push description

### Request method

<div className="md-block">

POST, Content-Type:"application/json"

</div>

### Request payload:

<div className="md-block">

| Field | Type | Required | Description |
| :--------: | :-------------------: | :--: | :--------- |
| event_time | int64 | Yes | Event timestamp in `milliseconds` |
| event_type | string | Yes | Event type, fixed value `i_custom` |
| event_id | string | Yes | Event ID, `the same event may retry multiple times due to timeout, receiver needs to deduplicate` |
| event_detail | object | No | Event details, fixed structure see [Event details](#EventDetail) below |
| person | [Person](/en/on-call/integration/webhooks/incident-webhook#Person) | No | Operator, only exists for human actions |
| incident | [Incident](/en/on-call/integration/webhooks/incident-webhook#Incident) | Yes | Incident details |

The fields of `person` and `incident` (including [Responder](/en/on-call/integration/webhooks/incident-webhook#Responder), [AssignedTo](/en/on-call/integration/webhooks/incident-webhook#AssignedTo), and [Image](/en/on-call/integration/webhooks/incident-webhook#Image)) are the same as in [Incident Webhook](/en/on-call/integration/webhooks/incident-webhook#request-payload), with these differences:

- `incident.alerts` additionally returns the associated alert list, described in [Alert](#Alert) below; the field is not returned when there is no associated alert.
- `incident.links` isn't returned; use Incident Webhook to get it.

<span id="Alert"></span>
**Alert**:

| Field | Type | Required | Description |
| :--------------: | :-----------: | :--: | :----------------- |
| alert_id | string | Yes | Alert ID |
| account_id | int64 | Yes | Account ID |
| integration_id | int64 | Yes | Integration ID |
| channel_id | int64 | Yes | Channel ID |
| title | string | Yes | Alert title |
| title_rule | string | No | Title generation rule |
| description | string | No | Alert description |
| alert_key | string | Yes | Alert association key |
| alert_severity | string | Yes | Severity, enum: Critical, Warning, Info |
| alert_status | string | Yes | Alert status, enum: Critical, Warning, Info, Ok |
| progress | string | Yes | Progress, enum: Triggered, Closed |
| created_at | int64 | Yes | Created time |
| updated_at | int64 | Yes | Updated time |
| start_time | int64 | Yes | First trigger time (time of first event received by platform), Unix seconds timestamp |
| last_time | int64 | Yes | Latest event time (time of latest event received by platform), Unix seconds timestamp |
| end_time | int64 | No | Alert recovery time (time platform last received end-type event), Unix seconds timestamp, default 0 |
| close_time | int64 | No | Close time, different from end_time, this is progress close, doesn't mean alert truly recovered. Unix seconds timestamp, default 0 |
| ever_muted | bool | Yes | Whether the alert has ever been silenced by a silence rule |
| labels | map[string]string | No | Label KV, both Key and Value are strings |
| event_cnt | int64 | No | Associated event count |
| images | [][Image](/en/on-call/integration/webhooks/incident-webhook#Image) | Yes | Alert image list; null when there are no images |

The alert object in custom actions has these limits:

- `incident`, `integration_ref_id`, and `data_source_type` aren't returned.
- `integration_name`, `integration_type`, `channel_name`, `channel_status`, `responder_name`, `responder_email`, `data_source_name`, and `data_source_ref_id` are always empty strings.
- `data_source_id` equals `integration_id`; use `integration_id`.

<span id="EventDetail"></span>
**event_detail** (fixed structure for i_custom):

| Field | Type | Required | Description |
| :-------- | :------: | :--: | :--- |
| integration_id | int64 | No | ID of the triggered custom action integration |
| integration_name | string | No | Name of the triggered custom action integration |

</div>

### Request response

HTTP status code 200 indicates successful push.

## Custom request body and value mapping

Custom actions support **custom request body** and **value mapping** the same way as Incident Webhook. Variable paths refer to fields in the [request payload](#request-payload) above. For syntax and examples, see [Incident Webhook](/en/on-call/integration/webhooks/incident-webhook#custom-request-body).

## Use cases

### Restart host

When host memory or CPU is maxed out, trigger a host restart script to quickly complete the restart.

### Information enrichment

When an incident occurs, call back your service to fetch tracing, logging, topology, and other details for the alert. Your service then calls the Flashduty Open API to update the incident, for example by adding labels or setting custom fields.

### Rollback changes

When an incident occurs, if a change caused it, directly trigger a callback to your deployment platform to start the rollback process and accelerate incident recovery.

### Update status page

When you confirm an incident affects production services, trigger external status page updates to promptly notify your customers or upstream/downstream parties.

## FAQ

1. **Is there a response timeout?**

   - Your service must respond within 2 seconds; Flashduty treats a slower response as a failure

2. **Will pushes continue after failure?**

   Flashduty retries only these network errors, at most once:
   - Connection or read/write timeout (`i/o timeout`)
   - Connection closed early by the peer (`EOF`)

   Flashduty doesn't retry when the request was sent and the wait for response headers timed out.
