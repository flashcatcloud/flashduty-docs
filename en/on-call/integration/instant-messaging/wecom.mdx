## Self-built app integration

1. Visit the [WeCom Admin Console](https://work.weixin.qq.com/wework_admin/frame#apps), go to App Management → **Apps**, and click **Create App**.

   ![WeCom: Self-built App Integration screenshot](https://docs-cdn.flashcat.cloud/images/png/ed274f6a897b808678a5a29b23adcb66.png)

2. Configure **App Logo**, **App Name**, and **App Visibility**.

   ![WeCom: Self-built App Integration screenshot](https://docs-cdn.flashcat.cloud/images/png/26ec124891e580a6d1e1035ba52636ba.png)

3. Create a WeCom integration in Flashduty, choose **Self-built app (recommended)** under **Application version**, and fill in the following under **App credentials**.

   - **Corp ID (My Company)**: find it at the bottom of the **My Company** page in the WeCom Admin Console.
   - **AgentId (app details)** and **Secret (app details)**: in **App Management**, click the app you just created and copy them from its details page.

   ![WeCom: Get the Corp ID on the My Company page screenshot](https://docs-cdn.flashcat.cloud/images/png/c032dc755a72550d57658dd5962dafe4.png)

4. Fill in the **Access domain**: a subdomain of a domain filed under your company, for example `flashduty.example.com`. Enter the domain only, without `https://` or a path. WeCom requires the trusted domain and callback URLs to be on a domain filed (ICP) under your company.

   If you use an on-premises WeCom deployment, turn on **Is on-premises deployment** and enter the **Endpoint**. Flashduty must be able to reach it, so add it to your allowlist.

5. Click **Save**. Flashduty generates the Token and EncodingAESKey for receiving messages and for the intelligent bot, so you don't enter them here. After saving, follow the next section, "Finish setup in WeCom".

## Finish setup in WeCom

This section applies only to self-built apps. Step 1 is done at your DNS provider and the rest on the app details page in the WeCom Admin Console. The step numbers on the integration detail page match this section. Flashduty checks steps 1–4 and 6 and ticks them automatically; confirm step 5 manually when you're done. Step 6 is optional.

<Note>
An on-premises Flashduty deployment has no step 1, so the step numbers on its detail page are one lower than in this doc. Put the verification file at the root of the access domain yourself (served directly over both http and https, without redirects), then click **I've verified it**; for the trusted IP, enter the egress IP of your Flashduty servers.
</Note>

<span id="step-dns"></span>

### 1. Add DNS records

At the DNS provider of the access domain, add the two CNAME records listed in step 1 of the integration detail page. The first proves you own the domain, so Flashduty can issue the HTTPS certificate; the second sends traffic to a Flashduty access address. You don't need your own Nginx or reverse proxy, or your own certificate.

Choose the access address by the domain's ICP filing:

| Access address | Location | Domains it works for |
| :--- | :--- | :--- |
| `wecom.flashduty.com` (default) | Hong Kong | Any ICP-filed domain |
| `cn.wecom.flashduty.com` | Mainland China | Domains whose ICP filing has been added to Alibaba Cloud; faster access in mainland China |

If your DNS provider supports geo-based resolution, set both. Alibaba Cloud blocks domains pointed at the mainland address without such a filing.

The step is ticked once both records resolve and the certificate is issued. Click **Check again** to refresh the status right away.

<span id="step-trusted-domain"></span>

### 2. Set the trusted domain

1. Open the app details › Developer API › **Web authorization and JS-SDK**, click **Set trusted domain**, and enter the access domain.
2. Click **Verify domain**, download `WW_verify_xxx.txt`, and click **Upload verification file** in step 2 of the integration detail page. Flashduty serves the file at the root of the access domain.
3. Go back to WeCom and click **Confirm** to finish verification. On the same page, also enter this domain as the OAuth2.0 web authorization callback domain.

The step is ticked once WeCom fetches the verification file.

<Note>
WeCom requires the domain's ICP filing entity to be your company or a related one (parent/subsidiary, head office/branch). Otherwise WeCom won't save it; use another domain or submit proof of the relationship to WeCom support. See WeCom's [Enterprise Internal Development Domain Configuration Guide](https://open.work.weixin.qq.com/wwopen/common/readDocument/40754).
</Note>

![WeCom: Set the trusted domain screenshot](https://docs-cdn.flashcat.cloud/images/png/09a91d682198d1c8f830b5ed523965ef.png)

### 3. Set up API message receiving

1. Open the app details › Receive messages › **Set API receiving**.
2. In step 3 of the integration detail page, click **Generate and show**, paste the URL, Token, and EncodingAESKey into WeCom, and click **Save**. WeCom calls the URL to verify as soon as you save.

The step is ticked once WeCom verifies the URL.

<Warning>
The Token and EncodingAESKey are shown only once, when they are generated, and can't be viewed after you leave the page, so copy them into WeCom right away. Don't click **Random** in WeCom: both sides must use the pair Flashduty generated. Regenerating invalidates the saved pair immediately, so enter the new values in WeCom and save.
</Warning>

If WeCom says the callback request failed, first make sure step 1 is done, then make sure the Token and EncodingAESKey were copied from the integration detail page.

![WeCom: Set API receiving screenshot](https://docs-cdn.flashcat.cloud/images/png/c990c27f7ad90af172e159fc4acfead7.png)

### 4. Set the trusted IP

At the bottom of the app details page, click **Configure** under **Trusted IPs** and enter the IP shown in step 4 of the integration detail page. WeCom lets you set trusted IPs only after step 2 or step 3 is done.

Every company using Flashduty enters this same IP. If WeCom says the IP belongs to a third-party service provider, send a screenshot of the error to Flashduty support. The step is ticked once Flashduty can call the WeCom API with the app's credentials.

![WeCom: Set the trusted IP screenshot](https://docs-cdn.flashcat.cloud/images/png/fe3b2b788dda5d331148ba0946631b91.png)

### 5. Set the workbench homepage

On the app details page, click **Set** under **Workbench homepage**, choose **Web page**, and enter the address shown in step 5 of the integration detail page. Members use this address when they open Flashduty from the WeCom workbench.

WeCom doesn't report this setting back, so click **I've set it** on the integration detail page when you're done.

![WeCom: Set the workbench homepage screenshot](https://docs-cdn.flashcat.cloud/images/png/595a71dd5624a37312676e83c45d79c4.png)

<span id="step-bot"></span>

### 6. Create an intelligent bot

Optional. Once it's set up, people can @mention the intelligent bot in WeCom direct and group chats to start an AI SRE session. AI SRE must be enabled for your account, and **Allow AI SRE conversations in IM** must be on in the integration (War Room is not required); otherwise the bot doesn't respond to messages.

1. In the WeCom client, go to **Workbench** › **Intelligent bots**, create a bot, and choose **Create manually** › **Create in API mode**. Have a member of your company create it: other members see the bot only after its creator shares it.
2. In the bot's API settings, choose **Use URL callback**. In step 6 of the integration detail page, click **Generate and show**, enter the URL, Token, and EncodingAESKey in WeCom, and save. WeCom sends one verification request to the URL, which Flashduty answers automatically.

The step is ticked once WeCom verifies the URL. For usage and troubleshooting, see [AI SRE intelligent bot](#aisre-bot) below.

<Warning>
The intelligent bot uses its **own** Token and EncodingAESKey, separate from the pair for receiving messages in step 3. Mixing the two causes signature verification failures.
</Warning>

## Third-party app integration

<Info>
As a WeCom service provider, Flashduty provides a long-term free version of the Flashduty app. This app requires WeCom API call authorization to use (passwordless login + message sending). This authorization currently supports **up to 60 days** free; beyond this usage period, Flashduty needs to purchase WeCom licenses for you before you can continue using it.
</Info>

1. Visit [WeCom Admin Console](https://work.weixin.qq.com/wework_admin/frame#apps), go to App Management → **Apps** page, click **Add Third-Party App**.

   ![WeCom: Third-Party App Integration screenshot](https://docs-cdn.flashcat.cloud/images/png/ae4d35a354aaf22dd41b7493200517bc.png)

2. Enter `Flashduty` in the search bar, after finding the app, click **Add**.

   ![WeCom: Third-Party App Integration screenshot](https://docs-cdn.flashcat.cloud/images/png/77347db478c45f4c9d238d587d323a78.png)

3. Modify app **Visibility**, recommend selecting all employees or specific department nodes to avoid modifying when new enterprise members join. Then click **Agree to the above authorization and add** to complete installation.

   ![WeCom: Third-Party App Integration screenshot](https://docs-cdn.flashcat.cloud/images/png/0821d1afdeb5db34c4c9b5548d5c8ca1.png)

4. Create a WeCom integration in Flashduty, choose **Third-party app (scan to install)** under **Application version**, choose **Flashduty app already installed** under **How to bind your enterprise**, and click **Save**.

5. Have any member of the enterprise scan the QR code that appears with the WeCom app and confirm the binding on the page that opens. The integration is saved automatically once confirmed.

If your enterprise hasn't installed the Flashduty app yet, you can skip steps 1–3: choose **Flashduty app not installed yet** under **How to bind your enterprise**. On save, the WeCom authorization page opens, an enterprise admin scans to install the app, and the enterprise is bound when installation completes.

## Linked users

In the **Linked Users** tab of the integration detail page, you can view the linking status between team members and WeCom accounts, and quickly complete batch linking.

### View linking status

The list shows every team member and their linking status. Filter by **All / Linked / Unlinked**, or search by name or email.

### One-click linking

When unlinked members exist, click the **One-Click Link** button. The system will attempt to obtain WeCom account IDs by phone numbers or emails and automatically link them, equivalent to members logging into Flashduty using the same information on WeCom.

<Tip>
The system can only push WeCom message notifications after members complete linking. If linking fails, verify that the member's phone number or email matches their WeCom account.
</Tip>

## Configure war room

<Warning>
War Room functionality is only supported in **Self-built app** mode.
</Warning>

After completing previous steps, in the Flashduty On-call integration configuration page's **Enhanced Features** section, check **Enable War Room** to activate this feature—no additional configuration needed.

<Warning>
Only one IM integration can have War Room enabled at a time. If another IM integration (such as Dingtalk, Feishu/Lark, or Slack) has it on, turn it off there first.
</Warning>

## AI SRE controls

Configure the following AI SRE control in the integration configuration page's **Enhanced Features** module. It is enabled by default:

- **Allow AI SRE conversations in IM**: Available without enabling War Room. It controls both entry points of this integration — @ AI SRE in group chats and direct chats with the bot. When disabled, the corresponding entry point does not trigger an AI SRE reply.

The two WeCom app modes support different AI SRE entry points. **Allow AI SRE conversations in IM** is shown in both modes, and the integration detail preview also shows its status:

| App mode | @ AI SRE in group chats | Direct chat with the bot |
| :--- | :--- | :--- |
| **Self-built app** | Supported | Supported |
| **Third-party app** | Not supported; switch to **Self-built app** mode | Supported |

These controls do not take effect until AI SRE is enabled for the account.

The automatic AI incident analysis that follows a War Room creation is no longer configured on this page: to start one when a War Room is created, add a rule in [Automations](/en/ai-sre/automations), choose the **War room created** trigger, and select the channels and severities to watch.

## AI SRE intelligent bot

@mention the intelligent bot in a WeCom direct or group chat to start an AI SRE investigation session without leaving WeCom. The intelligent bot can only be configured in **Self-built app** mode; for setup, see [6. Create an intelligent bot](#step-bot).

<Warning>
WeCom does not automatically add the intelligent bot to a War Room group after the War Room is created. To use AI SRE in the War Room, manually add the intelligent bot to the corresponding group chat.
</Warning>

### How to use

Once configured, **@mention the intelligent bot** in a WeCom direct or group chat and type a question or incident description to start an AI SRE session. Supported message types:

| Type | Description |
| :--- | :--- |
| **Text** | Ask a question or describe a problem directly |
| **Image** | Send a screenshot; AI will analyze the image content |
| **File** | Send a log or config file; AI will read and help investigate |
| **Quoted reply** | Quote a previous message to follow up; AI uses conversation history for context |

<Note>
WeCom intelligent bots use **pull-based streaming** (stream polling): while AI writes a reply, the WeCom client polls the callback URL with `msgtype=stream` requests until the reply is complete. WeCom handles this; you don't configure anything.
</Note>

### Troubleshooting

<AccordionGroup>

<Accordion title="The bot receives messages but returns no response">
Check in order:
1. Confirm that AI SRE is enabled for your account and **Allow AI SRE conversations in IM** is on in the integration.
2. Confirm that the URL entered in WeCom was copied from step 6 of the integration detail page, so its `integration_key` matches the integration.
3. Confirm that the Token and EncodingAESKey entered in WeCom are the pair generated in step 6, not the pair for receiving messages from step 3.
4. Check the bot's callback records in WeCom (if available) to see whether requests arrive and whether any error codes are returned.
</Accordion>

<Accordion title="'URL verification failed' when saving the callback URL">
- Confirm that [1. Add DNS records](#step-dns) is done and the certificate has been issued.
- Confirm that the Token and EncodingAESKey entered in WeCom exactly match the values most recently generated in step 6.
- Confirm that the `integration_key` parameter in the callback URL is correct and that the corresponding integration is enabled.
</Accordion>

<Accordion title="Signature verification failure (invalid signature)">
This usually means the Token or EncodingAESKey is wrong. The intelligent bot's credentials and the credentials for receiving messages in step 3 are **two independent pairs**. Regenerate them in step 6 of the integration detail page and update the bot's API settings in WeCom with the new values.
</Accordion>

</AccordionGroup>

## FAQ

<AccordionGroup>
<Accordion title="After clicking integration save button, system shows 'authorize app first' error?">
- Check if you've completed the app installation steps. For example, can you see the Flashduty On-call app in WeCom Workspace
- Check that **How to bind your enterprise** is set correctly: if your enterprise hasn't installed the app yet, choose **Flashduty app not installed yet**
</Accordion>

<Accordion title="How to complete account linking or message delivery shows 'App not linked'?">
1. Login to WeCom client (desktop or mobile), go to **Workspace**, find and open the Flashduty app
2. First entry requires login. Select your member account, after successful login with a password or SSO, Flashduty account and WeCom account will be linked
3. Subsequent app access will be automatically passwordless
</Accordion>

<Accordion title="How to send incident notifications?">
1. Before sending notifications, account linking must be completed as described in the previous question
2. Go to the specified channel, navigate to `Escalation Rules` → **Personal Channel**, select `WeCom` as notification method
3. Flashduty On-call supports customizing WeCom notification content. Go to **Template Management** page to set custom templates

<Note>
Custom area can display up to 8 lines; excess will be truncated by WeCom.
</Note>

![WeCom: How to send incident notifications? screenshot](https://docs-cdn.flashcat.cloud/images/png/9cb6a325b4b16875fec3e0c5054be25b.png)
</Accordion>

<Accordion title="How to handle alerts within WeCom?">
- Click card message to go directly to alert details page
- Click **Start Processing** to directly set alert to `Processing` status
- Click **Close Directly** to directly set alert to `Closed` status
- Click **Snooze 2 hours** to snooze the alert for 2 hours. For longer snooze times, click `...` in the card's top-right corner for more snooze options
</Accordion>

<Accordion title="Why does the card message have a 'Refresh Status' button?">
Due to WeCom limitations, after one card interaction, it can only be updated once within 72 hours. Each button operation counts as one interaction.

When alert status changes, Flashduty On-call requests to update card content. When alert status changes frequently, cards may not update in real-time due to exceeding update limits. You can click the **Refresh** button to manually get one card status update opportunity.
</Accordion>

<Accordion title="How to set Mac desktop to open with system default browser?">
On Mac, WeCom opens links in its built-in browser by default. Press `ctrl` + `command` + `shift` + `d` to enable debug mode, then select **Debug** → **Browser, WebView Related** → **Open Webpage with System Browser**. Press the same shortcut to leave debug mode; the setting stays.
</Accordion>

<Accordion title="Incident notification failed with 'WeCom license not enabled' prompt?">
Contact Flashduty customer service or your dedicated technical support to purchase and enable the license.
</Accordion>

<Accordion title="Why isn't War Room working as expected?">
See the **FAQ** section in [War Room documentation](/en/on-call/advanced/war-room).
</Accordion>

<Accordion title="Why does opening the app in WeCom Workspace show 'redirect_uri needs to use app trusted domain'?">
The `redirect_uri` in the workbench homepage address uses the access domain. Make sure [2. Set the trusted domain](#step-trusted-domain) is done and the access domain has passed WeCom's ownership verification, and that **Workbench homepage** is set to the address shown in step 5 of the integration detail page.
</Accordion>
</AccordionGroup>
