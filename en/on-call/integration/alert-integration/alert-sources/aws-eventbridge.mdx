This integration receives Amazon EventBridge events, either pushed directly by an API destination or relayed by an SNS topic. CloudWatch alarm, GuardDuty, Security Hub, AWS Health, Amazon Inspector, AWS Config and DevOps Guru events merge per alarm or finding and recover automatically when the source recovers. Every other event creates one alert.

## In Flashduty On-call
You can get the integration push URL in either of the following ways.

### Use a dedicated integration

Choose this option if all alerts go to one channel. It's the simpler setup.

<AccordionGroup>
  <Accordion title="View dedicated integration setup steps">
  
  1. In the Flashduty console, select **Channel** and open a channel
  2. Select **Configuration** → **Integrations** → **Private integration**, then click **Add an integration**
  3. Choose **AWS EventBridge** integration and click **Save** to generate a card
  4. Open the generated integration card and copy the **Push URL**
  
</Accordion>
</AccordionGroup>

### Use a shared integration

Choose this option if you need to route alerts to different channels based on the alert payload.

<AccordionGroup>
  <Accordion title="View shared integration setup steps">
  
  1. In the Flashduty console, go to **Integration Center → Alert Events**
  2. Select **AWS EventBridge** integration:
        - **Integration Name**: Define a name for this integration
  3. Configure the default route and select a channel. You can add more rules under **Routing** after creation
  4. Click **Save** and copy the generated **Push URL**
    
</Accordion>
</AccordionGroup>

## Configure in AWS EventBridge

<Steps>
<Step title="Create an API destination that points to Flashduty in Amazon EventBridge">

<Tabs>
<Tab title="API destination (recommended)">

**Where**: Amazon EventBridge › Integration › API destinations › Connections › Create connection

| Field | Value |
| --- | --- |
| Connection name (required) | `Flashduty` |
| Destination type (required, under Authorization) | `Other` |
| Authorization type (required) | `API Key` |
| API key name (required) | `Flashduty` |
| Value (required) | `{integration_key}`, the `integration_key` in the push URL |

Click **Create** to save.

<img alt="Connection settings" width="600" src="https://download.flashcat.cloud/flashduty/doc/aws-eb-4.png" />

**Where**: Amazon EventBridge › Integration › API destinations › Create API destination

| Field | Value |
| --- | --- |
| Name (required) | `Flashduty` |
| API destination endpoint (required) | `{integration_url}` |
| HTTP method (required) | `POST` |
| Connection type (required) | `Use an existing connection`, then select the `Flashduty` connection created above |

Click **Create** to save.

<img alt="API destination settings" width="600" src="https://download.flashcat.cloud/flashduty/doc/aws-eb-6.png" />

</Tab>
<Tab title="SNS topic">

**Where**: Amazon SNS › Subscriptions › Create subscription (if the topic does not exist yet, go to Topics › Create topic first and set `Type` to `Standard`)

| Field | Value |
| --- | --- |
| Topic ARN (required) | The SNS topic that forwards EventBridge events |
| Protocol (required) | `HTTPS` |
| Endpoint (required) | `{integration_url}`, which must be the push URL of **this** integration |

Click **Create subscription** and wait until the subscription status is `Confirmed`. Flashduty only visits subscription confirmation URLs on `sns.<region>.amazonaws.com`, `sns.<region>.amazonaws.com.cn` and `sns.<region>.amazonaws.eu`. For the full SNS topic and subscription steps, see the [AWS CloudWatch integration](/en/on-call/integration/alert-integration/alert-sources/aws-cloudwatch).

</Tab>
</Tabs>

</Step>
<Step title="Create an event rule in Amazon EventBridge">

**Where**: Amazon EventBridge › Rules › Create rule › Advanced Builder

| Field | Value |
| --- | --- |
| Builder (when the console offers a choice) | `Advanced Builder` |
| Name (required) | A name of your choice, for example `Flashduty-Events` |
| Event bus | `AWS default event bus` |
| Rule type (required) | `Rule with an event pattern`, then click **Next** |
| Event source (required) | `AWS events or EventBridge partner events` |
| Creation method / Method (required) | `Custom pattern (JSON editor)` |
| Event pattern (required) | Paste the event pattern below, then click **Next** |
| Target type (required) | `EventBridge API destination`, choose `Use an existing API destination` and the `Flashduty` one created in the previous step (for the SNS method choose `AWS service` › `SNS topic` and that topic) |
| Execution role (required) | `Create a new role for this specific resource` |
| Input transformer | Do not configure; send the full event |


Use an event pattern in the rule, for example:

```json
{
  "source": ["aws.guardduty", "aws.securityhub", "aws.health", "aws.inspector2", "aws.config", "aws.devops-guru", "aws.cloudwatch"],
  "detail-type": [
    "GuardDuty Finding",
    "Security Hub Findings - Imported",
    "Security Hub Findings - Custom Action",
    "AWS Health Event",
    "Inspector2 Finding",
    "Config Rules Compliance Change",
    "DevOps Guru New Insight Open",
    "DevOps Guru Insight Severity Upgraded",
    "DevOps Guru New Anomaly Association",
    "DevOps Guru Insight Closed",
    "CloudWatch Alarm State Change"
  ]
}
```

<Warning>
Do not filter out recovery states in the rule, or alerts cannot recover automatically. For example, matching only `"state": {"value": ["ALARM"]}`, `"newEvaluationResult": {"complianceType": ["NON_COMPLIANT"]}`, Security Hub `"findings": {"Workflow": {"Status": ["NEW"]}}` or Inspector `"status": ["ACTIVE"]` drops the recovery events.
</Warning>

AWS Health sends events to the Region where they occur; events of global services arrive in `us-east-1`. Create the rule in every Region you care about.

<img alt="Select the API destination as the target of an EventBridge rule" width="600" src="https://download.flashcat.cloud/flashduty/doc/aws-eb-7.png" />

</Step>
<Step title="Send a test CloudWatch alarm event and confirm">

**Where**: A terminal that can reach the Flashduty push URL

The rule only forwards events that AWS really emits. To verify right away, POST a test event shaped like the real one to the push URL:

```bash
curl -X POST '{integration_url}' \
  -H 'Content-Type: application/json' \
  -d '{"version":"0","id":"flashduty-test-1","detail-type":"CloudWatch Alarm State Change","source":"aws.cloudwatch","account":"123456789012","region":"us-east-1","resources":["arn:aws:cloudwatch:us-east-1:123456789012:alarm:flashduty-test"],"detail":{"alarmName":"flashduty-test","state":{"value":"ALARM","reason":"Flashduty integration test"}}}'
```

Send it again with `state.value` set to `OK` to confirm that the alert recovers automatically. A few seconds later, go back to Flashduty. The integration shows a **latest event time**, which means the setup works.
{/* console:
The checklist item "Receive the first event" is marked done at the same time.
*/}

</Step>
</Steps>

## Alert key and recovery

| Source | `detail-type` | Alert Key | Recovers when |
| :--- | :--- | :--- | :--- |
| CloudWatch | `CloudWatch Alarm State Change` | Alarm ARN (`resources[0]`) | `state.value` is `OK` |
| GuardDuty | `GuardDuty Finding` | Account + Region + `detail.id` | Never automatically |
| Security Hub | `Security Hub Findings - Imported`, `Security Hub Findings - Custom Action` | `ProductArn` + `Id` of each finding | `Workflow.Status` is `RESOLVED` or `SUPPRESSED`, or `RecordState` is `ARCHIVED` |
| AWS Health | `AWS Health Event` | `eventArn` + affected account | `statusCode` is `closed` |
| Amazon Inspector | `Inspector2 Finding` | `findingArn` | `status` is `CLOSED` or `SUPPRESSED` |
| AWS Config | `Config Rules Compliance Change` | Account + Region + rule name + resource type + resource ID | `complianceType` is `COMPLIANT` or `NOT_APPLICABLE` |
| DevOps Guru | All `DevOps Guru ...` events | Account + Region + `insightId` | `DevOps Guru Insight Closed` |
| Other events | Any | Event `id` | Never automatically |

- Later events of the same source (repeated GuardDuty findings, Security Hub updates, AWS Health progress) merge into the original alert
- When one Security Hub event carries several findings, each finding creates its own alert
- An event missing the Alert Key field listed above is rejected (HTTP 400)
- GuardDuty sends no event when a finding is archived, so close the alert manually

## Status and severity

EventBridge events have no common severity field, so every event triggers as Warning, as it always has. The source's own severity is kept in a label, and an [alert pipeline](/en/on-call/integration/alert-integration/alert-pipelines) can rewrite the severity based on it:

| Source | Severity label |
| :--- | :--- |
| GuardDuty | `guardduty_severity` (number) |
| Security Hub | `severity_label` |
| Amazon Inspector | `inspector_severity` |
| AWS Health | `event_type_category` |
| AWS Config | `compliance_type` |
| DevOps Guru | `insight_severity` |

For CloudWatch alarms, set the severity with `flashduty_severity: critical` (`critical`, `warning` or `info`) in the **Alarm description**, the same way as in the [AWS CloudWatch integration](/en/on-call/integration/alert-integration/alert-sources/aws-cloudwatch).

## Title and labels

- The alert title is `source::detail-type`, for example `aws.guardduty::GuardDuty Finding`
- Every event carries the labels `source`, `region`, `account`, `check` (`detail-type`), `detail` (the event `detail` as JSON) and `resources`
- The `summary` label is a readable summary: the finding or alarm title for sources with dedicated handling; for other events, in order, CloudTrail `eventSource eventName`, RDS `SourceIdentifier Message`, ECS `group stoppedReason`, or EC2 `instance-id state`
- Sources with dedicated handling also add source fields such as `finding_id`, `finding_arn`, `event_arn`, `config_rule_name` and `insight_id`; `resource` is the affected resource (DevOps Guru insights have none)

## Troubleshooting

- **API destination invocations fail**: Make sure the endpoint is the full push URL including `integration_key` and `HTTP method` is `POST`
- **SNS subscription stays in `Pending confirmation`**: Make sure the subscription points to this integration's push URL, then run **Request confirmation** in the SNS console
- **Alert does not recover**: Check whether the rule's event pattern filters out recovery states, and whether the target has an input transformer
- **One finding creates several alerts**: Make sure the event comes from a source in the table above and its `detail-type` is not rewritten
