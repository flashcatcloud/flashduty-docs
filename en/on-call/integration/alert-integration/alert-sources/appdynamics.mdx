Sync AppDynamics alerts to Flashduty through webhook.

<div className="hide">

## In Flashduty On-call
You can get the integration push URL in either of the following ways.

### Use a dedicated integration

Choose this option if all alerts go to one channel. It's the simpler setup.

<AccordionGroup>
  <Accordion title="View dedicated integration setup steps">
  
  1. In the Flashduty console, select **Channel** and open a channel
  2. Select **Configuration** → **Integrations** → **Private integration**, then click **Add an integration**, and enter the integration page
  3. Choose **AppDynamics** integration and click **Save** to generate a card
  4. Open the generated integration card and copy the **Push URL**
  
</Accordion>
</AccordionGroup>

### Use a shared integration

Choose this option if you need to route alerts to different channels based on the alert payload.

<AccordionGroup>
  <Accordion title="View shared integration setup steps">
  
  1. Go to the Flashduty console, select **Integration Center → Alerts**, and enter the integration selection page
  2. Select **AppDynamics** integration:
        - **Integration Name**: Define a name for this integration
  3. Configure the default route and select a channel. You can add more rules under **Routing** after creation
  4. Click **Save** and copy the generated **Push URL**
    
</Accordion>
</AccordionGroup>
</div>

## Configure in AppDynamics

<Steps>
<Step title="Create an HTTP Request Template in AppDynamics">

**Where**：AppDynamics › Alert & Respond › HTTP Request Templates › New

<img alt="HTTP Request Templates list" width="600" src="https://download.flashcat.cloud/flashduty/doc/appdyn-1.png" />

| Field | Value |
| --- | --- |
| Name (required) | `Flashduty` |
| Request URL › Method (required) | `POST` |
| Request URL › Raw URL (required) | `{integration_url}` |
| Payload › MIME Type | `application/json` |
| Payload › Payload Encoding | `UTF-8` |
| Payload (required) | Paste the JSON below |
| Response Handling Criteria › Failure Criteria | Status code `400` |
| Response Handling Criteria › Success Criteria | Status code `201` |

<img alt="Request URL settings" width="600" src="https://download.flashcat.cloud/flashduty/doc/appdyn-2.png" />

Payload:

```
{
	"policy_name":"${policy.name}",
	"message": "${latestEvent.eventMessage}",
	"application_name": "${latestEvent.application.name}",
	"link": "${latestEvent.deepLink}",
	"incident_id": "${latestEvent.incident.id}",
	"details": {
		"event_id": "${latestEvent.id}",
		"event_name": "${latestEvent.displayName}",
		"event_time": "${latestEvent.eventTime}",
		"event_type": "${latestEvent.eventType}",
		"health_rule_name":"${latestEvent.healthRule.name}",
		"node_name": "${latestEvent.node.name}",
		"severity": "${latestEvent.severity}"
	}
}
```

<img alt="Payload settings" width="600" src="https://download.flashcat.cloud/flashduty/doc/appdyn-3.png" />

<img alt="Response Handling Criteria settings" width="600" src="https://download.flashcat.cloud/flashduty/doc/appdyn-4.png" />

Click **Save**.

**Special Note (Optional Configuration)**

Configuration: `Custom Templating Variables`

<img alt="Custom Templating Variables settings" width="600" src="https://download.flashcat.cloud/flashduty/doc/appdyn-5.png" />

If you need to configure `Custom Templating Variables`, refer to the following JSON template. Here, custom_variables is a fixed format, and the variables within custom_variables are custom `Variables`. The names defined on the page must match the variable names referenced in the JSON template. These variables become labels of the same name on the Flashduty alert.

```
{
	"policy_name":"${policy.name}",
	"message": "${latestEvent.eventMessage}",
	"application_name": "${latestEvent.application.name}",
	"link": "${latestEvent.deepLink}",
	"incident_id": "${latestEvent.incident.id}",
	"details": {
		"event_id": "${latestEvent.id}",
		"event_name": "${latestEvent.displayName}",
		"event_time": "${latestEvent.eventTime}",
		"event_type": "${latestEvent.eventType}",
		"health_rule_name":"${latestEvent.healthRule.name}",
		"event_type_key": "${latestEvent.eventTypeKey}",
		"node_name": "${latestEvent.node.name}",
		"severity": "${latestEvent.severity}"
	},
	"custom_variables":{
		"host":"${host}"
	}
}
```

</Step>
<Step title="Create an HTTP Action in AppDynamics">

**Where**：AppDynamics › Alert & Respond › Actions › Create Action

1. Select `Actions` in the left navigation bar, choose the application type you want to create for, and click `Create`.
2. In the `Create Action` popup, select `Make an HTTP Request` and click `OK`.

   <img alt="Create Action dialog" width="600" src="https://download.flashcat.cloud/flashduty/doc/appdyn-6.png" />

3. In the `Create HTTP Action` popup, enter a `Name`, select the **Flashduty** template created in the previous step as the `HTTP Request Template`, and click `SAVE`.

   <img alt="Create HTTP Action dialog" width="600" src="https://download.flashcat.cloud/flashduty/doc/appdyn-7.png" />

</Step>
<Step title="Use the action in an alert policy">

**Where**：AppDynamics › Alert & Respond › Policies

1. Create or edit a policy (configure the alert rules as needed; that configuration is omitted here).
2. In the `Actions` section of the policy configuration page, click add and select the action created in the previous step.

   <img alt="Adding an action to a policy" width="600" src="https://download.flashcat.cloud/flashduty/doc/appdyn-8.png" />

3. In the policy's triggers (Health Rule Violation Events), select the events for a violation ending (Ended) and being canceled (Canceled) as well as the ones for a violation starting. Flashduty decides recovery from `event_type` in the notification: a type containing `CLOSE` or `CANCELED` recovers the matching alert. If you do not select these events, AppDynamics sends no recovery and the alert does not recover on its own.
4. After completing other configurations, click `Save`.

</Step>
<Step title="Trigger a health rule and verify">

Cause a violation of a health rule covered by the policy (or wait for a real one). A few seconds later, the integration in Flashduty shows a **Latest event time**, which means the setup works; after the violation ends, confirm the matching alert recovers.
{/* console:
The "Receive first event" item in the setup checklist turns green as well.
*/}

</Step>
</Steps>

## Alert Key and recovery

Flashduty uses `incident_id` from the payload as the Alert Key; if `incident_id` is still the unresolved `${latestEvent.incident.id}`, it uses `details.event_id` instead. The alert recovers when `details.event_type` contains `CLOSE` or `CANCELED`. The alert title is "application name::event name".
