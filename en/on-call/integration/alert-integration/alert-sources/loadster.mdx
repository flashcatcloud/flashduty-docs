Use the Loadster webhook integration to send monitor failure (**Monitor Fails**) and recovery (**Monitor Recovers**) notifications to Flashduty On-call. Each monitor maps to one Flashduty alert: the alert triggers when the monitor fails and closes automatically when it recovers.

<div className="hide">

## In Flashduty On-call

You can get the integration push URL in either of the following ways.

### Use a dedicated integration

1. In the Flashduty console, go to **Channels** and open a channel
2. Select **Configuration** → **Integrations** → **Private integration**, then click **Add an integration**
3. Select **Loadster** and click **Save**
4. Open the generated integration card and copy the **Push URL**

### Use a shared integration

1. In the Flashduty console, go to **Integration Center → Alert Events**
2. Select **Loadster** and enter an integration name
3. Configure the default route and select a channel. You can add more rules under **Routing** after creation
4. Click **Save** and copy the generated **Push URL**

</div>

## In Loadster

<Steps>
<Step title="Enable webhooks in Loadster">

**Where**: Loadster dashboard › Account › Integrations › Webhooks › Enable Webhooks

On the **Webhooks** card, click **Enable Webhooks**. Loadster then prompts for the URLs.

</Step>

<Step title="Enter the push URL in Loadster">

**Where**: Loadster dashboard › Account › Integrations › Webhooks

| Field | Value |
| --- | --- |
| Monitor Fails Webhook URL (required) | `{integration_url}` |
| Monitor Recovers Webhook URL (required, alerts recover through it) | `{integration_url}`, the same as above |
| Load Test Started Webhook URL (optional) | Leave empty |
| Load Test Finished Webhook URL (optional) | Leave empty |

Click **SAVE**.

<Note>
Webhooks are configured per account and apply to every monitor in the account. Loadster sends an HTTP POST request when a monitor event occurs and treats a 2xx response from Flashduty as success. If a request fails, Loadster retries it periodically.
</Note>

</Step>

<Step title="Verify the lifecycle">

Loadster webhooks have no test button, so verify with a real event. Make a monitor actually fail (for example, point an HTTP Request Monitor at a URL that returns 5xx) and confirm Flashduty receives a Critical alert and the integration shows **Latest event time**. Once the target recovers, confirm the alert closes automatically.
{/* console:
The checklist item "Receive the first event" is then complete as well.
*/}

</Step>
</Steps>

## Payload

Loadster POSTs the following fields as JSON. Flashduty parses them directly, so no template is needed:

| Field | Meaning | In Flashduty |
| :--- | :--- | :--- |
| `monitor.id` | Monitor ID | Alert Key, label `monitor_id` |
| `monitor.name` | Monitor name | Alert title, label `check` |
| `cycle.status` | Result of the check: `FAIL` on failure, `PASS` on recovery | Trigger or recovery, label `cycle_status` |
| `cycle.message` | Failure reason, for example `The monitoring script had an error!` | Added to the description |
| `cycle.responseTimeAvg` | Average response time in milliseconds | Added to the description |
| `url` | Link to the monitor in the Loadster dashboard | Added to the description |

When the monitor name is empty, the alert title is `Loadster monitor <monitor.id>`.

## Alert key

Flashduty uses `monitor.id` as the Alert Key. The failure and recovery notifications of one monitor carry the same `monitor.id`, so they land on the same alert. Renaming the monitor does not change the Alert Key. The top-level `id` of the request is a new UUID for every notification and is not part of the Alert Key.

## Status and severity

Loadster notifications carry no severity, so Flashduty maps them as follows:

| `cycle.status` | Flashduty status or severity |
| :--- | :--- |
| `PASS` | Recovery, keeps the earlier Critical severity |
| Any other value (observed: `FAIL`) | Critical |

Notifications without `monitor.id` (for example, load test started and finished notifications) are acknowledged and ignored without creating an alert. The Loadster webhook has no test button.

## FAQ

<AccordionGroup>
<Accordion title="Do I get repeated notifications while a monitor keeps failing?">

No. Loadster sends one failure notification when the monitor opens an incident and one recovery notification when it recovers; nothing is sent in between. Whether the first failed check opens an incident is controlled by the monitor's **Open an incident after N failures** setting.

</Accordion>

<Accordion title="Can I send only some monitors?">

The Loadster webhook applies to the whole account. To separate monitors, use routing rules on a shared integration in Flashduty and match on the `monitor_id` or `check` label.

</Accordion>
</AccordionGroup>

## Troubleshooting

- **Loadster does not push**: confirm webhooks are enabled and saved under **Account → Integrations → Webhooks**, and that both URLs are the complete push URL containing `integration_key`
- **Flashduty returns a parameter error**: the request body is not valid JSON
- **Flashduty returns success but no alert appears**: a request without `monitor.id` or `cycle.status` is acknowledged and ignored without creating an alert; confirm the webhook is set on the monitor events (Monitor Fails / Monitor Recovers), not on the load test events
- **The alert does not recover**: confirm **Monitor Recovers Webhook URL** is filled in and the recovery comes from the same monitor as the failure

For field details, see the Loadster documentation [Integration with Webhooks](https://loadster.com/manual/integration-with-webhooks).
