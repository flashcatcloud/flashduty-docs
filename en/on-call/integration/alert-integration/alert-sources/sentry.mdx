## In Flashduty On-call
You can get the integration push URL in either of the following ways.

### Use a dedicated integration

Choose this option if all alerts go to one channel. It's the simpler setup.

<AccordionGroup>
  <Accordion title="View dedicated integration setup steps">
  
  1. In the Flashduty console, select **Channel** and open a channel
  2. Select **Configuration** → **Integrations** → **Private integration**, then click **Add integration**
  3. Select **Sentry** integration and click **Save** to generate a card
  4. Open the generated integration card and copy the **Push URL**
  
</Accordion>
</AccordionGroup>

### Use a shared integration

Choose this option if you need to route alerts to different channels based on the alert payload.

<AccordionGroup>
  <Accordion title="View shared integration setup steps">
  
  1. In the Flashduty console, go to **Integration Center → Alert Events**
  2. Select **Sentry** integration:
        - **Integration Name**: Define a name for this integration
  3. Configure the default route and select a channel. You can add more rules under **Routing** after creation
  4. Click **Save** and copy the generated **Push URL**
    
</Accordion>
</AccordionGroup>
</div>

## Configure in Sentry

Sentry provides two types of alert mechanisms: Issue Alerts and Metric Alerts. While Issue Alerts support notifications through WebHooks in Integrations, Metric Alerts are limited to using Internal Integration for alert notifications. Notably, Internal Integration works with both Metric Alerts and Issue Alerts. Given the versatility of Internal Integration, we've chosen to standardize on this approach rather than relying on WebHooks separately, thus simplifying alert notification configuration.

<Steps>
<Step title="Create an Internal Integration in Sentry">

**Where**: Sentry › Settings › Developer Settings › Custom Integrations › Create New Integration › Internal Integration

In older Sentry versions the entry is **Settings → Custom Integrations**.

| Field | Value |
| --- | --- |
| Name (required) | `Flashduty` |
| Webhook URL (required) | `{integration_url}` |
| Alert Rule Action (required) | Turn it on, configured as shown below |
| PERMISSIONS › Issue & Event (required) | `Read` |
| WEBHOOKS › issue (required) | Check it. **Do not check error and comment** |

<img alt="Alert Rule Action settings of the Internal Integration" width="600" src="https://fcpub-1301667576.cos.ap-nanjing.myqcloud.com/flashduty/doc/sentry-1.png" />

After configuration, click **Save Changes** to complete the setup.

<img alt="Webhooks settings of the Internal Integration" width="600" src="https://fcpub-1301667576.cos.ap-nanjing.myqcloud.com/flashduty/doc/sentry-2.png" />

**Special notes about WEBHOOKS configuration:**

1. After checking **issue**, Flashduty can receive resolved events for issues, meaning when manually triggering resolved for an issue in the issue list, we will automatically recover the associated incident in Flashduty.
2. Other issue events such as create, assigned, archived, and unresolved are not supported.
3. If error and comment are also checked, Flashduty will not receive or process these types of events.

</Step>
<Step title="Use Flashduty in a Sentry alert rule">

**Where**: Sentry › Alerts › Create Alert

1. Select the type of Alert to create, such as Issue.

   <img alt="Select the alert type" width="600" src="https://fcpub-1301667576.cos.ap-nanjing.myqcloud.com/flashduty/doc/sentry-3.png" />

2. Configure trigger conditions as needed.
3. Under **THEN perform these actions**, **Add action** and select **Send a notification via**.

   <img alt="Add the Send a notification via action" width="600" src="https://fcpub-1301667576.cos.ap-nanjing.myqcloud.com/flashduty/doc/sentry-4.png" />

4. Select the **Flashduty** integration added above as the notification channel.

   <img alt="Select the Flashduty notification channel" width="600" src="https://fcpub-1301667576.cos.ap-nanjing.myqcloud.com/flashduty/doc/sentry-5.png" />

5. Configure other options as needed and click **Save Rule**.

</Step>

Let the rule match a real issue or metric alert. A few seconds later, the integration in Flashduty shows a **Latest event time**, which means the setup works. Then mark that issue as resolved in Sentry's issue list and confirm the matching Flashduty alert recovers.

## Payload

A Sentry Internal Integration posts a JSON object whose `data` carries one of three objects. Flashduty parses whichever one is present:

**Metric alert (`data.metric_alert`)**

| Field | Meaning | Use in Flashduty |
| :--- | :--- | :--- |
| `action` | Delivery action | Alert status and severity |
| `data.metric_alert.id` | Metric alert rule ID | Alert key |
| `data.description_text` | Alert description text | Alert title |
| `data.web_url` | Alert link | Label `web_url` |
| `data.metric_alert.projects` | Projects involved | Label `projectName`, projects separated by commas |

**Issue alert (`data.event`)**

| Field | Meaning | Use in Flashduty |
| :--- | :--- | :--- |
| `action` | Delivery action | Alert severity |
| `data.event.issue_id` | Issue ID | Alert key |
| `data.event.title` | Issue title | Alert title |
| `data.triggered_rule` | Triggered rule name | Label `check` |
| `data.event.culprit` | Culprit | Label `culprit` |
| `data.event.environment` | Environment | Label `environment` |
| `data.event.location` | Location | Label `location` |
| `data.event.message` | Error message | Label `message` |
| `data.event.url` | Issue detail link | Label `detail_url` |
| `data.event.web_url` | In-project link | Label `web_url` |
| `data.event.tags` | Event tag array | Each pair becomes a label with the tag's own name |

**Issue resolved (`data.issue`)**

| Field | Meaning | Use in Flashduty |
| :--- | :--- | :--- |
| `action` | Delivery action, only `resolved` is accepted | Alert recovery |
| `data.issue.id` | Issue ID | Alert key |
| `data.issue.title` | Issue title | Alert title |
| `data.issue.project.name` | Project name | Label `projectName` |
| `actor.name` | Person who resolved it | Label `operator` |

A metric alert does not read `data.description_title`, and an issue alert does not read `data.event.level`. When `data` carries none of the three objects, Flashduty returns a parameter error.

## Alert key

Flashduty takes the Alert Key from the pushed object: `data.metric_alert.id` for a metric alert, `data.event.issue_id` for an issue alert, and `data.issue.id` for an issue-resolved event.

The issue alert and the resolved event of one issue carry the same issue ID, so the resolved event closes the matching alert; repeated triggers of one metric alert rule land on one alert. Changing the title, severity, or event tags does not change the Alert Key.

## Labels

| Label | Source |
| :--- | :--- |
| `check` | Triggered rule name `data.triggered_rule`, issue alerts only |
| `culprit` | `data.event.culprit` |
| `environment` | `data.event.environment` |
| `location` | `data.event.location` |
| `message` | `data.event.message` |
| `detail_url` | `data.event.url` |
| `web_url` | `data.web_url` for a metric alert, or `data.event.web_url` for an issue alert |
| `projectName` | Project list of a metric alert (comma-separated), or `data.issue.project.name` of a resolved event |
| `operator` | `actor.name` of a resolved event |
| Keys from event tags | `data.event.tags` of an issue alert: the first value of each pair is the label name, the second is its value |

A metric alert writes only `web_url` and `projectName`. When a key in `data.event.tags` matches a built-in label (for example `environment`), the event tag overrides the built-in value.

## Troubleshooting

- **An alert does not recover**: an issue-resolved event must carry `action` set to `resolved`. If marking the issue resolved in Sentry's issue list does not recover the alert, check that the Internal Integration has `issue` selected
- **Flashduty returns a parameter error**: the `action` value is not supported. An issue alert accepts only `critical`, `warning`, and `triggered`; sending `resolved` on `data.event` is rejected, and recovery goes through `data.issue`
- **Every alert has Warning severity**: an issue alert takes its severity from `action`, not from `data.event.level`. Sentry issue alerts usually report `triggered`, which maps to Warning
- **A built-in label is overwritten**: a key in `data.event.tags` with the same name as a built-in label overrides it, so configure routing rules with the value that actually arrives
- **No alert is created**: check that the alert rule action is **Send a notification via** with `Flashduty` selected; a payload whose `data` carries none of `metric_alert`, `event`, or `issue` is rejected
