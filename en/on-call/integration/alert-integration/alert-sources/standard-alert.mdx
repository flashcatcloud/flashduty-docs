Push alert events from your own system to Flashduty through standard protocols.

:::tips
Flashduty has already adapted webhook protocols for most common alert systems. For these systems, you should first use the corresponding integration for simplicity. This integration provides a standard HTTP interface that requires your development for adaptation. The advantage is that you can push any alert events you want to handle through On-call.
:::

<div className="hide">

## Setup steps

### In Flashduty

You can obtain an integration push URL through either of the following two methods:

#### Use a dedicated integration

When you don't need to route alert events to different collaboration spaces, this method is preferred as it's simpler.

<AccordionGroup>
  <Accordion title="View dedicated integration setup steps">
  
  1. Enter the Flashduty console, select **Collaboration Space**, and enter the details page of a space
  2. Select **Configuration** → **Integrations** → **Private integration**, then click **Add integration**, and enter the add integration page
  3. Select **Standard Alert Event** integration, click **Save** to generate a card
  4. Open the generated integration card and copy the **Push URL**
    
</Accordion>
</AccordionGroup>

#### Use a shared integration

When you need to route alert events to different collaboration spaces based on the alert event's Payload information, this method is preferred.

<AccordionGroup>
  <Accordion title="View shared integration setup steps">
  
  1. Enter the Flashduty console, select **Integration Center → Alert Events** to enter the integration selection page
  2. Select **Standard Alert Event** integration:
        - **Integration Name**: Define a name for the current integration
  3. Configure the default route and select a channel. You can add more rules under **Routing** after creation
  4. Click **Save** and copy the generated **Push URL**
    
</Accordion>
</AccordionGroup>

</div>

## Configure in your system

This integration has no third-party product UI. Configuration happens in your own system and in the integration settings in Flashduty.

<Steps>
<Step title="Push alert events to Flashduty from your system">

**Where**: Your alerting system › the code or script that sends HTTP requests

| Item | Value |
| :-- | :--- |
| Method (required) | `POST` |
| URL (required) | `{integration_url}` |
| Header `Content-Type` (required) | `application/json` |
| Payload `title_rule` (required) | Alert title, up to `512` characters |
| Payload `event_status` (required) | `Critical`, `Warning`, `Info`, or `Ok` (capitalized); `Ok` auto-resolves the alert |
| Payload `alert_key` (optional) | Alert identifier used to update or resolve an existing alert; required when you send a resolve event |
| Payload `description`, `labels`, `images` (optional) | Description, labels, and images; limits are listed in "Request parameters" below |

Push on every state change: send `Critical` / `Warning` / `Info` when the alert fires and an `Ok` event with the same `alert_key` when it recovers, otherwise the alert stays open.

</Step>
<Step title="Configure field mapping in Flashduty (if your JSON does not match)">

**Where**: Flashduty console › Integration Center › Alert Events (dedicated integration: Flashduty console › Channels › Configuration › Integrations › Private integration)

In the integration list on the right, open your Standard Alert Event integration, then go to **Receive** › **Mappings** card. Its switch is at the right of the title row and is off by default; the mapping editor appears only when it is on. Configure **Field mapping** there.

Skip this step if your system can push the payload above as is. Otherwise, use **Field mapping** with `{{variable path}}` to map fields of the original JSON to the standard fields, and configure **Field value mapping** (shown only after field mapping is set) when values need translating. See "Field mapping and value mapping" below for the syntax and examples.

</Step>
<Step title="Push a test event and confirm">

**Where**: A terminal on the host of your system

```bash
curl -X POST '{integration_url}' \
-H 'Content-Type: application/json' \
-d '{
    "event_status": "Warning",
    "title_rule": "Flashduty integration test",
    "alert_key": "flashduty-test-1"
}'
```

A response with `request_id` and `alert_key` means the push succeeded. Return to Flashduty: the integration shows **Latest event time**. Then send an event with the same `alert_key` and `event_status` set to `Ok` to verify auto-resolve.
{/* console:
The "Receive the first event" item in the setup checklist turns green as well.
*/}

</Step>
</Steps>

## Request description

### Request method

<div class="md-block">

POST, Content-Type:"application/json"

</div>

### Request parameters:

<div class="md-block">

#### Headers:
Field|Required|Type|Description
:-:|:-:|:-:|:---
| Content-Type | Yes | string | Fixed value: `application/json`

#### Query strings:
Field|Required|Type|Description
:-:|:-:|:-:|:---
| integration_key | Yes | string | Integration key for access control. Obtained after adding integration.

#### Payload:

Field|Required|Type|Description
:-:|:-:|:-:|:---
| title_rule | Yes | string | Alert title, no more than `512` characters, will be truncated if exceeded. Supports dynamic title generation based on alert content, see [Customizing Incidents](/en/on-call/integration/alert-integration/alert-pipelines) for generation rules.
| event_status | Yes | string | Alert status. Enumerated values (case-sensitive): *Critical*, *Warning*, *Info*, *Ok*. When specified as Ok, it means automatic recovery of the alert.
| alert_key | No | string | Alert identifier, used to update or automatically recover existing alerts. You can customize this value, up to `255` bytes; a longer value is replaced by its MD5 (a 32-character hex string). The same value always yields the same MD5, so alert merging and recovery work as usual. You can also rely on system auto-generation, this value will be returned in the response. If you're reporting a recovery event, this value must exist.
| description | No | string | Alert description, no more than `2048` characters, will be truncated if exceeded.
| labels | No | map | Alert label collection, key is the label name, value is the label value. 1. Both key and value of labels are string type, case-sensitive. 2. Label key should not exceed `128` characters, following Prometheus label naming conventions. Value should not exceed `8192` bytes (8 KB) and is truncated if exceeded; the cut backs off to a UTF-8 character boundary. 3. Maximum of `50` labels. See `Label Content Reference` in [Best Practices](#best-practices). Example: "resource": "171.26.23.22", "check": "api latency > 500ms"
| images | No | [][image](#image) | Array of images, used for image display in frontend or Feishu/DingTalk application notifications.The system merged/overwritten based on alt, for the same alt (including empty strings), only one is retained

#### image structure <span id="image"></span>

Field|Required|Type|Description
:-:|:-:|:-:|:---
| alt | No | string | Image alternative text, limit 128 characters, truncated if exceeded.
| src | Yes | string | Image source, value: http/https URL or image_key returned by [Image Upload API](/en/on-call/integration/alert-integration/alert-sources/image-upload). Limit 256 characters, discarded if exceeded
| href | No | string | Hyperlink reference path, limit 256 characters, truncated if exceeded
    
</div>

### Request example

Request:

```
curl -X POST '{api_host}/event/push/alert/standard?integration_key={integration_key}' \
-H 'Content-Type: application/json' \
-d '{
    "event_status": "Warning",
    "title_rule": "cpu idle low than 20%",
    "labels": {
        "service": "engine",
        "cluster":"nj",
        "resource":"es.nj.01",
        "check":"cpu.idle<20%",
        "metric":"node_cpu_seconds_total"
    }
}' -v
```

Successful Response:

```
{
    "request_id": "0ace00116215ab4ca0ec5244b8fc54b0",
    "data": {
        "alert_key": "9qJ798NJoXS4UMVB5SHsNj"
    }
}
```

Failed Response:

```
{
    "request_id": "0ace00116215abc0ba4e52449bd305b0",
    "error": {
        "code": "InvalidParameter",
        "message": "integration_key is not a valid one"
    }
}
```

## Field mapping and value mapping

If your JSON doesn't match the standard payload above, configure **field mapping (field_mapping)** and **value mapping (value_mapping)** in the integration settings. Flashduty then converts your JSON into standard alert events.

<Tip>
Once field mapping is configured, the request body no longer requires a fixed format. It accepts any JSON object, and also supports batch push through JSON arrays (up to 100 items per request).
</Tip>

### Field mapping (field_mapping)

Use `{{variable.path}}` syntax to reference fields from the original JSON and map them to target fields of the standard alert event.

Supported target fields:

| Target field | Description |
| :--- | :--- |
| title | Alert title |
| title_rule | Alert title rule |
| description | Alert description |
| event_status | Alert status (Critical / Warning / Info / Ok) |
| alert_key | Alert identifier |
| labels | Alert labels |

The above is the whitelist of target fields supported by the field mapping editor in integration settings. The `images` field is not offered as a target in the console's field mapping editor (the underlying `field_mapping` API does accept it), so report it directly in the request payload.

**Variable syntax:**

- Use `.` to separate path levels, for example, `{{data.severity}}` references a nested field
- When the entire value is a single variable (for example, `"{{tags}}"`), the original data type is preserved (object, array)
- When a variable is mixed with other text (for example, `"{{host}} - {{check}}"`), variables are converted to strings for concatenation

**Two ways to map labels:**

- **Wildcard expansion**: `"labels": "{{tags}}"` — expands all children of the `tags` object as labels
- **Per-label mapping**: `"labels": {"env": "{{tags.env}}", "host": "{{hostname}}"}` — maps each label individually

**Example:**

Your system pushes the following format:

```json
{
  "alert_name": "CPU usage high",
  "status": "firing",
  "severity": "high",
  "host": "web-01",
  "tags": {
    "env": "production",
    "service": "api"
  }
}
```

Configure the following field mapping:

```json
{
  "title_rule": "{{alert_name}}",
  "event_status": "{{severity}}",
  "alert_key": "{{host}}::{{alert_name}}",
  "description": "Host {{host}} alert: {{alert_name}}",
  "labels": "{{tags}}"
}
```

### Value mapping (value_mapping)

When your source system's field values differ from Flashduty's standard (for example, using `high` instead of `Critical` for severity), configure value mapping for automatic conversion.

Value mapping is configured per **field path**, with each path containing a `source value → target value` mapping table.

**Example:**

```json
{
  "severity": {
    "high": "Critical",
    "medium": "Warning",
    "low": "Info",
    "resolved": "Ok"
  }
}
```

With the field mapping above, field mapping extracts `"severity": "high"` from the original JSON. Value mapping then converts it to `Critical` and writes it to the `event_status` field.

<Warning>
Every `{{...}}` variable must resolve to a value in the original JSON, or the request fails. Test your mapping with a small dataset first.
</Warning>

## No-event detection

The **No-event detection** card creates a Warning alert when no valid event arrives within the set time. Its switch is at the right of the card's title row and is off by default; when off, the card is a single row with no other options.

When it is on, the card shows these options:

| Setting | Description |
| :--- | :--- |
| **Detection period** | In minutes, 10 by default. Between 10 minutes and 48 hours. Only events that pass integration validation reset the timer |
| **Auto-close the alert when events resume** | Switch, on by default. When the next valid event arrives, the alert raised by no-event detection is closed |

## Best practices <span id="best-practices"></span>

1. Send events to Flashduty when alert status changes
2. When an alert recovers, send an event with status Ok to close the alert. Otherwise, the alert will remain open. If your alert system doesn't have recovery events, we recommend manually sending recovery events
3. Labels are event descriptions, and label content should be as rich as possible (specified when sending, or generated through enrichment rules), such as:
   - Alert source, like host, cluster, check, or metric
   - Alert ownership information, like team, owner
   - Alert category information, like class (api, db, net)

## FAQ

<details>
  <summary>Why haven't I received alerts in Flashduty?</summary>

  **In Flashduty**
  
  1. Check whether the integration shows **Latest Event Time**. If it doesn't, Flashduty hasn't received the push, so check your system first.
  2. If you use a **shared integration**, confirm that you've configured **routing rules**. Without them, Flashduty rejects new pushes because no channel can receive the alerts. Add a routing rule to the target channel.

  **In your system**

  1. Confirm that your request URL exactly matches the URL in the integration details.
  2. Confirm that your service can reach api.flashcat.cloud. If it can't, allow outbound access for the server or for Flashduty's domain.
  3. Print Flashduty's response and check its error message.

  If you still can't find the cause, contact us with the **request_id** from the response.
    
</details>

<details>
  <summary>Why was the push request successful but no new alerts or incidents were generated?</summary>

  Flashduty uses a 2-layer noise reduction mechanism:

  1. Flashduty checks for duplicate events. If a pushed event is identical to an earlier one, Flashduty discards it.
  2. If the new event has the same status, title, and description as the latest event of its alert, Flashduty discards the event but updates the alert's attributes.
  3. A drop, inhibit, or silence rule can also discard the new event.
  4. If the event creates a new alert, the second layer checks whether the alert can be grouped into an active incident. If it can, Flashduty adds it to that incident instead of creating a new one.

  For more information, please refer to [Alert Noise Reduction](/en/on-call/channel/noise-reduction).
</details>
