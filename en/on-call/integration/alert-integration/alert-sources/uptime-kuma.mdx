## In Flashduty On-call
You can get the integration push URL in either of the following ways.

### Use a dedicated integration

Choose this option if all alerts go to one channel. It's the simpler setup.

<AccordionGroup>
  <Accordion title="View dedicated integration setup steps">
  
  1. In the Flashduty console, select **Channel** and open a channel
  2. Select **Configuration** → **Integrations** → **Private integration**, then click **Add integration**
  3. Select **Uptime Kuma** integration and click **Save** to generate a card
  4. Open the generated integration card and copy the **Push URL**
  
</Accordion>
</AccordionGroup>

### Use a shared integration

Choose this option if you need to route alerts to different channels based on the alert payload.

<AccordionGroup>
  <Accordion title="View shared integration setup steps">
  
  1. In the Flashduty console, go to **Integration Center → Alert Events**
  2. Select **Uptime Kuma** integration:
        - **Integration Name**: Define a name for this integration
  3. Configure the default route and select a channel. You can add more rules under **Routing** after creation
  4. Click **Save** and copy the generated **Push URL**
    
</Accordion>
</AccordionGroup>

</div>

## In Uptime Kuma

<Steps>
<Step title="Set up the notification channel in Uptime Kuma">

**Where**: Uptime Kuma › Settings › Notifications

Click Setup to edit, fill in the fields below, then submit and save:

| Field | Value | Required |
| --- | --- | --- |
| Notification Type | `Flashduty (Flashduty)` | Required |
| Integration Key | `{integration_key}` (the integration_key parameter value from the integration push URL; the full push URL `{integration_url}` also works) | Required |
| Severity | Select as needed | Optional |

<Step title="Enable the notification on your monitors">

**Where**: Uptime Kuma › Add New Monitor › Notifications

<div class="md-block">

1. Click `Add New Monitor` or edit existing monitors, configure monitoring settings as needed
2. Enable the notification method created in the previous step in the `Notifications` section
3. If needed, add `Tags`. Note that only tags with both Key/Value will be pushed to Flashduty
4. Submit and save

</Step>

Make a monitor that has this notification enabled actually fail (for example, pause the monitored service) and wait for Uptime Kuma to send the alert, then restore the service and confirm the alert recovers in Flashduty (Uptime Kuma sends a recovery event when the monitor goes Up). Back in Flashduty, the integration shows **Latest event time**, which means setup works.

## Payload

The **FlashDuty** notification type in Uptime Kuma posts to the standard alert endpoint. Flashduty reads these fields:

| Field | Meaning | Use in Flashduty |
| :--- | :--- | :--- |
| `title` | Notification title: `Uptime Kuma Monitor 🔴 Down` when the monitor is down, `Uptime Kuma Monitor ✅ Up` when it recovers | Alert title |
| `description` | Built from the notification title, the monitor name, and the heartbeat message, in that order | Alert description |
| `event_status` | The **Severity** of the notification channel while the monitor is down, `Ok` on recovery | Alert status and severity |
| `alert_key` | Monitor ID | Alert key |
| `labels.resource` | Monitor address: the hostname when present, `hostname:port` for a `port` monitor, and the monitor URL when there is no hostname | Label `resource` |
| `labels.check` | Monitor name | Label `check` |
| `labels.<tag name>` | Each monitor tag | Label with the same name |

Uptime Kuma generates the notification title itself, and the monitor name sits in the description and the `check` label. With no **Severity** selected, a down notification is pushed as `Info`.

## Alert key

Uptime Kuma sends the monitor ID as `alert_key`. The down notification and the recovery notification of one monitor carry the same value, so the recovery closes the matching alert; repeated notifications sent while the monitor keeps failing merge into that same alert.

Different monitors have different IDs and produce separate alerts; changing the monitor name, address, or tags does not change the Alert Key.

## Status and severity

<div class="md-block">
  
When a monitor goes Down, the alert severity comes from the **Severity** set on the notification channel (table below); when it goes Up, a recovery event closes the alert of the same monitor.

Uptime Kuma to Flashduty alert severity mapping:

| Uptime Kuma | Flashduty |
| ------------ | -------- |
| Critical | Critical |
| Warning | Warning |
| Info | Info |

</div>

## Labels

| Label | Source |
| :--- | :--- |
| `resource` | Monitor address, preferring the hostname |
| `check` | Monitor name |
| Tag name | Each monitor tag; a tag with an empty value is not written |

## Troubleshooting

- **A test notification opened an alert**: the **Test** button of the notification channel sends a test message, so Flashduty opens an Info alert titled `Uptime Kuma Alert`. That message uses a random `alert_key` and never recovers on its own; close it in Flashduty after the test
- **Every alert title is Uptime Kuma Monitor 🔴 Down**: Uptime Kuma generates the title itself, and the monitor name sits in the description and the `check` label. Match on labels or rewrite the title with an [alert processing pipeline](/en/on-call/integration/alert-integration/alert-pipelines)
- **An alert does not recover**: it recovers only when Uptime Kuma decides the monitor is up again and sends an Up notification; check that the monitor has recovered and the notification is still attached to it
- **Monitor tags are missing from labels**: a tag with a name but no value is not written; add the value and it appears as a label
- **Uptime Kuma reports FlashDuty notification failed**: check that Integration Key holds the integration key or the full push URL, and that the integration still exists
