Sync SolarWinds alert events to Flashduty through webhook.

## In Flashduty On-call
You can get the integration push URL in either of the following ways.

### Use a dedicated integration

Choose this option if all alerts go to one channel. It's the simpler setup.

<AccordionGroup>
  <Accordion title="View dedicated integration setup steps">
  
  1. In the Flashduty console, select **Channel** and open a channel
  2. Select **Configuration** → **Integrations** → **Private integration**, then click **Add integration**
  3. Choose **SolarWinds** integration, click **Save** to generate a card
  4. Open the generated integration card and copy the **Push URL**
  
</Accordion>
</AccordionGroup>

### Use a shared integration

Choose this option if you need to route alerts to different channels based on the alert payload.

<AccordionGroup>
  <Accordion title="View shared integration setup steps">
  
  1. In the Flashduty console, go to **Integration Center → Alert Events**
  2. Select **SolarWinds** integration:
        - **Integration Name**: Define a name for this integration
  3. Configure the default route and select a channel. You can add more rules under **Routing** after creation
  4. Click **Save** and copy the generated **Push URL**
    
</Accordion>
</AccordionGroup>
</div>

## Configure SolarWinds

SolarWinds has five alert types (Anomaly, Entity, Event, Log, Metric Group), each requiring its own alert channel, so create five webhook channels, one per type you use.

<Steps>
<Step title="Create a webhook notification service in SolarWinds">

**Where**: SolarWinds › Settings › Notification Services › Webhook › CREATE CONFIGURATION

| Field | Value |
| --- | --- |
| Method (required) | `POST` |
| Name (required) | Recommended format `Type_Flashduty`, for example `Anomaly_Flashduty` |
| Destination URL (required) | `{integration_url}` (generated after you enter an integration name in Flashduty and save) |
| Content Type (required) | `application/json` |
| Select Custom Body Template Based On The Alert Types (required) | The type you are creating, for example Anomaly Based Alert |
| HTTP POST Body | Generated by the system for the selected type. **Do not modify the generated template** |

Click **CREATE** when done.

<img alt="Selecting Webhook on the SolarWinds Notification Services page" width="600" src="https://download.flashcat.cloud/flashduty/doc/sw-1.png" />

<img alt="Create Configuration form of a Webhook channel with the generated HTTP POST body" width="600" src="https://download.flashcat.cloud/flashduty/doc/sw-2.png" />

Repeat to create webhook channels for the other types.

</Step>
<Step title="Use the channel in a SolarWinds alert policy">

**Where**: SolarWinds › Alerts › Alert Settings › create or edit a policy › Actions

Configure the alert rule as needed (omitted here). In the **Actions** section:

| Field | Value |
| --- | --- |
| Services (required) | `Webhook` |
| Configuration (required) | The channel from the previous step, for example `Anomaly_Flashduty` (its type must match the alert type) |
| Send an additional notification when the Alert is cleared | Keep enabled so Flashduty receives the recovery notification |

Click **Save** after completing the other settings.

<img alt="Webhook service and clear notification selected on the alert's Actions step" width="600" src="https://download.flashcat.cloud/flashduty/doc/sw-4.png" />

</Step>
<Step title="Trigger an alert and confirm">

**Where**: SolarWinds › Alerts › Alert Settings

The test notification SolarWinds offers when creating a webhook channel only proves that the Flashduty URL is reachable; it does not replace a real alert. Let an alert rule that uses the channel fire. After a few seconds, go back to Flashduty. If the integration shows a **Latest event time**, the setup works. When the condition clears, the alert recovers automatically.
{/* console:
The checklist item "Receive the first event" is then complete as well.
*/}

</Step>
</Steps>

## Payload

The five SolarWinds alert channels post different JSON structures. Flashduty reads these fields:

| Field | Meaning | Use in Flashduty |
| :--- | :--- | :--- |
| `name` | Alert name | Alert title, label `check` |
| `severity` | Alert severity | Alert severity |
| `description` | Alert description | Alert description |
| `detailUrl` | Alert detail link | Source of the Alert Key, label `detail_url` |
| `reason` | Clear reason | Treated as recovery when it is `DISABLED` or `AUTOMATIC` |
| `entities[]` | Affected entities | Label `entities` (JSON); the first entity's `reason` also counts for recovery |
| `sWindsEvents` | Event alert list | Label `event` (JSON) |
| `affectedEvaluations` | Affected evaluations | Label `affected_evaluations` (JSON) |
| `tags` | Entity tag array | Label `tags` (JSON) |
| `runbook`, `condition`, `additionalInfo`, `recordCount`, `threshold`, `timespanStart`, `timespanEnd`, `query` | Alert context | Labels `runbook`, `condition`, `additional_info`, `record_count`, `threshold`, `timespan_start`, `timespan_end`, `query` |

`id` and `priority` are not read; the severity comes from `severity` alone.

## Alert key

Flashduty uses the MD5 of `detailUrl` as the Alert Key. The trigger and clear notifications of one alert carry the same detail link, so the clear notification closes the matching alert.

When a payload has no `detailUrl`, every delivery opens a new alert and the clear notification cannot close the original one. Changing the alert name, severity, reason, or tags does not change the Alert Key.

## Status and severity

<div class="md-block">

| SolarWinds | Flashduty |
| --- | --- |
| Critical | Critical |
| Warning | Warning |
| Info | Info |

Any other value is treated as Info. The alert recovers when a cleared notification carries a `reason` of `DISABLED` or `AUTOMATIC`.

</div>

## Labels

| Label | Source |
| :--- | :--- |
| `check` | Alert name `name` |
| `runbook` | Runbook `runbook` |
| `detail_url` | Alert detail link `detailUrl` |
| `condition` | Trigger condition `condition` |
| `additional_info` | Additional information `additionalInfo` |
| `record_count` | Record count `recordCount` |
| `threshold` | Threshold `threshold` |
| `timespan_start` / `timespan_end` | Evaluation window `timespanStart` / `timespanEnd` |
| `query` | Query `query` |
| `entities` | JSON of the affected entity array |
| `event` | JSON of the event list `sWindsEvents` |
| `affected_evaluations` | JSON of the affected evaluation array |
| `tags` | JSON of the entity tag array, for example `[{"key":"...","value":"..."}]` |

Labels with empty values are not written.

## Troubleshooting

- **An alert does not recover**: only a clear notification whose `reason` is `DISABLED` or `AUTOMATIC` counts as recovery. When the alert policy does not enable **Send an additional notification when the Alert is cleared**, SolarWinds sends no clear notification
- **A clear notification opens a new alert**: the payload has no `detailUrl`, so Flashduty cannot match it to the trigger notification. Keep the HTTP POST Body that SolarWinds generates and do not remove that field
- **The severity is not what you expect**: `severity` recognizes only the uppercase values `CRITICAL`, `WARNING`, and `INFO`; any other value, including lowercase, is treated as Info. `priority` plays no part
- **A label value is a JSON string**: `entities`, `event`, `affected_evaluations`, and `tags` are written as JSON strings, so routing rules match them as strings
- **Flashduty returns a parameter error**: the request body must be a valid JSON object
