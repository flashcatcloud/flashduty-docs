## In Flashduty On-call
You can get the integration push URL in either of the following ways.

### Use a dedicated integration

Choose this option if all alerts go to one channel. It's the simpler setup.

<AccordionGroup>
  <Accordion title="View dedicated integration setup steps">
  
  1. In the Flashduty console, select **Channel** and open a channel
  2. Select **Configuration** → **Integrations** → **Private integration**, then click **Add integration**
  3. Choose **Jiankongbao** integration and click **Save** to generate a card
  4. Open the generated integration card and copy the **Push URL**
  
</Accordion>
</AccordionGroup>

### Use a shared integration

Choose this option if you need to route alerts to different channels based on the alert payload.

<AccordionGroup>
  <Accordion title="View shared integration setup steps">
  
  1. In the Flashduty console, go to **Integration Center → Alert Events**
  2. Select **Jiankongbao** integration:
        - **Integration Name**: Define a name for this integration
  3. Configure the default route and select a channel. You can add more rules under **Routing** after creation
  4. Click **Save** and copy the generated **Push URL**
    
</Accordion>
</AccordionGroup>
</div>

## Alert key

Flashduty uses the monitoring task ID `task_id` as the Alert Key. Alerts raised by the same monitoring task, whichever monitored URL or check they come from, carry the same `task_id` and merge into one Flashduty alert. Changes to the task name, status, severity, time, or `msg_id` do not change the Alert Key.

If you need separate alerts per monitored URL, split the monitoring into several tasks so each task has its own `task_id`.

## Status and severity

<div class="md-block">

| Jiankongbao field | Flashduty |
| --- | --- |
| `message_status` = `2` (recovery) | Recovery |
| `message_type` = `1` | Warning |
| `message_type` = `2` | Info |
| `message_type` empty or any other value | Info |

</div>

When `message_status` is `2`, Flashduty closes the alert for that `task_id`; notifications with any other value create or update the alert according to `message_type`. A recovery notification carries the same `task_id` as the trigger notification, so it closes the alert created when the task started failing.

## Alert content

- **Title**: `<monitoring task name> / <metric summary> - <monitoring type>`, taken from the `check`, `task_summary`, and `task_type` labels
- **Description**: the `content` field

| Label | Source |
| :--- | :--- |
| `check` | Monitoring task name `task_name` |
| `task_summary` | Metric summary `task_summary` |
| `task_type` | Monitoring type `task_type` |
| `task_groups` | Task groups `task_groups` |
| `server_id` | Server ID `server_id` |
| Keys in `message_detail` | When the field is a JSON object, each key-value pair becomes a label, for example `metric`, `value`, `location_type` |

## Troubleshooting

- **Several alerts from one task merge into one**: the Alert Key comes from `task_id`, so alerts of one monitoring task merge. Split the task if you need separate alerts
- **The alert does not recover**: make sure the recovery notification has `message_status` set to `2` and comes from the same monitoring task (`task_id`). Also check that the task still has the webhook notification enabled
- **Flashduty returns a parameter error**: make sure the callback uses the JSON data format and the request body contains `task_id`
