Push EMQX alert events to Flashduty through Webhook.

<div className="hide">

## In Flashduty On-call

You can get the integration push URL in either of the following ways.

### Use a dedicated integration

Choose this option if all alerts go to one channel. It's the simpler setup.

<AccordionGroup>
  <Accordion title="View dedicated integration setup steps">

  1. In the Flashduty console, select **Channel** and open a channel
  2. Select **Configuration** → **Integrations** → **Private integration**, then click **Add integration**
  3. Select **EMQX** integration and click **Save** to generate a card
  4. Open the generated integration card and copy the **Push URL**

</Accordion>
</AccordionGroup>

### Use a shared integration

Choose this option if you need to route alerts to different channels based on the alert payload.

<AccordionGroup>
  <Accordion title="View shared integration setup steps">

  1. In the Flashduty console, go to **Integration Center → Alert Events**
  2. Select **EMQX** integration:
        - **Integration Name**: Define a name for this integration
  3. Configure the default route and select a channel. You can add more rules under **Routing** after creation
  4. Click **Save** and copy the generated **Push URL**

</Accordion>
</AccordionGroup>
</div>

## In EMQX

EMQX Cloud (hosted service) has a built-in Flashduty alert integration type. Self-hosted EMQX forwards system alarm events through the rule engine. Choose the one that matches your deployment.

<Steps>
<Step title="Configure alert push in EMQX">

<Tabs>
<Tab title="EMQX Cloud (hosted service)">

**Where**: EMQX Cloud console › Your deployment › Alerts › Alert Integrations › Webhook integration area › + New

| Field | Value |
| --- | --- |
| Type (required) | `FlashDuty` |
| URL (required) | `{integration_url}` |

Click **Confirm** to save. When an alert fires, EMQX Cloud pushes it to the push URL with a POST request, carrying four labels: `deployment_id`, `level`, `message`, and `region`. EMQX Cloud has no separate recovery configuration, so skip the next step.

</Tab>
<Tab title="Self-hosted EMQX">

**Where**: EMQX Dashboard › Integration › Rules › Create

<Note>
The rule engine supports the `$events/sys/alarm_activated` and `$events/sys/alarm_deactivated` system alarm events starting from EMQX 5.8.5. Make sure your EMQX version is 5.8.5 or later.
</Note>

<Warning>
The quick Webhook setup on the EMQX Dashboard **Monitoring → Alarms** page pushes EMQX's native alarm format, which does not match the event format required by Flashduty. Follow the steps below to customize the request body through the rule engine.
</Warning>

| Field | Value |
| --- | --- |
| SQL (required) | See below; matches alarm activation events |
| Action (required) | Add an **HTTP Server** action |
| Connector URL (required) | `{integration_url}` |
| Request method (required) | `POST` |
| Request body (required) | See the template below |

SQL:

```sql
SELECT
  name,
  message,
  node
FROM
  "$events/sys/alarm_activated"
```

Request body template, which converts alarm fields into the Flashduty standard alert event format:

```json
{
  "event_status": "Critical",
  "alert_key": "emqx::${node}::${name}",
  "title_rule": "EMQX alarm: ${message}",
  "description": "${message}",
  "labels": {
    "alarm_name": "${name}",
    "node": "${node}"
  }
}
```

The `${name}`, `${message}`, and `${node}` variables in the template are replaced with the field values output by the rule SQL. Save the rule.

</Tab>
</Tabs>

</Step>
<Step title="Create the alarm recovery rule in EMQX (self-hosted EMQX only)">

**Where**: EMQX Dashboard › Integration › Rules › Create

Create another rule following the previous step. The action is configured the same way; the differences are:

| Field | Value |
| --- | --- |
| SQL (required) | Change the event to `"$events/sys/alarm_deactivated"`; same `SELECT` fields |
| Request body (required) | Same template as the previous step, but `event_status` fixed to `Ok` |

```sql
SELECT
  name,
  message,
  node
FROM
  "$events/sys/alarm_deactivated"
```

The `alert_key` matches the activation rule, so the corresponding alert in Flashduty recovers automatically when the alarm is deactivated.

</Step>
<Step title="Trigger an alarm and confirm Flashduty receives the event">

**Where**: EMQX Cloud console › Alerts › Alert Integrations (EMQX Cloud); EMQX Dashboard › Monitoring › Alarms (self-hosted EMQX)

- EMQX Cloud: click **Test** on the saved integration. EMQX sends a sample alert, which only confirms the push URL is reachable; confirm fields and severity with a real alert.
- Self-hosted EMQX: the rules fire only when a system alarm is activated or deactivated and there is no test button. The **Active** tab under **Monitoring › Alarms** lists currently active alarms; wait for a real alarm.

After a few seconds, go back to Flashduty. If the integration shows a **Latest event time**, the setup works.
{/* console:
The checklist item "Receive the first event" is then complete as well.
*/}

</Step>
</Steps>

## Status and severity

<div class="md-block">

**EMQX Cloud (hosted service)**: EMQX Cloud automatically maps alert levels as follows:

| EMQX Cloud Alert Level | Flashduty |
| --- | --- |
| Critical | Critical |
| Error / Warning | Warning |
| Info | Info |

**Self-hosted EMQX**: The alert severity is determined by the `event_status` field in the rule's request body template. In the examples above, alarm activation pushes `Critical` and alarm deactivation pushes `Ok`. You can change the activation severity to `Warning` or `Info` in the template. Valid values of `event_status` are `Critical`, `Warning`, `Info`, and `Ok`.

</div>

## FAQ

<details>
<summary>Why am I not receiving alerts in Flashduty?</summary>

**In Flashduty**

1. Check whether the integration shows a **latest event time**. If not, Flashduty has not received any push; troubleshoot the EMQX side first.
2. If you are using a **shared integration**, confirm that you have configured **routing rules**. Without routing rules, the system rejects new pushes because there is no channel to receive your alerts. In this case, configure a routing rule to the target channel.

**In EMQX**

1. Self-hosted EMQX: Make sure the rule's request body template matches the examples above, and `event_status` is one of `Critical`, `Warning`, `Info`, `Ok`; otherwise Flashduty rejects the request.
2. On the rule details page of the EMQX Dashboard, check the rule's runtime statistics and confirm the action succeeds without failures.
3. Make sure the EMQX nodes can access the public domain `api.flashcat.cloud`.

If the issue persists after these steps, please contact us **with the request_id from the push response**.

</details>
