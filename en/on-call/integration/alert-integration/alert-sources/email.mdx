Generate a unique email address in Flashduty to synchronize alert triggers and recoveries through email.

<div className="hide">

## Create an Email integration

You can obtain an email address through either of these two methods:

### Use a dedicated integration

Choose this option if all alerts go to one channel. It's the simpler setup.

<AccordionGroup>
  <Accordion title="View dedicated integration setup steps">
  
  1. In the Flashduty console, select **Channel** and open a channel
  2. Select **Configuration** → **Integrations** → **Private integration**, then click **Add an integration**, and enter the integration page
  3. Choose **Email** integration, click **Save** to generate a card
  4. Click the generated card to view the **Email Address**, copy it for later use, and you're done
    
</Accordion>
</AccordionGroup>

### Use a shared integration

Choose this option if you need to route alerts to different channels based on the alert payload.

<AccordionGroup>
  <Accordion title="View shared integration setup steps">
  
  1. Go to the Flashduty console, select **Integration Center → Alerts**, and enter the integration selection page
  2. Select **Email** integration:
        - **Integration Name**: Define a name for the current integration
        - **Email Address**: Set an easy-to-remember prefix for the email, which must be unique within your account
  3. Configure the default route and select the corresponding channel (after the integration is created, you can go to `Route` to configure more routing rules)
  4. After saving, copy the **Email Address** for later use
    
</Accordion>
</AccordionGroup>
</div>

## Configure the Email integration

<Steps>
<Step title="Save the integration and copy the email address in Flashduty">

**Where**: Flashduty › Integration Center › your email integration › Configuration › Email address

The system generates a unique email prefix. You can change it:

| Rule | Description |
| --- | --- |
| Characters | Letters and digits only; lowercase is recommended |
| Length | 50 characters at most |
| Uniqueness | Unique within your account |

The address takes effect only after you click **Save**. Emails sent to it before then are rejected. After saving, copy the full email address.

</Step>
<Step title="Add the address as an alert recipient in the sending system">

**Where**: sending system › alert notification settings › recipients

In the alert notifications of your monitoring system, cloud service, or script, add the email address from the previous step as a recipient. If the system has a dedicated Flashduty integration (for example Prometheus, Zabbix, or Grafana), use that instead: a dedicated integration reads the alert severity and recovery status, while email alerts always have Warning severity.

</Step>
<Step title="Send a test email from the sending system">

**Where**: sending system › alert notification settings › send test (if there's no test option, wait for a real alert email)

Send an email in the same format as your real alerts, because you'll select part of its subject in the next step. When it arrives, it shows up in the integration's example emails, and the integration shows a **Latest event time**.
{/* console:
The checklist item "Receive the first event" is then complete as well.
*/}

</Step>
<Step title="Answer two questions on a real email in Flashduty">

**Where**: Flashduty › Integration Center › your email integration › Configuration

**Question 1: How should emails about the same problem be grouped?**

| Option | When to use | Behavior |
| --- | --- | --- |
| Every email is a new alert | Notification emails that aren't resent | Each email creates a new alert; nothing is merged or closed |
| Merge when the subject is identical (default for new integrations) | Reminders resent with the same subject | Emails with an identical subject merge into the same open alert |
| Identify by part of the subject (recommended) | Trigger and recovery subjects differ, for example `PROBLEM: …` and `RESOLVED: …` | Select the part of an example subject that identifies the problem, and the system builds the Alert Key rule from it |

After choosing **Identify by part of the subject**:

1. Under **Example email**, pick the email you received in the previous step, or paste the subject and body of an email
2. In the subject, select the part that identifies the problem, for example host plus check `web-01 disk`. Leave out status words such as `PROBLEM` and `RESOLVED` and values that change every time
3. The system generates a regex with exactly one capture group, for example `^(?:PROBLEM|RESOLVED): (\S+ \S+) usage`, that matches both trigger and recovery emails. Click **Edit regex** to adjust it if needed

**Question 2: How do you recognize a recovery email?**

| Option | Behavior |
| --- | --- |
| Subject contains keywords | Enter keywords from recovery subjects, for example `RESOLVED` or `OK`. An email whose subject contains any of them closes the alert with the same Alert Key |
| No recovery emails | Alerts must be closed manually, or turn on silence detection below |

**Other emails**: choose whether emails that match no rule **create an alert** (Warning severity) or are **discarded**. Discarded emails still show up in the example emails and the checklist, tagged "Discarded".

Click **Save**.

</Step>
<Step title="Check that trigger and recovery emails match in Flashduty">

**Where**: Flashduty › Integration Center › your email integration › Configuration › Pair check: do trigger and recovery match

Pick or paste one trigger email and one recovery email:

- Both get the same Alert Key: the recovery email closes the alert, and you're done.
- The keys differ: the page shows what was extracted from each email. Go back to question 1 and adjust the selection or the regex.

**This email becomes** shows the result for the example email: create an alert, close an alert, or discard it, plus the severity, title, Alert Key, and labels. If a rule matches but its regex captures nothing, the page warns that the Alert Key falls back to the email subject.

</Step>
</Steps>

## How rules work

Your answers to questions 1 and 2 are saved as one **trigger** rule and one **close** rule. Expand **Advanced** to edit the underlying rules directly (rule type, filters, Alert Key source field, and regex). Rules of existing integrations show up in **Advanced** as they are. If the rules don't fit the shape of questions 1 and 2, **Advanced** stays open and the rules aren't rewritten.

- Each email is checked against close rules first, then trigger rules, each in the order you configured them, and the first match wins.
- The Alert Key regex must be a valid RE2 expression and may be written as `/…/`. It is validated on save; an invalid expression is rejected with the message "Please enter a valid regex". At least one trigger rule is required.
- The Alert Key is built from the regex capture groups, joined with `,`. **If the regex captures nothing, the system builds the Alert Key from the email subject**, so a bad rule doesn't lose alerts.
- The Alert Key can be extracted from the email subject or the email body.
- When no rule matches, the **Other emails** choice applies: create an alert (Alert Key built from the subject) or discard the email.

### Why /(.*)/ can't be used as the Alert Key regex

`/(.*)/` captures the whole subject. The trigger email `PROBLEM: web-01 disk usage 93%` and the recovery email `RESOLVED: web-01 disk usage 71%` get different Alert Keys, so the recovery email finds no matching alert and the alert is never closed.

Capture only the part that identifies the problem. For the two emails above, use:

```
^(?:PROBLEM|RESOLVED): (\S+ \S+) usage
```

Both emails capture `web-01 disk` and get the same Alert Key. Add a close rule "subject contains `RESOLVED`", and the recovery email closes the alert the trigger email created.

## Silence detection

In the integration card (edit and preview), the **Silence Detection** (Heartbeat) setting sits below the push settings: if no valid event arrives within the configured interval, the system generates a Warning alert.

| Setting | Description |
| :--- | :--- |
| **Enable Silence Detection** | Switch, off by default. When on, only upstream events that pass integration validation refresh the detection time |
| **Detection Interval (minutes)** | A Warning alert is generated if no valid event arrives within this interval. Must be an integer between 10 minutes and 48 hours (default 10 minutes) |
| **Auto-recover on new event** | Switch, on by default. When the next valid event arrives, the alert raised by silence detection is recovered automatically |

## Important notes

1. The system will reject emails larger than 5MB
2. If the email text content exceeds 128KB, the system will truncate it and add a label in the incident details:

   ```
   body_cut = true
   ```

3. If the email contains attachments, the system will discard them and add a label in the incident details:

   ```
   attachment_stripped = true
   ```

4. For new alerts triggered by email, **the title is the email subject, and the description is the email content**. The sender is in the `from` label

5. If you modify your account domain, this email address will also change, so remember to update the push URL

## Status and severity

Currently, all alerts pushed to Flashduty through the email integration are set to Warning severity. However, you can customize the severity using the [alert pipeline](/en/on-call/integration/alert-integration/alert-pipelines).
