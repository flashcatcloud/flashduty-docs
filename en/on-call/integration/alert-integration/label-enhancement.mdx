<Tip>**Plan requirement**: Basic label enhancement requires an On-call Standard or higher subscription. Advanced label enhancement (such as API mapping) requires a Pro or higher subscription. [Learn more](https://flashcat.cloud/flashduty/price/)</Tip>

## Core uses

Labels drive the whole alert workflow: filtering the incident list, routing alerts to channels, matching escalation rules, grouping alerts, and matching silence and inhibition rules. Label enhancement lets these steps use information the source data doesn't provide directly.

## Configure label enhancement

Go to Integration Center → Alert Events, open your integration in the list on the right, then go to **Label enrichment** → **Add label rule**.

<Note>
To turn off label enhancement for an integration, delete all rules and save (applies to both alert and change events). The edit page then shows **No label rules**; click **Add label rule** to configure rules again.
</Note>

### Enhancement types

| Type | Description | Example |
| :--- | :--- | :--- |
| **Extract** | Extract content from title/description/labels using regex | Extract IP address from description |
| **Combine** | Concatenate new labels using template syntax | Combine domain + event ID to generate log link |
| **Map** | Convert values to readable names with a mapping table | Map resource ID to resource type |
| **Delete** | Remove specified labels | Delete sensitive info labels |

#### Mapping methods

When source label values vary or aren't meaningful on their own, map them to new labels and values. When adding a mapping rule, choose **Schema** or **API**:

| Mapping Type | Description | Use Case |
| :--- | :--- | :--- |
| **Schema (Mapping Table)** | Static mapping with a predefined CSV mapping table | Mapping relationships are relatively fixed with limited data |
| **API (API Mapping)** | Dynamic mapping by calling external API service | Need to query external systems (your own mapping service) for real-time data |

### Configuration options

| Option | Description |
| :--- | :--- |
| **Condition** | Only applies to events (both alert events and change events) matching the conditions, see [Configure Filter Conditions](/en/on-call/configuration/filter-conditions) |
| **Override** | When enabled, overrides an existing label with the same name; off by default |
| **Preview** | Preview rule effects with a real alert, see [Preview rules](#preview-rules) |

<Tip>
Multiple rules execute sequentially from top to bottom. Flashduty skips a rule that doesn't match and generates no label for it.
</Tip>

### Preview rules

The **Preview** card on the right of the editor runs your current rules, unsaved changes included, on one raw event and reports the result in two parts: a label table, and **How this event was processed**.

- The label table lists every label after the preview: an added label is prefixed with `+`, a changed label shows old value → new value, a removed label is struck through. Each change names the rule that made it (**Added by rule N** / **Changed by rule N** / **Dropped by rule N**), and a label a rule should have produced but didn't is marked **Not generated** (**Rule N did not match**).
- **How this event was processed** gives one line per rule: which labels it produced, or why it did nothing. The rule card header on the left also shows **Applied** / **No match** / **Skipped** / **Error**.

The event source switches between **Recent events** and **Custom**. **Recent events** picks one of the raw events the integration received (each integration keeps its latest 20 events for 7 days, at most one every 10 seconds); when the event you want isn't in the list, switch to **Custom** and paste an event JSON. The preview runs exactly what the editor holds; in **Recent events** mode edited lines are highlighted and you can revert them.

A mapping rule also shows the row it matched in the mapping table inside the rule, with the match column marked **(match column)**; the labels it generated are green and summed up as **Found 1 row for this raw event; adds …**. Sample values in the regex and template editors come from the same event.

When a rule does nothing, the preview names the reason:

| Message | Meaning |
| :--- | :--- |
| Skipped: conditions not met | The event does not meet the conditions set on the rule |
| No match: the regex did not match the value of `labels.host` | The regex did not match the source field's value |
| No match: the event has no `labels.host` | The event has no such source field |
| No match: the mapping table has no row for this event, no labels added | The mapping table has no matching row |
| Skipped: `owner_team` already exists and overwrite is off | The target label exists and **Override** is off |
| Error: … | The rule failed; the message carries the detail, for example the mapping service call failed |
| Applied, but no label changed | The rule ran and changed no label |
| Not previewed: this rule or an earlier one is incomplete | This or an earlier rule is incomplete, so the preview does not run it |

A preview covers at most 50 rules. A rule whose mapping type is **API** makes the preview call your mapping service for real, so it needs edit permission on the integration; without it the preview shows **Previewing mapping-API rules requires edit permission** and the rest of the page keeps working.

### Condition fields

Label enhancement rules apply to both alert events and change events, and the fields usable in conditions are the union of the two:

| Field | Description |
| :--- | :--- |
| `labels.<name>` | Any label; label names are unrestricted |
| `data_source_id`, `integration_id` | Data source (integration) ID; the two fields are equivalent |
| `severity`, `event_severity`, `alert_severity` | Alert event severity; the three fields are equivalent, only carried by alert events |
| `status` | Event status: alert status for alert events, change status for change events |
| `title` | Event title |
| `description` | Event description |
| `title_rule` | Alert title rule ID, only carried by alert events |
| `alert_key` | Unique identifier of the alert event |
| `change_key` | Unique identifier of the change event |

<Note>
Flashduty validates condition fields when you save a rule. Fields outside this vocabulary make the save fail, such as typos or fields from other rule families like `incident_severity` or `dedup_key`.
</Note>

<Tab title="Mapping: API">
**Example**: Need to query responsible team, service tier, and other dynamic data from your own mapping service based on host information in alerts.

<Steps>
<Step title="Create Mapping Service">
1. Go to **Configuration** → **Mappings** → **API** → **Create API**
2. Fill in service configuration:

   | Configuration | Description | Example |
   | :--- | :--- | :--- |
   | Service Name | Readable name for the service | Asset Query Service |
   | Description | Service purpose description | Query asset info by host IP |
   | Request URL | API request address | `https://mapping-api.example.com/v1/enrich-event` |
   | Headers | HTTP request header configuration | `X-Auth-Token: your-token` |
   | Timeout | Request timeout, 1-3 seconds, default 2 seconds | 1 |
   | Retry Count | Retry count on failure, 0-1 times, default 0 times | 1 |

<Tip>

</Tip>
</Step>

<Step title="Configure Mapping Rule">
Add a mapping rule in label enhancement, use the radio toggle to select mapping type as `API`:
1. Select the created mapping service
2. Configure `Result Label List`: specify label names expected from API response, for example, `owner_team`, `service_tier`, `host_ip`
3. Enable `Override` option as needed
</Step>

<Step title="Verify Mapping Result">
When an alert is triggered, Flashduty automatically calls the configured API service, sends alert event data to the external system, and adds the returned labels to the alert.
</Step>

## Mapping data management

<Note>
Each account can create up to 20 mapping tables and 50 mapping services (APIs). Each mapping table holds up to 10,000 rows by default. Creating a table or uploading data fails with a limit-exceeded error once a quota is reached.
</Note>

### Mapping table data management

In the mapping table details page, you can manage mapping table data:

| Feature | Description |
| :--- | :--- |
| Data Search | Search by source label value |
| Data Add | Manually add mapping data |
| Data Upload | Upload new data mapping table, will overwrite existing data |
| Data Download | Download current mapping table data locally |
| Data Display | Display current mapping table data, can edit or delete |

<Frame>
<img src="https://docs-cdn.flashcat.cloud/images/png/477563cfc4e3759e8584edd34fa5bf9a.png" alt="Mapping table data management" />
</Frame>

A mapping table that is still referenced cannot be deleted. The delete is refused with **Delete failed, resource is in use.**, and the objects still referencing it are listed by type; select one to open its configuration:

- **Integrations**: a label enhancement rule uses this mapping table
- **Escalation rule**, **Schedule**: a notification robot has **Enable @ mentions** on and uses this table as its **User information mapping**. Turning **Enable @ mentions** off keeps the selected table, which still counts as a reference

Remove these references first (switch to another table, clear the mapping table selection, or delete the robot), then delete the mapping table.

<Tip>
For frequently changing mapping relationships (like data synced from a CMDB), we recommend using API mapping, or use [Flashduty API](/en/api-reference/on-call/alert-enrichment/mapping-data-write-upsert) for automated mapping table updates.
</Tip>

### Mapping service API specification

For the request body, response format, forbidden headers, and implementation tips for your own mapping service, see [Label Mapping API](/en/on-call/integration/alert-integration/alert-sources/label-mapping-api).
