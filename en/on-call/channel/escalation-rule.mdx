Escalation rules determine **when**, **through which channels**, **to whom**, and **how to escalate on timeout** when an incident occurs. Through direct messaging, group chat, and multi-level escalation mechanisms, they ensure important incidents always get a response.

## Configuration elements

An escalation rule contains six core elements. The system matches rules from top to bottom, **stopping after the first successful match**.

You can enable or disable individual escalation rules. Flashduty skips disabled rules during matching, so they trigger no notifications. You can also copy an escalation rule to the current channel or another channel to quickly reuse existing configurations; see [Copy an Escalation Rule](#copy-an-escalation-rule).

### 1. Trigger conditions

Determines which incidents trigger the current rule.

**Effective Time**: Controls when the rule participates in matching.

- **Off (Default)**: Active 24/7
- **On**: Only participates in matching within specified time ranges; incidents outside this time will skip this rule. Two modes supported:
  - **Specific Time Period**: for example, only active on weekdays (Monday-Friday 9:00-18:00)
  - **Service Calendar**: Reference a predefined [Service Calendar](/en/on-call/configuration/service-calendar), for example, only active on "Trading Days", automatically excluding holidays

**Incident Filter**: Controls which incidents the rule matches.

- **Off (Default)**: All incidents may match this rule
- **On**: Only incidents matching the filter conditions hit this rule; unmatched incidents continue matching subsequent rules. You can add multiple condition groups — conditions within a group are ANDed, groups are ORed; each condition supports **Match** / **Not Match** operators, with available keys:
  - **Integration Source (First Alert)**: Match by the integration that produced the incident's first alert; options are the integrations available to the current channel (both shared and dedicated)
  - **Severity**: Multi-select Critical / Warning / Info
  - **Title**, **Description**: Support exact, wildcard, regex, CIDR, and numeric comparison matching modes
  - **Labels**: Match by alert label key-value pairs (for example, `service=payment`); load keys from recent alert data or enter them manually

### 2. Notification recipients

Determines who receives notifications.

| Recipient Type | Description |
| :---------- | :------------ |
| **Schedule (Recommended)** | Assign to currently on-call personnel |
| **Team** | Assign to all members of a team |
| **Individual** | Assign to specific personnel |
| **Combination Mode** | You can select multiple types simultaneously |

<Tip>
For dynamic routing to owners based on alert content (for example, auto-assign based on `owner` label), refer to [Dynamic Assignment](/en/on-call/advanced/dynamic-notifications).
</Tip>

### 3. Notification methods

Determines how Flashduty reaches users.

<Tabs>
  <Tab title="Direct Message (Reach Individuals)">
    Point-to-point messaging to specific assignees, supports phone calls, SMS, email, app push, IM direct messages (Feishu/Lark, Dingtalk, WeCom, Slack, Microsoft Teams).

    - **Follow Personal Preferences (Recommended)**: Notification methods configured by members in [Personal Settings](/en/on-call/configuration/personal-settings)
    - **Follow Unified Settings**: Enforce notification methods (for example, must send SMS), overriding member personal preferences
  </Tab>
  <Tab title="Group Chat (Reach Groups)">
    Send to instant messaging groups, with support for @ mentioning relevant personnel.

    - **IM App Groups**: Supports Feishu/Lark, Dingtalk, WeCom, Slack, and Microsoft Teams groups (WeCom is available only in existing configurations, not in new rules). Complete the [IM Integration](/en/on-call/integration/instant-messaging/lark) first. Disabled IM apps stay in the app dropdown, labeled "(Disabled)", but you can't select them as notification targets. Re-enable the app in Integrations first. The group-chat picker automatically excludes platform-created chats such as war rooms (placeholder: "Select … group chat (war rooms excluded)"); stale targets render as **Chat unavailable** and can be removed
    - **Group Bots**: Supports Feishu/Lark, Dingtalk, WeCom, Slack, Telegram, Zoom, and other Webhook bots. Telegram requires configuring a Webhook notification address and Chat IDs, Zoom requires configuring a Webhook address and Verify Token, and supports enabling @ mention functionality. See [Notification Channel Configuration](/en/on-call/configuration/notifications)

    <Note>
    **Don't use any of the above IM platforms?** Select any bot type and set the webhook URL to your own server endpoint. Flashduty doesn't validate the domain. Then implement that bot's message protocol on your server. See [FAQ](/en/on-call/quickstart/faq#custom-bot-notifications).
    </Note>

    <Info>
    **Cross-team webhook address scoping.** When you select a Webhook bot address in a dispatch policy, Flashduty groups addresses by owner:

- **Current Channel**: already referenced by this channel
- **Same Team**: referenced by other channels in the same team
- **Other Team**: referenced only by channels in other teams

 Other-team addresses are collapsed until you expand them. Selecting one shows a **Cross-team** badge and a warning. When you save a rule with cross-team addresses, Flashduty asks you to confirm, so alerts don't reach another team's chat by accident.

    When selecting or pasting a Webhook address from **Other Team**, Flashduty prefixes the alias with the source team name (for example, `team-name-alias`). It skips the prefix if the alias already starts with it. When you paste an address, it adds the prefix only if the alias is empty. You can still edit the alias afterward.
    </Info>
  </Tab>
</Tabs>

### 4. Delay window

Wait before sending the first notification, to filter out incidents caused by transient flapping.

- Range: 0 – 3600 seconds, default `0` (disabled, notify immediately)
- During the delay window, if the incident is **auto-closed** or **manually closed**, the system does not send a notification

<Tip>
  For monitors that often recover on their own (such as transient flaps or brief network timeouts), setting a reasonable delay window can significantly reduce unnecessary interruptions.
</Tip>

### 5. Notification template

Every escalation rule **must** select a notification template, which determines the message format delivered to each channel.

- Create and enable the template first under [Notification Templates](/en/on-call/configuration/templates)
- You can pick different templates for different escalation rules to format messages for specific scenarios

### 6. Escalation rules

This is the key mechanism for ensuring incident closure. When first-level responders don't respond or complete handling, the system automatically escalates to the next level.

**Loop Notification**:

In each escalation level, you can enable the **Loop Notification** feature. If the incident is still unresolved at that level, Flashduty repeats the notification at the configured interval, up to the maximum count. The interval is at least 0.5 minutes, in 0.5-minute steps.

**Escalation Conditions**:

- **Not closed**: Incident not closed within N minutes after trigger
- **Not closed and not acknowledged**: Incident neither closed nor acknowledged within N minutes after trigger

The minimum escalation timeout is 1 minute.

**Typical Scenarios**:

| Scenario | Escalation Path |
| :------ | :-------------------------------- |
| Level 1 → Level 2 | Level 1 on-call (SRE) no response for 15 min → Escalate to Level 2 development experts |
| Primary/Backup Escalation | Primary on-call no response for 10 min → Escalate to backup on-call |
| Tiered Reporting | Technical staff unresolved for 30 min → Escalate to Tech Lead → Escalate to CTO |

**Level management**:

- **Default first level**: Flashduty creates the first level with each new rule. It escalates after a **30-minute timeout**, sends **no repeated notifications**, and uses notification methods that **follow personal preferences**
- **Add or remove levels**: you can add or remove levels freely; a rule must keep at least 1 level
- **Reorder**: you can move a level up or down, or insert a new level between any two existing levels

## Copy an escalation rule

Click the **Copy** icon on an escalation rule card to set the new rule's name, target channel and description:

| Field | Description |
| :--- | :--- |
| **Rule name** | Required; defaults to "Copy \<original name\>", **39 characters max** |
| **Channel** | This channel or another channel (non-admins can choose only channels they manage) |
| **Description** | Optional; defaults to the original description, **500 characters max** |

The copy keeps the source rule's full configuration: trigger conditions, notification targets, notification methods, delay window, notification template, and escalation levels. It does **not** keep the rule's position in the list, so move the new rule where you want it. After copying to another channel, click **Go to view** to open the new rule.

## Best practices

<AccordionGroup>
  <Accordion title="Fallback Policy" icon="shield">
    Keep a default policy **without filter conditions** at the bottom of the list and assign it to the SRE team or administrators. It catches incidents that misconfigured filters would otherwise miss.
  </Accordion>
  <Accordion title="Avoid Over-notification" icon="bell-slash">
    - For low-priority `Info` / `Warning` level alerts, recommend using only IM messages, not phone calls or SMS
    - Use the **Loop Notification** feature cautiously to avoid alert bombardment
  </Accordion>
  <Accordion title="Reasonable Channel Splitting" icon="layer-group">
    Don't try to manage all company alerts in one channel. Splitting channels by functional module or team, with each channel maintaining independent and simple escalation rules, is key to reducing maintenance costs.
  </Accordion>
</AccordionGroup>

## FAQ

<AccordionGroup>
  <Accordion title="Alerts are generated but no notifications received?" icon="circle-question">
    Go to Incident Details → **Timeline** to check if notification status is normal for each channel. If there are failure messages, use them for troubleshooting. Contact technical support for more issues.
  </Accordion>
  <Accordion title="Notification method doesn't match personal preference settings?" icon="circle-question">
    Flashduty On-call direct messaging supports two modes: "Follow Personal Preferences" and "Follow Unified Settings". Only in "Follow Personal Preferences" mode will the system send notifications according to your personal settings.

    Go to Channel Details → **Escalation Rules** to check current settings.
  </Accordion>
  <Accordion title="What's the difference between webhook integrations and group bot webhooks?" icon="circle-question">
    These are two different features — do not confuse them:

    - **Webhook integrations** ([Alert Webhook](/en/on-call/integration/webhooks/alert-webhook), [Incident Webhook](/en/on-call/integration/webhooks/incident-webhook)): When alerts or incidents change, Flashduty pushes event data to your URL. External systems, such as ticketing or automation platforms, can then act on it
    - **Group bot webhooks** (this page, "Notification Methods → Group Chat"): Set an IM group bot's webhook URL in an escalation rule. Flashduty then posts incident notifications to that group chat

    In short: webhook integrations are for **data export**, group bots are for **notification delivery**.
  </Accordion>
</AccordionGroup>
