Open API lets you call Flashduty through HTTP endpoints to query and manage entity data such as incidents, channels, and schedules. Using the API is essentially the same as logging into the [Flashduty Console](https://console.flashcat.cloud) and performing operations through the UI.

<Tip>
**Not sure if you need Open API?** Flashduty offers multiple data interaction methods:

- **Open API** (this guide) — You actively call Flashduty to query or operate on data. See the [API Catalog](/en/openapi/api-catalog) for all available endpoints.
- **Standard Alert Events** — Push alerts from your custom monitoring system to Flashduty to trigger incident handling. See [Custom Alert Events](/en/on-call/integration/alert-integration/alert-sources/standard-alert).
- **Custom Change Events** — Push change events to correlate with incidents for root cause analysis. See [Custom Change Events](/en/on-call/integration/change-integration/custom-event).
- **Webhook Push** — Flashduty proactively pushes incident/alert event notifications to your system. See [Incident Webhook](/en/on-call/integration/webhooks/incident-webhook) and [Alert Webhook](/en/on-call/integration/webhooks/alert-webhook).
- **Custom Actions** — Trigger external operations from the incident detail page. See [Custom Actions](/en/on-call/integration/webhooks/custom-actions).
</Tip>

## Request specifications

### Request URL

All APIs are served over **HTTPS** from a single endpoint:

```
https://api.flashcat.cloud
```

### Method and headers

Almost every operation is a `POST` with a JSON body, so set:

```
Content-Type: application/json
```

A few read operations use `GET` with query parameters (for example the status page reads and the Prometheus-compatible label query); each operation page shows its method. Send `{}` as the body of a `POST` that takes no parameters.

### Character encoding

All requests and responses use **UTF-8**.

### Response language

Error messages are localized. The language is taken, in order, from the `locale` query parameter, the `lang` query parameter, then the `Accept-Language` header, for example `Accept-Language: en-US` or `zh-CN`. Field names, enum values, and error codes are never translated.

## Authentication

All Open APIs authenticate with an **APP Key**.

### Obtaining an APP key

<Steps>
  <Step title="Sign in to console">
    Sign in to the [Flashduty Console](https://console.flashcat.cloud)
  </Step>
  <Step title="Create APP Key">
    Hover over the avatar in the lower left, select **APP Key** in the **Personal center** column, enter a name, choose a permission scope, then click Add. See [Personal settings](/en/on-call/configuration/personal-settings#app-key).

    - **All permissions**: Does not add an API-scope restriction, but remains limited by the creator's current role permissions.
    - **Custom permissions**: Select at least one available API permission. The APP Key can call only APIs in the selected scope.
  </Step>
</Steps>

<Warning>
An APP Key's effective access is constrained by both its permission scope and the creator's current role permissions. Store the full key securely as soon as it is created; it cannot be viewed again after you leave the creation page. Do not hardcode it in client code; load it from an environment variable or a secret manager, and delete keys you no longer use.
</Warning>

You can edit an existing APP Key's name and permission scope from the APP Key list.

### What to do if an APP key is exposed

If an APP key may have been exposed (for example, committed to a public repository or shown in logs or screenshots), replace it:

<Steps>
  <Step title="Create a replacement key">
    In **Personal center → APP Key**, create a new APP key.
  </Step>
  <Step title="Switch your integrations">
    Move every integration, script, and configuration that uses the old key to the new key, and confirm the calls work.
  </Step>
  <Step title="Disable or delete the old key">
    Disable or delete the old key in the APP key list. Requests that use it then return `401 Unauthorized`.
  </Step>
</Steps>

### Passing the APP key

Pass the key as the `app_key` query parameter:

```bash
curl -X POST 'https://api.flashcat.cloud/incident/list?app_key=YOUR_APP_KEY' \
  -H 'Content-Type: application/json' \
  -d '{"start_time": 1712000000, "end_time": 1712086400, "limit": 20}'
```

Or send it in the `Fd-App-Key` request header, which keeps the key out of URLs and access logs:

```bash
curl -X POST 'https://api.flashcat.cloud/incident/list' \
  -H 'Fd-App-Key: YOUR_APP_KEY' \
  -H 'Content-Type: application/json' \
  -d '{"start_time": 1712000000, "end_time": 1712086400, "limit": 20}'
```

When both are present, the query parameter wins. A missing or invalid key returns `401 Unauthorized`.

<Note>
Using Go? Use the official [Go SDK](/en/developer/go-sdk) to call Flashduty — you get typed request parameters, response structs, and error codes out of the box, with no hand-written HTTP.
</Note>

## Response structure

All responses are JSON with the same envelope:

| Field | Type | Always present | Description |
| --- | --- | :---: | --- |
| `request_id` | string | ✅ | Request ID, also returned in the `Flashcat-Request-Id` response header. Include it when contacting support. |
| `data` | any | | Operation-specific payload, documented on each operation page. Operations with no payload return `{}` or omit `data` entirely, so do not rely on its presence. Absent on errors. |
| `error` | object | | Present only when the request failed. |

Success returns HTTP `200`. Failures return the HTTP status listed in the [error code list](/en/openapi/rate-limits#error-codes), but branch on `error.code`, not on the status.

### Response examples

<Tabs>
  <Tab title="Success Response">
```json
{
  "request_id": "01HK8XQE3Z7JM2NTFQ5YJ8P9R4",
  "data": {
    "team_id": 1467226103121,
    "team_name": "SRE"
  }
}
```
  </Tab>
  <Tab title="Error Response">
```json
{
  "request_id": "01HK8XQE3Z7JM2NTFQ5YJ8P9R4",
  "error": {
    "code": "InvalidParameter",
    "message": "The specified parameter team_name is not valid."
  }
}
```
  </Tab>
</Tabs>

### Error object structure

| Field | Type | Always present | Description |
| --- | --- | :---: | --- |
| `code` | string | ✅ | Stable error code, see the [error code list](/en/openapi/rate-limits#error-codes) |
| `message` | string | ✅ | Human-readable description in the response language; may name the offending field. Do not parse it. |

## Data conventions

- **Timestamps** are Unix epoch integers. Most are in **seconds**; some (most AI SRE and RUM timestamps, incident feed entries, audit logs) are in **milliseconds**. Every time field states its unit in its description.
- **Enums** are case-sensitive strings or integers; each field lists its allowed values and what they mean.
- **IDs** are returned as integers or strings exactly as documented per field; send them back in the same type.
- **Lists** are paginated; see [About pagination](/en/openapi/pagination).
- **Updates**: each update operation states, per field, whether an omitted field keeps its current value or is cleared.
