title: "About pagination"
description: "Flashduty Open API pagination mechanism"
---

List operations return results in pages. Most use page-number pagination; operations over large or fast-changing collections also accept a cursor. The parameters an operation supports, and their limits and defaults, are documented on its page — the values below are the common defaults, not guarantees for every operation.

## Page-number pagination

### Request parameters

| Parameter | Type | Description |
| --- | --- | --- |
| `p` | integer | Page number, starting at 1. Omitted or `0` means 1. offset = (p - 1) × limit |
| `limit` | integer | Items per page. Typically at most 100, default 20; some operations use other bounds, shown on their page. |

### Response fields

| Field | Type | Description |
| --- | --- | --- |
| `total` | integer | Number of matching items (see [About total](#about-total)) |
| `has_next_page` | boolean | Whether another page exists |

### Example

<Tabs>
  <Tab title="Request Example">
```json
{
  "p": 1,
  "limit": 20
}
```
  </Tab>
  <Tab title="Response Example">
```json
{
  "total": 1000,
  "has_next_page": true,
  "items": []
}
```
  </Tab>
</Tabs>

### Depth limit

<Warning>
On On-call list operations, `p × limit` must be at most 10,000. Deeper pages fail with `400 InvalidParameter`. To walk further, use cursor pagination where the operation supports it, or narrow the filters (for example, a shorter time range).
</Warning>

Page-number pagination can skip or repeat items when objects are created or deleted between two calls, because offsets shift. Use a cursor for complete, stable exports.

---

## Cursor pagination

Pass `search_after_ctx` from the previous response to get the next page. A cursor is opaque: do not build or modify it, and keep the other request parameters unchanged between pages. When `search_after_ctx` is set, `p` is ignored.

On List incidents and List alerts you can start with page-number pagination and switch at any time: every non-empty page also returns `search_after_ctx`, the cursor after its last item.

### Request parameters

| Parameter | Type | Description |
| --- | --- | --- |
| `search_after_ctx` | string | Cursor from the previous response. Omit it for the first page. |
| `limit` | integer | Items per page, bounds as documented on the operation page. |

### Response fields

| Field | Type | Description |
| --- | --- | --- |
| `has_next_page` | boolean | Whether another page exists |
| `search_after_ctx` | string | Cursor for the next page. In cursor mode it is returned only when `has_next_page` is `true`. |

### Example

<Tabs>
  <Tab title="Request Example">
```json
{
  "search_after_ctx": "658bcbae6ab5a67b3b800230",
  "limit": 20
}
```
  </Tab>
  <Tab title="Response Example">
```json
{
  "total": 1000,
  "has_next_page": true,
  "search_after_ctx": "658ba7f9566077d6090e8d51",
  "items": []
}
```
  </Tab>
</Tabs>

## About total

`total` is not always exact. To keep large queries fast, operations over incidents, alerts, alert events, post-mortems, and mapping data stop counting at 1,000:

<Warning>
- When fewer than 1,000 items match, `total` is exact.
- When 1,000 or more match, `total` is 1,000, meaning "1,000 or more".
</Warning>

<Tip>
Use `has_next_page`, not `total`, to decide whether to fetch another page: `has_next_page` does not depend on `total` and stays accurate past 1,000 items.
</Tip>
