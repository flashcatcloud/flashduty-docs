The Query Workbench (Explore) is an ad-hoc query interface in Flashduty Monitors for running temporary queries against data sources without creating alert rules. It supports Prometheus, Loki, VictoriaLogs, Alibaba Cloud SLS, Tencent Cloud CLS, and MySQL, PostgreSQL, Oracle, ClickHouse, Elasticsearch data sources.

## Access

- **From the data source list**: Go to **Monitors → Data Sources** and click the "Query Workbench" entry on the target data source row.
- **Direct URL**: Navigate to `/monit/explore` and select a data source in the page.
- **From incident/alert labels**: In the label area of incident or alert detail, the "Explore" icon on query-type label rows opens the workbench with the alert's triggering query and time window pre-filled.

## Query Types

Different data sources support different query types, switched above the editor:

| Data Source | Query Type | Description |
|-------------|-----------|-------------|
| Prometheus | Graph + Raw | Shows both a line chart and raw samples |
| Prometheus | Graph only | Shows only the line chart (range query) |
| Prometheus | Raw only | Shows only raw samples (instant query) |
| Loki | Range | Returns log lines within the time range |
| Loki | Instant | Returns matching log lines at the current moment |
| VictoriaLogs | Raw logs | Returns raw log lines |
| VictoriaLogs | Instant stats | Returns instant aggregate statistics |
| VictoriaLogs | Range stats | Returns range trend statistics |
| SLS / CLS | — | No query type selector; vendor-classified logs/tables |
| MySQL / PostgreSQL / Oracle / ClickHouse / ES | — | SQL/query expression executed directly |

> Before a query is routed to Edge for execution, it goes through a syntax check: Prometheus data source expressions must pass a PromQL/MetricsQL syntax validation — invalid expressions are rejected upfront with the parser error detail and are never sent for execution. Other data source types are not affected by this check.

## Result Display

The result area auto-layouts based on data source and query type:

- **Prometheus**: Split pane — line chart (Graph) on top, raw samples (Raw) below, with a draggable splitter.
- **Other data sources**: Single result pane showing log view, table view, or samples view depending on the query type.

### Graph Features

- **Drag-to-zoom**: Drag-select a time range on the chart to zoom in.
- **Legend facet filtering**: The legend area supports searching by label value and grouping by metric name. Series beyond the display limit are collapsed; click to expand.
- **Tooltip**: Hover to see values for all series at a given time point. Series beyond the limit are summarized in the tooltip.

### Log Time Distribution

When the query type includes logs, a log time distribution chart appears above the result area:

- Time range ≤ 24 hours: auto-loaded.
- 24 hours – 30 days: requires manual click to load.
- Beyond 30 days: not supported.

### Log View

Log-type query results are displayed row by row; each row contains the timestamp, body, and a field summary. If a batch of results contains fields whose value is identical in every row (common fields, such as Loki's stream labels), these fields are shown in the summary on every row by default, but they take up width on each row repeatedly.

- The **Common Fields** button on the toolbar lists the fields that are identical across every row in the current batch, with their values; after checking **Hide Inline** in the popover, these common fields are collapsed out of the inline summary, and each row keeps only the content that differs (with a "+N fields" hint displayed)
- **Hide Inline** is off by default (common fields are shown by default); the toggle is session state, not persisted — refreshing the page restores the default
- Clicking a row expands its details; the details always show all fields of that row, unaffected by the **Hide Inline** toggle

## Query Parameters

In addition to the query expression, some data sources support private parameters:

| Parameter | Data Sources | Description |
|-----------|-------------|-------------|
| Limit | Loki / VictoriaLogs | Caps the number of returned rows |
| Min step (seconds) | Prometheus | Lower bound for auto step calculation |
| Direction | Loki / VictoriaLogs | Latest-first or earliest-first |
| Project / Logstore | SLS | Required; used in the request URL |
| Region / Topic / Syntax | Tencent CLS | Required |
| PowerSQL | SLS | Enables PowerSQL mode |
| Time macros | SQL data sources | `$__timeFilter(column)`, `$__timeFrom()`, `$__timeTo()` make the time range take effect |

## AI Query Generation

An AI button sits in the top-right corner of the query statement input and appears when you hover or focus the input. Open it, describe in plain language what you want to query, and the assistant returns **one** ready-to-use statement together with an explanation of what it does and what is still yours to decide.

Before answering, the assistant reads the current editor: the scene, the data source type, the data source's private parameters, the draft statement you are writing, and the workbench's current time range — if you change the data source or query type mid-conversation, what it reads changes too. It can also inspect real data first (list available metric names, run one probe query to see the returned labels) and then validate the finished statement; a statement that fails validation is never delivered.

Applying a statement places the whole query at once: **the statement, the data source's private parameters, the query type, and when needed the data source itself** — if the statement was written for another data source, applying it switches to that data source first, and you can choose to run it right away.

The same button sits on the statement input of every QL editor, and the assistant understands your intent from the scene:

| Scene | Entry point |
|-------|-------------|
| Query Workbench (`scene=explore`) | The statement input on this page |
| Alert rule query (`scene=rule_query`) | The alert rule's query statement input (including the query preview dialog) |
| Recovery condition (`scene=rule_recover`) | The recovery condition statement input |
| Related query (`scene=rule_relate`) | The related query statement input |
| Entity category configuration (`scene=entity_def`) | The entity category's discovery PromQL input |
| Entity alert rule (`scene=entity_rule`) | The entity alert rule's alert condition PromQL input |

The capability is provided by the AI backend app `query-assistant`; the sessions it creates are incognito by default and do not appear in the session history list.

## Querying Programmatically Through Data Source Tools

The workbench query capability is also a query tool on the data source tool entry: for `POST /monit/datasource/tools/invoke`, `tool` takes `<type>.query`, where `type` matches the data source types the workbench supports (`prometheus`, `mysql`, `postgres`, `oracle`, `clickhouse`, `elasticsearch`, `loki`, `victorialogs`, `sls`, `tencent_cls`). The query runs on the same execution path as the workbench, so syntax validation, result structure, and Edge version requirements are identical; the tool's `type` prefix must match the selected data source's type, otherwise you get `invalid_request`.

Parameters are `expr` plus `execution`:

| Field | Type | Description |
|-------|------|-------------|
| `expr` | string | The query statement, same syntax as the workbench |
| `execution` | object | Required; describes how the query runs |

`execution` fields and mode constraints:

| Field | Type | Description |
|-------|------|-------------|
| `kind` | string | `instant` (instant; accepts only `to_ms`), `range` (range; requires `from_ms`, `to_ms`, `max_data_points`, optional `min_step_seconds`), `window` (window; requires `from_ms`, `to_ms`) |
| `from_ms` / `to_ms` | number | Millisecond timestamps |
| `max_data_points` | number | Data point cap for range queries, 2–5000, required in `range` mode |
| `min_step_seconds` | number | Lower bound for the auto step (seconds), optional in `range` mode |

For range queries the `step_seconds` sent to Edge is derived server-side from `from_ms`, `to_ms`, `max_data_points` (and the optional `min_step_seconds`) — you neither need nor should pass it yourself.

`kind` and extra fields per data source type:

| Data Source Type | Allowed `kind` | Extra requirements |
|------------------|----------------|--------------------|
| `prometheus`, `loki` | `instant` or `range` | Prometheus `instant` accepts only `to_ms` |
| `victorialogs` | All three, with their fields complete | `from_ms` is required; `limit` and `direction` apply only to `window` mode. Workbench mapping: raw logs use `window`, instant stats use `instant`, range stats use `range` |
| `mysql`, `postgres`, `oracle`, `clickhouse`, `elasticsearch`, `sls`, `tencent_cls` | `window` only | SLS requires `project` and `logstore`, `powersql` optional; Tencent CLS requires `region`, `topic_id`, and `syntax` (`cql` or `lucene`) |

Log-type data sources also accept `limit` and `direction`, with the same meaning as the workbench's Limit / Direction (the `direction` is `latest` or `earliest`; `limit` caps at 100 for SLS and 1000 for the other log types). Fields not listed here are ignored; passing an explicit `null` for a known field is rejected. The outer result carries `datasource_id`, `tool`, and `data`, where `data` has the same `explore_result.v1` structure the workbench returns (`samples`, `frames`, or `logs`). As in the workbench, the entry requires the data source to be `enabled=true`.

For the full parameter list, error codes, and request examples, see [data source tools invoke](/en/api-reference/monitors/data-sources/monit-datasource-tools-invoke); the CLI equivalent is `flashduty monit-query <datasource-id> --tool '<type>.query'`, documented in the [CLI](/en/developer/cli) reference.

## Query History

Each successful query is automatically saved to query history, which stores only the query expression — not the time range or results. History is isolated per data source, stored in the browser locally, and retains up to 200 entries. When the limit is exceeded, the oldest entry is evicted. Oversized query expressions are not saved to history but the query itself still succeeds. You can delete individual entries or clear all history for the current data source from the history panel.

## Sharing and URL State

The workbench encodes the current data source, query expression, time range, and query type into URL parameters. Copy the browser address bar to share the current query state — opening the link restores it automatically. If the data source in the link doesn't exist, is disabled, or the user lacks permissions, the page prompts and does not auto-execute.

## Edge Version Requirements

The Query Workbench relies on monit-edge to execute queries. If the Edge version in the data source's cluster is too low or versions are mixed, the page shows an upgrade prompt and disables querying. All Edge instances in the cluster must be upgraded to the required version before use.
