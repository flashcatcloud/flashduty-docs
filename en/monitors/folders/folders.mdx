Monitors uses a tree-structured folder hierarchy to organize and manage alert rules. Every alert rule must belong to a folder. You can use the hierarchical structure for categorized management and configure team access permissions at different levels.

**Menu Entry**: Alert Rules (left-side tree navigation)

## Folder tree

The left side of the page displays the folder tree structure. You can:

- **Create folders**: Create subfolders within the tree
- **Select folders**: Click a folder to view its details and associated alert rules
- **Nested hierarchy**: Supports multiple nesting levels to meet complex organizational needs

When a folder holds a rule that needs attention, the folder icon on its tree node is replaced by a red warning icon. It appears when at least one rule in the folder still has active alerts, or its runtime status is one of **Execution error**, **Status is stale**, **Edge offline**, or **No matching data source**. The mark is inherited upward: when a subfolder has an issue, every parent folder shows the icon too, so a collapsed top-level folder tells you which branch to open and investigate. Rules that run normally, are waiting for a runtime status, are outside their effective time, have a pending configuration, or are disabled do not raise it, and only the folders and rules you have query permission on are counted.

The **My / All** switch at the top of the tree decides which folders appear:

| Scope | What it shows |
|------|---------|
| **My** (default) | Folders of the teams you belong to, folders you created, and their subfolders |
| **All** | Every folder in the account; folders you can't edit show a lock icon and are view-only |

Your choice is remembered. Opening another team's folder or rule from a link switches the page to **All** for that visit and returns to your own choice afterwards.

## Folder details

When a folder is selected, the right side displays its detailed information:

| Property | Description |
|----------|-------------|
| **Name** | Folder name; authorized users can click the edit icon to modify |
| **Notes** | Supplementary description; authorized users can click the edit icon to modify |
| **Updated By** | The user who last modified this folder |
| **Created By** | The user who created this folder |
| **Updated At** | Last modification time |
| **Created At** | Creation time |

## Move rules to another folder

You can move alert rules to a different folder. The rules themselves do not change, only where they belong.

- **One rule**: choose **Move** in the `⋮` menu at the end of its row.
- **Several rules**: select them, then click **Move** above the list.
- **On the rule's edit page**: **Group** in block 1 is a dropdown; pick the target group and save to move the rule there.

Both open the **Move to another folder** dialog:

| Action | Description |
|------|------|
| **Search folders** | Type a keyword to filter the folder tree by name; matches keep their full path |
| Choose a folder | Click the target folder in the tree |
| **Confirm** | Stays disabled while the selected folder is the rule's current folder |

If the folder tree fails to load, you see `Failed to load folders` and a **Retry** button. After a successful move the list refreshes; if it fails, the rules stay in their original folder.

## Team access control

Folders support team-based access control by binding teams to folders to restrict operation permissions.

### Permission inheritance

The **Permission Inheritance** table below the folder details shows the complete path from the current folder to the root node, along with the team bound at each level.

| Column | Description |
|--------|-------------|
| **Node Path** | Complete path from the root node to the current node |
| **Associated Team** | The team bound at this level; authorized users can click the edit icon to modify |

### Permission evaluation rules

Viewing and editing are evaluated separately. Every member of the account can view all folders and the rules inside them; whether you can edit — create, rename, delete, move, clone, and change the rules and dashboards inside — follows these rules:

1. The **owner account** and **Admin** can edit every folder
2. The creator of the folder or any of its parent folders can edit
3. When the folder or any of its parent folders has a bound team, that team's members can edit

Folders that match none of these rules are read-only; a folder with no team bound anywhere in its chain is editable only by the owner account, Admins, and creators.

A folder you can't edit shows a lock icon, and hovering it says "Read-only: you are not in this group's team". You can still open it and read its rules and dashboards, but the create, edit, delete, move, and clone entries are greyed out, and it can't be the target of a move or clone.

<Tip>
It is recommended to bind teams at the top-level folders so that subfolders naturally inherit the access scope. This allows you to partition alert rule management permissions by department or project.
</Tip>
