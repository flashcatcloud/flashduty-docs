Monitors organizes alert rules with a tree of groups. This page is titled Folder management, and the English console uses both names: the tree menus say group (**Add subgroup**, **Edit group**, **Delete group**), while the move dialog (**Move to another folder**, **Search folders**, **Failed to load folders**) and the warning-icon hint say folder. Every alert rule must belong to a group. You can use the hierarchy for categorized management and configure team access permissions at different levels.

**Menu Entry**: Alert Rules (left-side group tree)

## Group tree

The left side of the page displays the group tree. You can:

- **Select groups**: Click a group to view its details and associated alert rules
- **Nested hierarchy**: Supports multiple nesting levels to meet complex organizational needs

When a group holds a rule that needs attention, the group icon on its tree node is replaced by a red warning icon. It appears when at least one rule in the group still has active alerts, or its runtime status is one of **Execution error**, **Status is stale**, **Edge offline**, or **No matching data source**. The mark is inherited upward: when a subgroup has an issue, every parent group shows the icon too, so a collapsed top-level group tells you which branch to open and investigate. Rules that run normally, are waiting for a runtime status, are outside their effective time, have a pending configuration, or are disabled do not raise it, and only the groups and rules you have query permission on are counted.

The **My / All** switch at the top of the tree decides which groups appear:

| Scope | What it shows |
|------|---------|
| **My** (default) | Groups of the teams you belong to, groups you created, and their subgroups |
| **All** | Every group in the account; groups you can't edit show a lock icon and are view-only |

Your choice is remembered. Opening another team's group or rule from a link switches the page to **All** for that visit and returns to your own choice afterwards.

## Group actions

| Action | Where |
|------|-------|
| **Create a top-level group** | Select **+** next to the search box at the top of the tree; the new group is created directly under the root |
| **Create a subgroup** | Open the group's `⋮` menu and select **Add subgroup** |
| **Create a peer group** | Open the group's `⋮` menu and select **Add peer group** |
| **Edit the name, notes, and associated teams** | Open the group's `⋮` menu and select **Edit group**, or select the group and click the edit icon in the details header |
| **Delete a group** | Open the group's `⋮` menu and select **Delete group**, or select the group and click the delete icon in the details header, then confirm |
| **Change the hierarchy** | Drag a group onto another group to make it a subgroup, or into the gap between two groups to make it a peer group. A read-only group can't be a drop target, and a read-only group can't be dragged |

When you create or edit a group, fill in **Group name** (required), **Notes**, and **Associated teams**. Associated teams are inherited down the hierarchy: a group's associated teams also have access to all its subgroups.

## Group details

When a group is selected, the right side displays its details:

| Property | Description |
|----------|-------------|
| **Name** | Group name; authorized users can click the edit icon to modify |
| **Creator** | The user who created this group |
| **Updater** | The user who last modified this group |
| **Updated at** | Last modification time |
| **Note** | Supplementary description; authorized users can click the edit icon to modify |

## Move rules to another group

You can move alert rules to a different group. The rules themselves do not change, only where they belong.

- **One rule**: choose **Move** in the `⋮` menu at the end of its row.
- **Several rules**: select them, then click **Move** above the list.
- **On the rule's edit page**: **Group** in block 1 is a dropdown; pick the target group and save to move the rule there.

Both open the **Move to another folder** dialog:

| Action | Description |
|------|---------|
| **Search folders** | Type a keyword to filter the folder tree by name; matches keep their full path |
| Choose a folder | Click the target folder in the tree |
| **Confirm** | Stays disabled while the selected folder is the rule's current folder |

If the folder tree fails to load, you see `Failed to load folders` and a **Retry** button. After a successful move the list refreshes; if it fails, the rules stay where they were.

## Team access control

Groups support team-based access control by binding teams to groups to restrict operation permissions.

### Management team of each node

The **Management team of each node** table below the group details shows the complete path from the current group to the root node, along with the team bound at each level.

| Column | Description |
|--------|-------------|
| **Node** | Complete path from the root node to the current group |
| **Management team** | The team bound at this level; authorized users can click the edit icon to modify |

### Permission evaluation rules

Viewing and editing are evaluated separately. Every member of the account can view all groups and the rules inside them; whether you can edit — create, rename, delete, move, clone, and change the rules and dashboards inside — follows these rules:

1. The **owner account** and **Admin** can edit every group
2. The creator of the group or any of its parent groups can edit
3. When the group or any of its parent groups has a bound team, that team's members can edit

Groups that match none of these rules are read-only; a group with no team bound anywhere in its chain is editable only by the owner account, Admins, and creators.

A group you can't edit shows a lock icon, and hovering it says "Read-only: you are not in this group's team". You can still open it and read its rules and dashboards, but the create, edit, delete, move, and clone entries are greyed out, and it can't be the target of a move or clone.

<Tip>
It is recommended to bind teams at the top-level groups so that subgroups naturally inherit the access scope. This allows you to partition alert rule management permissions by department or project.
</Tip>
