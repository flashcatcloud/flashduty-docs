Monitors lets you export selected alert rules as a YAML file from the rule list, and import alert rules from rule files of several sources. This makes it easy to migrate rules between environments, or to move from Prometheus or Nightingale to Flashduty.

## Export alert rules

**Entry point**: In the alert rule list, select the rules you want to export and click the **Export** button in the batch action bar at the bottom.

The selected rules are packaged into a rule file (Flashduty Rules YAML format, default filename `alert-rules.yaml`), and the file content is shown in the export drawer. You can:

- **Download**: save the rule file locally
- **Copy**: copy the file content to the clipboard

<Note>
The export includes all selected rules at once, and the result reports the number of rules exported. The file content is YAML and can be used directly for a later import.
</Note>

## Import alert rules

**Entry point**: Click the **Import** button in the upper-right corner of the alert rule list page (requires alert rule creation permission). Imported rules are created in the currently selected folder.

### Supported file formats

Upload a single `.yaml`, `.yml`, or `.json` file (no larger than 1 MB). The source format is detected automatically:

| Source type | Description |
|-------------|-------------|
| **Flashduty Rules YAML** | A rule file generated by the **Export** feature |
| **Flashduty Rules JSON** | A legacy Flashduty rule JSON export file |
| **Prometheus Rules YAML** | A native Prometheus alerting rules file |
| **Nightingale Rules JSON** | A Nightingale v6-v9 alert rule JSON file |

### Import flow

Import follows a two-step "validate first, then commit" flow:

1. **Upload and validate**: After you select a file, validation runs automatically and shows the **Validation results**: the status and notes for each rule in the file, the detected source type, and counts of ready / skipped / invalid rules.
2. **Confirm and commit**: In the validation results table, select the rules to import (all **Ready** rules are selected by default), configure the import options, and click **Import** to commit. Before committing, the selected rules are validated again against their live state; when finished, the result shows how many rules were imported, skipped, and invalid.

The per-rule statuses in the validation results mean:

| Status | Description |
|--------|-------------|
| **Ready** | The rule passed validation and can be imported |
| **Skipped** | The rule is skipped, for example because a rule with the same name exists and the conflict policy is **Skip rules with the same name**; see the notes column for the reason |
| **Invalid** | The rule has errors and cannot be imported; see the notes column for the reason |

The notes column shows the details for each rule. Notes come in two levels: **warning** means the rule can be imported but involves a lossy conversion or behavior worth attention; **error** means the rule cannot be imported.

### Import options

| Option | Description |
|--------|-------------|
| **Name conflict handling** | How to handle rules whose name already exists in the target folder:<br/>- **Skip rules with the same name** (default): conflicting rules are not imported and are marked as **Skipped** during validation<br/>- **Create a copy**: conflicting rules are imported as copies |
| **Enable rules after import** | Only configurable when the source type is Flashduty Rules YAML. Off by default, so imported rules stay disabled; for other source types, the enabled state is decided by the system |
| **Push events to Flashduty channels** | The Flashduty channels that alert events from the imported rules are pushed to; empty by default |

<Tip>
The list refreshes automatically after the import finishes. If no rule was imported at all, the import dialog stays open and shows the skip/invalid reasons so you can adjust the options and retry.
</Tip>

## Notes on importing Nightingale rules

Nightingale and Flashduty alert rules have different capability models. When importing a Nightingale rules JSON file, the format is converted automatically and some settings cannot be fully preserved. Note the following default behavior and lossy conversions:

- **Always imported disabled**: All Nightingale rules remain disabled after import. Review datasource matching and conversion warnings before enabling them manually.

Conversion warnings you may see during import include:

| Warning | Description |
|---------|-------------|
| Doris datasource mapping | Doris was mapped to MySQL and will match all MySQL data sources |
| Multi-severity conditions trimmed | Only the highest-severity alert condition was kept; all others were dropped |
| Severity inhibition not preserved | Nightingale severity inhibition settings were not preserved |
| Query join not preserved | Nightingale query join settings were not preserved |
| Recovery behavior approximated | Nightingale recovery behavior was approximated using AlertRule capabilities |
| Recovery notification not preserved | The recovery notification flag was not preserved; AlertRule lifecycle behavior will be used |
| Notification config not preserved | Nightingale notification targets, callbacks, and notification pipelines were not preserved |
| Extra config not preserved | Nightingale extra, event relabel, or task-template settings were not preserved |
| Timezone conversion | The Local timezone was replaced with Asia/Shanghai |
| Default evaluation interval | The evaluation interval was absent, so durations were converted using a 15-second interval |
| Effective window normalized | The all-day effective window was normalized to 00:00-23:59 |
| Repeat notifications approximated | Unlimited notifications were approximated with AlertRule's maximum repeat count |

<Warning>
Importing Nightingale rules involves the lossy conversions listed above. Check the warning for each rule in the validation results, make sure the converted result meets your expectations before committing, and verify rule behavior manually after import.
</Warning>
