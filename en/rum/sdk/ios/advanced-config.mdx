This page covers advanced use of the iOS RUM SDK: manually tracking views, actions, resources and errors; adding global attributes and user information; modifying or discarding events; sampling and remote configuration; and correlating with distributed tracing.

<Note>
The SDK is compatible with the Datadog open-source protocol. Dependencies added through Swift Package Manager or CocoaPods use names like `FlashcatCore` and `FlashcatRUM`, while code imports modules like `DatadogCore` and `DatadogRUM`, so Datadog ecosystem docs and examples apply directly.
</Note>

## Enrich user sessions

### Custom views

By default, the RUM SDK automatically tracks `UIViewController` and SwiftUI `View`. You can also track specific views manually, or add custom attributes to automatically tracked views.

<Note>
Call `RUMMonitor.shared().startView()` to start tracking a new RUM view. All views with the same `key` are grouped together in the RUM Explorer.
</Note>

<Tabs>
<Tab title="Swift">
```swift
import DatadogRUM

// In your UIViewController
override func viewDidAppear(_ animated: Bool) {
    super.viewDidAppear(animated)
    RUMMonitor.shared().startView(
        key: "view-key",
        name: "View Name",
        attributes: ["foo": "bar"]
    )
}

override func viewDidDisappear(_ animated: Bool) {
    super.viewDidDisappear(animated)
    RUMMonitor.shared().stopView(
        key: "view-key",
        attributes: ["foo": "bar"]
    )
}
```
</Tab>

<Tab title="Objective-C">
```objective-c
@import DatadogObjc;

// In your UIViewController
- (void)viewDidAppear:(BOOL)animated {
    [super viewDidAppear:animated];
    [[RUMMonitor shared] startViewWithKey:@"view-key" 
                                     name:@"View Name" 
                               attributes:@{@"foo": @"bar"}];
}

- (void)viewDidDisappear:(BOOL)animated {
    [super viewDidDisappear:animated];
    [[RUMMonitor shared] stopViewWithKey:@"view-key" 
                              attributes:@{@"foo": @"bar"}];
}
```
</Tab>
</Tabs>

<Note>
**Parameters:**
- `key` (String) - Unique identifier for the view; use the same key for `startView` and `stopView`
- `name` (String) - Name of the view
- `attributes` (Dictionary) - Attributes attached to the view (optional)
</Note>

### Custom Actions

In addition to automatically tracked user actions, you can manually track specific custom actions (taps, scrolls, swipes, and so on).

<Tabs>
<Tab title="Swift">
```swift
import DatadogRUM

// In your UIViewController
@IBAction func didTapDownloadResourceButton(_ sender: UIButton) {
    RUMMonitor.shared().addAction(
        type: .tap,
        name: sender.currentTitle ?? "",
        attributes: ["resource_id": "123"]
    )
}
```
</Tab>

<Tab title="Objective-C">
```objective-c
@import DatadogObjc;

- (IBAction)didTapDownloadResourceButton:(UIButton *)sender {
    [[RUMMonitor shared] addActionWithType:RUMActionTypeTap 
                                      name:sender.currentTitle 
                                attributes:@{@"resource_id": @"123"}];
}
```
</Tab>
</Tabs>

<Note>
When you call `addAction()`, the RUM SDK creates a RUM action and attaches all new resources, errors, and long tasks to it until the view is considered fully loaded.
</Note>

### Custom resources

The Flashduty iOS SDK automatically tracks network requests made through an instrumented `URLSession`. You can also track custom resources manually (third-party APIs, GraphQL queries, and so on).

<Tabs>
<Tab title="Swift">
```swift
import DatadogRUM

// In your network client
RUMMonitor.shared().startResource(
    resourceKey: "resource-key",
    request: request,
    attributes: ["foo": "bar"]
)

// On success
RUMMonitor.shared().stopResource(
    resourceKey: "resource-key",
    response: response,
    size: size,
    attributes: ["foo": "bar"]
)

// On failure
RUMMonitor.shared().stopResourceWithError(
    resourceKey: "resource-key",
    error: error,
    attributes: ["foo": "bar"]
)
```
</Tab>

<Tab title="Objective-C">
```objective-c
@import DatadogObjc;

// In your network client
[[RUMMonitor shared] startResourceWithResourceKey:@"resource-key" 
                                           request:request 
                                        attributes:@{@"foo": @"bar"}];

// On success
[[RUMMonitor shared] stopResourceWithResourceKey:@"resource-key" 
                                        response:response 
                                            size:size 
                                      attributes:@{@"foo": @"bar"}];
```
</Tab>
</Tabs>

<Warning>
The `resourceKey` must be unique per call so the RUM iOS SDK can match a resource's start with its completion.
</Warning>

### Custom errors

To track a specific error, notify `RUMMonitor` when it happens:

<Tabs>
<Tab title="Swift">
```swift
import DatadogRUM

RUMMonitor.shared().addError(
    message: "Error message",
    type: "ErrorType",
    source: .source,
    stack: "Error stack trace",
    attributes: ["foo": "bar"],
    file: #file,
    line: #line
)
```
</Tab>

<Tab title="Objective-C">
```objective-c
@import DatadogObjc;

[[RUMMonitor shared] addErrorWithMessage:@"Error message"
                                    type:@"ErrorType"
                                  source:DDRUMErrorSourceCustom
                                   stack:@"Error stack trace"
                              attributes:@{@"foo": @"bar"}
                                    file:file
                                    line:line];
```
</Tab>
</Tabs>

<Note>
For more on error reporting, see [iOS Error Reporting](/en/rum/error-tracking/error-reporting/ios).
</Note>

## Track custom global attributes

Besides the default attributes the SDK captures, you can add custom global attributes to every RUM event. Use them to filter and group by business information (cart value, user tier, ad campaign) and to compare performance and error distribution across user groups.

<Tabs>
<Tab title="Swift">
```swift
import DatadogRUM

// Add a global attribute
RUMMonitor.shared().addAttribute(forKey: "user_plan", value: "premium")

// Remove a global attribute
RUMMonitor.shared().removeAttribute(forKey: "user_plan")
```
</Tab>

<Tab title="Objective-C">
```objective-c
@import DatadogObjc;

// Add a global attribute
[[RUMMonitor shared] addAttributeForKey:@"user_plan" value:@"premium"];

// Remove a global attribute
[[RUMMonitor shared] removeAttributeForKey:@"user_plan"];
```
</Tab>
</Tabs>

<Warning>
**Reserved keys:** the following keys are used internally by the SDK and cannot be used: `date`, `error.kind`, `error.message`, `error.stack`, `error.source_type`, `view.id`, `view.url`, `view.loading_time`, `view.referrer`, `application.id`
</Warning>

## Track user sessions

Adding user information to RUM sessions lets you follow a specific user's journey and see which users are most affected by errors.

<Tabs>
<Tab title="Swift">
```swift
import DatadogCore

Datadog.setUserInfo(
    id: "1234",
    name: "John Doe",
    email: "john@doe.com"
)
```
</Tab>

<Tab title="Objective-C">
```objective-c
@import DatadogObjc;

[DDDatadog setUserInfoWithId:@"1234"
                        name:@"John Doe"
                       email:@"john@doe.com"
                   extraInfo:nil];
```
</Tab>
</Tabs>

<Warning>
Only standard user fields are supported: `id`, `name`, `email`, and `anonymous_id`. Other user attributes are not supported. If needed, configure them under `context`.
</Warning>

<Note>
**Parameters:**
- `usr.id` (String) - Unique user identifier
- `usr.name` (String) - User-friendly name, displayed by default in the RUM UI
- `usr.email` (String) - User email, displayed when no name is set
- All attributes are optional; provide at least one
</Note>

## Track background events

You can track events that happen while the app runs in the background (such as crashes and network requests).

<Tabs>
<Tab title="Swift">
```swift
import DatadogRUM

RUM.enable(
    with: RUM.Configuration(
        applicationID: "<RUM_APPLICATION_ID>",
        trackBackgroundEvents: true
    )
)
```
</Tab>

<Tab title="Objective-C">
```objective-c
@import DatadogObjc;

DDRUMConfiguration *configuration = [[DDRUMConfiguration alloc] 
    initWithApplicationID:@"<RUM_APPLICATION_ID>"];
configuration.trackBackgroundEvents = YES;

[RUM enableWith:configuration];
```
</Tab>
</Tabs>

<Warning>
Tracking background events may create additional sessions, which can affect billing. If you have questions, contact Flashduty support.
</Warning>

### App Hang Detection

An App Hang is a period during which the main thread is blocked and the UI cannot respond to user input. On iOS it is the only data source behind the **Unresponsive Time Rate** metric in the analytics dashboard.

<Warning>
`appHangThreshold` **defaults to `nil`, which means App Hang detection is off**. Unless you set it explicitly, your iOS app reports no App Hang data and the "Unresponsive Time Rate" card stays empty.
</Warning>

```swift
RUM.enable(
    with: RUM.Configuration(
        applicationID: "<RUM_APPLICATION_ID>",
        appHangThreshold: 0.25    // Record main-thread blocks longer than 250ms
    )
)
```

Notes:

- The minimum allowed value is `0.1` seconds; lower values are raised to 0.1 automatically. For production, **0.25–0.5 seconds** is recommended, as a lower threshold produces a lot of noise.
- The SDK detects hangs with a 2.5% tolerance, so hangs lasting very close to the threshold may not be reported.
- Enable crash reporting as well, otherwise App Hang errors are reported without a stack trace.
- An App Hang that never recovers, and ends with the system terminating the app, is recorded as a fatal error: it counts toward the crash count and lowers the crash-free rate. Non-fatal hangs are recorded as errors with `error.category = App Hang`.
- Android has no equivalent option: its main-thread freeze threshold is fixed at 5 seconds.

### Automatically track views

To track views automatically, set `uiKitViewsPredicate` or `swiftUIViewsPredicate` when initializing RUM.

For **UIKit**, use the `DefaultUIKitRUMViewsPredicate` class:

```swift
import DatadogRUM

RUM.enable(
    with: RUM.Configuration(
        applicationID: "<RUM_APPLICATION_ID>",
        uiKitViewsPredicate: DefaultUIKitRUMViewsPredicate()
    )
)
```

For **SwiftUI**, use the `DefaultSwiftUIRUMViewsPredicate` class:

```swift
import DatadogRUM

RUM.enable(
    with: RUM.Configuration(
        applicationID: "<RUM_APPLICATION_ID>",
        swiftUIViewsPredicate: DefaultSwiftUIRUMViewsPredicate()
    )
)
```

You can also implement a custom `predicate` to customize tracking behavior.

### Automatically track User Actions

To track user actions automatically, set `uiKitActionsPredicate` or `swiftUIActionsPredicate` when initializing RUM.

For **UIKit**:

```swift
import DatadogRUM

RUM.enable(
    with: RUM.Configuration(
        applicationID: "<RUM_APPLICATION_ID>",
        uiKitActionsPredicate: DefaultUIKitRUMActionsPredicate()
    )
)
```

For **SwiftUI**:

```swift
import DatadogRUM

RUM.enable(
    with: RUM.Configuration(
        applicationID: "<RUM_APPLICATION_ID>",
        swiftUIActionsPredicate: DefaultSwiftUIRUMActionsPredicate(isLegacyDetectionEnabled: true)
    )
)
```

### Automatically track network requests

To track network requests (resources and errors) automatically, set `urlSessionTracking` when initializing RUM and enable `URLSessionInstrumentation`:

```swift
import DatadogRUM

RUM.enable(
    with: RUM.Configuration(
        applicationID: "<RUM_APPLICATION_ID>",
        urlSessionTracking: RUM.Configuration.URLSessionTracking()
    )
)

URLSessionInstrumentation.enable(
    with: .init(
        delegateClass: SessionDelegate.self
    )
)
```

To correlate RUM resources with backend traces, configure `firstPartyHostsTracing`; see [Integrate RUM with Distributed Tracing](#integrate-rum-with-distributed-tracing).

### Automatically track errors

All fatal and non-fatal iOS errors are collected automatically, with full error details and the metadata of the current RUM view attached.

Fatal errors include app crashes. Non-fatal errors include:

- **Swift errors**: errors thrown with Swift `throw`
- **Objective-C exceptions**: Objective-C exceptions

View error details in the RUM Explorer and Error Tracking.

## Modify or discard RUM events

Before RUM events are sent to Flashduty, you can modify them or drop them entirely with event mappers, which you set when creating the RUM configuration:

```swift
import DatadogRUM

let configuration = RUM.Configuration(
    applicationID: "<RUM_APPLICATION_ID>",
    viewEventMapper: { RUMViewEvent in
        return RUMViewEvent
    },
    errorEventMapper: { RUMErrorEvent in
        return RUMErrorEvent
    },
    resourceEventMapper: { RUMResourceEvent in
        return RUMResourceEvent
    },
    actionEventMapper: { RUMActionEvent in
        return RUMActionEvent
    },
    longTaskEventMapper: { RUMLongTaskEvent in
        return RUMLongTaskEvent
    }
)

RUM.enable(with: configuration)
```

```objective-c
@import DatadogObjc;

DDRUMConfiguration *configuration = [[DDRUMConfiguration alloc] initWithApplicationID:@"<RUM_APPLICATION_ID>"];

[configuration setViewEventMapper:^DDRUMViewEvent * _Nonnull(DDRUMViewEvent * _Nonnull RUMViewEvent) {
    return RUMViewEvent;
}];

[configuration setErrorEventMapper:^DDRUMErrorEvent * _Nullable(DDRUMErrorEvent * _Nonnull RUMErrorEvent) {
    return RUMErrorEvent;
}];

[configuration setResourceEventMapper:^DDRUMResourceEvent * _Nullable(DDRUMResourceEvent * _Nonnull RUMResourceEvent) {
    return RUMResourceEvent;
}];

[configuration setActionEventMapper:^DDRUMActionEvent * _Nullable(DDRUMActionEvent * _Nonnull RUMActionEvent) {
    return RUMActionEvent;
}];

[configuration setLongTaskEventMapper:^DDRUMLongTaskEvent * _Nullable(DDRUMLongTaskEvent * _Nonnull RUMLongTaskEvent) {
    return RUMLongTaskEvent;
}];
```

Each mapper is a Swift closure with the signature `(T) -> T?`, where `T` is the concrete RUM event type. This lets you change parts of an event before it is sent.

For example, to redact sensitive information in a RUM resource's `url`, implement a custom `redacted(_:) -> String` function and use it in `resourceEventMapper`:

```swift
let configuration = RUM.Configuration(
    applicationID: "<RUM_APPLICATION_ID>",
    resourceEventMapper: { RUMResourceEvent in
        var RUMResourceEvent = RUMResourceEvent
        RUMResourceEvent.resource.url = redacted(RUMResourceEvent.resource.url)
        return RUMResourceEvent
    }
)
```

```objective-c
DDRUMConfiguration *configuration = [[DDRUMConfiguration alloc] initWithApplicationID:@"<RUM_APPLICATION_ID>"];

[configuration setResourceEventMapper:^DDRUMResourceEvent * _Nullable(DDRUMResourceEvent * _Nonnull RUMResourceEvent) {
    return RUMResourceEvent;
}];
```

Returning `nil` from the error, resource, or action mapper drops the event entirely; it is not sent to Flashduty. The view event mapper must not return `nil` (to drop a view, customize your `UIKitRUMViewsPredicate` implementation; see [Automatically Track Views](#automatically-track-views)). For example, to drop actions whose target name contains "password":

```swift
actionEventMapper: { actionEvent in
    if actionEvent.action.target?.name?.contains("password") == true {
        return nil  // Discard this event
    }
    return actionEvent
}
```

Depending on the event type, only certain attributes can be modified:

| Event type | Attribute key | Description |
| --- | --- | --- |
| RUMActionEvent | `RUMActionEvent.action.target?.name` | Action name |
| | `RUMActionEvent.view.url` | URL of the view linked to this action |
| RUMErrorEvent | `RUMErrorEvent.error.message` | Error message |
| | `RUMErrorEvent.error.stack` | Error stack trace |
| | `RUMErrorEvent.error.resource?.url` | URL of the resource the error refers to |
| | `RUMErrorEvent.view.url` | URL of the view linked to this error |
| RUMResourceEvent | `RUMResourceEvent.resource.url` | Resource URL |
| | `RUMResourceEvent.view.url` | URL of the view linked to this resource |
| RUMViewEvent | `RUMViewEvent.view.name` | View name |
| | `RUMViewEvent.view.url` | View URL |
| | `RUMViewEvent.view.referrer` | URL that linked to the initial view of the page |

## Get the RUM session ID

The RUM session ID is useful for troubleshooting. For example, attach it to support requests, emails, or bug reports so your support team can find the user's session in Flashduty later.

You can read the session ID at runtime without waiting for the `sessionStarted` event:

```swift
import DatadogRUM

RUMMonitor.shared().currentSessionID(completion: { sessionId in
    currentSessionId = sessionId
})
```

```objective-c
@import DatadogObjc;

[[RUMMonitor shared] currentSessionIDWithCompletion:^(NSString * _Nullable sessionId) {
    // use session ID
}];
```

## Set tracking consent (GDPR compliance)

To comply with GDPR, the Flashduty iOS SDK requires a tracking consent value at initialization. `trackingConsent` can be one of:

| Value | Behavior |
| --- | --- |
| `.pending` | The SDK collects and batches data but does not send it to Flashduty; it waits for a new consent value to decide what to do with the batched data |
| `.granted` | The SDK collects data and sends it to Flashduty |
| `.notGranted` | The SDK collects no data; no logs, traces, or RUM events are sent |

To change the consent value after initialization, call `Datadog.set(trackingConsent:)`. The SDK changes its behavior accordingly. For example, if the current consent is `.pending`:

- changing it to `.granted` sends all current and future data to Flashduty;
- changing it to `.notGranted` wipes all current data and stops collecting future data.

```swift
import DatadogCore

Datadog.set(trackingConsent: .granted)
```

```objective-c
@import DatadogObjc;

[DDDatadog setWithTrackingConsent:DDTrackingConsentGranted];
```

## Data management

### Clear all data

Delete all unsent data stored by the SDK with the `Datadog.clearAllData()` API:

```swift
import DatadogCore

Datadog.clearAllData()
```

```objective-c
@import DatadogObjc;

[DDDatadog clearAllData];
```

### Stop data collection

Use the `Datadog.stopInstance()` API to stop a named SDK instance (or the default instance if the name is `nil`) from collecting and uploading further data.

```swift
import DatadogCore

Datadog.stopInstance()
```

```objective-c
@import DatadogObjc;

[DDDatadog stopInstance];
```

Calling this disables the SDK and all active features such as RUM. To resume collection, you must initialize the SDK again. Use this API if you want to change the configuration dynamically.

## Sampling

By default, RUM collects data for all sessions. Set a sample rate (percentage) with `sessionSampleRate` to reduce the number of sessions collected. For example, to collect 90% of sessions:

```swift
import DatadogRUM

RUM.enable(
    with: RUM.Configuration(
        applicationID: "<RUM_APPLICATION_ID>",
        sessionSampleRate: 90
    )
)
```

```objective-c
@import DatadogObjc;

DDRUMConfiguration *configuration = [[DDRUMConfiguration alloc] initWithApplicationID:@"<RUM_APPLICATION_ID>"];
configuration.sessionSampleRate = 90;

[RUM enableWith:configuration];
```

Sampled-out sessions collect no views or related telemetry.

## Remote configuration

Starting with SDK 0.6.0, the session sample rate can be adjusted online from the console under **Application Management → Remote Configuration**, with no code change or new release. The feature is off by default and has to be enabled at initialization:

```swift
import DatadogRUM

RUM.enable(
    with: RUM.Configuration(
        applicationID: "<RUM_APPLICATION_ID>",
        sessionSampleRate: 100,             // used until the console publishes a rate
        remoteConfigurationEnabled: true
    )
)
```

```objective-c
@import DatadogObjc;

DDRUMConfiguration *configuration = [[DDRUMConfiguration alloc] initWithApplicationID:@"<RUM_APPLICATION_ID>"];
configuration.remoteConfigurationEnabled = YES;

[RUM enableWith:configuration];
```

Once enabled:

- The SDK requests the configuration from the RUM intake when `RUM.enable()` is called, and again each time a new session is created. A rate published in the console applies to the **next new session**; a session already under way is not affected.
- The delivered values are persisted locally, so the first session after a cold start is already drawn under the last delivered rate.
- A failed, timed-out or unreadable response leaves the values in force untouched; they are never cleared. When remote configuration is disabled in the console, the SDK falls back to the `sessionSampleRate` passed at initialization.
- The iOS SDK reads only the **session sample rate** and **custom configuration keys**; the other settings have no effect. Read the custom keys with `RUMMonitor.shared().getRemoteConfig()`, which returns `nil` when remote configuration is off or the console set none.

To decide sampling by your own business rules, use the `beforeSampling` callback. Each time a new session is about to be drawn it receives the rate that would apply (`sessionSampleRate`) and the console's custom keys (`custom`); return a rate to override it, or `nil` to leave it alone. It runs synchronously inside session creation, so keep it fast and non-blocking; a value outside 0–100 is ignored.

```swift
RUM.enable(
    with: RUM.Configuration(
        applicationID: "<RUM_APPLICATION_ID>",
        remoteConfigurationEnabled: true,
        beforeSampling: { context in
            // e.g. collect every session of internal accounts, keep the console's rate for the rest
            isInternalUser ? 100 : nil
        }
    )
)
```

To collect the current user regardless of the sample rate (for example while investigating one user's issue), call `RUMMonitor.shared().setForcedSession()`: every session drawn afterwards is collected for the lifetime of the process, while a session already under way is not re-decided.

For the console side (settings, publishing and when a version takes effect), see [Application Management · Remote Configuration](/en/rum/quickstart/app-management#remote-configuration).

## Integrate RUM with distributed tracing

Correlating requests from your iOS app with their backend traces lets you see the frontend experience together with backend, infrastructure, and log information in one place, so you can pinpoint where a problem is.

### Configuration

Initialize the RUM SDK and use `firstPartyHostsTracing` to list your app's API domains:

```swift
import DatadogRUM

RUM.enable(
    with: RUM.Configuration(
        applicationID: "<RUM_APPLICATION_ID>",
        urlSessionTracking: RUM.Configuration.URLSessionTracking(
            firstPartyHostsTracing: .trace(
                hosts: [
                    "api.example.com",
                    "example.com"
                ],
                sampleRate: 20
            )
        )
    )
)

URLSessionInstrumentation.enable(
    with: .init(
        delegateClass: SessionDelegate.self
    )
)
```

```objective-c
@import DatadogObjc;

DDRUMConfiguration *configuration = [[DDRUMConfiguration alloc] initWithApplicationID:@"<RUM_APPLICATION_ID>"];

DDURLSessionTracking *urlSessionTracking = [DDURLSessionTracking new];
[urlSessionTracking setFirstPartyHostsTracing:[DDRUMFirstPartyHostsTracing alloc] initWithHosts:@[@"api.example.com", @"example.com"] sampleRate:20];

configuration.urlSessionTracking = urlSessionTracking;

[RUM enableWith:configuration];

[DDURLSessionInstrumentation enableWithConfiguration:[DDURLSessionInstrumentationConfiguration alloc] initWithDelegateClass:[SessionDelegate class]]];
```

**Parameters:**

- `hosts`: list of domains to trace
- `sampleRate`: percentage of requests to trace (0–100), default 100

### How correlation works

The distributed tracing protocol adds the `traceparent` and `tracestate` HTTP headers:

```
traceparent: [version]-[trace id]-[parent id]-[trace flags]
```

- `version`: currently `00`
- `trace id`: 128-bit trace ID, hex-encoded to 32 characters
- `parent id`: 64-bit span ID, hex-encoded to 16 characters
- `trace flags`: whether the trace is sampled; `01` means sampled, `00` means not sampled

```
tracestate: dd=s:[sampling priority];o:[origin]
```

- `sampling priority`: `1` means the trace is sampled
- `origin`: always `rum`, meaning collected by the RUM SDK

**Example:**

```
traceparent: 00-00000000000000008448eb211c80319c-b7ad6b7169203331-01
tracestate: dd=s:1;o:rum
```

### Verification

After adding the configuration, inspect requests sent from your app in Xcode's network debugging tools or a proxy (such as Charles or Proxyman). If they carry these headers, the configuration is correct.

## Best practices

- Make sure `applicationID` and `clientToken` are configured correctly, or data cannot be uploaded.
- Tune the sample rate and privacy settings to your app's needs to balance data volume and compliance.
- In event mappers, only modify the attributes listed as modifiable above.
- For complex view tracking scenarios, implement a custom `ViewsPredicate`.
