In Error Tracking, all Issues have a status that helps you categorize and prioritize problems.

## Status types

| Status | Description |
|--------|-------------|
| **For Review** | New or regressed Issues that need attention |
| **Reviewed** | Categorized Issues that need fixing, now or later |
| **Ignored** | Issues that don't need further investigation or handling |
| **Resolved** | Issues that have been fixed and no longer occur. Resolved comes in two modes, **Resolved** and **Resolved in next version**, which differ in what happens when the error comes back (see [Resolve mode](#resolve-mode)) |

<Info>
All newly discovered Issues have an initial status of **For Review**. Flashduty automatically updates status based on specific conditions, and you can also manually adjust it.
</Info>

## Auto-resolve issues

Flashduty automatically marks inactive or resolved Issues as **Resolved**:

<AccordionGroup>
  <Accordion title="Version-based Auto-resolve">
    If the last reported version of an Issue is more than 14 days old and the error hasn't reappeared in newer versions, the system will automatically resolve it.
  </Accordion>
  <Accordion title="Time-based Auto-resolve">
    If the `version` tag is not set, when an Issue has no new error reports in the past 14 days, the system will automatically resolve it.
  </Accordion>
</AccordionGroup>

<Tip>
Properly configuring your application's `version` tag is crucial for accurately identifying resolved Issues.
</Tip>

## Auto-reopen issues

Flashduty has Issue detection capability. When a resolved Issue reappears and meets the condition set by its **resolve mode**, the system automatically reopens it and marks it as **For Review** status, and adds a **Regression** label.

### What is regression?

Regression refers to a previously fixed problem appearing again, most often an unexpected return after a code update. Flashduty's regression detection automatically identifies these situations, reopening related Issues instead of creating duplicate Issues, thereby preserving the complete context and history of the problem.

### Regression detection mechanism

When an error is grouped into a **Resolved** Issue, whether it counts as a regression depends on the Issue's **resolve mode** (see [Resolve mode](#resolve-mode)):

<Warning>
- **Resolved in next version** (default): only a version the Issue has not seen before triggers detection
- **Resolved**: any recurrence triggers detection, including repeats in the same version
- An error without a `version` tag triggers detection in both modes
- An error that occurred before the Issue's resolve time does not trigger detection (duplicate delivery, or an old error an SDK buffered offline and sent late)
</Warning>

Once regression is detected, Flashduty will:

<Steps>
  <Step title="Change Status">
    Automatically change the Issue status to **For Review**
  </Step>
  <Step title="Add Label">
    Add a **Regression** label to the Issue for quick identification
  </Step>
</Steps>

### Associated version configuration

Regression detection considers the service version information when the error occurred. With **Resolved in next version** (default), detection is triggered only in a version the Issue has not seen before, after it was marked **Resolved**. With **Resolved**, versions are not compared, so a recurrence in the same version also triggers detection.

```javascript
window.FC_RUM.init({
  applicationId: "<YOUR_APPLICATION_ID>",
  clientToken: "<YOUR_CLIENT_TOKEN>",
  service: "<SERVICE_NAME>",
  env: "<ENV_NAME>",
  version: "1.0.0", // Ensure correct version number is set
});
```

<Note>
Without a version tag, a resolved Issue that gets new errors is still marked "Regression". However, the system can't tell whether the errors came from a new version.
</Note>

## Resolve mode

In the status dropdown, **Resolved** is split into two options by what should happen when the error comes back. Both set the Issue to resolved:

| Dropdown option | Behavior on recurrence |
|------|------|
| **Resolved** | Reopens whenever it occurs again, including in the same version |
| **Resolved in next version** | Reopens only when it occurs in a version the Issue has not seen before |

- You can switch between the two at any time in the status dropdown. Switching only the mode does not change the Issue's statistics or alert state.
- New Issues default to **Resolved in next version**, and so do Issues the system resolves automatically.
- An error without a `version` tag reopens the Issue in both modes, because without version information old and fixed code cannot be told apart.
- On reopening, the Issue goes to **For Review**, is marked as a regression, and records when and in which version it regressed. The status cell in the list is narrow, so both modes show as **Resolved**; the details panel adds a "Resolved in next version" label next to it.

## Manually update status

You can manually update Issue status anywhere Issues are displayed, including the Issue list or details panel.

<Frame caption="Manually Update Issue Status">
  <img src="https://docs-cdn.flashcat.cloud/images/png/a57c54a6a28915dec4480a9db9411e30.png" alt="Manually Update Status" style={{maxWidth: "600px", margin: "0 auto", display: "block"}} />
</Frame>

Click the current status and select the new status from the dropdown menu. The dropdown has 5 options: **For Review**, **Reviewed**, **Resolved**, **Resolved in next version**, and **Ignored**. The two resolved options each show their reopen behavior beneath them; see [Resolve mode](#resolve-mode).

## Best practices

- **Continuous Monitoring**: Regularly check Issues in **For Review** status to ensure new issues and regressions are handled promptly
- **Version Management**: Always configure the correct version tag for your application so the system can accurately identify resolved issues
