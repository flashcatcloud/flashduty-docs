In Error Tracking, all Issues have a status that helps you categorize and prioritize problems.

## Status types

| Status | Identifier | Description |
|--------|------------|-------------|
| **For Review** | `for_review` | New issues or regressions that need attention |
| **Reviewed** | `reviewed` | Categorized issues that need fixing, can be handled immediately or later |
| **Ignored** | `ignored` | Issues that don't require further investigation or handling |
| **Resolved** | `resolved` | Issues that have been fixed and are no longer occurring; split by how a recurrence is handled into two selectable options, **Resolved** and **Resolved in next version** (see [Resolve mode](#resolve-mode)) |

<Info>
All newly discovered Issues have an initial status of **For Review (for_review)**. Flashduty automatically updates status based on specific conditions, and you can also manually adjust it.
</Info>

## Auto-resolve issues

Flashduty automatically marks inactive or resolved Issues as **Resolved (resolved)**:

<AccordionGroup>
  <Accordion title="Version-based Auto-resolve">
    If the last reported version of an Issue is more than 14 days old and the error hasn't reappeared in newer versions, the system will automatically resolve it.
  </Accordion>
  <Accordion title="Time-based Auto-resolve">
    If the `version` tag is not set, when an Issue has no new error reports in the past 14 days, the system will automatically resolve it.
  </Accordion>
</AccordionGroup>

<Tip>
Properly configuring your application's `version` tag is crucial for accurately identifying resolved Issues.
</Tip>

## Auto-reopen issues

Flashduty has Issue detection capability. When a resolved Issue reappears and meets the condition set by the Issue's **resolve mode**, the system automatically reopens it and marks it as **For Review (for_review)** status, while recording the event as "Regression" in the activity timeline.

### What is regression?

Regression refers to previously fixed problems reappearing — most often unexpectedly, after a code update. Flashduty's regression detection automatically identifies these situations, reopening related Issues instead of creating duplicate Issues, thereby preserving the complete context and history of the problem.

### Regression detection mechanism

When an error is grouped into a **Resolved (resolved)** Issue, whether it counts as a regression depends on the Issue's **resolve mode** (see [Resolve mode](#resolve-mode) below):

<Warning>
- Resolve mode **Resolved in next version (`version`, the default)**: detection is triggered only when the error recurs in a version the Issue has not seen before
- Resolve mode **Resolved (`any`)**: any recurrence triggers detection, including a repeated occurrence in the same version
- When an error carries no `version` tag, both resolve modes trigger detection
- An error that occurred before the Issue was resolved does not trigger detection (a redelivered duplicate, or an old error an SDK buffered offline and flushed late)
</Warning>

Once regression is detected, Flashduty will:

<Steps>
  <Step title="Change Status">
    Automatically change the Issue status to **For Review (for_review)**
  </Step>
  <Step title="Add Label">
    Add a **Regression** label to the Issue for quick identification
  </Step>
</Steps>

### Associated version configuration

Regression detection considers the service version information when the error occurred. With the default resolve mode **Resolved in next version (`version`)**, detection is only triggered in new versions after the Issue is marked as **Resolved (resolved)** — versions the Issue has not seen before; with resolve mode **Resolved (`any`)**, the version is not compared, so a recurrence in the same version triggers detection too.

```javascript
window.FLASHCAT_RUM.init({
  applicationId: "rum-application-id",
  environment: "production",
  version: "1.0.0", // Ensure correct version number is set
});
```

<Note>
Without a version tag, a resolved Issue that gets new errors is still marked "Regression". However, the system can't tell whether the errors came from a new version.
</Note>

## Resolve mode

In the status selector, **Resolved** is split into two options by how a recurrence of the error is handled. Both write the `resolved` status; they differ in the Issue's resolve mode field, `resolve_mode`:

| Selector option | Resolve mode | Behaviour on recurrence |
|-----------------|--------------|-------------------------|
| **Resolved** | `any` | Reopens if it occurs again: a repeated occurrence in the same version reopens it too |
| **Resolved in next version** | `version` | Reopens only if it occurs in a newer version: only a recurrence in a version the Issue has not seen before reopens it |

- You can switch between the two options at any time in the status selector; switching only the resolve mode changes neither the Issue's statistics nor its alert state.
- New Issues default to **Resolved in next version (`version`)**; Issues created before resolve mode existed are also treated as `version`, so their behaviour stays the same as before.
- When the system auto-resolves an Issue, it also writes `version`.
- When an error carries no `version` tag, both resolve modes reopen the Issue — without version information there is no way to tell the fixed code from the old one.
- On reopen, the Issue is set to **For Review (for_review)** and marked "Regression", and the time and version of the recurrence are recorded. The status cell in the list is too narrow to show both, so both resolve modes display as **Resolved**; the details panel additionally prints "Resolved in next version" next to it.

## Manually update status

You can manually update Issue status anywhere Issues are displayed, including the Issue list or details panel.

<Frame caption="Manually Update Issue Status">
  <img src="https://docs-cdn.flashcat.cloud/images/png/a57c54a6a28915dec4480a9db9411e30.png" alt="Manually Update Status" style={{maxWidth: "600px", margin: "0 auto", display: "block"}} />
</Frame>

Click the current status and select the new status from the dropdown menu. The dropdown has 5 options: **For Review**, **Reviewed**, **Resolved**, **Resolved in next version**, and **Ignored**; each of the two Resolved options shows its own reopen hint below the label — see [Resolve mode](#resolve-mode) for the difference.

## Best practices

- **Continuous Monitoring**: Regularly check Issues in **For Review (for_review)** status to ensure new issues and regressions are handled promptly
- **Version Management**: Always configure the correct version tag for your application so the system can accurately identify resolved issues

<Tip>
By effectively managing Issue status, your team can focus more on solving important problems, reduce time spent handling noise, and improve overall development efficiency.
</Tip>
