<Update label="2026-10-25" description="🧭 Query and analyze in the RUM Explorer with AI SRE, a custom dashboard belongs to one application, errors split into Issues by where they were raised">

### RUM Explorer: query and analyze with AI SRE

The sparkle at the left of the query box opens AI SRE now — on an account with AI SRE enabled, for a member who may chat in it; ⌘ + Enter in normal query mode does the same, Ctrl + Enter on Windows and Linux. Say in one sentence what you are looking for and AI SRE writes it into the page: the box's conditions, the event type, the time range, and the chart in analytics, then runs the query itself. The status bar under the query box reports the turn — filling in the query, querying (counting seconds past 3), N found, query complete, no data, query failed, stopped; **Undo change** puts the page back the way it was before the write, and works only while the box still holds what AI SRE wrote. **Stop** ends a running turn; clicking the status bar or pressing Esc only folds the conversation without ending it, leaving the results in view. An account without AI SRE, or one out of AI SRE credits, keeps the basic natural-language query at the same entry: a sentence becomes DQL, previewed before you apply it. See [Data query syntax guide](/en/rum/explorer/data-query).

### RUM dashboards: a dashboard belongs to one application

A custom dashboard now belongs to the application it was created in, and every panel's query reads that application only, so the panel editor drops its application picker: the old **Page application** option (`$app`, resolved to the page's current application) survives only in definitions saved before this change. The Insights tab bar lists the current application's dashboards (by title, up to 100) and **Manage dashboards** lists every application's; opening another application's dashboard from the manage page or a link first switches the page to the application it belongs to, then opens it. Switching the application by hand on a dashboard tab leaves that dashboard and returns to the **Overview** tab, which belongs to the new application. A copy of another application's dashboard stays in that application. Dashboards saved before this change take the application of their first query that reads a concrete one; an old dashboard that reads no concrete application no longer appears in the application's tabs and can no longer be edited, so create it again under its application. See [RUM custom dashboards](/en/rum/analytics/custom-dashboards).

### RUM errors split by where they were raised

The same error message raised from two different places in the code now makes two Issues instead of one. The location is taken from what survives a rebuild: for a Web JS error, the script and function of its top meaningful stack frame; for Android, the throw site of the exception chain's root cause plus the first app-code frame below it; for an iOS crash, the crash site plus the first app-code frame below it — line and column numbers, build hashes and minified or obfuscated names take no part, so a new release does not split one bug into new Issues. A minified frame that cannot be told apart is not used as a location, and such errors keep grouping by type and message. An iOS frame the SDK could not resolve can only be told apart by its offset inside the image, and that offset is stable within one build only, so such a crash can become a new Issue after every release — uploading dSYMs changes how the stack reads in the console, not how it is grouped. Existing browser and Android Issues keep receiving their message from every location, with their status, assignee and history; iOS crashes do not carry over to the old signal-only Issue and start anew by crash location. A custom fingerprint still takes precedence. See [Error grouping](/en/rum/error-tracking/error-aggregation).

</Update>

<Update label="2026-10-20" description="📋 Table and card views for routing rules, and connector credentials no longer follow a changed destination">

### Routing rules in a table or card view

The routing-rule list now offers two presentations, chosen at the top right: **table** and **card**. Cards are laid out in routing order; the number at a card's top right turns into a drag handle on hover, and dropping it on another card reorders the rules exactly like dragging the order column in the table. Each card keeps the **more actions** (⋯) menu. In the card view the **View** menu gains an **Last modified** switch that hides that line at the bottom of each card. The choice is remembered per member: reloading the page, opening another tab, or switching to another collaboration space shows the last view you picked. See [Routing rules](/en/on-call/channel/escalation-rule).

### Connector credentials no longer follow a changed destination

The people who can edit an MCP server or an A2A agent are not necessarily the people who enter its credentials, so a credential only holds for the destination it was entered for. Changing an MCP server's **transport / command / args / URL**, or an A2A agent's **Card URL**, moves the destination: every shared secret already stored in the config must be typed again in the same edit, otherwise the save fails and lists the keys to re-enter; every member's per-user credential is revoked at the same time, so each member re-enters their key or authorises again against the new destination. Replacing only the OAuth metadata revokes members' per-user credentials alone. Protected values in lists and detail pages are now shown as a plain `****` with no leading or trailing characters, and a member who can view but not edit also loses the MCP args and sees the credentials and every query value in a URL masked. See [MCP](/en/ai-sre/mcp) and [Agent](/en/ai-sre/agents).

</Update>

<Update label="2026-10-19" description="📊 RUM custom dashboards, a redesigned template detail page with send test, native Feishu tables, hosted access domains for WeCom apps, Feishu apps created by QR code">

### RUM custom dashboards: build your own under Insights

The Insights tab bar no longer holds only the built-in dashboards: the **+** menu at its right end offers **New dashboard** (requires the **Dashboards Manage** permission) and **Manage dashboards**, and a custom dashboard opens as an extra tab (up to 100 tabs are listed); **Save to dashboard** on an analytics chart also turns the current question into one full-width panel. A panel asks the same aggregation question as the explorer — event type, aggregation and field, group by and top N, plus a DQL filter (since 2026-10-25 a dashboard belongs to one application and its panels always read that application) — and draws as a time series, table, stat or text panel. Dashboard variables come in field-value and custom kinds, referenced in a panel's DQL as `${name}`, and a new dashboard starts with `env` / `service` / `version` field variables. Every save leaves a revision (the last 20 are kept), and a deleted dashboard goes to the trash for 30 days and can be restored from the manage page. See [RUM custom dashboards](/en/rum/analytics/custom-dashboards).

### A redesigned template detail page, with send test

The preview on the right of the template detail page renders by content block: native and Markdown tables are counted separately, and the bottom line gives the channel's format and its used / limit bytes; when the channel does not render Markdown tables or the content exceeds its limit, a yellow notice above the preview says so (the send fails, is truncated, or falls back to a compact summary). A built-in template, and any member without edit permission, opens read-only — **Built-in · Read-only** next to its name, with **Copy as new template** as the primary action; when you can edit, the old **Edit** button becomes **Template settings** and delete moves into **More actions**.

The preview header gains **Send test**: it renders the editor's current content (including unsaved edits) with the incident you pick and really sends it — to your own direct chat for an IM app, or to a group the bot has joined (a WeCom app has no group option), to a robot address you type in for this one send, or to your account's email; SMS and voice are not offered. A test message's title carries a `[Test]` prefix and the last line names the template and the sender, and its card buttons only answer "this is a test message, its buttons do not change any incident"; each member can send 5 per minute. A template syntax error makes a real notification fall back to the built-in template silently, while a test send reports it. See [Notification templates](/en/on-call/configuration/templates).

### Feishu apps: native tables instead of Markdown tables

Templates gain a **Native tables** switch (`feishu_app_card_v2_table_enabled`, off by default): when it is on, a GFM Markdown table in the template renders as a Feishu Card 2.0 native table component, so the recipient sees a table rather than the Markdown source. One card carries at most 5 native tables, each with at most 8 columns, 100 rows, 10 rows per page and 2000 bytes per cell; exceeding any of them, or a card over 30 KB, makes every table in the content go out as a Markdown table instead, and the preview says why. Apart from Feishu apps and the WeCom bot's markdown_v2, no channel renders Markdown tables, and the preview warns that the recipient will see the table source. See [Notification templates](/en/on-call/configuration/templates).

### WeCom self-built apps: Flashduty hosts the access domain

Integrating a self-built WeCom app needs one required field, **Access domain** (the bare domain, and it must sit under a subject filed by your enterprise). After you save, step 1 of the detail page hands you the DNS records: one certificate-hosting dns-01 delegation that proves the domain is yours, from which Flashduty issues and renews the HTTPS certificate, and one access CNAME — the mainland entry points at `cn.wecom.flashduty.com`, the international one at `wecom.flashduty.com`, and either one alone serves the domain — after which Flashduty proxies the domain directly, with no Nginx of your own and no certificate to apply for. Step 2 downloads `WW_verify_xxx.txt` from WeCom's **Set trusted domain → Apply for domain verification** and uploads it to the detail page, where Flashduty serves it from the domain's root path (WeCom does not follow redirects, so both http and https must answer). A domain a status page or another Flashduty account already holds cannot be hosted, and self-hosted deployments have no step 1. See [WeCom](/en/on-call/integration/instant-messaging/wecom).

### Feishu integrations: create a Flashduty-managed app by QR code

Creating a Feishu integration now offers three choices: **Create a new app (recommended)** / **Use an existing app** / **Enter credentials manually**. With either of the first two, saving shows a Feishu QR code; once you scan it, Flashduty creates (or takes over) the app in your Feishu tenant and finishes all of its configuration — the event and callback encryption strategy and request URLs, the bot and web app abilities, the scopes the features you enabled need — then publishes a new version; the credentials stay with Flashduty, so the detail page shows only the App ID, the current version and the state. Feishu asks its admin to approve twice (the app first, then the configuration version), and the detail page and integration list show that as "Pending admin review (1/2)", "Configuration pending review (2/2)", "New version in review" and so on, re-checking every 10 seconds, with **Copy message for admin** at hand. An integration set up by hand can click **Switch to Flashduty-managed** to scan and upgrade, with the App Secret and push URL unchanged and no gap in notifications; a self-hosted deployment cannot reach Feishu's QR endpoints and keeps manual credentials only. See [Feishu/Lark](/en/on-call/integration/instant-messaging/lark).

### Channel rule lists are now tables

The **Escalation rule**, **Silence rule**, **Inhibit rule**, and **Drop rule** lists in a channel's configuration changed from cards to tables, and each row expands to show the rule's details. All escalation rules appear on one page; drag the **Order** column to reorder them. Expand a rule to see its match conditions and levels, and select **Edit** to open the editor at that section. The silence list adds an **Effective time** column, and **Last modified** is hidden by default (show it from the view menu). See [Escalation rules](/en/on-call/channel/escalation-rule).

### Self-built WeCom apps link members automatically

After you save a self-built WeCom app integration, members are linked automatically, as with DingTalk and Feishu: the system looks up each member's WeCom account by phone number, then by email, and rescans every hour. Third-party apps still use **One-click link**. If the first link is refused or doesn't finish (for example, WeCom doesn't trust Flashduty's IP yet, or the DingTalk or Feishu app's lookup permission isn't active yet), the system retries 1, 2, 5, and 10 minutes later and stops at the first run that finishes. Members outside the app's visible range are retried on the next scan. See [WeCom](/en/on-call/integration/instant-messaging/wecom#linked-users).

### Regenerate DingTalk event subscription keys on the integration detail page

Step 2 of the DingTalk integration detail page has a new **Generate and show** button (**Generate again** once keys are stored). It creates a new **Encrypted aes_key** and **Signing token** pair and saves it right away. The new values are shown only this once and are gone when you leave the page, so copy them into DingTalk's event subscription immediately. Regenerating asks you to confirm first and invalidates the saved pair at once; it requires edit permission on the integration. See [DingTalk](/en/on-call/integration/instant-messaging/dingtalk).

### IM cards guide you to the resolve form

When you close an incident from a DingTalk, Feishu, Slack, Microsoft Teams, or WeCom card and the incident's channel requires a resolve form, the bot replies to you with an **Open the resolve form** link. The incident closes after you submit the form on the incident page. Previously the click gave no feedback in this case. See [Custom forms](/en/on-call/configuration/custom-forms).

### Status page custom domains and WeCom access domains can't be shared

A domain can't be both a status page custom domain and the Flashduty-hosted access domain of a self-built WeCom app. Saving a status page is refused if any account's WeCom integration already holds the domain, and saving a WeCom access domain is refused if a status page or another Flashduty account already uses it; use a different domain. See [Configure status page basics](/en/on-call/statuspage/create-manage-page).

### AI SRE can look up the original text after context compaction

After a session is compacted, the earlier messages and tool results are still kept. When a later step needs an exact value from that part (an ID, host name, metric value, threshold, log line, error text, or command), the agent looks it up in the original instead of relying on the summary, and says so if it can't find it. Images and attachments are kept only as placeholders, and a sub-agent's internal steps are not included. See [Console chat · Context compaction](/en/ai-sre/sessions#context-compaction).

### Artifacts support multi-file pages, canvases, slides, video, audio, and tables

AI SRE can publish a multi-file HTML page, with its styles, scripts, and images, as an artifact: up to 255 files and 64 MiB per publish. New viewers:

- **Canvas**: several pages laid out on a surface you can pan and zoom (2%–400%); select a board to view it full window
- **Slides**: 1920×1080 pages, navigated with the arrow keys or Space, with **Present** for full screen
- **Tables**: csv / tsv files with a sticky header, showing up to 1000 rows and 200 columns
- **Video and audio**: mp4, webm, mov and mp3, m4a, wav play in the browser's own player

See [Artifacts](/en/ai-sre/artifacts).

<Update label="2026-10-18" description="📈 RUM data queries get a timeout and a per-account concurrency limit, hash-route single-page apps split views by route">

### RUM data queries get a timeout and a per-account concurrency limit

RUM data queries run for at most 55 seconds and facet counts for at most 28 seconds. On timeout they return "The query timed out. Please narrow the time range or reduce the group-by fields." (HTTP 400); narrow the time range or use fewer group-by fields. An account can run only a limited number of queries at once; extra queries wait in a queue, and the wait counts toward the same timeout. A query that times out or whose client disconnects is also stopped on the server. See [Data query syntax guide](/en/rum/explorer/data-query).

### Hash-route single-page apps split views by route

For single-page apps that use hash routing (URLs like `/app/#/list`), the part after `#` that starts with `/` is now included in the view's URL path and path group: each route becomes its own view and its own row in performance analysis. The route's query string is dropped, and path segments that contain digits are grouped as `?`. Only data reported after the release is affected. See [Web SDK advanced configuration](/en/rum/sdk/web/advanced-config#override-default-rum-view-names).

</Update>

<Update label="2026-10-16" description="🤖 AI SRE automations can run in the IM chat that created them, RUM Issue gains a resolve mode, DingTalk and Feishu integrations link members automatically on save">

### AI SRE automations gain an execution place: rules can be bound to the IM chat that created them

Each automation rule now has an **execution place**, fixed at creation: **Web** (default) or **IM**. When you ask the agent to create a rule in an IM group or direct chat, the rule is bound to that chat; the console's create entries always create **Web** rules. The execution place cannot be changed afterwards, and the console offers no **Clone** for IM rules.

Every run of an IM rule opens a new session in the original chat and posts the conclusion back to that chat. If the chat's scope or session has changed by the time the rule fires (for example after `/scope` or `/new`), the run is **skipped** (reason `chat_scope_mismatch`) and the rule stays enabled. The rule list gains an **Execution place** column. See [AI SRE automations](/en/ai-sre/automations#execution-place-where-a-rule-runs).

### RUM Issue resolve mode: Reopen on recurrence / Reopen in a new version

The **Reopen on recurrence** and **Reopen in a new version** options in the issue status dropdown are two ways of handling recurrence for the same resolved state:

- **Reopen on recurrence**: if the error occurs again, even in the same version, the issue is reopened as pending and marked **regression**.
- **Reopen in a new version** (default): the issue reopens only when the error appears in a version the issue has not seen before; repeats within the same version do not reopen it.

You can switch between the two at any time. See [Issue status management](/en/rum/error-tracking/issue-status).

### DingTalk and Feishu integrations link members automatically on save

After you save or edit a DingTalk or Feishu integration, the system tries to link members right away and then rescans every enabled integration hourly: it exchanges each member's profile phone number (Feishu also uses email) for an IM account ID, with no action from the member and no need to sign in through IM first. To retry immediately, click **One-click link** on the integration detail page. WeCom still uses the page's **One-click link**. See [DingTalk](/en/on-call/integration/instant-messaging/dingtalk) and [Feishu](/en/on-call/integration/instant-messaging/lark).

### DingTalk: members linked by phone get single-chat cards and @mentions

DingTalk members linked by phone number didn't receive single-chat cards and weren't @mentioned in group cards. They now are, and @mentions of on-call members work too. Repeat notifications in DingTalk, Slack, and Microsoft Teams groups @mention the responders again. See [DingTalk](/en/on-call/integration/instant-messaging/dingtalk).

### Reordering escalation rules no longer changes their modified time

After you drag to reorder escalation rules, each rule keeps its **Last modified** time. Previously a single drag made every rule in the channel show as just modified. See [Escalation rules](/en/on-call/channel/escalation-rule).

### Standard alert events: alert_key over 255 bytes is replaced by its MD5

When you push an event whose `alert_key` is longer than 255 bytes (bytes, not characters), the system uses its MD5, a 32-character lowercase hex string, as the alert identifier and returns it in the response. The same value always gives the same MD5, so grouping and recovery are unaffected; later events can use either the original value or the returned one. See [Standard alert event](/en/on-call/integration/alert-integration/alert-sources/standard-alert).

### Alert rules: additional tags edited row by row, with Go template values

In the rule form and in batch edit, **Additional tags** now takes one tag per row: the label name on the left, the label value on the right, and **Add label** for a new row. A value that contains `{{` is rendered as a Go template, with `$labels`, `$annotations`, `$values`, `$severity`, and `$status` available; a value that starts with `[TPL]` is still passed to On-call as is. Label names are trimmed, must be unique, and can't start with `__alert_rule_`. If a template fails to render, only that label is dropped and the alert is still sent. See [Get started with Flashduty Monitors](/en/monitors/quickstart/quickstart#append-label-syntax).

### AI SRE posts a note in IM after dispatching a sub-agent

In IM, when AI SRE hands an investigation to a sub-agent and expects it to take more than a minute, it first posts one message saying what it sent the sub-agent to find out and roughly how long that should take. It sends nothing more while waiting, and the conclusion arrives separately when the sub-agent finishes. If the agent already replied earlier in the turn, no extra message is sent. See [IM platform · How a reply reaches the chat](/en/ai-sre/im#how-a-reply-reaches-the-chat).

</Update>

### Wildcard values in filter conditions now match literally

In a wildcard value (one that contains `*` or `?`), only `*` (any number of characters) and `?` (exactly one character; previously zero or one) are wildcards. Every other character, including `.`, `(`, `)`, `[`, `]`, and `|`, matches literally instead of being read as a regular expression. For example, `host[0-9]*` only matches values that start with `host[0-9]`; for a character class or a group, write a regular expression wrapped in `/`, such as `/^host[0-9]+.*$/`.

Existing wildcard values that used regular-expression syntax were rewritten to the equivalent `/…/` expression and still match the same alerts. Values with only parentheses or a single `.` were not rewritten and now match literally, so check such conditions. Values such as `C++*`, which previously failed to save with a syntax error, can now be saved. See [Filter conditions](/en/on-call/configuration/filter-conditions#matching-methods).

### AI-assisted noise reduction: let AI analyze a channel's noise and configure it

The **Alert grouping** and **Flapping detection** pages under a channel's **Noise reduction** gain a **Let AI configure noise reduction** button (shown when AI SRE is enabled for the account and you can access AI SRE sessions). It opens the AI SRE panel on the right with the channel as context and a prefilled question; the built-in **channel-noise** skill reads the channel's alert history and recommends grouping or flapping settings.

Only **Alert grouping** and **Flapping detection** can be written, and each change needs your consent first; at the moment of saving, a confirmation card lists each changed field with its before and after values. Event grouping, silence, inhibition and drop rules only get suggestions. See [Noise reduction](/en/on-call/channel/noise-reduction).

### Alert rules: simpler investigation-entry preview, a dialog for moving rules

For an investigation entry whose variable values and query contain no `{{`, **Preview jump** uses the form's current values (including unsaved edits) and the current time, so you need not save the rule first and the rule need not have an active alert. Entries that use `{{ }}` still preview from an active alert's configuration snapshot. The default **time range** of a new entry is now **60** minutes before and **30** minutes after the alert.

Moving rules in the rule list now opens a **Move to another folder** dialog with a search box for folders. See [Alert rules · Investigation entries](/en/monitors/alert-rules/investigation-entries) and [Folders](/en/monitors/folders/folders).

### New alert integration: Alibaba Cloud DataWorks

Alert integrations now include **Alibaba Cloud DataWorks**, which pushes Alibaba Cloud DataWorks Intelligent Monitor (Operation Center) alert events to Flashduty On-call through a custom webhook. See [Alibaba Cloud DataWorks integration](/en/on-call/integration/alert-integration/alert-sources/aliyun-dataworks-op).

### Alert grouping: non-strict mode explained, no confirm dialog when switching

With **Strict mode** off, the page now explains that a field empty on both sides counts as a match, but at least one field must have a value; alerts whose compared fields are all empty don't group. With it on, any empty field counts as different. Switching the grouping method card no longer opens a confirm dialog: the page shows that method's settings right away, keeps what you entered, and applies the change only after you select **Save**. See [Noise reduction](/en/on-call/channel/noise-reduction).

### DingTalk and Feishu: questions typed right after @ AI SRE are answered

In DingTalk and Feishu groups, a question typed right after the @ mention with no space used to be treated as an empty message and got no reply. It's now answered. In DingTalk, an @ message that carries only an image or file is also processed instead of skipped. See [IM platform](/en/ai-sre/im).

### Moving and cloning dashboards uses a searchable folder dialog

**Move to another folder** and **Clone to another folder** in the dashboard list's **More** menu now open the same dialog as moving alert rules: **Search folders** at the top filters the folder tree, and you can **Retry** if loading fails. When moving, the confirm button stays disabled while the dashboard's current folder is selected. See [Dashboards](/en/monitors/dashboards/dashboards).

### Monitors lists remember rows per page

The alert rule, active alert, dashboard, data source, engine, and lost-alert rule lists, plus the query result tables, remember the rows-per-page value you choose. It's stored in your browser, so it persists across refreshes and later visits but doesn't sync across browsers or devices; the current page number isn't remembered. See [Active alerts](/en/monitors/alert-rules/active-alerts).

### Remote configuration for Electron apps

Electron apps now show the **Remote configuration** tab, where you can change **Session sample rate**, **Capture additional sessions on error**, and **Custom settings** without a release. The SDK setup page has a new **Allow remote configuration** switch (on by default); when on, the generated main-process `init()` includes `remoteConfigurationEnabled: true`. It requires `@flashcatcloud/electron-sdk` 0.4.0 or later; remote configuration isn't delivered to the renderer process. See [Application management](/en/rum/quickstart/app-management#remote-configuration).

</Update>

### Investigation entries: from an alert straight to a dashboard or the Query Workbench

The alert-rule form gains a **sixth** block, **Investigation entries**: a rule can carry up to **20** jump targets that take you from an alert straight to a related dashboard or the Query Workbench.

- **Add dashboard entry**: pick a dashboard, set **Open at** to the whole dashboard, a tab, a group, or a panel, and fill the dashboard variables' **variable values**
- **Add query entry**: choose a data source (leave it empty to use the alert event's own data source), a query type, query statements, and query parameters
- Each entry takes a **purpose** (one line saying what it helps confirm) and a **time range** (minutes before and after the alert; the sum must be greater than 0), and entries can be dragged into a display order
- Variable values can reference the alert's labels as `$labels` and the event data source as `$datasource`

### RUM: unsampled sessions now upload once they error
