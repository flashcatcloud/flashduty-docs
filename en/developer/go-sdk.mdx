## Overview

`go-flashduty` is the official open-source Go client for Flashduty, covering every REST endpoint of the Flashduty Open API. It follows the design of [go-github](https://github.com/google/go-github): service groups, typed requests and responses, and a composable transport layer. It maps 1:1 to the OpenAPI spec. Each method makes exactly one HTTP call, returns `(*T, *Response, error)` (actions with no data payload return `(*Response, error)`), and does no implicit aggregation or enrichment across endpoints.

<Note>
The SDK is deliberately "thin." Consumer-side logic such as short-ID resolution and cross-endpoint orchestration belongs in the caller (CLI / MCP), not stuffed into the SDK or shoehorned into an endpoint. This keeps the SDK strictly one-to-one with the API — predictable, generatable, and verifiable.
</Note>

The module path is `github.com/flashcatcloud/go-flashduty`, the package name is `flashduty`, and the source is open-sourced under Apache-2.0 at [flashcatcloud/go-flashduty](https://github.com/flashcatcloud/go-flashduty).

## Quick start

Here is a minimal runnable example: construct the client, list incidents in the "Triggered" state, and handle the returned triple `(data, *Response, error)`.

```go
package main

import (
	"context"
	"fmt"
	"log"

	flashduty "github.com/flashcatcloud/go-flashduty"
)

func main() {
	client, err := flashduty.NewClient("YOUR_APP_KEY")
	if err != nil {
		log.Fatal(err)
	}

	list, resp, err := client.Incidents.List(context.Background(), &flashduty.ListIncidentsRequest{
		Progress:    "Triggered",
		ListOptions: flashduty.ListOptions{Limit: 20},
	})
	if err != nil {
		log.Fatal(err)
	}

	fmt.Printf("request_id=%s total=%d has_next=%t\n", resp.RequestID, resp.Total, resp.HasNextPage)
	for _, inc := range list.Items {
		fmt.Printf("[%s] %s\n", inc.IncidentSeverity, inc.Title)
	}
}
```

Methods that return data give three values (as `client.Incidents.List` above does):

| Return value | Type | Description |
|--------|------|------|
| data | `*T` | The endpoint's typed response body (for example, `*IncidentListResponse`); `nil` on failure |
| `*Response` | `*flashduty.Response` | Wraps `*http.Response` and carries envelope metadata such as `RequestID` and pagination |
| `error` | `error` | `*ErrorResponse` on failure, `*RateLimitError` on 429 |

Actions with no data payload return only two values, `(*Response, error)`, for example `client.Incidents.Ack`, `client.RuleFolders.WriteMove`, and `client.Applications.WriteDelete`; methods with no request body take only `ctx`, for example `client.RuleFolders.ReadList(ctx)` and `client.Knowledge.PackReadGet(ctx)`.

<Tip>
`app_key` is used for authentication, and the SDK injects it as a query parameter on every request automatically. Create one in the Flashduty console under **Personal center → APP Key**. See [Personal settings](/en/on-call/configuration/personal-settings#app-key). You can also authenticate with an OAuth access token instead: build the client with `NewClientWithAccessToken` (see [Create a client](#create-a-client)).
</Tip>

## Create a client

`NewClient` takes an `app_key` plus zero or more `Option`s. An empty `app_key` returns an error directly. The default Base URL is `https://api.flashcat.cloud`, the default HTTP timeout is 30 seconds, and the default User-Agent is `go-flashduty`.

```go
client, err := flashduty.NewClient("YOUR_APP_KEY",
	flashduty.WithBaseURL("https://api.flashcat.cloud"),
	flashduty.WithTimeout(10*time.Second),
	flashduty.WithUserAgent("my-app/1.0"),
	flashduty.WithHTTPClient(customHTTPClient),
	flashduty.WithTransport(customRoundTripper),
	flashduty.WithLogger(myLogger),
	flashduty.WithRequestHeaders(staticHeaders),
	flashduty.WithRequestHook(func(req *http.Request) { /* e.g. inject traceparent */ }),
)
```

| Option | Description |
|--------|------|
| `WithBaseURL(raw string)` | Override the API base URL (default `https://api.flashcat.cloud`). Use it to point at your own gateway for private deployments; the address may carry a path prefix (with `https://gateway.example.com/api`, requests go to `/api/<endpoint>`, with or without a trailing `/`); an invalid URL errors at the `NewClient` stage |
| `WithTimeout(d time.Duration)` | Set the overall timeout of the underlying HTTP client |
| `WithUserAgent(ua string)` | Set the `User-Agent` header carried on every request |
| `WithHTTPClient(hc *http.Client)` | Replace the underlying `*http.Client`; ignored when `nil` |
| `WithTransport(rt http.RoundTripper)` | Set a custom `http.RoundTripper`, the idiomatic hook for middleware such as retry, caching, tracing, and rate limiting; ignored when `nil` |
| `WithLogger(l Logger)` | Set a custom logger; ignored when `nil` |
| `WithRequestHeaders(h http.Header)` | Set static headers appended to every request, applied after the SDK's own headers (`Content-Type`, `Accept`, `User-Agent`) |
| `WithRequestHook(hook func(*http.Request))` | Register a callback invoked before each request is sent, for injecting per-request headers (such as W3C `traceparent`) |

<Info>
**Private deployment**: point the client at your own Flashduty gateway address with `WithBaseURL` — everything else stays exactly the same.
</Info>

### OAuth access token

Besides the `app_key`, the SDK accepts an OAuth access token. A client from `NewClientWithAccessToken(accessToken, opts...)` sends `Authorization: Bearer <token>` on JSON, GET, and file-upload requests, and doesn't add the `app_key` query parameter. Use one credential or the other, not both. An empty token returns an error directly (`flashduty: access token is required`); everything else matches `NewClient`, so every `Option` still applies and the default Base URL, timeout, and User-Agent are the same.

```go
client, err := flashduty.NewClientWithAccessToken(accessToken,
	flashduty.WithTimeout(10*time.Second),
)
```

Access tokens are issued by the Flashduty OAuth authorization server, whose address is the API base URL (default `https://api.flashcat.cloud`). A client discovers it at `/.well-known/oauth-authorization-server` and gets a token through an authorization-code + PKCE flow. The token calls the public API as its account, with the same access as that account's `app_key`. A token is valid only at the deployment that issued it, so do not point `WithBaseURL` at another gateway when you authenticate with one.

### Public and dedicated integrations

Public integrations are account-level (`/integration/*`), managed in the Integration Center, and attach to channels through subscriptions or routing; call them with `client.Integrations`. A dedicated integration belongs to one channel (`/channel/integration/*`); call it with `client.DedicatedIntegrations`, which has eight methods: `ReadInfo`, `ReadList`, `WriteCreate`, `WriteUpdate`, `WriteDelete`, `WriteEnable`, `WriteDisable`, and `WriteRotateKey`.

- Choose the service by who owns the integration, not by the integration ID: `ReadInfo`, `WriteUpdate`, and the rest accept only dedicated integration IDs, and a public integration ID is rejected. Insufficient permissions never switch you to the other group.
- Omitted fields keep their stored value on an update. `ChannelIntegrationUpdateRequest.Description` is a `*string` of at most 499 characters: nil keeps the stored description, and a pointer to an empty string clears it.
- A nil `Settings` keeps the stored configuration, while a non-nil empty map submits `{}` as the replacement configuration, in which masked (`******`) or omitted secret fields keep their stored value.

For the permissions each direction needs, how `integration_key` may be used, and the masking rules, see [Get dedicated integration detail](/en/api-reference/on-call/dedicated-integrations/channel-integration-read-info) and [Update dedicated integration](/en/api-reference/on-call/dedicated-integrations/channel-integration-write-update).

### Status page drafts

`client.StatusPages.DraftCreate` (`POST /status-page/draft/create`) stores a status page event draft for a human to review and publish from the console; it is never directly visible to the public.

- Request `Draft` is the typed struct `CreateStatusPageDraftRequestDraft`, not arbitrary JSON: `PageID`, `Type` (`incident` or `maintenance`), `Name`, and `Message` are required; `ChangeID` (greater than 0 appends an update to an existing event), `Status`, and `AffectedComponents` are optional; for a new maintenance you can set `StartTime` / `EndTime` (Unix seconds) for the window; `PageName` (for console display) and `V` (the payload format version, stored as-is) are additional fields. The server keeps fields outside the struct, but the SDK has nowhere to put them, so they cannot be sent through the SDK.
- The draft is at most 64 KB serialized; the response returns a `draft_id` matching `draft_[A-Za-z0-9]{22}`, which the console review link carries.
- Request `Source` is a marker of the drafting origin, at most 64 characters.

For the publish flow and how long drafts are kept, see [Create a status page draft](/en/api-reference/on-call/status-pages/status-page-draft-create).

### Knowledge

- Exported types: `KnowledgePackItem`, `KnowledgeFileItem`, `KnowledgeWarning`, and the various `Knowledge*Request` / `Knowledge*Response` structs.

### AI SRE artifacts

`client.Artifacts` covers the 11 operations under `/safari/artifact/*`: gallery reads `ReadGet`, `ReadList`, `ReadGetFileState`; files `ReadSign`, `ReadStream`; writes `WritePublish`, `WriteUpdate`, `WriteDelete`; public sharing `WriteShareEnable`, `WriteShareRevoke`, `WriteShareSync`.

- `ReadStream` downloads or previews a file with a signed token; the success body is a file, not a JSON envelope, with the raw bytes on `Response.Raw`.
- A public-share snapshot can go stale: when `share_enabled` is true and `share_file_id` differs from `file_id`, call `WriteShareSync` to refresh the snapshot with the latest content.
- Exported types: `PublishedArtifactItem`, `ArtifactShareState`, `SignedUrLs`, and the various `Artifact*Request` / `Artifact*Response` structs.
- The artifact list pages with its own `Page` / `Limit`, see [Pagination](#pagination); for visibility, signed-URL lifetime, and sharing rules, see [List artifacts](/en/api-reference/ai-sre/artifacts/artifact-read-list) and [Download or preview a file](/en/api-reference/ai-sre/artifacts/artifact-read-stream).

### Automation rules

`client.Automations` covers `/safari/automation/*`. A rule's **execution destination** (scope and where it runs) is fixed at creation time:

- `AutomationRuleCreateRequest.RunIn` (`run_in`) is `current-chat` (binds the rule to the authenticated live IM conversation) or `web` (runs in the web console). Omitted, the server decides: `current-chat` for an authenticated IM invocation, `web` otherwise. Sending `current-chat` outside a live IM conversation is rejected.
- `AutomationRuleCreateRequest.TeamID` (`team_id`) is a `*int64`: an explicit `0` means personal scope and a value greater than 0 picks a team in the account. Omitted, it inherits the authenticated IM conversation's scope when one is present; otherwise the server applies its normal default. A `current-chat` rule's scope must match that conversation's scope.
- `AutomationRuleUpdateRequest` no longer has `TeamID` (nor `RunIn`): scope and execution destination are immutable after creation. Old code that set `TeamID` on an update request should drop the line — otherwise it will not compile.

The war room creation trigger's fields behave differently on the two request types:

- On the create request they are plain values: `AutomationRuleCreateRequest.WarRoomTriggerEnabled` (`bool`), `WarRoomChannelIDs` (`[]int64`), `WarRoomSeverities` (`[]string`). On the update request all three are pointers (`*bool` / `*[]int64` / `*[]string`): nil leaves the field unchanged, a non-nil value is sent.
- The server creates the trigger when it is given one: `WarRoomTriggerEnabled` is true, or `WarRoomChannelIDs` is non-empty. In that case both the channel list and the severity list (`Critical` / `Warning` / `Info`) must be non-empty, and a missing one is rejected as an invalid parameter; severities alone do not create a trigger.
- Passing an empty slice on update is the same as omitting it: the server treats an empty list as not provided and keeps the stored value, so filters can only be replaced wholesale with non-empty lists — an empty array does not clear them.
- On the way back, `AutomationRuleItem.WarRoomTriggerEnabled` always has a value (false when there is no such trigger), while `WarRoomTriggerID`, `WarRoomChannelIDs`, and `WarRoomSeverities` are empty (`""` / empty slices).

For what the fields mean and when the trigger fires, see [Automations · War room created](/en/ai-sre/automations#war-room-created); for the request validation, see [Create Automation rule](/en/api-reference/ai-sre/automations/automation-rule-write-create).

### Rule folders

`client.RuleFolders` covers the six operations under `/monit/folder/*`.

- `ReadList` (`POST /monit/folder/list`) and `ReadHealth` (`POST /monit/folder/health`) take no request body: the first returns a flat `[]FolderItem` that you rebuild into a tree in the client from `ParentID` / `ParentPath` (dashboards and alert rules share that same tree); the second returns a `FolderHealthOutput`, whose `FolderHealthItem.HasIssue` marks a folder that — or whose visible descendant — has active alerts or rule runtime issues.
- On the write side `WriteCreate` (`/monit/folder/create`) and `WriteUpdate` (`/monit/folder/update`) return the `FolderItem`, while `WriteMove` (`/monit/folder/move`) and `WriteDelete` (`/monit/folder/delete`) return only a `*Response`.
- Further exported types are `FolderCreateRequest`, `FolderUpdateRequest`, `FolderMoveRequest`, and `FolderDeleteRequest`.
- For the name constraint, the replacement semantics of an update, and the `FolderNotEmpty` error, see [Update monitor folder](/en/api-reference/monitors/rule-folders/monit-folder-write-update) and [Delete monitor folder](/en/api-reference/monitors/rule-folders/monit-folder-write-delete).

### Diagnostic queries

`client.Diagnostics` has two methods: `QueryData` (`POST /monit/query/data`) returns a stable `query_result.v1` structured result (`result.kind` is one of `frames`, `records`, or `samples`); `QueryExplore` (`POST /monit/query/explore`) runs an explore query against a configured data source and returns the data source's native `explore_result.v1` shape. Reach for `QueryExplore` when you need the native result shape (raw logs included) and `QueryData` when you need the stable `query_result.v1` contract; for log-pattern and metric-trend analysis, use `client.DataSources.ToolsInvoke` with `prometheus.metric_trends`, `loki.log_patterns`, or `victorialogs.log_patterns`.

`QueryExplore`'s Go types and constraints:

- Result: `ExploreData.format` is always `explore_result.v1`; `ExploreResult.Kind` is `frames` (columnar tables or time series, see `ExploreFrame` / `ExploreField`), `samples` (instant values with labels, `ExploreSample`), or `logs` (log entries as `ExploreLogEntry`, at most 1,000, or 100 for an SLS data source; when truncated, `has_more` is true and `applied_limit` reports the effective cap).
- Request: `QueryExploreExecution.Kind` is `instant`, `range`, or `window`; `ToMs` is required for all three, `range` additionally requires `FromMs` and `MaxDataPoints`, `window` additionally requires `FromMs`, and `MinStepSeconds` is accepted only for `range`.
- `Args` is required in the request: pass an empty `map[string]string{}` when you have no macros — a nil Go map serializes to `null`, which does not satisfy the schema.
- `execution.effective_step_seconds` echoes the step actually used after applying `max_data_points` and `min_step_seconds`.

For the data source types, Edge version requirements, and request body cap, see [Query structured data](/en/api-reference/monitors/diagnostics/monit-read-query-data) and [Run an explore query](/en/api-reference/monitors/diagnostics/monit-read-query-explore).

### RUM remote config and repositories

Beyond application management, `client.Applications` (RUM applications) covers the five RUM remote configuration methods: `RemoteConfigReadGet`, `RemoteConfigReadHistoryList`, `RemoteConfigReadPreview`, `RemoteConfigWriteUpdate`, and `RemoteConfigWriteHistoryRevert`.

- Main types: `RemoteConfig` (`enabled`, `activation`, `default`, `rules`, `custom`, `refresh_on_foreground`), `RemoteConfigValues` (the capture and sampling knobs a configuration can set), `RemoteConfigRule` (`match` conditions plus the `set` values), `RemoteConfigHistoryItem` (with `version`, `reason`, `content_hash`, and `updated_by`), and the `GetRemoteConfigRequest` / `ListRemoteConfigHistoryRequest` / `PreviewRemoteConfigRequest` / `UpdateRemoteConfigRequest` / `RevertRemoteConfigRequest` structs with their matching `*Response` types.
- The application's own `WriteCreate` / `WriteUpdate` / `ReadInfo` / `ReadInfos` / `ReadList` also carry `repositories` (`[]RUMApplicationRepository`, a body-only field): it links the application to the source code repositories that build it — ordered, first entry is the primary repository, at most 10 entries, each one a `Repo` (GitHub repository in `owner/name` form, required) plus an optional `Subdir` (the directory holding the application inside the repository — `.` is the repository root, an empty value is saved as `.`). Passing it on create establishes the links; on update, passing it replaces the whole list, an empty array clears the links, and omitting it leaves them unchanged; `ReadInfo` / `ReadInfos` / `ReadList` echo it back on `RUMApplicationItem`. Linking grants no access by itself: AI sessions can only read repositories granted to the account's GitHub App installations. This field is currently available through the API and SDK only; the console's application management page does not expose repository links.
- For the preview matching rules, see [Preview remote config](/en/api-reference/rum/applications/rum-application-remote-config-read-preview); for the validation on publish and revert, see [Update remote config](/en/api-reference/rum/applications/rum-application-remote-config-write-update).

### Data source tool invocation

`client.DataSources.ToolsInvoke` (`POST /monit/datasource/tools/invoke`) executes one deterministic tool against a configured datasource: `tool` is a single tool name prefixed by the datasource type (for example, `mysql.overview`), and `params` is the tool-specific JSON parameters (omitted means `{}`; an explicit `null` is invalid). Alongside diagnostic tools, the entry supports `<type>.query` query tools.

- Build a query-tool request with `NewDatasourceQueryInvokeRequest(datasourceID, tool, params)` and pass the matching typed struct for that tool: `PrometheusQueryParams`, `MySQLQueryParams`, `PostgresQueryParams`, `OracleQueryParams`, `ClickHouseQueryParams`, `ElasticsearchQueryParams`, `LokiQueryParams`, `VictoriaLogsQueryParams`, `SLSQueryParams`, or `TencentCLSQueryParams`. All of them pair `expr` with an `execution` (`DatasourceQueryExecution`).
- `DatasourceQueryExecution`'s `FromMS` / `ToMS` are Unix-millisecond `*int64` values, and every optional field is a pointer: a nil pointer omits the key and lets the server apply its default.
- Query-tool `params` may not be empty: `NewDatasourceQueryInvokeRequest(..., nil)` returns an error, unlike the general "omitted means `{}`" rule.
- The response is a `DatasourceToolResult`: `data` is tool-specific JSON and never null, `summary` is optional, and a `truncated` object with `reason` signals truncation.

```go
req, err := flashduty.NewDatasourceQueryInvokeRequest(12345, "prometheus.query",
	flashduty.PrometheusQueryParams{
		Expr: "sum by (job) (rate(http_requests_total[5m]))",
		Execution: flashduty.DatasourceQueryExecution{
			Kind: "instant",
			ToMS: flashduty.Int64(1789000000000),
		},
	})
if err != nil {
	log.Fatal(err)
}
out, _, err := client.DataSources.ToolsInvoke(ctx, req)
```

For the tool catalog, which execution modes each data source type allows, and the request body and timeout caps, see [Invoke a data source tool](/en/api-reference/monitors/data-sources/monit-datasource-tools-invoke).

### Prometheus label values

`client.DataSources.ReadPrometheusLabelValues(ctx, dataSourceID, labelName)` (`GET /monit/prometheus/api/v1/label/{label_name}/values`) lists every value of one label on a Prometheus-compatible data source through the monitoring proxy: the label name goes in the URL path (the SDK escapes it), and the target data source is selected by the `X-DSID` request header — the SDK sets it from the `dataSourceID` argument (a `0` ID or an empty `labelName` errors immediately).

- Its success body is not the Flashduty `{request_id, data}` envelope: the response decodes straight into `PrometheusLabelValuesResponse` (`data` carries the label-value strings when `status` is `success`; `errorType` and `error` are present when it is `error`). `Sessions.Subscribe`, `Sessions.Export`, and `Artifacts.ReadStream` likewise return a stream or a file directly.
- Any non-2xx response puts the raw body verbatim into `*ErrorResponse.Message` (`Code` is usually empty), treating the platform's `text/plain` bodies and the data source's own JSON error shape alike.

For what an empty result means (no `X-DSID`, or an old Edge version in the cluster) and the required Edge version, see [List Prometheus label values](/en/api-reference/monitors/data-sources/monit-prometheus-read-label-values).

### Data source configuration

`client.DataSources`'s `payload` is the typed struct `DsPayload` (`*DsPayload` in list and detail responses), filled per `type_ident`: `Prometheus`, `Loki`, `Mysql`, `Oracle`, `Postgres`, `Clickhouse`, `Elasticsearch`, `SLS`, `TencentCls`, `Victorialogs`, plus the diagnostic-only `RedisNode`, `RedisSentinel`, `MongodbMongod`, `MongodbMongos`, and `Kafka`.

- `enabled` and `alerting_enabled` are independent: `enabled` (whether business execution is enabled) defaults to true on create; `alerting_enabled` (whether alert evaluation is allowed) defaults to true for alerting types and false for diagnostic-only types; omitting either on update preserves the current value and an explicit `null` is invalid. Disabling (`enabled` false) is rejected with a conflict when enabled rules reference the datasource.
- `payload` is always `null` in `/monit/datasource/list` responses and populated in create, update, and info responses; the diagnostic types' `password` and Kafka's `tls_key` echo back only `${env:...}` references, and on update, omitting those fields keeps the stored value while an empty string clears it.
- For the allowed `type_ident` values, each type's connection address rules, and credential requirements, see [Create datasource](/en/api-reference/monitors/data-sources/monit-datasource-write-create).

### Service calendar events

`client.Calendars` covers `/calendar/*`: events through `CalEventDelete`, `CalEventUpsert`, `CalEventList`, and calendars through `CalendarCreate`, `CalendarList`, `CalendarInfo`, `CalendarUpdate`, `CalendarDelete`.

- `CalEventIDRequest` (`CalEventDelete`) supports two usages: pass `EventID` to delete a single event, or omit it and pass both `StartAt` and `EndAt` (`YYYY-MM-DD`, `EndAt` exclusive) to clear the calendar's own events off those days. Pass one or the other; `CalID` is always required.
- `CalEventUpsert` creates or updates an event the calendar owns over `[StartAt, EndAt)` (`IsOff` true marks a day off, false a working-day override): omit `EventID` to create a new event, and a given `EventID` must be an existing event of that calendar.
- Alongside `Items` (sorted by `StartAt`) and `Total`, `CalEventListResponse` carries a required `Days`: a `map[string]CalDay` keyed by `YYYY-MM-DD` that gives the resolved state of every day in the scope. `CalDay.Layer` is `custom` / `holiday` / `weekly`: the calendar's own events outrank the linked holiday calendars, which outrank the weekly workdays; inside one layer a working-day event beats a day off, and a day no event covers is a working day.
- For the overlap handling on write and the request validation, see [Upsert calendar event](/en/api-reference/on-call/calendars/cal-event-upsert).

### Incident work items

The `WorkItem*` methods on `client.Incidents` (`/incident/work-item/*`) manage an incident's action items and post-mortem follow-ups: `WorkItemList`, `WorkItemCreate`, `WorkItemUpdate`, `WorkItemDelete`, `WorkItemComplete`, `WorkItemConvert`, `WorkItemResetAssignees`, and `WorkItemBindPostMortem`.

- Work-item status is a closed enum: `Status` on `CreateWorkItemRequest` / `UpdateWorkItemRequest` and `TargetStatus` on `ConvertWorkItemRequest` accept only `open`, `in_progress`, `done`, or `cancelled`, with creation taking `open` when the field is omitted or blank.
- `WorkItemComplete`'s `CompleteWorkItemRequest.TargetStatus` accepts only `done`; any other value is rejected.
- `UpdateWorkItemRequest.Version` is the optimistic lock: it must equal the item's current version.

For licensing, who may complete an item, and the idempotency rules, see [Complete a work item](/en/api-reference/on-call/incidents/incident-work-item-complete).

## Response timestamps

Time fields in responses are self-describing `Timestamp` (Unix seconds) or `TimestampMilli` (milliseconds) types. Types shared by requests and responses are the exception (see the warning below). They serialize to RFC3339 strings in the local time zone, so JSON, logs, and LLM-facing output are directly readable; the raw epoch is still one method call away.

- **Serialization (outbound)**: a non-zero value serializes to a quoted RFC3339 string (`TimestampMilli` uses RFC3339Nano to preserve millisecond precision). A zero value serializes to the bare integer `0`, meaning unset rather than a 1970 date. The SDK's response structs do not tag time fields with `omitempty`, so the field is still present when you re-serialize; test for unset with `0` or `.IsZero()`.
- **Deserialization (inbound)**: it accepts both numeric epoch (the raw wire form) and RFC3339 strings (so a serialized value round-trips losslessly), and also accepts `null` (→ 0).

```go
inc := list.Items[0]

fmt.Println(inc.StartTime)            // 2026-05-30T14:37:11+08:00  (String / fmt / TOON)
b, _ := json.Marshal(inc.StartTime)   // "2026-05-30T14:37:11+08:00"
epoch := inc.StartTime.Unix()         // 1780123031  (raw wire value)
t := inc.StartTime.Time()             // time.Time
zero := inc.StartTime.IsZero()        // whether it's the unset sentinel
```

| Method | Returns | Description |
|------|------|------|
| `.Time()` | `time.Time` | Get the standard time value |
| `.Unix()` | `int64` | Get the raw wire value (`Timestamp` in seconds, `TimestampMilli` in milliseconds) |
| `.IsZero()` | `bool` | Whether it's the unset sentinel (0) |
| `.String()` | `string` | RFC3339 in the local time zone; `"0"` when unset |

<Warning>
**Request-side time fields are still `int64`** — the API expects a numeric epoch on the wire. Note: most endpoints take **seconds**, but RUM and webhook history-related endpoints take **milliseconds**.

**Types shared by requests and responses are the same.** `AlertRuleV2` (the return type of `AlertRules.ReadInfoV2` / `WriteCreateV2` / `WriteUpdateV2`, that is, `POST /monit/rule/v2/info`, `/v2/create`, and `/v2/update`) keeps `created_at` / `updated_at` as bare `int64` Unix seconds with `omitempty`, not `Timestamp`. Such fields have no `Unix()` / `String()` / `IsZero()` methods, so convert the seconds yourself — writing `rule.UpdatedAt.Unix()` as in the `Timestamp` examples will not compile.
</Warning>

<Note>
`AlertRuleV2`'s `investigation_targets` (the same return type of `AlertRules.ReadInfoV2` / `WriteCreateV2` / `WriteUpdateV2`) has this shape:

- The field itself is `[]InvestigationTarget`, at most 20 entries with no duplicates, and the serialized list must not exceed **32 KiB** (32768 bytes); exceeding it returns `investigation_targets must not exceed 32768 bytes`. On the update endpoint it is presence-based — omitting it keeps the saved configuration, sending `[]` clears it. Each entry may carry an optional `purpose`: one-sentence plain text saying what the entry helps confirm (**do not put line breaks in it**; the server validates ≤512 bytes and requires valid UTF-8 with no control characters, while the console caps the input at 200 characters, so the API accepts somewhat more than the console, but 200 CJK characters can already exceed 512 bytes). `purpose` is literal text, not a template, and is not part of alert identity or de-duplication.
- Each entry is a **closed tagged union**, and `Kind` decides which sub-object you supply. `dashboard` (opens a dashboard panel) requires `Dashboard`, and `query` (opens an Explore query) requires `Query`. Supplying the other one, or an unknown field, is rejected.
- `TimeRange` (`InvestigationTimeRange`: `BeforeSeconds` and `AfterSeconds`) is required on **every** saved entry — both directions are non-negative and at least one is greater than zero.
- The `Dashboard` entry (`DashboardInvestigationTarget`) takes its variables in `Variables`: a `map[string]string` keyed by variable name whose values are literal, and may reference event labels through `{{ }}` templates. `DashboardID` and `Variables` are required and `TargetID` is optional; `DashboardID` and `TargetID` must both be canonical UUIDv7 values.
- The `Query` entry uses `QueryInvestigationTarget`: `Query` is required and is a `DashboardQuery` — `Mode` is `instant`, `range`, or `window`, `Expr` is an expression in the target data source's own language that may use `{{ }}` templates, `Args` are named parameters passed through verbatim and must not contain templates, and `MinStepSeconds` is only accepted when `Mode` is `range`. `DatasourceID` may be omitted (or set to 0), which runs the query on the alert event's own datasource.
</Note>

## Pagination

Most list endpoints embed `ListOptions`; zero values are omitted and never override server defaults (the backend defaults to `p=1`, `limit=20`).

| Field | Type | Wire field | Description |
|------|------|-----------|------|
| `Page` | `int` | `p` | 1-based page number |
| `Limit` | `int` | `limit` | Max items returned per page |
| `SearchAfterCtx` | `string` | `search_after_ctx` | The opaque cursor echoed by the previous page, for deep pagination; pass it back to fetch the next page |

Three exceptions:

- The artifact list, `client.Artifacts.ReadList`, uses `ArtifactListRequest`'s own `Page` / `Limit`, whose wire fields are `page` rather than `p`; `Limit` above 100 is capped at 100, and the response carries only `items` and `total`, with no `has_next_page`.
- Webhook history, `ListWebhookHistoryRequest`, requires `Limit` (1–100) and pages only through its own `SearchAfterCtx`.
- The data source list, `client.DataSources.ReadList`, is not paginated: `/monit/datasource/list` returns a `DataSourceListResponse` array.

On the response side, `*Response` carries `Total`, `HasNextPage`, and `SearchAfterCtx`. We recommend walking page by page with the search-after cursor:

```go
req := &flashduty.ListIncidentsRequest{
	ListOptions: flashduty.ListOptions{Limit: 50},
}

// Cap iterations to avoid an infinite loop if the cursor misbehaves.
for page := 0; page < 100; page++ {
	list, resp, err := client.Incidents.List(ctx, req)
	if err != nil {
		log.Fatal(err)
	}

	for _, inc := range list.Items {
		fmt.Printf("%s: %s\n", inc.IncidentID, inc.Title)
	}

	if !resp.HasNextPage {
		break
	}
	// Advance the cursor to fetch the next page.
	req.ListOptions.SearchAfterCtx = list.SearchAfterCtx
}
```

## Error handling

An unsuccessful call returned by the Flashduty API — whether the envelope carries an error or the HTTP status is non-2xx — returns `*ErrorResponse`. It has `Code`, `Message`, an optional `Reason`, and `RequestID` fields; when troubleshooting, give `RequestID` to the support team to pinpoint the request. `Reason` carries the server-supplied optional cause (the envelope's `DutyError` has the same field, JSON `reason`,omitempty); when non-empty it is also appended to the end of the error string, as `, reason X`.

When the API returns 429, the error is promoted to `*RateLimitError`: it embeds `*ErrorResponse` (so `errors.As` for `*ErrorResponse` still matches) and additionally carries a `RetryAfter` hint. `Code` values match the Open API [error code list](/en/openapi/rate-limits#error-codes).

<Note>
For **generated endpoints**, if you receive a non-2xx response with a non-JSON body, the SDK returns a plain `error`, not `*ErrorResponse`. This indicates that a gateway, load balancer, proxy, or other intermediary produced the response, usually because the request exceeded an intermediary timeout. Retry the request or split a long-running batch into smaller batches, and do not assume that `errors.As(err, &apiErr)` matches this error.

The hand-written `client.DataSources.ReadPrometheusLabelValues` method is the exception: it parses no envelope and instead puts a non-2xx response's raw body verbatim into `*ErrorResponse.Message`, treating the platform's `text/plain` 4xx/5xx bodies and the data source's own JSON error shape alike (429 is still promoted to `*RateLimitError`). `errors.As(err, &apiErr)` therefore does match there — `Code` is usually empty, so read `Message` and `Response.StatusCode` to identify the cause.
</Note>

```go
_, _, err := client.Incidents.Info(ctx, &flashduty.IncidentInfoRequest{
	IncidentID: "does-not-exist",
})

var rl *flashduty.RateLimitError
if errors.As(err, &rl) {
	// Back off as the server requests, then retry.
	time.Sleep(rl.RetryAfter)
	return
}

var apiErr *flashduty.ErrorResponse
if errors.As(err, &apiErr) {
	fmt.Printf("api error code=%s request_id=%s\n", apiErr.Code, apiErr.RequestID)
	return
}
```

Typed predicate functions save string comparisons and see through wrapped errors (using `errors.As` internally):

| Helper | Description |
|----------|------|
| `IsNotFound(err)` | Whether the resource does not exist |
| `IsRateLimited(err)` | Whether requests are too frequent (429) |
| `IsUnauthorized(err)` | Whether unauthorized |
| `IsAccessDenied(err)` | Whether access is denied |
| `IsInvalidParameter(err)` | Whether a parameter is invalid |
| `ErrorCodeOf(err)` | Extract the error code, returning an `ErrorCode` constant (such as `ErrorCodeAccessDenied`, `ErrorCodeUnauthorized`) |

```go
switch flashduty.ErrorCodeOf(err) {
case flashduty.ErrorCodeAccessDenied, flashduty.ErrorCodeUnauthorized:
	// Handle auth failure
}
```

## Retry

The core client has **no** built-in automatic retry. Compose the optional `retry` subpackage through the transport layer — a safe-by-default retrying `http.RoundTripper`.

Features of `github.com/flashcatcloud/go-flashduty/retry`:

- **Retry conditions**: HTTP 429, any 5xx (status ≥ 500), and transport errors. Other 4xx and all 2xx/3xx return immediately.
- **Backoff policy**: deterministic exponential backoff (`MinWait * 2^attempt`, capped at `MaxWait` each time); no random jitter. When a valid integer `Retry-After` header is present, it takes precedence (also capped at `MaxWait`).
- **Safe replay**: retries only when the body is replayable (`req.Body` is nil or `req.GetBody` is non-nil). Each retry rebuilds the body on a clone, and the caller's `*http.Request` is never modified. All requests the SDK builds set `GetBody`, so POST bodies are safely replayable.
- **Respects cancellation**: if the request context is canceled while waiting out a backoff, it returns the context error immediately.

```go
import "github.com/flashcatcloud/go-flashduty/retry"

client, err := flashduty.NewClient("YOUR_APP_KEY",
	flashduty.WithTransport(retry.New(
		retry.WithMaxRetries(3),
	)),
)
```

| Option | Default | Description |
|--------|--------|------|
| `retry.WithMaxRetries(n int)` | `3` | Max retries after the first attempt; a negative number disables retry |
| `retry.WithMinWait(d time.Duration)` | `500ms` | Base backoff duration (the wait before the first retry) |
| `retry.WithMaxWait(d time.Duration)` | `30s` | Upper bound on a single backoff wait |
| `retry.WithBase(base http.RoundTripper)` | `http.DefaultTransport` | The underlying RoundTripper that actually performs the request |

<Tip>
The `retry` subpackage is pure `net/http` and deliberately does not import the parent `flashduty` package, so it never introduces a circular dependency. Both `retry.New()` and `&retry.Transport{}` (zero value) work out of the box.
</Tip>

## AI SRE sessions

Driving an AI SRE session from Go takes three steps: write a user turn, subscribe to the event stream to read the replies, and export the whole transcript when you need a record. The first two use `client.Sessions.WriteMessage` and `client.Sessions.Subscribe`; the third uses `client.Sessions.Export` in [Streaming export](#streaming-export).

### Session writes (create a session, send a message, upload attachments)

Send one user turn with `client.Sessions.WriteMessage` (`POST /safari/session/message`). Omit `SessionID` to start a new session, in which case `AppName` (such as `ai-sre`) and `EntryKind` are required, and `EntryKind` is `web`, `im`, or `api`. `Query` is the message text, at most 32000 characters.

Every other field is optional:

- `Parts`: extra message parts, each a `SessionMessagePart` whose `Type` is `text` or `file`. A `text` part uses `Text`; a `file` part uses `File` (a `SessionFilePart` with `Mime`, `Filename`, `ObjectKey`, and `Size`) pointing at a file already uploaded to that session.
- `Surface`: tags where the turn originated, for example `cli`.
- `DeliveryMode`: negotiates how replies are delivered. With `reply_only`, the agent answers only through its reply tool; `SessionMessageAck.DeliveryMode` in the response is the mode the server actually accepted, and it's empty when the requested mode was not granted.
- `Steering`: marks this message as sent while a turn was already running. With `true`, that running turn takes the message in at its next step and answers it, so the answer comes from that turn's event stream rather than only from this message's own invocation; with no turn running the field is ignored and the message is queued as usual.
- `EnvironmentKind`: the execution environment, `cloud` or `byoc`; `EnvironmentID` picks a specific environment of that kind.
- `TeamID`: binds a new session to a team, 0 for account scope.

`WriteMessage` returns as soon as the server has durably queued the turn (HTTP 202), and the response holds only `SessionID`, `InvocationID`, `RootInvocationID`, and the granted `DeliveryMode`. The turn runs asynchronously, so **replies are not in that response**; read them from the session event stream (see Session event stream below).

An attachment must belong to an existing session. To upload before the first message, create an empty session first with `WriteCreate` (`POST /safari/session/create`): `AppName` is required, `EntryKind` is `web`, `im`, `api`, or `automation`, and `TeamID` is immutable once the session exists.

`UploadAttachment` (`POST /safari/attachment/upload`) stores a file under a session. `SessionID`, `File`, and `Filename` on `SessionAttachmentUploadRequest` are all required, and one file can be at most 50 MB. `FilePart()` on the returned `SessionAttachment` turns it into a `SessionMessagePart` for the next message's `Parts`:

```go
att, _, err := client.Sessions.UploadAttachment(ctx, &flashduty.SessionAttachmentUploadRequest{
	SessionID: sessionID,
	File:      f,
	Filename:  "trace.log",
})
if err != nil {
	return err
}

_, _, err = client.Sessions.WriteMessage(ctx, &flashduty.SessionMessageRequest{
	SessionID: sessionID,
	Parts: []flashduty.SessionMessagePart{
		{Type: "text", Text: "Which errors are in this log?"},
		att.FilePart(),
	},
})
```

When `Parts` is set, the server ignores `Query`, so put the text in a `text` part.

### Session event stream (Subscribe, SSE)

`client.Sessions.Subscribe` (`POST /safari/session/subscribe`, `Accept: text/event-stream`) opens the session's event stream and returns an `io.ReadCloser`. The stream first replays persisted events strictly newer than your cursor, then keeps tailing live frames; `Export` instead reads the whole transcript once as NDJSON, so the two serve different jobs.

Read frames with `NewSessionFrameReader` and `Next()`:

```go
rc, _, err := client.Sessions.Subscribe(ctx, &flashduty.SessionSubscribeRequest{SessionID: sessionID})
if err != nil {
	return err
}
defer rc.Close()

fr := flashduty.NewSessionFrameReader(rc)
for {
	frame, err := fr.Next()
	if errors.Is(err, io.EOF) {
		return nil // the server finished the stream
	}
	var streamErr *flashduty.SessionStreamError
	if errors.As(err, &streamErr) {
		return streamErr
	}
	if err != nil {
		return err
	}
	handle(frame)
}
```

- **Cursor**: `SessionSubscribeRequest.LastEventAt` is Unix milliseconds, and 0 replays from the start of the session; `LastEventID` only breaks ties between events that share the same millisecond. Put the previous frame's `CreatedAt` and `EventID` back into those two fields to resume after it, so a reconnect doesn't repeat events you already handled.
- **Lifetime**: the stream has no time limit, and the server closes it after an idle period. `ctx` bounds the stream, so cancel `ctx` to stop it. The returned `io.ReadCloser` belongs to the caller and you **must** `Close` it.
- **End and errors**: `Next()` returns `io.EOF` on the `[DONE]` sentinel or a clean close, a `*SessionStreamError` for an in-band error record, and the transport error (including context cancellation) otherwise. A non-2xx status is still the regular JSON error envelope: `Subscribe` reads and closes it and returns a typed error with a `nil` `io.ReadCloser`, matching the generated endpoints.
- **Frame fields**: `SessionEventFrame` carries `EventID`, `CreatedAt`, `Type`, `AgentPath`, `Payload` (raw JSON), `InvocationID`, `RootInvocationID`, `DeliveryMode`, `IsError`, and `ErrorCode`. A persisted event has `EventID` and `CreatedAt`, and its `Type` is the author (`user`, `assistant`, and so on); an ephemeral frame (`turn_complete`, `assistant_token`, and so on) has no `EventID`, and its `Type` is the frame type.
- **Relation to `reply_only`**: for a turn sent with `DeliveryMode: "reply_only"`, the replies appear only on this stream, never in the `WriteMessage` response.

## Streaming export

`client.Sessions.Export` exports the full event transcript of an AI SRE session, returning an `io.ReadCloser` (an NDJSON stream, `application/x-ndjson`) rather than a JSON envelope. The first line is always a `session_meta` envelope, and each later line is a session event. When `req.IncludeSubagents` is true, each `subagent_dispatch` line is followed by the subagent's full event stream.

Because the response body can be large, read it line by line and write directly to a file — do **not** buffer the whole transcript into memory. The returned `io.ReadCloser` is the live HTTP response body, held by the caller and which you **must** `Close` (a `defer` close is correct). `Export` uses the client's `*http.Client`, so its overall timeout (30 seconds by default) also bounds reading the body; raise it with `WithTimeout` for a large transcript, or pass a client without a timeout through `WithHTTPClient`. `Subscribe` is not bound by that timeout. Pair it with `NewExportScanner` to scan line by line and `DecodeExportLine` to decode a line into an `ExportLine`:

```go
rc, _, err := client.Sessions.Export(ctx, &flashduty.SessionExportRequest{
	SessionID:        "your-session-id",
	IncludeSubagents: true,
})
if err != nil {
	return err
}
defer rc.Close()

sc := flashduty.NewExportScanner(rc)
for sc.Scan() {
	line, err := flashduty.DecodeExportLine(sc.Bytes())
	if err != nil {
		return err
	}
	// Use line.Type to distinguish: session_meta, user_message, llm_call,
	// tool_call, subagent_dispatch, final_answer, agent_text, error
	_ = line
	// You can also write sc.Bytes() to a file as-is.
}
return sc.Err()
```

<Note>
`NewExportScanner` uses a per-line buffer large enough for wide event lines, such as tool output or LLM calls. It isn't bound by the default 64KB token limit. On any non-2xx status, the body is a regular JSON error envelope. Like other generated endpoints, `Export` reads and closes it and returns a typed error (`*ErrorResponse`, or `*RateLimitError` on 429) with a `nil` `io.ReadCloser`.
</Note>
