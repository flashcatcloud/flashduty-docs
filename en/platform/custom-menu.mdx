Custom menus let administrators add navigation entries to the console sidebar, embedding external system pages or internal links directly into the Flashduty navigation tree. Members with a custom role see a menu only after you authorize that role on the menu.

<Note>
Custom menus are available only in private deployments.
</Note>

**Navigation path**: Platform → Custom Menu

## Create a menu

<Steps>
  <Step title="Open the Custom Menu page">
    Go to **Platform → Custom Menu** and click **New Menu**.
  </Step>
  <Step title="Fill in menu details">
    Complete the following fields:

    | Field | Required | Limit | Description |
    | --- | :---: | --- | --- |
    | **Chinese label** | One of the two | Max 6 characters | Menu name shown in the Chinese locale; if empty, the Chinese locale shows the English label |
    | **English label** | One of the two | Max 20 characters | Menu name shown in the English locale; if empty, the English locale shows the Chinese label |
    | **Icon** | No | — | Shown for top-level menus only; accepts an HTTPS image URL, base64, or SVG source. Uses a default icon if empty |
    | **URL** | Yes | Max 2048 chars | Target address to open or embed when the menu is clicked. Enter a full URL or an in-app path; it can't conflict with an existing system path |
    | **Open mode** | Yes | Embedded or new tab | See description below |
    | **Authorized roles** | No | — | Custom roles that can see this menu; if empty, no custom role can see it |
  </Step>
  <Step title="Choose an open mode">
    The open mode determines what happens when a user clicks the menu entry:

    - **Embedded**: Renders the target page inside the console main content area as an embedded frame. Use this for internal tools you want members to access without leaving Flashduty — for example, a Grafana dashboard or an internal knowledge base. The target page must permit iframe embedding (its HTTP response headers must not set `X-Frame-Options: DENY` or `X-Frame-Options: SAMEORIGIN`).
    - **New tab**: Opens the target URL in a new browser tab. Use this for external systems or pages that do not support iframe embedding.
  </Step>
  <Step title="Configure authorized roles">
    In the **Authorized roles** field, select the roles that can see this menu entry.

    <Warning>
    Preset roles (**Admin**, **Responder**, **Viewer**) can't be selected. They automatically have access to every custom menu. Use **custom roles** for authorization instead.
    </Warning>

    If no roles are selected, members with custom roles can't see the menu.
  </Step>
  <Step title="Save">
    Click **Save**. Members of the selected roles can see the menu in the sidebar.
  </Step>
</Steps>

## Edit a menu

Click the **Edit** button next to a menu in the list to modify any of its fields.

<Note>
After you change **Authorized roles**, roles in the new list gain access and roles removed from the list lose it.
</Note>

## Delete a menu

Click the **Delete** button on any row to remove that menu. **Members of the authorized roles will no longer see the menu entry after their next login or permission refresh.**

## Menu ordering

The menu list supports drag-and-drop reordering. Custom menus can be nested up to two levels; system menus can't be reordered.

## Quota

Each account can have at most **100** custom menus. At the limit, delete unused menus before adding new ones.

## Permission details

- **Visibility**: Only members with access see the menu in the sidebar. Everyone else sees no entry.
- **Preset roles**: Admin, Responder, Viewer, and the account owner always see every custom menu.
- **Adding and deleting**: After you add a menu, existing custom roles don't gain access automatically; select them in the menu's **Authorized roles**. Deleting a menu removes the matching access.

For how preset and custom roles differ, see [Permission Design](/en/platform/permission-design).
