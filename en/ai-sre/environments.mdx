## Overview

---

An **Environment** is where your AI SRE agent actually executes actions. Every tool call the agent makes — running commands, reading and writing files, executing Skills, connecting to MCP servers — happens inside an Environment.

AI SRE provides two types of Environments:

<CardGroup cols={2}>
  <Card title="Self-hosted Environment (BYOC)" icon="server">
    A persistent Runner process deployed **on your own machine**. It maintains a long-lived connection (WebSocket) to AI SRE and stands by to receive tasks at any time. You have full control over which machine it runs on and which internal resources it can reach.
  </Card>
  <Card title="Cloud Sandbox" icon="cloud">
    A temporary container managed by the system. No installation required — works out of the box. It pauses automatically when the session is idle and wakes up when you send the next message. This is the **default fallback** when no Runner is online.
  </Card>
</CardGroup>

The selection logic is straightforward: **when your account has an online self-hosted Runner, AI SRE uses it first; otherwise it falls back to the cloud sandbox.** You can also pin a specific Runner or force the cloud sandbox in the chat input area.

<Note>
Throughout this page, "Environment" and "Runner" refer to the same thing: the record you manage in the console is called an **Environment**, while the process actually running on your machine is called a **Runner**. One Environment record maps to one Runner process.
</Note>

## Why self-host (BYOC)

---

The cloud sandbox is great for getting started quickly and for investigations that don't require access to your internal network. When you need to reach your real environment, a self-hosted Runner is where it pays off. BYOC (Bring Your Own Compute) puts execution back in your hands:

<AccordionGroup>
<Accordion title="Data residency" icon="key">
  The Runner runs on your own machine, so command output, logs, and files produced by tool execution all stay within your environment. Sensitive data can be read and analyzed by the agent without leaving your network boundary.
</Accordion>
<Accordion title="Network reachability / low latency" icon="server">
  The cloud sandbox can only reach a controlled set of public domains by default — it cannot access services behind your VPC, private network, or dedicated line. Deploy a Runner on a machine that has direct connectivity to those targets, and the agent can query internal databases, call internal APIs, and log into jump hosts directly — with lower latency since there is no extra public-internet hop.
</Accordion>
<Accordion title="Security and compliance" icon="users">
  You control the OS account, file-system permissions, and egress policy of the machine the Runner runs on. Combined with the scope and permissions model, you can restrict a Runner to be visible only to specific teams, satisfying least-privilege and audit requirements.
</Accordion>
</AccordionGroup>

<Tip>
A self-hosted Environment is your own machine — AI SRE does not take over its egress control. The proxy policy that lets you configure allowed domains per environment in the cloud sandbox does not apply to BYOC, which is why the self-hosted Environment form **does not include network access configuration**. Egress is entirely governed by the machine's own network and firewall policies.
</Tip>

## Connecting a Runner

---

Go to **`Environments`** in the left sidebar of AI SRE to create and connect a self-hosted Runner. The process has two parts: creating the record in the console to get a Token, then installing and starting the Runner on the target machine.

<Steps>
<Step title="Create an Environment record">
  Click **Create Environment** in the top right and fill in the form:

  | Field | Type | Required | Description |
  |---|---|---|---|
  | Name | String | Yes | A unique display name for this Environment. Must be unique within the account; max 128 characters. |
  | Scope | Account / Team | Yes | Account scope is visible to all members in the account; team scope is visible and editable only by members of that team (see [Scope](#scope) below). |
  | Tags | String list | No | Tags used for task routing, comma-separated — e.g. `linux, docker, gpu`. |

  After the record is created, an **onboarding guide** appears containing the connection credential **Token** and a ready-to-use installation command.
</Step>

<Step title="Get the Token (connection credential)">
  The Token is the **sole credential** a Runner uses to connect to AI SRE. Keep it safe and do not share it externally. It is injected into the Runner process together with the installation command.

  <Warning>
  The Token effectively grants execution capability to a Runner. If it is leaked, someone else could impersonate that Environment. If you suspect a leak, delete the Environment from the list and recreate it. You can view the Token again at any time by clicking the **Token button** (key icon) in the list row.
  </Warning>
</Step>

<Step title="Install and start on the target machine">
  The onboarding guide provides two installation methods. The `TOKEN` and `URL` placeholders in the commands are automatically filled in with your Environment's actual values:

  <Tabs>
  <Tab title="Linux (systemd)">
    Run a single command on the target machine as root / sudo. The script installs the binary and registers it as a persistent systemd service:

    ```bash
    curl -fsSL <install.sh> | sudo TOKEN=<your-token> URL=<connect-url> bash
    ```

    The installation script is **idempotent**: the same command works for both the initial install and upgrades — if the binary is already at the latest version, it is skipped automatically.
  </Tab>
  <Tab title="Manual / macOS">
    Two steps: first install only the binary (without registering a systemd service), then start the process manually:

    ```bash
    # ① Install binary only
    curl -fsSL <install.sh> | sudo bash -s -- --no-service

    # ② Start manually
    FLASHDUTY_RUNNER_TOKEN=<your-token> FLASHDUTY_RUNNER_URL=<connect-url> flashduty-runner run
    ```
  </Tab>
  </Tabs>

  <Note>
  The `connect-url` is the WebSocket address the Runner dials into AI SRE (typically `wss://api.flashcat.cloud/safari/environment/ws`), injected by the deployment configuration. You do not need to fill it in manually — the onboarding guide already shows the complete, copy-ready command.
  </Note>
</Step>

<Step title="Verify online status">
  Once the Runner starts and completes the handshake, it continuously sends **heartbeats** to AI SRE. Return to the Environments list — the row's status will change from **Pending** (never connected) to **Online**:

  | Status | Meaning |
  |---|---|
  | Pending | The record was created but the Runner has never connected. The list shows a "View onboarding guide" link. |
  | Online | The Runner is currently connected with a healthy heartbeat and ready to accept tasks. |
  | Offline | The Runner connected at some point but its heartbeat has since been lost. |

  Once online, the list also populates the machine's **machine info** (OS / architecture / hostname), the Runner **version**, and the **last heartbeat** time (e.g. "just now", "N minutes ago", "N hours ago"). When a newer version is available, an "Upgrade available" prompt appears in the version column — click it to reopen the onboarding guide and upgrade using the same idempotent command.
</Step>
</Steps>

<Tip>
Upgrades and uninstallation are also covered in the same onboarding guide. Re-running the installation command on an already-installed Runner upgrades it. Two uninstall commands are provided: `--uninstall` removes the installation while keeping configuration, and `--purge` removes everything including configuration and data.
</Tip>

## Selecting an environment in a session

---

A persistent **environment selector** (environment chip) sits at the **bottom of the chat input area** and lets you specify which Environment the current session runs in. Clicking it expands three options:

| Option | Meaning |
|---|---|
| **Auto** | AI SRE automatically picks the best available environment: uses an online Runner if one exists in your account, otherwise falls back to the cloud sandbox. This is the default for new sessions. |
| **Cloud Sandbox · Default** | Forces the system-managed cloud sandbox, ignoring any self-hosted Runners. |
| **Self-hosted Environment** | Lists all visible Runners in your account. Select a specific one. **Offline / unconnected Runners are grayed out and not selectable** — you can see they exist, but you cannot select a Runner that is currently offline. |

The bottom of the selector also has an **"Add self-hosted Environment"** link that takes you directly to the Environments page to create a new Runner.

<Warning>
The environment selection **persists with the session** and is **locked for the lifetime of a session**: the environment determined when the session's first message is sent is recorded and used for all subsequent turns — it does **not** change if you switch the selector afterward. To use a different environment, create a new session.
</Warning>

When you open a historical session, the selector shows the environment that session was originally locked to, in read-only mode, along with its current status. If the originally bound Runner is now offline or deleted, the chip is marked with a red dot indicating "Offline / Deleted". Clicking it shows the reason and provides a "Go to Environments" link. In this state the session cannot accept new messages — you need to bring the corresponding Runner back online, or create a new session using the cloud sandbox instead.

## Scope

---

Like other Customize resources (Skills, Knowledge Packs, MCP, A2A Agents), every Environment has a two-level scope field `team_id`:

| Scope | `team_id` | Visibility |
|---|---|---|
| Account | `0` | Visible to all members in the account |
| Team | `>0` | Visible and editable only by members of that team |

In the Environments list, the Scope column shows an **Account** chip for account-scoped records and the corresponding **team name** for team-scoped records. The ScopeBar above the list lets you filter by account or team.

**Edit permissions** follow the unified rules:

1. Account owner or account admin → can edit any Environment.
2. Team member → can edit team-scoped Environments belonging to their team.
3. There is no "creator override" — you do not need to be the creator to edit under the above rules.

**How sessions pick a Runner (runtime visibility)**:

<Note>
Scope is a tag for **editing and ownership** — the **account is the only security boundary at runtime**. When a session needs to fall back or automatically select a Runner, the system picks one from **all online BYOC Runners in that account** by matching tags; the auto-selection does not hard-filter by team. Assigning a Runner a team-level scope primarily controls "who can see and edit it in the console", not "which sessions can use its compute".
</Note>

If a session is **bound to a team** (for example, launched from a war room incident or explicitly assigned a team in the UI), that team's Skills, MCP, and Knowledge are prioritized for assembly within the session, while compute scheduling for the Environment still uses the account as the boundary. For the full mechanism of team binding and on-demand mounting, see [Custom Resources and Scope](/en/ai-sre/customize).

## Troubleshooting

---

When investigating Runner issues, start by checking the **Status** and **Last heartbeat** columns in the Environments list — these fields directly reflect whether AI SRE currently recognizes the Runner.

<AccordionGroup>
<Accordion title="Runner shows Offline" icon="bug">
  **Offline** status means the Runner connected at some point, but AI SRE has not received a heartbeat from it in approximately **90 seconds** and has marked it as disconnected. Common causes and how to investigate:

  - **Process has exited**: Log in to the target machine and check whether the Runner process or systemd service is running (`systemctl status flashduty-runner`). A crash or OOM kill will interrupt heartbeats.
  - **Machine or network interruption**: The machine shutting down, going to sleep, losing network connectivity, or having its egress to AI SRE blocked by a firewall will all prevent heartbeats from reaching AI SRE.
  - **How to recover**: Restart the Runner and keep it running — it will reconnect automatically and resume heartbeats. The list status will return to Online after the next heartbeat.
</Accordion>

<Accordion title="Runner stays Pending / never connects" icon="wrench">
  **Pending** status means this Environment record has **never** successfully connected since it was created. Check each of the following:

  - **Was the installation command fully executed?** Confirm that `curl ... | sudo TOKEN=... URL=... bash` ran without errors and the binary was installed.
  - **Does the Token match?** The `TOKEN` the Runner uses must be exactly the Token for this Environment. Using a Token copied from a different Environment or an old record will cause authentication to fail and the connection will not be established. You can retrieve and verify the Token by clicking the Token button in the list row.
  - **Is the connect address reachable?** The `URL` (WebSocket address) the Runner dials must be **reachable from the target machine**. Verify connectivity to that address from the machine first, then investigate further up the stack.
</Accordion>

<Accordion title="Sending a message shows 'connection timeout' or gets no response" icon="server">
  Session execution requires an **online** Environment. When the selector is pinned to a specific Runner and that Runner is not online, AI SRE does not silently reassign the session elsewhere (sessions are locked one-time) — it blocks the session and reports that the Environment is unavailable. How to handle this:

  - Confirm that the selected Runner shows **Online** in the Environments list. If it is offline or pending, recover it using the steps above first.
  - Temporary workaround: switch the selector to **Auto** or **Cloud Sandbox** to let the session use the cloud fallback. Note that environment binding is one-time — **existing sessions** already locked to an offline Runner cannot be reassigned. You need to **create a new session** and switch there.
  - If the Runner shows Online but execution still times out, the issue is most likely between the Runner's machine and the target resource (database, internal API, etc.) rather than between the Runner and AI SRE — investigate network and permissions on the target resource side.
</Accordion>
</AccordionGroup>

<Tip>
The fastest way to determine "where the problem is": check the status first. **Offline / Pending** means the issue is between the Runner and AI SRE (check heartbeat, check the process, check egress). **Online but execution fails** means the issue is between the Runner and the resource being investigated (check the target resource's network and permissions).
</Tip>
