## Overview

An automation lets AI SRE run a **hidden session** on a cadence you set. The session does not appear in the session list in the left sidebar of the console. Instead, it runs in the background from a fixed **task prompt**. The agent completes the work and produces results such as routine inspections, operational insights, or incident post-mortems.

Each automation is a **rule**. A rule carries at least one trigger:

- **Schedule (cron)**: set the cadence with a 4-field or 5-field cron expression (for example, every Monday morning or every day at 09:15); it runs automatically when the time comes.
- **Call via API**: generate a trigger URL with a Bearer token. An external system triggers the rule on demand with a `POST` and passes the context for the run in the request body.
- **On-call incident trigger**: select the On-call channels and severities to watch, then start a diagnostic run when a matching incident appears.
- **War room created**: select the channels and severities to watch, then start a diagnostic run when a matching incident gets a war room. This run's session lives in the war room's IM group chat, not in the console.

When to use it: hand recurring routine inspections (such as a daily health check) and periodic insight / post-mortem reports to AI SRE to run automatically. Or wire AI SRE into your existing pipeline, change system, or On-call incident flow so an event kicks off a diagnosis.

Entry point: **AI SRE → Automations** in the left navigation.

<Note>
Every run produced by an automation is, at its core, still an AI SRE session — it is marked as hidden and not mixed into your everyday session list. A run at the **Web** execution place can always be opened from the run history to see the full conversation, tool calls, and artifacts. The conversation of an **IM** run (including **War room created** runs) is in the IM group and cannot be opened from the console; see "Execution place" below.
</Note>

## Creating an automation

The page header offers two ways to create a rule. **Create via chat** opens a session with a prefilled prompt. The agent asks questions to work out the task and its schedule, so there's no form to fill in. **Create** opens a start panel with two entry points:

<Steps>
  <Step title="Start from scratch">
    Choose **Start from scratch** to open a blank form and manually fill in the name, task prompt, and triggers. This suits cases where you already know what you want the agent to do and want a fully custom prompt.
  </Step>
  <Step title="From a preset template">
    Below, a set of **preset template** cards is listed (shown in Chinese or English to match the UI language). Common ones include **Weekly On-call Review**, **Alert Governance**, **On-call Incident Analysis**, and **On-call Load Analysis**. Click any template card to prefill the form with the template's name and task prompt; tweak from there.
  </Step>
</Steps>

A template's create form can also be opened by link from other pages: `/ai-sre/automations/new?template=TEMPLATE_KEY`. If the link also carries `oncall_incident_channel_ids=ID1,ID2`, the channels of the **On-call incident** trigger are preselected. Such links can be shared and still work after a refresh.

Either entry point leads to the same configuration form. Both console entries always create a rule at the **Web** execution place; to run a rule in an IM chat, create it from that IM conversation:

### Create from an IM conversation (bound to the current session)

When you ask the agent in an IM group or direct chat to create an automation without naming an execution place, the rule is bound to **this conversation** and inherits its scope (including the bound team). The CLI equivalent is to omit `--run-in` when running `flashduty automation create` from an IM conversation (see [CLI](/en/developer/cli)).

- After binding, runs happen in that chat instead of creating sessions in the console; the bound chat is fixed. How the session is opened depends on the chat: with **AI SRE uses thread replies in regular group chats** turned on in the integration, each run opens a new session; with it off, or in a direct chat, the run continues the session that chat already has.
- To run it on **Web** instead, say so at creation (ask for execution on the Web console in the conversation, or add `--run-in web` on the CLI). It cannot be changed afterwards; recreate the rule.
- Do not pass chat, platform, integration, or session IDs yourself; the server resolves and authorizes the current session.

## Configuration fields

The configuration form has the following fields:

| Field | Required | Notes |
|---|---|---|
| Name | Yes | The rule name, up to 255 characters. Placeholder example: `Weekly on-call insights`. |
| Scope | Yes | Use the **scope selector** to choose **Personal** or a **Team**. Scope determines the rule's ownership and edit permissions. It also limits the self-hosted Runners you can select in **Environment** to account-global Runners and Runners of the scope's team. A scope cannot be changed after creation; the rule detail page shows it as **Pinned scope**. |
| Environment | No | Use the **environment picker** to choose the runtime environment: **Auto** (the system picks the best available environment, the default), **Cloud Sandbox**, or a **self-hosted (BYOC) Runner**. After picking a team scope, a team Runner that does not belong to that scope is cleared automatically. A rule at the **IM** execution place does not use the environment chosen here (see "Execution place" below). |
| Task prompt | Yes | Describe the task for AI SRE to perform, written in a rich-text editor. This prompt is exactly what is sent to the agent on each run. Placeholder: `Describe the task for Flashduty AI SRE to perform.` |
| Time zone | No | A field on the **Schedule** trigger card (see "Schedule (cron)" below): the **rule time zone** the cron expression is read in. Pick an IANA zone name (for example `Asia/Shanghai`) from a searchable dropdown; the options are ordered by their UTC offset. On create it defaults to your effective time zone (member time zone first, falling back to the account time zone). When no zone is available the field is left empty and the create request omits it. |

<Note>
For **Environment**, "Auto" has the system pick the best available environment at each run; "Cloud Sandbox" is a platform-managed ephemeral sandbox; a self-hosted Runner runs on your own machine. See <a href="/en/ai-sre/environments">Environments</a> for the differences and how to connect them.
</Note>

## Execution place (where a rule runs)

Each rule has an **execution place**, fixed at creation and not editable in the console afterwards:

- **Web** (default): each run is a hidden session in the console. A rule created in the console always has this value.
- **IM**: runs happen in the IM group or direct chat the rule was bound to at creation. A retry of the same run reuses that session (and its thread when thread replies are on); the bound chat never changes. A **War room created** run does not run in this chat — it opens its own session in the war room's group. How a run opens its session depends on the chat:
  - **AI SRE uses thread replies in regular group chats** is on for this IM integration: each run **opens a new session** in the group and a new thread.
  - That setting is off, or the run is in a direct chat: the run continues the chat's current session and is appended as an ordinary message, so it sees the conversation earlier in that session. A new session is created only when the chat has none yet, or has just been reset with `/new`.

The **Where it ran** column of the rule list and the same item in the detail page's configuration show this value (`IM` or `Web`). When one rule enables **War room created** along with other triggers, the column shows two badges: **War room → IM** and **Other triggers → Web**. **War room created** is the only trigger that ignores the rule's execution place; it runs in the war room's own group (see "War room created" below).

A rule at the **IM** execution place differs from a Web rule in a few ways:

- The console offers no **Clone**; to switch to Web, recreate the rule.
- The console does not expose these runs' sessions: the run history shows `-` in the Name column, clicking the row only shows **This analysis is in IM. Open IM to view it.**, and running it manually from the rule row does not open a session.
- It does not use the rule's **Environment**; it uses the environment already chosen in that chat (change it with `/env` in the conversation). The form still shows the environment picker, but it has no effect on IM runs.
- **A stale binding skips the run**: if the bound chat's scope or session has changed when a run fires (for example `/scope` changed the bound team in the group, or the group started a new session), the run is **skipped**, with status `Skipped` and a reason line saying the bound chat's scope or session has changed. The rule stays enabled and is never moved to another chat; recreate the rule to change chats.

### Specifying it through the API or CLI (`run_in`)

Console-created rules are always **Web**. When creating through the API or CLI, set `run_in` explicitly:

| Field | Type | Description |
|---|---|---|
| `run_in` | string | `current-chat`: bind the rule to the **live IM conversation** the caller authenticated from; only valid when the call is made from that IM conversation, and rejected anywhere else. `web`: run in the console. When omitted, calls from an IM conversation use `current-chat` and all others use `web`. |
| `team_id` | int64 | The rule's scope. An explicit `0` means personal; a value above `0` is a team in the account. When omitted, a call from an IM conversation inherits that conversation's scope. With `run_in=current-chat`, an explicit value must match the conversation's scope. |

`update` does not accept `run_in`: like scope, the execution place cannot be changed after creation. For the CLI flags see [CLI](/en/developer/cli).

## Triggers

A rule must have **at least one trigger** configured. The current console form exposes **Schedule**, **Call via API**, **On-call incident**, and **War room created** in the "Triggers" section, and all four can be enabled at the same time.

### Schedule (cron)

Runs automatically on a time cadence. The cadence supports two cron forms:

- **4 fields**: `hour day-of-month month day-of-week`; the system adds `minute=0`, suitable for top-of-hour tasks.
- **5 fields**: `minute hour day-of-month month day-of-week`, suitable for minute-level tasks. For example, `15 9 * * *` means every day at 09:15.

6-field cron expressions with seconds are not supported. The minute must be one fixed integer; other fields support only the simple forms below:

| Segment | Allowed values |
|---|---|
| Minute (5-field only) | A fixed integer from `0` to `59` |
| Hour | `*`, `*/n` (`n` from 1 to 23), or one fixed integer from `0` to `23` |
| Day of month | `*` or `1`–`31` |
| Month | `*` or `1`–`12` |
| Day of week | `*` or `0`–`7` (both `0` and `7` mean Sunday) |

You can't set both day of month and day of week: one of the two must be `*`, or the save is rejected with this message under the cron field: "Do not set both a day of month and a day of week. Change one of them to *." A 4-field expression works the same way, so its day of month and day of week also can't both be set.

To avoid hand-writing the expression, the UI offers four modes:

| Mode | Meaning |
|---|---|
| Hourly | Runs once per hour; defaults to the top of the hour, and can also use a fixed minute |
| Daily | Pick a time; runs at that time every day |
| Weekly | Pick a weekday + time; runs at that time each week |
| Custom | Type a 4-field or 5-field cron expression directly |

<Warning>
**Time zone**: **Schedule** runs use the **Time zone** chosen on the trigger card; all four modes (**Hourly / Daily / Weekly / Custom**) share this setting.
</Warning>

<Note>
The actual execution time may differ from the set time by a **few minutes**. This is intentional, to spread out system load. Do not treat a rule as a second-accurate timer.
</Note>

Suppose you edit a rule that is **enabled** and already has its next run scheduled. If you change the cron expression or the **time zone**, the trigger card shows a note: **the occurrence that is already scheduled and has not started yet (`<time>`, `<old zone>`) will not run. The next one is recalculated on the `<new zone>` clock, and its real start can be up to 5 minutes later than that minute.**

The note appears only when the schedule actually changes. Switching the time zone between an empty value and `UTC` doesn't count, because both use the same clock. The note also doesn't appear when the **Schedule** trigger is off or the rule has no pending run.

### Call via API (HTTP POST)

Lets you trigger this automation on demand from an external system, independent of a time cadence.

<Steps>
  <Step title="Enable and save">
    Add **Call via API** under "Triggers" and save the rule. On a successful save, the system generates a one-time **Token** and **trigger URL** for triggering, and opens a dialog containing a `curl` example.
  </Step>
  <Step title="Save the Token">
    The Token is **shown only once**: copy and save it immediately. After you close the dialog you cannot view it again — you can only regenerate (rotate) a new one, and regenerating invalidates the old Token.
  </Step>
  <Step title="Trigger externally">
    Call the trigger URL with `POST`, placing the Token in the `Authorization: Bearer` header, and pass the context for this run in the `text` field of the request body. The `curl` example shown in the dialog looks like:
  </Step>
</Steps>

```bash
curl -X POST 'https://<trigger-url>' \
  -H 'Authorization: Bearer <token>' \
  -H 'Content-Type: application/json' \
  -d '{"text":"Describe the event or context for this run."}'
```

The `text` in the request body is passed to the agent as context for this run, on top of the task prompt configured on the rule.

On success, `data` returns the new hidden session. Save `session_id`, or use `session_url` to open the full conversation, tool calls, and artifacts for this run:

```json
{
  "data": {
    "type": "routine_fire",
    "session_id": "<session-id>",
    "session_url": "https://<console>/ai-sre/chat?session_id=<session-id>"
  }
}
```

<Tip>
A rule can enable **both** "Schedule" and "Call via API" at the same time: it runs automatically on the cadence and can also be kicked off on demand from outside. Each trigger occupies its own row and can be **removed** independently.
</Tip>

### On-call incident trigger

Add the **On-call incident** trigger when you want AI SRE to start automatically from On-call incidents. Only incidents matching the selected channels and severities start a run.

<Steps>
  <Step title="Add the trigger">
    Click the **On-call incident** card in "Triggers". The form expands channel and severity conditions.
  </Step>
  <Step title="Select channels">
    Select the On-call channels to watch in the **Channel** dropdown. Personal-scope rules can select visible account channels; team-scope rules narrow the channel list to the selected team.
  </Step>
  <Step title="Select severities">
    Select one or more severities from `Critical`, `Warning`, and `Info`. When this trigger is enabled, at least one channel and one severity are required.
  </Step>
  <Step title="Set similar-incident merging">
    **Merge similar incidents into one analysis** is on by default. If a new incident is similar enough to one that is already being analyzed, it joins that analysis instead of starting its own session. With it off, every incident is analysed separately. See [Merging similar incidents into one analysis](#merging-similar-incidents-into-one-analysis) for the rules.
  </Step>
</Steps>

If you create or update a rule through the API, use these fields:

| Field | Type | Notes |
|---|---|---|
| `oncall_incident_trigger_enabled` | boolean | Whether the On-call incident trigger is enabled. |
| `oncall_incident_channel_ids` | int64[] | On-call channel IDs to watch. Creating or enabling this trigger requires at least one valid ID. |
| `oncall_incident_severities` | string[] | Incident severities to watch. Supported values are `Critical`, `Warning`, and `Info`; creating or enabling this trigger requires at least one value. |
| `oncall_incident_merge_similar` | boolean | Whether **Merge similar incidents into one analysis** is on. On by default; omitting this field is treated as on. |

When a matching event arrives, the system creates a run with `trigger_kind: "oncall_incident"` and passes event context such as `incident_id`, `channel_id`, and `severity` into the session. The same incident — the same trigger and the same `incident_id` — always reuses the same run, avoiding duplicate hidden sessions for one incident. When the switch is on, a **different** incident that is similar enough to one under analysis also joins that run instead of starting its own session. See "Merging similar incidents into one analysis" below.

When the run finishes, AI SRE writes one summary comment back to the incident that triggered it. The comment puts the conclusion first, keeps the body concise, and ends with a link to the full session. The write-back record also carries a persistent **Continue conversation** entry. Use it to open the session straight from the conclusion on the incident timeline. See [Incident Timeline · AI SRE Action Records](/en/on-call/incident/search-view-incident#ai-sre-action-records). The comment travels through the incident's existing notification chain, such as incident card refreshes and thread replies in IM. Anyone watching the incident sees the analysis without opening the console. This applies to every rule with the On-call incident trigger enabled — including rules with custom prompts — with no extra configuration.

#### Merging similar incidents into one analysis

**Merge similar incidents into one analysis** (`oncall_incident_merge_similar`) is on by default. It decides whether an incident event starts its own session or joins an analysis already running under **the same rule**. When it is on, an incident that matches the trigger is first compared for similarity against that rule's runs:

- At a similarity of **0.9 or above**, the incident joins the highest-scoring analysis instead of starting a hidden session of its own. 0.9 is a fixed platform value, the same bar [intelligent grouping](/en/on-call/channel/noise-reduction) uses by default, and it does not move with a channel's grouping configuration.
- Below 0.9, the incident starts a run of its own as usual.
- With the switch off, no similarity comparison happens and every incident is analysed separately.

The candidates are the incident that analysis is working on plus the incidents already merged into it. The merge affects only AI SRE's run routing. **It doesn't combine the two incidents in Flashduty**, and the session's bound incident stays the same. Both incidents still exist, notify, and escalate on their own. A merged-in incident has no session of its own, so it also gets no summary comment of its own. If the analysis judges that it shares the root cause, it leaves a cross-reference comment on that incident's timeline and covers it in the conclusion.

In that analysis's chat, a merge appears as one process line: `Joined this analysis` + `#<num> <title>`, labeled `Similarity <score>` with two decimal places. The title is the merged incident's name and opens that incident's page in a new tab. In run history, that run likewise shows which analysis took it.

Two platform limits are fixed and not configurable:

- **One analysis takes in at most 20 incidents.** Once it is full it stops receiving similar incidents, and later ones start a new run, which carries on absorbing.
- **A finished run can only be joined within 60 minutes of finishing.** A run still `running` or `retrying` is always joinable. A run that finished well (`succeeded` / `partial`) stays joinable for 60 minutes after it completed, and after that a similar incident starts a new run. Failed, skipped, and abandoned runs are never joined.

<Note>
The similarity comparison requires the account's AIOps capability and a Pro or higher subscription. If AIOps is off or the edition doesn't qualify, no comparison runs, and every incident starts its own run.
</Note>

### War room created

Add the **War room created** trigger when you want AI SRE in the room as soon as an incident gets a war room. Only war-room creation events matching the selected channels and severities start a run.

<Steps>
  <Step title="Add the trigger">
    Click the **War room created** card in "Triggers". The form expands channel and severity conditions; severity is preselected as `Critical`.
  </Step>
  <Step title="Select channels">
    Select the channels to watch in the **Channel** dropdown. Personal-scope rules can select visible account channels; team-scope rules narrow the channel list to the selected team. When this trigger is enabled, at least one channel is required.
  </Step>
  <Step title="Select severities">
    Select one or more severities from `Critical`, `Warning`, and `Info`. When this trigger is enabled, at least one severity is required.
  </Step>
</Steps>

<Note>
This run's session is created in the war room's **IM group chat**, not in the console — the trigger card states "The session is created in the IM group chat." and adds a platform caveat: due to platform limits, this may not apply to WeCom and DingTalk integrations.
</Note>

If you create or update a rule through the API, use these fields:

| Field | Type | Notes |
|---|---|---|
| `war_room_trigger_enabled` | boolean | Whether the war-room-created trigger is enabled. |
| `war_room_channel_ids` | int64[] | Channel IDs to watch. Creating or enabling this trigger requires at least one valid ID. |
| `war_room_severities` | string[] | Severities to watch. Supported values are `Critical`, `Warning`, and `Info`; creating or enabling this trigger requires at least one value. |

When a matching war room is created, the system creates a run with `trigger_kind: "war_room_created"` and passes context such as `incident_id`, `channel_id`, and `severity` into the session. This run does not open a new console session: it runs an analysis directly in the war-room group, and the conclusion is posted back into that group. Under one trigger, a single incident starts only one run — a repeated event does not open a second session.

**Environment**: this trigger does not use the rule's **Environment** — an analysis in the war room uses the execution environment already chosen for that group. When the war room is a rule's only trigger, the form hides the environment picker and only says "Analysis in the war room uses the execution environment already chosen for that group. This rule does not pick one." When the rule also enables the schedule / API / incident triggers, the picker stays and shows "Schedule, API, and incident triggers use the execution environment chosen here. The war room trigger uses the group's execution environment and does not change that choice."

The preset template **War room initial analysis** (template key `war_room_initial_analysis`, category **Incident Response**) prefills this trigger and the `Critical` severity; the channels are not prefilled, so you pick them yourself.

## Run history

Every rule keeps its run history. Click a rule row to open its detail page: the left column shows **Configuration** and the right column shows **Run History**. The **Run manually** button at the top of the right column triggers a run directly. That button does not appear when **War room created** is the rule's only trigger — those runs happen in the IM group, so the rule has no console run.

Run history is shown as a table with these columns:

| Column | Notes |
|---|---|
| Name | The title of the run's hidden session, or the session ID if it can't be resolved; `-` for a run at the **IM** execution place (its conversation is in the IM group). A run merged into another analysis has no session of its own, so this shows its incident (`#<num> <title>`) and, on the line below, the analysis it joined |
| Started at | The start time of the run |
| Duration | How long the run took |
| Triggers | The trigger type of the run, such as `Schedule`, `HTTP POST`, `On-call incident`, `Run manually`, or `War room created` (war_room_created) |
| Where it ran | Where the run happened: `IM` (the session is in the IM group, as for a war-room-created run) or `Web` (a hidden session in the console) |
| Status | The status of the run (see the table below) |

Run status values:

| Status | Meaning |
|---|---|
| `running` | Running |
| `retrying` | Retrying |
| `succeeded` | Succeeded. A run at the **IM** execution place succeeds as soon as its request is in that chat's session, and **Duration** stops there: later silence in the chat, a tool failure, or a follow-up from you does not change the run's status. A run at the **Web** execution place settles only when the analysis ends with a final reply |
| `partial` | Partially succeeded |
| `failed` | Failed |
| `skipped` | Skipped. Three situations share this status. The trigger decided not to run, for example because the rule's owner is inactive or the schedule stopped. The incident joined another running analysis (see "Merging similar incidents into one analysis" above). Or, for a rule at the **IM** execution place, the bound chat's scope or session had changed when it fired (see "Execution place" above) |
| `blocked` | Blocked. The run produced real output but stopped at a connector that needs a human. The connector isn't set up yet, or an admin must complete its authorization in the console |
| `abandoned` | Abandoned (terminated by the system after running too long without completing) |

Three filters are available above the table:

- **Time range**: defaults to the **last 30 days**, adjustable, with a maximum span of **180 days**.
- **Status**: filter by the run statuses above, or choose **All statuses**.
- **Trigger type**: choose from `All trigger types` / `Run manually` / `Schedule` / `HTTP POST` / `On-call incident` / `War room created`.

Run records returned by the API also include `trigger_kind`, which can be `schedule`, `manual`, `http_post`, `oncall_incident`, `war_room_created`, or `debug`. `manual` means the run was started through the run-now API, `oncall_incident` means it was started by a matching On-call incident event, and `war_room_created` means it was started by the war-room-created trigger (its session is in the IM group). A run with `execution_place` `im` returns no session identity: `session_id` and `joined_session_id` are empty and `result_json` is not sent, leaving only the status, time, and error fields. A run merged into another analysis has no `session_id` of its own. Instead, `joined_session_id` holds that analysis's session ID and `joined_session_name` holds its session name. If both are empty, the run has its own hidden session.

Click a row to jump to the chat page of the hidden session for that run, where you can view the full messages, tool calls, and artifacts of that run. A run that happened in IM (for example, one started by the War room created trigger) does not navigate; it shows the message **This analysis is in IM. Open IM to view it.** — you read that analysis in the IM group. A run merged into another analysis has no session of its own, so clicking it opens the analysis that took over the incident.

### The reason line on an unsuccessful run

When a run's status is `failed`, `blocked`, `abandoned` or `skipped`, the **Name** column shows the **reason** under the session name (hover for the full text). Common reasons:

| Reason | What to do |
|---|---|
| AI SRE is not enabled, or this period's credits or balance are used up; the run did not execute | Enable or top up on the AI SRE tab of **Payment → Plan** |
| The On-call subscription has expired or its plan does not include AI SRE; AI SRE is paused | Renew or upgrade on the On-call tab of **Payment → Plan** |
| The run did not finish in time and was abandoned | Click **Run manually** on the rule detail page to retry |
| The run was interrupted | Click **Run manually** on the rule detail page to retry |
| The run ended without a final reply | Click **Run manually** on the rule detail page to retry |
| The bound chat's scope or session has changed; the run did not execute | The rule stays enabled and still runs in the original chat; recreate the rule to change chats |
| Joined another analysis | Click the row to open the analysis that took over the incident |

Other reasons show the text recorded by the system.

<Note>
Run history is shown on the rule's detail page, so viewing it requires edit permission on the rule.
</Note>

## Management and permissions

### Enable / disable, edit, and delete

Each rule offers a set of actions in the **Actions** column:

| Action | Notes |
|---|---|
| Enable / Disable | An inline switch. When disabled, the rule is kept but no longer triggers; disabling does not delete existing run history. |
| Run manually | Starts one real run manually from the rule row. The action performs preflight checks first. For a rule at the **Web** execution place it creates a hidden session and opens it; for an **IM** rule it starts in the bound IM chat, and the console only shows **Manual run submitted. Check the run history for progress.** Manual runs are limited to one per rule per minute. When **War room created** is the rule's only trigger, neither the list nor the detail page offers this action — such a rule produces no console run, and calling the run-now API returns an error. |

Clicking anywhere on the rule row opens its detail page, where you can edit the configuration, delete the rule, and view its run history (see "Run History" above).

Rules you **cannot edit** are view-only: you cannot toggle them or use their actions.

Above the list there are also two filters: **Scope** (All / Personal / Team, where selecting "Team" lets you multi-select specific teams) and **Status** (All statuses / Enabled / Disabled).

### Scope and permissions

Automation rules share the two-level scope used by other AI SRE resources. For the general rules, see [Scope and permissions](/en/ai-sre/context#scope-and-permissions). What is specific to automations:

- **A rule's scope can't be changed after creation.** To move a rule, click **Clone** on the rule detail page and pick a new scope for the copy (rules at the **IM** execution place have no Clone).
- A team rule keeps running after its creator leaves the team. A personal rule is disabled automatically once its creator is no longer an active account member.
- A **personal rule** can be viewed and managed only by its creator. Account owners and admins see it in the list, but opening its detail page is denied.
- **HTTP POST trigger** checks only the trigger URL's Bearer token: an external system holding the token can start a run, which creates a hidden session under the rule's personal or team scope. The On-call incident and War room created triggers don't use that token; their runs belong to the rule's scope in the same way.
