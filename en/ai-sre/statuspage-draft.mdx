## Overview

---

Publishing a status page event notifies subscribers immediately and appears on the public page within seconds — and it cannot be undone. That is why **the publish action always belongs to a person**. AI SRE's built-in `statuspage_draft` tool follows this principle: the Agent only **drafts**, validating and saving the draft server-side; you then review every field in the console's real publish form and press Publish yourself. The Agent never publishes or updates a status page event directly, under any circumstances.

A draft takes one of three shapes:

| Shape | Description |
|---|---|
| New incident | Draft a new event for an unexpected outage: title, initial status (Investigating / Identified / Monitoring / Resolved), message, and affected components |
| New maintenance | Draft a new event for planned maintenance: title, planned window, message, and affected components |
| Appended update | Draft a progress update (new status + message + component status changes) on an event that is **already open**, without creating a new event |

Before drafting, the Agent checks whether the target status page already has an open event covering the same issue. If it does, the Agent drafts an appended update instead of opening a second event — to customers, two events for the same incident read as two separate outages.

## Workflow

---

<Steps>
  <Step title="Ask the Agent to publish">
    In an AI SRE session, describe the status page update you want, for example "publish an incident about degraded web console performance" or "append an identified-status update to the open incident". Describe the affected components and the current status clearly, and the Agent drafts accordingly.
  </Step>
  <Step title="The Agent drafts and saves">
    The Agent calls the `statuspage_draft` tool, which submits the draft content (title, status, message, affected components, and so on) to the server for validation and storage. The validation rules match the console publish form, so a draft that passes is one that can actually be published.
  </Step>
  <Step title="Preview on the review card">
    A review card appears in the chat, rendered in the same style as the status page console: the title, the current status (or the planned maintenance window), the full message body (rendered Markdown), the affected components with their impact statuses, and the destination status page. If anything about the draft needs attention, the card lists it as a warning.
  </Step>
  <Step title="Click Review to open the publish form">
    Click the **Review** button on the card to open the corresponding publish form of the status page console in a new tab (the new-event form or the add-update form). The draft content is prefilled automatically from the draft ID in the link — no manual retyping.
  </Step>
  <Step title="Review and publish manually">
    Check every field in the form — especially **affected components** (the field reviewers most often need to correct) and **notify subscribers** — then click Publish. The publish action is yours; the Agent takes no part in it.
  </Step>
</Steps>

<Note>
Drafts are stored server-side, and the card link carries only the draft ID (in the form `?draft=<draft ID>`); the form reads the draft content from the server when it opens. So even if you refresh the page or reopen the link later, the content stays intact as long as the draft has not expired.
</Note>

## Card states

---

The review card queries the server for the draft's latest state, and its action button changes accordingly:

| State | Appearance | Meaning and action |
|---|---|---|
| Pending review | The **Review** button is clickable | The draft is valid and unpublished. Click to continue in the console form |
| Published | The button is disabled and reads "Published"; the destination becomes a clickable link | The draft has been published (by you or another member). Click the link to view the published event |
| Expired | The button is disabled and reads "Draft expired" | The draft has passed its retention period and been cleaned up (or does not exist). Ask the Agent to draft a new one |

## Draft rules

---

Storage and field constraints are enforced server-side:

| Rule | Description |
|---|---|
| Retention | A draft is retained for **30 days** after creation, published or not, and then deleted automatically |
| Publish count | Each draft can be published **exactly once**. Reusing it afterwards reports that it was already published, preventing duplicate events |
| Title | Required, 1–255 characters |
| Message | Required, Markdown format; supported elements match the console editor |
| Draft size | The full draft payload must not exceed **64 KB** |
| Maintenance window | For a new maintenance, the planned end time must be later than the planned start time |
| Affected components | Components must belong to the target status page; component statuses are validated per event type (incident: Operational / Degraded / Partial Outage / Full Outage; maintenance: Operational / Under Maintenance) |
| Event status | Incident: Investigating → Identified → Monitoring → Resolved; appended maintenance update: Scheduled / Ongoing / Completed. A new maintenance carries no status — whether the window advances automatically is the reviewer's choice in the form |
| Update target | An appended-update draft must point at an event of the same type (incident to incident, maintenance to maintenance) on the same status page |

<Warning>
Once published, a draft is marked as published and cannot be used again. To keep communicating progress after publishing, ask the Agent to draft a new appended update.
</Warning>
