## Overview

---

AI SRE has two kinds of "agent" resources. Both **extend the main agent's (AI SRE's) ability to collaborate and divide work**, but differ in direction and form:

<CardGroup cols={2}>
  <Card title="Subagents" icon="robot">
    Specialized workers spawned **inside this platform**, invoked by the main conversation or a Skill to execute a **self-contained task** — read logs, run a search, make a change, and so on. When done, they return the result to the parent agent.
  </Card>
  <Card title="A2A agents (Agent-to-Agent)" icon="satellite-dish">
    Registrations that point to **external agents**. AI SRE **delegates tasks to a remote agent** over the standard A2A protocol; at the same time, this platform's AI SRE also exposes an Agent Card that external A2A clients can call back into, for incident / war-room coordination and bidirectional event streams.
  </Card>
</CardGroup>

Both are dispatched through the same built-in tool, **`agent_dispatch`**: the main agent provides an `agent_name`, a `prompt`, and a short `title`; the platform immediately returns a `task_id` and resumes the parent conversation's turn. The dispatched agent runs in an isolated sub-session, and on completion re-injects its final result into the parent agent as a new message in the form of a `<task-notification>`.

<Note>
The dispatch result of both subagents and A2A agents appears in the conversation as the same kind of "task card (chip)": the icon distinguishes the type (subagent 🤖, A2A 🛰️), and the card shows the agent name, the intent of this task (`title`), the run status (initializing / in progress / completed / failed / interrupted / waiting for input / waiting for authorization), and usage such as tool-call count, tokens, and duration. Click the card to view the sub-session's full process in the right-hand panel.
</Note>

<Tip>
**The description is the core signal for agent selection.** Before dispatching, the main agent sees a "list of available agents," each item being `name (type): description`. Descriptions should be written as prescriptive imperatives (e.g. "USE THIS FIRST for ...", "prefer-over-X when ...") that state clearly **when it should be preferred, what it is good at, and what it is not suited for** — the more precise the description, the better the main agent dispatches the right task to the right agent.
</Tip>

## Subagents

---

A subagent is a specialized worker that **the main conversation or a Skill can invoke to execute a task**. It is spawned within this platform, has its own system prompt (role and methodology), toolset, and (optionally) model, runs in a sub-session isolated from the parent conversation, and returns only its **final message** to the parent agent — the intermediate tool output stays in the sub-session and does not pollute the parent conversation's context.

### Built-in subagents

AI SRE ships with out-of-the-box runtime subagents that `agent_dispatch` can call without any configuration:

<CardGroup cols={2}>
  <Card title="general" icon="user-gear">
    A general-purpose worker. It has full tool access (read, write, execute, web, skills, MCP), used to take on a self-contained task that can be described fully in one shot and return a self-explanatory result the parent agent can adopt directly.
  </Card>
  <Card title="explore" icon="magnifying-glass">
    A read-only explorer. It can only use `grep`, `glob`, and `read`, used to quickly locate evidence in a code base or knowledge dump and return a compact summary; it does not analyze, assume, or recommend — it leaves the conclusion to the parent agent.
  </Card>
</CardGroup>

<Note>
Built-in subagents are injected by the runtime at session start, do not appear in the resource list, and cannot be deleted or edited. They share the same `agent_dispatch` mechanism as your custom subagents.
</Note>

### Subagent configuration

Each custom subagent is defined by the fields below. `description` and `prompt` are key to shaping its behavior — the former decides **when it is selected**, the latter decides **how it works once selected**.

| Field | Type | Default | Description |
| --- | --- | --- | --- |
| `subagent_name` | string | — | The subagent identifier; `agent_dispatch` dispatches by this name. Unique within the account |
| `description` | string | — | The subagent description, the core signal for the main agent's selection; write it as a "USE THIS FIRST / prefer-over-X"-style imperative |
| `prompt` | string | — | The subagent's system prompt, the body of its role and methodology; once dispatched, this is its operating brief. The platform appends a common worker spec afterward (use absolute paths, no emoji, working directory resets on each tool call, etc.) |
| `max_steps` | int | `20` | The max number of reasoning / tool-call steps allowed per task; it stops on reaching the limit |
| `model` | string | inherits default | An optional model override (`provider/model` form); leave empty to use the account default model |
| `tool_allowlist` | string[] | empty (no extra restriction) | Further narrows the allowlist of tools available to this subagent. Empty means inherit the default (all available except platform-suppressed tools); non-empty exposes **only** the listed tools. For example, restrict a triangulation-only subagent so it cannot touch `bash`. Listing an already-suppressed tool (such as `agent_dispatch`) has no effect |
| `status` | enum | `enabled` | `enabled` / `disabled`. Only enabled subagents can be dispatched |
| `team_id` | int64 | `0` | Scope: `0` = account, `>0` = team. See "Scope" below |

<Warning>
Subagents currently exist as **account resources**, invoked in conversation via `agent_dispatch` and visualized in dispatch cards and the sub-session panel. They **do not yet have a standalone graphical management page**; during the beta, to create or adjust custom subagents, contact Flashduty for help configuring them. The built-in `general` / `explore` subagents work with no configuration.
</Warning>

### Dispatch and the sub-session panel

When the main agent calls `agent_dispatch`:

<Steps>
  <Step title="Dispatch">
    Provide `agent_name`, `prompt`, and a 4–8 word imperative `title`. The platform immediately returns a `task_id` (status `async_launched`) and resumes the parent turn — the parent agent **does not block waiting**, and can keep working or dispatch several parallel tasks at once.
  </Step>
  <Step title="Run">
    The subagent runs in an isolated sub-session `sub-<task_id>`. A live-refreshing task card appears in the parent conversation, showing in-progress status and accumulating usage.
  </Step>
  <Step title="View the process">
    Click the task card to open the sub-session's full conversation in the right-hand **subagent panel** (reusing the main chat-area components). The panel can expand to full width or split side by side with the main chat. While running, click "Stop subagent" to request an interruption.
  </Step>
  <Step title="Return the result">
    When the subagent finishes, its **final message** is re-injected into the parent conversation as a `<task-notification>`, and the main agent continues its answer accordingly. On failure / interruption, the card and panel show the full terminal error.
  </Step>
</Steps>

## A2A agents

---

A2A (Agent-to-Agent) agents connect AI SRE to the **external agent ecosystem**. There are two directions:

<CardGroup cols={2}>
  <Card title="Outbound" icon="arrow-up-right-from-square">
    The **remote A2A agents** registered in the list. AI SRE delegates tasks to them over the A2A protocol — also via `agent_dispatch`, sharing the same dispatch and card mechanism as subagents (task cards mark the A2A type with 🛰️).
  </Card>
  <Card title="Inbound" icon="arrow-down-to-bracket">
    This platform's AI SRE is itself an A2A agent and exposes an **Agent Card**. An external A2A client that fills in the Card address can call Flashduty's AI SRE back, for incident / war-room coordination and bidirectional event streams.
  </Card>
</CardGroup>

The list and management entry for A2A agents is the **Customize → Agents** page (the menu tab is **Agents**).

### Register an outbound A2A agent

On the A2A Agents list page, click **Add A2A agent** and fill in the form:

| Field | Type | Default | Description |
| --- | --- | --- | --- |
| Name | string | — | The A2A agent identifier (e.g. `metrics-analyzer`). Required |
| Scope | account / team | — | The scope: **account** (visible across the account) or a **team** (visible and editable only by that team's members). Required; see "Scope" below |
| Description | string | — | Briefly describe what this A2A agent does. It enters the main agent's "list of available agents" as a selection signal — write it as a prescriptive imperative |
| Card URL | string | — | The base URL of the remote A2A agent (e.g. `https://flashai.flashcat.cloud`). Required. The platform validates that it is a legal http/https address and rejects ones pointing at loopback, intranet, link-local, or cloud-metadata addresses (SSRF protection) |
| Auth type | enum | `none` | The credential type attached to outbound requests: `none` / `bearer` (Bearer Token) / `api_key` (custom Header + Key) |
| Streaming | bool | on | Whether to interact with the remote in streaming mode |
| Per-user auth mode | enum | `shared` | See the "Authentication modes" table below |

#### Authentication modes

A2A agents support three ways of supplying credentials, determining how different users provide credentials when calling the same remote agent:

<AccordionGroup>
  <Accordion title="Shared (shared, default)" icon="users">
    All users share one set of credentials, configured under "Auth type" (Bearer Token or API Key). Best when a team shares a single remote account.
  </Accordion>
  <Accordion title="Per-user key (per_user_secret)" icon="key">
    Each user provides their own key on the first call; the key is encrypted and stored at the account level. Configure a "Key Schema" with a Header name (required), placeholder, and help link (optional) to guide the user on the first call.
  </Accordion>
  <Accordion title="Per-user OAuth (per_user_oauth)" icon="shield-halved">
    Users each authorize through an OAuth 2.1 flow; an authorization window pops up automatically on the first call to the A2A agent, and credentials are stored per user once complete.
  </Accordion>
</AccordionGroup>

<Note>
For security, saved sensitive fields (such as `token`, `api_key`, `client_secret`) are returned **masked** when read. When editing, leaving a sensitive field empty means "keep the current value" rather than "clear it" — the stored credential is overwritten only when you explicitly change it.
</Note>

### Inbound: let external agents call AI SRE

On the A2A Agents page, expand the "**Let external agents call Flashduty's AI SRE**" panel at the top to get this account's AI SRE **Agent Card** address:

```
<your-endpoint-domain>/safari/a2a/ai-sre/agent-card
```

Fill this address into any A2A client to call Flashduty's AI SRE agent over the A2A protocol.

**Authentication**: add `Fd-App-Key: <your app_key>` to the request header (or use the `?app_key=` query parameter). The capabilities the Agent Card declares include:

| Skill | Description |
| --- | --- |
| `investigate_incident` | End-to-end root-cause a Flashduty incident, correlating logs, metrics, and recent changes |
| `analyze_logs` | Query and summarize a target service's logs within a given time window |
| `analyze_metrics` | Query and summarize a target service's metrics within a given time window |

<Tip>
The Agent Card also declares Flashduty's "run options" A2A extension: the caller can override `incognito` (whether to hide it in the session list, hidden by default), `visibility` (`private` / `account`), and the run environment (`cloud` / `byoc` with a specific `environment_id`) on demand in `message.metadata`. The extension is optional, and a plain A2A client can call normally without dealing with it.
</Tip>

### Incident and war-room coordination

When a session **enters via incident routing** (for example, AI SRE triggered from an incident or war room), the platform binds the corresponding `incident_id` to the run and surfaces it as session context in the main agent's prompt, so troubleshooting is anchored to the right incident from the start. Building on this, AI SRE can operate on the incident further within the conversation using built-in skills — read incident details, query the timeline, create / view a war room, correlate changes, and so on.

<Warning>
The **automatic coordination** between A2A and incidents is currently supported in concept and still evolving: incident auto-binding is a stub implementation today, and the bidirectional cross-agent event stream will be filled out version by version. Do not treat it as a fully available capability — during the beta, rely on the features actually enabled.
</Warning>

## Create and manage

---

The full lifecycle of A2A agents is managed on the **Customize → Agents** page. The built-in subagents work out of the box; custom subagents are configured with Flashduty's help during the beta (see above).

<AccordionGroup>
  <Accordion title="Create" icon="plus">
    A2A: click **Add A2A agent**, fill in name, scope, Card URL, authentication, and save. You must choose a definite scope (account or team) on creation; the submit button stays disabled until one is selected.
  </Accordion>
  <Accordion title="Enable / disable" icon="toggle-on">
    Toggle an A2A agent's enabled state with the switch in the list. Only **enabled** agents enter the main agent's available list and can be dispatched by `agent_dispatch`; once disabled, they are immediately invisible to dispatch. Subagents are likewise controlled by the `status` field.
  </Accordion>
  <Accordion title="Inspect / edit" icon="pen-to-square">
    Click any row in the list to open the form, where you can view and edit name, description, scope, Card URL, authentication config, streaming, and auth mode. Without edit permission the form is **read-only**.
  </Accordion>
  <Accordion title="Delete" icon="trash">
    Remove an A2A agent from the current scope. **Active sessions that delegate to it will fail.** Deletion has a confirmation prompt.
  </Accordion>
  <Accordion title="Filter by scope" icon="filter">
    The scope filter bar at the top of the list switches between "All," "Account only," and "a specific team," to focus the view amid many resources. Each row is also labeled with its scope (account / team name).
  </Accordion>
</AccordionGroup>

## Scope

---

Subagents, A2A agents, and the other Customize resources (Skills, Knowledge Packs, Connectors/MCP, Environments) share the same **two-level scope** model, determined by the `team_id` field on each row:

| `team_id` | Scope | Visibility |
| --- | --- | --- |
| `0` | Account | Visible to all members of the account |
| `>0` | Team | Visible only to that team's members |

**Edit permission**: the account owner or an account admin can edit any agent; a team member can edit team-scoped agents of **their own team**; there is no "creator keeps rights" exception. Without edit permission, the row appears **read-only** in the list.

**Runtime visibility**: at session start, the main agent's list of available agents surfaces only **account-scoped** resources and the resources of the **team the current session is bound to** (such as the team brought in by an incident / war room, or one explicitly selected in the UI). After the agent reads a team's knowledge (`.flashduty/knowledge/team_<id>/DUTY.md`), that team's Skills, connectors, and agents are mounted into the current session on demand. **The account is the only security perimeter at runtime; team is merely an ownership and editing label.**

<Note>
For the full description of the scope model (including permission rules and runtime loading details), see [Customize resources and scope](/en/ai-sre/customize).
</Note>
