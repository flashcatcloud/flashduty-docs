## Overview

---

A2A (Agent-to-Agent) is a standard protocol that lets different agents call one another. In AI SRE, the **A2A Agents** resource connects AI SRE to an external agent ecosystem in two directions:

<CardGroup cols={2}>
  <Card title="Outbound" icon="arrow-up-right-from-square">
    **Remote A2A agents** registered in the list. AI SRE **delegates** tasks to them via the standard A2A protocol — for example, an external agent that specializes in metrics analysis or integrates with an internal system.
  </Card>
  <Card title="Inbound" icon="arrow-down-to-bracket">
    AI SRE itself is an A2A agent and exposes an **Agent Card**. External A2A clients can add the Card URL to **call back into** Flashduty's AI SRE for incident / war room integration and bidirectional event streaming.
  </Card>
</CardGroup>

Delegation is **asynchronous**: after AI SRE hands a task to a remote agent it does **not block**, the conversation turn resumes immediately and can continue working or dispatch multiple tasks in parallel. When the remote agent finishes, its result is injected back into the conversation as a new message. Each A2A delegation appears in the conversation as a **task card** (🛰️) showing the remote agent name, task intent, run status (initializing / in progress / completed / failed / interrupted), and usage metrics such as tool call count, tokens, and elapsed time. Click the card to view the full delegation trace in the right-hand panel.

<Tip>
**Description is the core signal for agent selection.** Before delegating, AI SRE sees a list of available agents where each entry is `name: description`. Write descriptions as prescriptive imperatives (e.g. "USE THIS FIRST for ...", "prefer-over-X when ..."), clearly stating **when to prefer it, what it excels at, and what it is not suited for** — the more precise the description, the better AI SRE can route tasks to the right agent in the right context.
</Tip>

The A2A Agents list and management UI are in the **Customize → Agents** page (menu tab: **Agents**).

## Register an Outbound A2A Agent

---

On the A2A Agents list page, click **Add A2A Agent** and fill in the form:

| Field | Type | Default | Description |
| --- | --- | --- | --- |
| Name | string | — | Identifier for the A2A agent (e.g. `metrics-analyzer`). Required. |
| Scope | Account / Team | — | Visibility scope: **Account** (visible to all members in the account) or a specific **Team** (visible and editable only by members of that team). Required — see "Scope" below. |
| Description | string | — | A brief description of what this A2A agent does. It appears in AI SRE's available-agent list as a selection signal — write it as a prescriptive imperative. |
| Card URL | string | — | The base URL of the remote A2A agent (e.g. `https://flashai.flashcat.cloud`). Required. The platform validates that it is a valid http/https address and rejects loopback, private, link-local, or cloud-metadata addresses (SSRF prevention). |
| Auth type | enum | `none` | Credential type attached to outbound requests: `none` / `bearer` (Bearer Token) / `api_key` (custom header + key). |
| Streaming | bool | On | Whether to interact with the remote agent in streaming mode. |
| User-level auth mode | enum | `shared` | See "Auth Modes" below. |

### Auth Modes

A2A agents support three credential-supply modes that determine how credentials are provided when different users call the same remote agent:

<AccordionGroup>
  <Accordion title="Shared (shared, default)" icon="users">
    All users share a single set of credentials configured under "Auth type" (Bearer Token or API Key). Suitable when the whole team shares one remote account.
  </Accordion>
  <Accordion title="Per-user secret (per_user_secret)" icon="key">
    Each user provides their own secret key on first use; the key is encrypted and stored at the account level. Configure the header name (required), placeholder, and help link (optional) in "Secret Schema" to guide users on first call.
  </Accordion>
  <Accordion title="Per-user OAuth (per_user_oauth)" icon="shield-halved">
    Each user authorizes individually via an OAuth 2.1 flow. An authorization popup appears automatically on first use of the A2A agent, and credentials are stored per user after completion.
  </Accordion>
</AccordionGroup>

<Note>
For security, sensitive fields that have already been saved (such as `token`, `api_key`, and `client_secret`) are returned **masked** when you read them back. When editing, leaving a sensitive field blank means "keep the current value" — not "clear it." The stored credential is only overwritten when you explicitly change the field.
</Note>

## Inbound: Let External Agents Call AI SRE

---

Expand the "**Let external agents call Flashduty's AI SRE**" panel at the top of the A2A Agents page to get your account's AI SRE **Agent Card** URL:

```
<your access domain>/safari/a2a/ai-sre/agent-card
```

Add this URL to any A2A client to call Flashduty's AI SRE agent via the A2A protocol.

**Authentication**: include `Fd-App-Key: <your app_key>` in the request header (or use the `?app_key=` query parameter). The Agent Card advertises the following skills:

| Skill | Description |
| --- | --- |
| `investigate_incident` | End-to-end root-cause analysis for a Flashduty incident, correlating logs, metrics, and recent changes. |
| `analyze_logs` | Query and summarize logs for a target service within a specified time window. |
| `analyze_metrics` | Query and summarize metrics for a target service within a specified time window. |

<Tip>
The Agent Card also advertises Flashduty's "run options" A2A extension. Callers can override `incognito` (whether to hide the session in the session list; hidden by default), `visibility` (`private` / `account`), and the environment (`cloud` / `byoc` with a specific `environment_id`) in `message.metadata`. This extension is optional — plain A2A clients can ignore it and call normally.
</Tip>

### Incident and War Room Integration

When a session **arrives via an incident route** (for example, triggered from an incident or war room), the platform binds the corresponding `incident_id` to the run and surfaces it as session context in AI SRE's prompt, anchoring troubleshooting to the correct incident from the start. From there, AI SRE can use built-in skills to further act on the incident — reading incident details, querying timelines, creating / viewing war rooms, linking changes, and more. For IM-side war room auto-diagnosis, see [IM Integration](/en/ai-sre/im).

<Warning>
**Automatic incident integration** via A2A is conceptually supported and actively evolving: incident auto-binding is currently a placeholder implementation, and bidirectional event streaming across agents will be incrementally completed in future releases. Do not treat this as a fully production-ready capability — during the beta, only features that have been explicitly enabled should be relied upon.
</Warning>

## Create and Manage

---

The full lifecycle of A2A agents is managed on the **Customize → Agents** page.

<AccordionGroup>
  <Accordion title="Create" icon="plus">
    Click **Add A2A Agent**, fill in the name, scope, Card URL, and authentication settings, then save. You must select an explicit scope (account or team) before the submit button becomes active.
  </Accordion>
  <Accordion title="Enable / Disable" icon="toggle-on">
    Use the toggle in the list to switch an A2A agent's enabled state. Only **enabled** agents appear in AI SRE's available-agent list and can receive delegated tasks; disabling an agent makes it immediately invisible to delegation.
  </Accordion>
  <Accordion title="Inspect / Edit" icon="pen-to-square">
    Click any row in the list to open the form, where you can view and edit the name, description, scope, Card URL, auth configuration, streaming setting, and auth mode. If you do not have edit permission, the form is displayed as **read-only**.
  </Accordion>
  <Accordion title="Delete" icon="trash">
    Remove an A2A agent from the current scope. **Active sessions that have delegated tasks to it will fail.** A confirmation prompt is shown before deletion.
  </Accordion>
  <Accordion title="Filter by scope" icon="filter">
    The scope filter bar at the top of the list lets you switch between "All", "Account-level only", and a specific team, making it easy to focus on a subset of resources. Each row also shows a tag indicating its scope (account or team name).
  </Accordion>
</AccordionGroup>

## Scope

---

A2A agents share the same **two-level scope** model as other custom resources (Skills, Knowledge Packs, MCP, Environments), determined by the `team_id` field on each row:

| `team_id` | Scope | Visibility |
| --- | --- | --- |
| `0` | Account-level | Visible to all members in the account |
| `>0` | Team-level | Visible to members of that team only |

**Edit permission**: the account owner or account admin can edit any agent; team members can edit team-level agents within **their own team**. There is no creator-retains-rights exception. When you do not have edit permission, the corresponding row in the list is displayed as **read-only**.

**Runtime visibility**: at session start, AI SRE's available-agent list only includes **account-level** resources and resources belonging to the **team bound to the current session** (e.g. the team brought in by an incident / war room, or explicitly selected in the UI). A team's Skills, MCP, and A2A agents are only mounted into the current session on demand after the agent reads that team's knowledge (`.flashduty/knowledge/team_<id>/DUTY.md`). **The account is the only security boundary at runtime; team is an ownership and editing tag.**

<Note>
For the full scope model specification — including permission rules and runtime loading details — see [Custom Resources & Scope](/en/ai-sre/customize).
</Note>
