This page offers three independent paths. Complete the one that fits your current situation and stop when you reach its completion criteria; you do not need to follow all three in order.

<Warning>
Keep production systems read-only during your first use: ask AI SRE to query, analyze, and provide evidence. Product-configuration writes required to create Knowledge, install MCP, or create an Environment may still proceed after you confirm each one. Without your approval, do not make production changes, restart services, roll back, or send external notifications.
</Warning>

## 5 minutes: Investigate an existing incident

**Prerequisites**: Your account is on On-call Pro or higher and already has an incident.

<Steps>
  <Step title="Create a chat">
    Go to **AI SRE → Chat → New Chat**.
  </Step>
  <Step title="Insert an incident reference">
    Type `@` in the input box, search for the incident, and insert its reference. Before sending, confirm that the incident reference capsule appears in the input box.
  </Step>
  <Step title="Send your first investigation request">
    Send:

    > Analyze this incident. First list the investigation plan, then provide evidence for every conclusion. Do not make any production changes.
  </Step>
  <Step title="Review the investigation">
    Wait for AI SRE to show the investigation plan, tool calls, intermediate findings, and conclusion. Expand the tool calls to see what it queried and what each call returned.
  </Step>
</Steps>

### Completion criteria

You have an investigation with a plan, tool calls, and intermediate findings, and every conclusion maps to evidence. You can continue asking questions in the same context without pasting the incident details again.

### If it does not work

- AI SRE is missing: confirm that the account is on On-call Pro or higher and that the current member has access to AI SRE.
- `@` does not find the incident: confirm that the current account has an incident, that you are in the correct account, and that you can view the target incident.
- The message has no incident context: before sending, confirm that the reference capsule remains in the input box. If it was removed, type `@` and insert it again.
- You get a conclusion without evidence: confirm that you sent the complete request above, then ask, “Map each conclusion to the corresponding tool output or incident field.”

### Next step

Read [Console sessions](/en/ai-sre/sessions) for details about references, tool calls, follow-up questions, and session management.

## 15 minutes: Build your first team knowledge

This path does not depend on the previous one. Create a new session and use the team selector to bind the target team before sending the first message.

<Steps>
  <Step title="Start /init">
    In the session bound to the target team, type `/init` and send it.
  </Step>
  <Step title="Confirm the scope">
    Verify that the team AI SRE shows is the target team, then confirm the write scope. One `/init` session uses one scope throughout.
  </Step>
  <Step title="Complete the scan and correction">
    Let AI SRE scan channels, incidents from the last 30 days, teams, and members. Check its summary of services and frequent incidents, then add or correct anything missing.
  </Step>
  <Step title="Approve the first knowledge write">
    Continue until you have at least one `services.md` or runbook. Review the file list and summaries item by item, then explicitly approve the write; do not use a vague “OK” to skip item-by-item confirmation.
  </Step>
</Steps>

### Completion criteria

The target team's knowledge base contains at least one `services.md` or runbook that you approved item by item, and it is linked from `DUTY.md`. You can stop here; the next `/init` run continues from the existing knowledge.

### If it does not work

- The scope is not the target team: do not continue writing. Create a new session, bind the correct team before the first message, and run `/init` again.
- The scan is empty: confirm that the account has incidents and channels. For a new account, continue with the cold-start interview and enter service information manually.
- The write fails: confirm that you belong to the target team and can edit its knowledge base.
- AI SRE is about to write immediately: ask it to list every file it will create or update with a summary, then approve each item before it writes.

### Next step

Read the full [`/init` setup flow](/en/ai-sre/init) for all interview phases, outputs, and safety boundaries.

## 30 minutes: Connect a real data source

You can complete this path on its own. Based on where the target system is reachable, **choose one** of the following connection options. A public MCP server does not also require a Runner, and a BYOC-only Runner does not require an MCP server first.

### Option A: Public MCP server

<Steps>
  <Step title="Install a public MCP server">
    For a publicly reachable HTTP Streaming or SSE MCP server, go to **Plugins → MCP → Browse Marketplace**, choose a template, and click Install. Follow the new conversation to enter the endpoint, authorize credentials, and verify connectivity.
  </Step>
  <Step title="Confirm the MCP server is callable">
    Confirm that the MCP server appears in the list and that AI SRE can discover and call it in a conversation.
  </Step>
</Steps>

**Completion criteria for this option**: The MCP server is installed and callable by AI SRE.

### Option B: BYOC-only Runner

<Steps>
  <Step title="Deploy a BYOC Runner">
    If the target is in a VPC or private database, or you need to run a local command, open **Environments**, create a self-hosted Environment, and follow its setup guide to deploy the BYOC Runner on a machine that can reach the target.
  </Step>
  <Step title="Confirm the Environment is online">
    Wait for the Environment to show Online. AI SRE can use a read-only CLI directly on the Runner to query the target system. Configure a local MCP server only when the target tool itself requires MCP; it is not a prerequisite for the BYOC path.
  </Step>
</Steps>

**Completion criteria for this option**: The Environment shows Online; no MCP server is required.

### Shared final step: Run one read-only query

Create a chat in the corresponding Environment and ask AI SRE to use the installed public MCP server, or a read-only CLI directly on the BYOC Runner, to read a metric, list resources, or retrieve a recent record. Confirm that the output comes from the target system.

### Completion criteria

Your chosen connection option meets its completion criteria, and AI SRE successfully completes one read-only query against the target system.

### If it does not work

- A public MCP server cannot connect: check the endpoint, HTTP Streaming or SSE transport, credentials, TLS settings, and whether the service allows access from the cloud Sandbox.
- The Runner remains Pending or Offline: check the Runner process, Token, connection URL, outbound firewall, and last heartbeat.
- A read-only CLI on the Runner cannot reach the target: confirm that the session uses that Runner, then check the Runner's network path, read credential, and local permissions.
- The query is denied: first confirm that the credential has read access. For a public MCP server, check server authorization; for a BYOC Runner, check the read-only command allow rules. Do not broaden it to write access just to pass verification.

### Next step

Read [MCP (external tool connections)](/en/ai-sre/mcp) and [Environments (BYOC Runner)](/en/ai-sre/environments).
