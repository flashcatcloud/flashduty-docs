## Overview

---

AI SRE's capabilities can be extended through custom resources. In the console, you equip agents with skills, connect external tools, capture team knowledge, and specify where agents run — and the agent calls on those resources on demand when diagnosing incidents.

All custom resources are organized under three entry points, corresponding to the left-side menu in AI SRE:

<CardGroup cols={2}>
  <Card title="Plugins" icon="puzzle-piece">
    The `Plugins` menu. Contains three tabs: **Skill** (skills), **Agents** (remote A2A agents), and **MCP** (external tools). Extend what the agent can execute and whom it can delegate to.
  </Card>
  <Card title="Knowledges" icon="book">
    The `Knowledges` menu. Capture operational knowledge — DUTY.md, runbooks, and more — as Knowledge Packs that are mounted at session start or on demand for the agent to reference.
  </Card>
  <Card title="Environments" icon="server">
    The `Environments` menu. Manage your self-hosted environments (BYOC Runners). All tool calls, MCP connections, and skill executions run inside the selected environment.
  </Card>
</CardGroup>

<Note>
Whether a given entry point appears in the menu depends on whether you have the corresponding access permission for that account (see [Permission Model](#permission-model) below). Entry points you don't have access to will not appear in the navigation.
</Note>

## Scope: Account & Team

---

Every resource type under Customize (Skills, Knowledge Packs, MCP, A2A Agents, Environments) carries the same two-level scope field `team_id`:

- `team_id = 0` — **Account scope**: visible across the entire account.
- `team_id > 0` — **Team scope**: visible only to members of that team.

In the console this choice is presented as an "Account or Team…" scope selector; the "Scope" column in the list shows whether each row belongs to the "Account" or to a specific team.

| Resource Type | Console Entry | Account Scope (team_id=0) | Team Scope (team_id>0) |
|---|---|---|---|
| Skill | Plugins → Skill | Visible and loadable in all sessions account-wide | Visible only to that team's members; loaded only in that team's sessions |
| MCP | Plugins → MCP | Callable by all agents account-wide | Visible and editable only by that team's members |
| A2A Agent | Plugins → Agents | Visible account-wide; can be delegated to by AI SRE | Visible and editable only by that team's members |
| Knowledge Pack | Knowledges | Visible to all agents account-wide | Loaded only in that team's sessions |
| Environment | Environments | Selectable in all sessions account-wide | Visible and editable only by that team's members |

<Tip>
The console describes this as: "Account scope is visible across the entire account; team scope is visible only to members of that team." For Knowledge Packs specifically: "Account-scoped knowledge is visible to all agents in the account. Team-scoped knowledge is loaded only in that team's sessions. Each target can have at most one Pack."
</Tip>

When a resource does not belong to your team, the list marks it as "Read-only (other team)" — you can view it, but you cannot edit it.

## Permission Model

---

Edit permissions mirror Flashduty's integration (fc-datasource) team permission rules, but **without the "creator retains rights" clause**. Rules are evaluated in the following order:

1. **Account owner** or **account admin** (RBAC role id = `2`) → can edit **any** resource in the account (any scope).
2. **Team member** → can edit team-scoped resources belonging to **their own team**.
3. **No creator privilege** → a resource's creator does not gain any extra edit rights simply by having created it.

<Note>
Account-scoped (team_id=0) resources can only be edited by account owners or account admins; regular team members can see them but cannot modify them. When an edit is denied, the agent receives an explanatory message indicating which resource it belongs to, your role, and which teams you can write to (to facilitate "fork to your team").
</Note>

### List API Conventions

The list endpoint for every resource type follows the same envelope:

| Field | Type | Default | Description |
|---|---|---|---|
| `team_ids` | `[]int64` | empty | Filter by team; if omitted, no restriction applies |
| `include_account` | `bool` | `true` | Whether to also include account-scoped (team_id=0) rows |

Every row in list and detail responses carries `team_id`, `team_name`, and `can_edit`, which the console uses to render the "Scope" column and to enable or disable buttons. On create/update, `team_id` is a required field and can be reassigned to a different scope on update.

## How Resources Are Loaded at Runtime

---

Visibility rules in the **edit UI** and in a **running session** are two separate systems — understanding this distinction helps you predict which resources an agent will actually have access to during a session.

**At session start**, the resources exposed to the agent in its prompt are limited to:

- All **account-scoped** resources (team_id=0); plus
- Resources belonging to the **team bound to the current session** (for example, brought in by a war room incident or explicitly selected in the console).

Skills and MCP from other teams will **not** appear in `<available_skills>` / `<available_mcp_servers>` at session start.

**On-demand mounting during a session**: when the agent reads a team's knowledge entry point (`.flashduty/knowledge/team_<id>/DUTY.md`), that team's full bundle — skills, MCP, and knowledge — is mounted into the **current session** as a persistent `<system-reminder>`, making it visible and usable by the agent from that point forward.

<Note>
**The account is the only security boundary at runtime**; the team is merely an ownership and editing label. This means any team's resources within the same account can be legitimately mounted during a session by the agent reading that team's knowledge; resources from other accounts are never visible under any circumstance.
</Note>

The following flow illustrates on-demand mounting step by step:

<Steps>
  <Step title="Session starts">
    The agent sees account-level resources and the resources of the session's bound team.
  </Step>
  <Step title="A team's knowledge is referenced during diagnosis">
    During incident investigation, the agent reads `.flashduty/knowledge/team_<id>/DUTY.md` — typically because the incident is owned by or involves that team.
  </Step>
  <Step title="That team's resources are mounted into the session">
    The team's skills, MCP, and knowledge are immediately mounted into the current session, and the agent can call on them right away.
  </Step>
  <Step title="Resources remain available for the rest of the session">
    The mount is retained as a persistent system-reminder until the session ends.
  </Step>
</Steps>
