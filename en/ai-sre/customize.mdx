## Overview

---

You extend what AI SRE can do through Customize resources. In the console you equip the Agent with skills, connect external tools, capture team knowledge, and decide where it runs — and the Agent draws on these resources on demand while diagnosing an incident.

All Customize resources live under three entry points, matching the AI SRE left-hand menu:

<CardGroup cols={2}>
  <Card title="Plugins" icon="puzzle-piece">
    The `Plugins` menu. It has three tabs: **Skill**, **Agents** (subagents and A2A agents), and **MCP** (connectors). They extend the capabilities the Agent can execute and the agents it can delegate to.
  </Card>
  <Card title="Knowledges" icon="book">
    The `Knowledges` menu. Capture operational knowledge such as DUTY.md and runbooks as Knowledge Packs, loaded at session start or on demand for the Agent to retrieve.
  </Card>
  <Card title="Environments" icon="server">
    The `Environments` menu. Manage your self-hosted environments (BYOC Runners). The Agent's tool calls, MCP connections, and Skill execution all run in the selected environment.
  </Card>
</CardGroup>

<Note>
Whether an entry point appears in the menu depends on whether you hold the matching access permission in that account (see [Permission model](#permission-model) below). Entry points you lack permission for do not appear in the navigation.
</Note>

## Scope: account and team

---

**Every** kind of resource under Customize (Skills, Knowledge Packs, Connectors/MCP, subagents, A2A agents, Environments) carries the same two-level scope field, `team_id`:

- `team_id = 0` — **account scope**: visible across the entire account.
- `team_id > 0` — **team scope**: visible only to members of that team.

In the console this choice appears as an "account or team…" scope selector; the "Scope" column in each list shows whether the row belongs to the "account" or to a specific team.

| Resource type | Console entry | Account scope (team_id=0) | Team scope (team_id>0) |
|---|---|---|---|
| Skill | Plugins → Skill | Visible and loadable in every session in the account | Visible only to team members, loaded only in that team's sessions |
| Connector MCP | Plugins → MCP | Callable by every Agent in the account | Visible and editable only by team members |
| Agent (subagent / A2A) | Plugins → Agents | Visible in the account, delegatable by the orchestrating agent | Visible and editable only by team members |
| Knowledge Pack | Knowledges | Visible to every Agent in the account | Loaded only in that team's sessions |
| Environment | Environments | Selectable by every session in the account | Visible and editable only by team members |

<Tip>
The console phrases it this way: "Account scope is visible across the entire account; team scope is visible only to members of that team." For knowledge: "Account-scoped knowledge is visible to every Agent in the account. Team-scoped knowledge is loaded only in that team's sessions. Each target can have at most one Pack."
</Tip>

When a resource does not belong to a team you are in, the list marks it "read-only (other team)" — you can view it, but not edit it.

## Permission model

---

Edit permission mirrors the team permission rules of Flashduty integrations (fc-datasource), but **drops the "creator keeps rights" clause**. The rules are evaluated in this order:

1. **Account owner** or **account admin** (RBAC role id = `2`) → can edit **any** resource in the account (any scope).
2. **Team member** → can edit team-scoped resources of **their own team**.
3. **No creator privilege** → creating a resource grants no extra edit rights to the creator.

<Note>
Account-scoped resources (team_id=0) can be edited only by the account owner or an account admin; an ordinary team member can see them but cannot change them. When an edit is denied, the Agent receives an explanatory message stating the resource's ownership, your role, and the teams you can write to (to make "fork into your team" easy).
</Note>

### List API convention

The list API for every resource type follows the same envelope:

| Field | Type | Default | Description |
|---|---|---|---|
| `team_ids` | `[]int64` | empty | Filter by team; omit to apply no restriction |
| `include_account` | `bool` | `true` | Whether to also include account-scoped rows (team_id=0) |

Every list and detail row stamps `team_id`, `team_name`, and `can_edit` on the response, which the console uses to render the "Scope" column and the enabled/disabled state of buttons. On create / update, `team_id` is a required field and can be reassigned to another scope on update.

</Warning>

## How loading works at runtime

---

Resource visibility follows two different rule sets in the "editing UI" versus the "session runtime" — understanding this helps you anticipate which resources the Agent can actually use within a single session.

**At session start**, the resources exposed to the Agent in the prompt are limited to:

- All **account-scoped** resources (team_id=0); plus
- The resources of the **team the current session is bound to** (for example, brought in by a war-room incident, or explicitly selected in the console).

Other teams' Skills / MCP do **not** appear in `<available_skills>` / `<available_mcp_servers>` at the start of the session.

**On-demand mounting during a session**: when the Agent reads a team's knowledge entry point (`.flashduty/knowledge/team_<id>/DUTY.md`), that team's entire set of resources — Skills, MCP, and knowledge — is mounted into the **current session** as a persistent `<system-reminder>`, visible and usable by the Agent from that moment on.

<Note>
**The account is the only security perimeter at runtime**; team is merely an ownership and editing label. That is, the Agent may legitimately mount any team's resources within the account during a session by reading that team's knowledge; cross-account resources are never visible under any circumstances.
</Note>

The following flow illustrates "on-demand mounting" intuitively:

<Steps>
  <Step title="Session starts">
    The Agent sees account-scoped resources plus the resources of the team the session is bound to.
  </Step>
  <Step title="Reference a team's knowledge during diagnosis">
    While locating the incident, the Agent reads `.flashduty/knowledge/team_<id>/DUTY.md` — usually because the incident belongs to or involves that team.
  </Step>
  <Step title="That team's resources mount into the session">
    The team's Skills, MCP, and knowledge mount into the current session, and the Agent can call them immediately.
  </Step>
  <Step title="Resources stay available for the rest of the session">
    The mount persists as a system-reminder until the session ends.
  </Step>
</Steps>
