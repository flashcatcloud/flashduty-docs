## Overview

---

AI SRE's capabilities can be extended through extensible resources. In the console you equip the agent with skills, connect external tools (MCP), capture team knowledge, and specify where the agent runs — and the agent will load these resources on demand when diagnosing incidents.

These resources are managed through three entry points, corresponding to the AI SRE left sidebar menu:

<CardGroup cols={2}>
  <Card title="Plugins" icon="puzzle-piece">
    The `Plugins` menu. Contains three tabs: **Skill** (skills), **Agents** (remote A2A agents), and **MCP** (external tools). Extends the capabilities the agent can execute and the parties it can delegate to.
  </Card>
  <Card title="Knowledges" icon="book">
    The `Knowledges` menu. Captures operational knowledge such as DUTY.md and runbooks as Knowledge Packs, which are mounted at session start or on demand for the agent to consult.
  </Card>
  <Card title="Environments" icon="server">
    The `Environments` menu. Manages your self-hosted environments (BYOC Runners). Tool calls, MCP connections, and Skill execution all run inside the selected environment.
  </Card>
</CardGroup>

<Note>
Whether a menu entry is visible depends on whether you have the corresponding access permission for that account. Entries you do not have access to will not appear in the navigation.
</Note>

## Scope: Account and Team

---

**Every** resource type in AI SRE (skills, knowledge, MCP, A2A agents, environments) carries the same two-level scope field `team_id`:

- `team_id = 0` — **Account scope**: visible to everyone in the account.
- `team_id > 0` — **Team scope**: visible only to members of that team.

In the console this choice appears as an "Account or Team…" scope selector; the "Scope" column in the list indicates whether a row belongs to the account or a specific team.

| Resource type | Console entry | Account scope (team_id=0) | Team scope (team_id>0) |
|---|---|---|---|
| Skill | Plugins → Skill | Visible and loadable in all sessions across the account | Visible only to that team's members; loaded only in that team's sessions |
| MCP | Plugins → MCP | Callable by all agents across the account | Visible and editable only to that team's members |
| A2A agent | Plugins → Agents | Visible account-wide; can be delegated to by AI SRE | Visible and editable only to that team's members |
| Knowledge Pack | Knowledges | Visible to all agents in the account | Loaded only in that team's sessions |
| Environment | Environments | Selectable by all sessions across the account | Visible and editable only to that team's members |

<Tip>
The console phrases this as: "Account scope is visible to everyone in the account; team scope is visible only to members of that team." For knowledge, it adds: "Account-scoped knowledge is visible to all agents in the account. Team-scoped knowledge is loaded only in that team's sessions. Each target can have at most one Pack."
</Tip>

When a resource does not belong to your team, the list marks it as "Read-only (other team)" — you can view it, but you cannot edit it.

**Edit permissions**: the account owner or an account administrator can edit any resource in the account; team members can edit team-scoped resources in their own team (no "creator retains rights" exception). Each resource page documents its own permission specifics.

## How Resources Are Loaded at Runtime

---

Resource visibility follows two separate rule sets — one for the "edit UI" and one for "session runtime". Understanding this helps you predict which resources the agent can actually use in a given session.

**At session start**, the resources exposed to the agent in the prompt are limited to:

- All **account-scoped** resources (team_id=0); plus
- Resources belonging to the **team bound to the current session** (for example, brought in by a war room incident or explicitly selected in the console).

Skills and MCP servers from other teams will **not** appear in `<available_skills>` / `<available_mcp_servers>` at the beginning of the session.

**On-demand mounting during the session**: when the agent reads a team's knowledge entry (`.flashduty/knowledge/team_<id>/DUTY.md`), that team's full resource bundle — skills, MCP, and knowledge — is mounted into the **current session** as a persistent `<system-reminder>`, and becomes visible and available to the agent from that point on.

<Note>
**The account is the only security boundary at runtime**; teams are simply ownership and editing labels. This means the agent can legitimately mount resources from any team within the same account by reading that team's knowledge during a session; resources from other accounts are never visible under any circumstances.
</Note>

The following steps illustrate the on-demand mounting flow:

<Steps>
  <Step title="Session starts">
    The agent sees account-level resources and the resources of the session's bound team.
  </Step>
  <Step title="Team knowledge referenced during diagnosis">
    During incident investigation, the agent reads `.flashduty/knowledge/team_<id>/DUTY.md` — typically because the incident is owned by or involves that team.
  </Step>
  <Step title="That team's resources are mounted into the session">
    The team's skills, MCP servers, and knowledge are immediately mounted into the current session and the agent can call them right away.
  </Step>
  <Step title="Resources remain available for the rest of the session">
    The mount persists as a permanent system-reminder until the session ends.
  </Step>
</Steps>
