Data masking decides which content in an AI SRE session is replaced with a placeholder before it is sent to the model. Use it when a session touches production passwords, access tokens, or customer personal data: the agent can still investigate without receiving the original values.

## Open the masking settings for a session

Open **More** in the top-right of an AI SRE session and select **Data masking**. The item appears only when your deployment has data masking enabled.

Masking is per session: each session keeps its own rules and word list, and a change applies to that session only. Once enabled, everything the session sends to the model is replaced first, including messages already stored in the session and credential values actually injected into the execution environment.

## How masked content appears

A replacement looks like `[MASK_PASSWORD_3f9a…]`. The model sees only the placeholder, never the original value.

| Term type | In the session UI | Notes |
| --- | --- | --- |
| **Data term** | Restored to the original value | For content you need to read yourself, such as host names and email addresses |
| **Secret term** | Always shows the placeholder | Never displayed again after saving, for anyone including you |

Content caught by automatic detection (passwords, tokens, email addresses, and so on) is handled as a data term.

## Automatic detection

**Automatic detection** is a set of category switches covering common credentials and personal data:

| Category | Covers | Default |
| --- | --- | --- |
| **Keys and passwords** | Access tokens, private keys, passwords inside connection strings | On |
| **Basic personal data** | Email addresses, phone numbers, national ID and bank card numbers | On |
| **Additional personal data** | Social security number, passport, IBAN, birthday, MAC address, device serial number | Selected; turn each one off as needed |
| **Operational identifiers** | Home directory, login and host name, public IP, bucket name | Off by default; turn on as needed |

Operational identifiers are off by default because those values are often exactly what you investigate (a public IP, a bucket name). Once turned on, they also reach the session only as placeholders.

## Custom terms

**Custom terms** cover values automatic detection misses. Enter one term per line:

- **Data term**: for example a host name or a customer domain. The UI restores it; the model always sees the placeholder.
- **New secret term**: for example a temporary password or a freshly rotated token. Not displayed after saving.
- **Ignore case**: match regardless of letter case.
- **Whole words only**: replace only complete words, so `db` is not replaced inside a longer identifier such as `db-proxy`.

## Custom formats

When your company has its own key format (an internally issued prefix, a token with a fixed shape), add a rule under **Custom formats**:

| Field | Description |
| --- | --- |
| **Rule category** | The category name shown for matches of this rule, for example `INTERNAL_TOKEN` |
| **Prefix** | Detect by prefix, for example `acme_` |
| **Regex** | Detect by RE2 regular expression, for example `acme_[A-Za-z0-9]{32}` |

Use either prefix or regex, not both. Verify the rule with the preview before saving.

## Private detection model

Names and addresses in free text have no fixed format; the **private detection model** detects this kind of content:

- Processed only inside Flashduty's own service, never sent to a model vendor.
- **Minimum confidence** sets the threshold; matches below it are left unmasked so ordinary text is not damaged.
- When your deployment has no private detection model configured, this section is unavailable; the other rules still apply.

## Preview and apply

**Preview** lets you verify rules before saving: enter sample text, select **Preview**, and the panel shows the masked result and how many items matched. The preview shows only the replacement, never the original value.

**Session summary** shows how many masked items this session has stored, split by category and by source (built-in rule, custom word, custom rule, detection model, and so on). Select **Save settings** to write the change; it takes effect for the session immediately.

## Limits

| Item | Limit (default) |
| --- | --- |
| Masked items per session | 1,000 |
| Length of one term | 16 KB |
| Text per preview or send | 256 KB |

Once the limit is reached, new terms are not saved. Clear custom terms you no longer need.

## FAQ

<AccordionGroup>
  <Accordion title="Can AI SRE still locate the problem after masking?">
    Yes. A placeholder keeps its category (for example `[MASK_TOKEN_…]`) and its position, so the model can still tell that a token appears here, in which log line and which service; it just cannot see the value. If you need to read the value in the UI, add it as a **data term** rather than a secret term.
  </Accordion>
  <Accordion title="Does a forked session inherit the masking rules?">
    When you fork a session or continue it into a new one, Flashduty re-checks your access to the source session and then carries its word list to the new session, so one line of investigation does not end up with two different masking results.
  </Accordion>
  <Accordion title="Does masking rewrite stored messages?">
    No. Stored content is unchanged; messages are replaced when they are next sent to the model, and the original record stays as it is.
  </Accordion>
</AccordionGroup>
