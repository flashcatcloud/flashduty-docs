## Overview

---

A Knowledge Pack is the operational knowledge you hand to AI SRE: a `DUTY.md` file together with a set of runbooks, FAQs, service catalogs, cluster configs, and other files. When a session starts, the agent reads `DUTY.md` first, then follows the references inside it to fetch additional files on demand — bringing your team's incident-handling experience, naming conventions, and system topology into every diagnosis.

Each **target** (account or team) can have at most one Knowledge Pack:

- **Account-level** knowledge is visible to all agents under the account.
- **Team-level** knowledge is loaded only in sessions bound to that team, and is visible only to members of that team.

A Knowledge Pack is one type of AI SRE customizable resource and follows the unified two-level scope model. The scope rules for other resources (skills, connectors, agents, and runner environments) are consistent with this page — see [Customizable Resources & Scope](/en/ai-sre/customize) for the full picture.

<Note>
  Knowledge Pack content is used to **refine** the agent's domain context (persona, methodology, system knowledge) but does not override the system's security and behavioral guardrails. If a piece of knowledge instructs the agent to bypass safety rules, it is treated as unauthorized content and ignored, not as a higher-priority directive.
</Note>

## DUTY.md Structure

---

`DUTY.md` is the **catalog entry point** for the entire Knowledge Pack. It is itself the table of contents — the agent reads the full `DUTY.md` and then fetches other files on demand via `@filename` references. The system does not attach a separate file list alongside `DUTY.md`; the catalog is the body.

References use the `@<filename>` style, where the filename points to another file within the same Pack (flat naming, no directory hierarchy):

```markdown
# On-Call Knowledge Overview (DUTY.md)

## Service Catalog
Our core services and owners are listed in @services.md.

## Common Incident Playbooks
- API 5xx spike: see @runbook-api-5xx.md
- Database connection pool exhausted: see @runbook-db-pool.md

## Clusters & Environments
Production cluster topology and access methods are in @cluster.yaml.
```

After reading `DUTY.md`, the agent decides which `@references` to expand based on the current incident, then reads the corresponding files — substantive content lives in the referenced sibling files, while `DUTY.md` only holds the link list.

<Tip>
  This layered `@reference` architecture keeps `DUTY.md` concise and readable. `DUTY.md` acts as a map; runbooks, service catalogs, and configs are the detail pages it points to. The agent does not need to load all files into context at once — it expands only the branches relevant to the current incident.
</Tip>

**File constraints** (enforced at create and edit time):

| Constraint | Value | Notes |
| --- | --- | --- |
| Allowed extensions | `.md` `.yaml` `.yml` `.json` `.txt` `.sh` | Other extensions are rejected |
| Single file limit | 1 MiB | Cannot be saved if exceeded |
| Per-Pack limit | 5 MiB | The usage bar in the console reflects this quota |
| File count limit | 100 | No new files can be added once this limit is reached |
| Directory hierarchy | Not allowed | Filenames must be flat; `/` and subdirectories are not permitted |
| Dotfiles | Not allowed | Filenames cannot start with `.` |

## Creating and Editing

---

Go to **Customize → Knowledge Pack** to create, edit, enable/disable, and delete Knowledge Packs for your account or teams. The list shows each Pack's **name / scope / files / status / actions**, with a scope filter at the top to switch between account and team views.

<Steps>
  <Step title="Create a Knowledge Pack">
    Click **New Knowledge Pack**, fill in a **name** (optional — defaults to the target label if left blank), and choose a **scope**: account or a specific team. Each target can have only one Pack; targets that are already taken are hidden from the dropdown.
  </Step>
  <Step title="Edit files">
    Click a row in the list to open the viewer. The left panel shows the file tree; the right panel is an inline editor. Click **New File** to enter a filename (e.g. `runbook.md`), or use **Upload** to import a local file. Markdown files support both **Preview** and **Source** views. Click **Save** after editing.
  </Step>
  <Step title="Monitor usage">
    The **Usage** bar on the left shows real-time consumption against the 5 MB quota. The bar turns red when you are close to the limit, prompting you to clean up or split files.
  </Step>
  <Step title="Enable / Disable / Delete">
    Use the toggle in the list to **enable or disable** the entire Pack — when disabled, the files are retained but the Pack is no longer loaded into AI SRE sessions. **Delete** removes the Pack and all of its files.
  </Step>
</Steps>

**Reference consistency checks**: when you save a file, if an `@reference` inside it points to a file that does not exist in the Pack, a non-blocking `unresolved_reference` warning is returned (saving still succeeds). When you delete a file that is still referenced by other files, a `still_referenced_by` conflict is shown first, and you can choose to **force delete**.

<Note>
  The agent can also maintain the Knowledge Pack during a session using natural language — for example, "add a runbook", "update services.md", or "record this incident pattern". It will read, edit, and save directly within the scope of the current session, without you having to leave the conversation. Structured onboarding (initial setup) is handled by a dedicated guided flow, not the inline editor.
</Note>

## How the Agent Uses Knowledge

---

Knowledge is not injected into the prompt all at once; instead it follows a **catalog-first, expand-on-demand** approach:

<Steps>
  <Step title="Session start: load the catalog">
    When a session starts, the system inlines the `DUTY.md` for the current scope into the `<available_knowledge>` block of the prompt (without an attached file list). Sessions bound to a team load both the account-level and that team's `DUTY.md`; sessions with no team binding load only the account-level one.
  </Step>
  <Step title="Follow references to fetch files">
    After reading `DUTY.md`, the agent decides which `@references` to expand based on the current incident, then uses the `read` tool to fetch `knowledge/<scope>/<filename>` for the specific content. Files are pulled from storage on demand and written to the runner environment's working directory.
  </Step>
  <Step title="Mount other teams' knowledge on demand">
    When cross-team troubleshooting is needed, the agent reads `knowledge/team_<id>/DUTY.md`, and the system mounts that team's full knowledge bundle (DUTY.md and runbooks) along with its skills and connectors into the current session, persisting for the remainder of the session. Each team is mounted at most once per session.
  </Step>
</Steps>

<Tip>
  Cross-team mounting is triggered only when the agent **explicitly reads** a team's `knowledge/team_<id>/DUTY.md` — it cannot be accidentally triggered by vague file traversal. Once mounted, that team's knowledge, skills, and connectors remain available for the rest of the session.
</Tip>

## Scope and Visibility

---

Every Knowledge Pack carries a scope identifier `team_id`: `0` means account-level (globally visible within the account); a value greater than `0` means team-level (visible only to members of that team).

| Dimension | Account-level (`team_id = 0`) | Team-level (`team_id > 0`) |
| --- | --- | --- |
| Visibility | All agents / sessions in the account | Only sessions and members of that team |
| Edit permission | Account owner or account admin | Members of that team, or the account owner / admin |
| Shown in prompt | All sessions | Only sessions bound to that team |
| Readable at runtime | Entire account | Entire account (reading triggers mounting) |

**Edit permissions**: the account owner or an account admin can edit any Knowledge Pack. Team members can edit team-level Packs belonging to their team. There is no "creator retains extra rights" rule. The console grays out rows the current user cannot edit, and disables toggles and action buttons when `can_edit` is false.

**Runtime visibility**: at session start, the prompt surfaces only **account-level** resources plus resources belonging to the **team bound to the current session**. The binding comes from an explicitly specified team or the team associated with a war-room incident. Knowledge from other teams is mounted on demand during the session, when the agent reads that team's `DUTY.md`.

<Warning>
  The account is the only runtime security boundary; the team is an "edit / ownership" tag, **not** a "readable at runtime" boundary. This means any session within an account can read and mount knowledge from any other team in that account — this is the foundation of cross-team collaborative troubleshooting. If certain knowledge is sensitive to other teams within the account, evaluate carefully whether it is appropriate to include it in a Knowledge Pack.
</Warning>

This two-level scope model applies uniformly to all customizable resources within an account (skills, connectors, agents, and runner environments). See [Customizable Resources & Scope](/en/ai-sre/customize) for the complete rules.

## Best Practices

---

<AccordionGroup>
  <Accordion title="Treat DUTY.md as a catalog, not as body content" icon="book">
    Put only a link list and one-line pointers in `DUTY.md`; move all substantive content into sibling files referenced with `@`. This keeps the catalog concise and readable, and lets the agent expand only the branches relevant to the current incident, avoiding unrelated content consuming context.
  </Accordion>
  <Accordion title="One topic per file" icon="wrench">
    Each runbook should focus on one type of incident or one service (e.g. `runbook-api-5xx.md`, `runbook-db-pool.md`), using a clear filename as a semantic index. Because Packs use flat naming (no subdirectories), filename prefixes serve as your "directory structure".
  </Accordion>
  <Accordion title="Use structured file types where appropriate" icon="code">
    Structured information such as service catalogs, cluster topologies, and threshold configurations is well-suited to `.yaml` / `.json` (e.g. `services.md`, `cluster.yaml`), allowing the agent to both read and parse it directly. Script snippets can use `.sh`.
  </Accordion>
  <Accordion title="Keep references consistent" icon="bug">
    After adding or renaming a file, update the `@references` in `DUTY.md` and any related files at the same time. The `unresolved_reference` warning on save and the `still_referenced_by` prompt on delete will help you catch broken links promptly.
  </Accordion>
  <Accordion title="Put common content at account level, team-specific content at team level" icon="users">
    Use the account-level Pack for conventions shared across teams (naming standards, general troubleshooting methods, platform access patterns). Use team-level Packs for that team's service catalog, on-call playbooks, and upstream/downstream dependencies. Sessions bound to a team receive both.
  </Accordion>
  <Accordion title="Let the agent help you maintain it" icon="comments">
    When troubleshooting surfaces new incident-handling insights, ask the agent directly to "add a runbook" or "record this incident pattern". It will read, edit, and save within the current scope, writing the experience back into the Knowledge Pack — creating a continuously growing feedback loop.
  </Accordion>
</AccordionGroup>
