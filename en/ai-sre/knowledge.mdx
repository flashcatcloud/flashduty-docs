## Overview

---

A Knowledge Pack is the operational knowledge you hand to AI SRE: a `DUTY.md` file plus a set of runbooks, FAQs, service catalogs, cluster configs, and other documents. When a session starts, the agent reads `DUTY.md` first, then follows the references inside it to fetch additional files on demand — bringing your team's incident-handling experience, naming conventions, and system topology into every diagnosis.

Each **target** (account or team) can have at most one Knowledge Pack:

- **Account-level** knowledge is visible to all agents within the account.
- **Team-level** knowledge is loaded only in sessions bound to that team and is visible only to members of that team.

A Knowledge Pack is one of AI SRE's custom resources and follows the unified two-level scope model. The scope rules for other resources (Skills, MCP, A2A Agents, Environments) are consistent with this page; see [Custom Resources & Scope](/en/ai-sre/customize) for the full rules.

<Note>
  Knowledge Pack content is used to **refine** the agent's domain context (persona, methodology, system knowledge) — it does not override the system's safety and behavioral guardrails. If a knowledge file instructs the agent to bypass safety rules, that instruction is treated as unauthorized content and ignored, not as a higher-priority directive.
</Note>

## DUTY.md Structure

---

`DUTY.md` is the **table-of-contents entry point** for the entire Knowledge Pack. It is the catalog itself — the agent reads `DUTY.md` in full and then pulls other files on demand via `@filename` references. The system does not attach a separate file listing alongside `DUTY.md`; the catalog is the content.

References use the `@<filename>` style, where the filename points to another file in the same Pack (flat naming, no directory hierarchy):

```markdown
# On-call Knowledge Overview (DUTY.md)

## Service Catalog
See @services.md for our core services and their owners.

## Common Incident Procedures
- API 5xx spike: see @runbook-api-5xx.md
- Database connection pool exhausted: see @runbook-db-pool.md

## Clusters & Environments
See @cluster.yaml for production cluster topology and access details.
```

After reading `DUTY.md`, the agent decides which `@references` to expand based on the current incident, then reads the corresponding files — substantive content lives in the referenced sibling files, while `DUTY.md` holds only the link list.

<Tip>
  This layered `@reference` architecture keeps `DUTY.md` concise and readable. Think of `DUTY.md` as a map, with runbooks, service catalogs, and configs as the detail pages it points to. The agent doesn't need to load every file into context at once — it only expands the branches relevant to the current incident.
</Tip>

**File constraints** (enforced at create and edit time):

| Constraint | Value | Notes |
| --- | --- | --- |
| Allowed extensions | `.md` `.yaml` `.yml` `.json` `.txt` `.sh` | Other extensions are rejected |
| Per-file limit | 1 MiB | Files exceeding this cannot be saved |
| Per-pack limit | 5 MiB | The usage bar in the console reflects this quota |
| Max file count | 100 | No new files can be added once the limit is reached |
| Directory hierarchy | Not allowed | Filenames must be flat — no `/` or subdirectories |
| Dot files | Not allowed | Filenames cannot start with `.` |

## Creating and Editing

---

Go to **Customize → Knowledge Pack** to create, edit, enable/disable, or delete Knowledge Packs for your account or teams. The list shows each Pack's **Name / Scope / Files / Status / Actions**, and you can use the scope filter at the top to switch between account and team views.

<Steps>
  <Step title="Create a Knowledge Pack">
    Click **New Knowledge Pack**, enter a **Name** (optional — if left blank, the target label is used as the default), and select a **Scope**: account or a specific team. Each target can have only one Pack; targets that already have a Pack are hidden from the dropdown.
  </Step>
  <Step title="Edit files">
    Click any row in the list to open the viewer. The left panel shows the file tree; the right panel is an inline editor. Click **New File** and enter a filename (e.g., `runbook.md`), or use **Upload** to import a local file. Markdown files support both **Preview** and **Source** views. Click **Save** when done.
  </Step>
  <Step title="Monitor usage">
    The **Usage** bar on the left updates in real time to show current usage against the 5 MB quota. The bar turns red as you approach the limit, prompting you to clean up or split files.
  </Step>
  <Step title="Enable / Disable / Delete">
    Use the toggle in the list to **enable or disable** an entire Pack. When disabled, the files are preserved but the Pack is no longer loaded into AI SRE sessions. **Delete** removes the Pack and all its files permanently.
  </Step>
</Steps>

**Reference consistency checks**: when you save a file, any `@reference` that points to a file not found in the Pack generates a non-blocking `unresolved_reference` warning (the save still succeeds). When you delete a file that is still referenced by other files, you'll see a `still_referenced_by` conflict prompt and can choose to **force delete**.

<Note>
  The agent can also maintain the Knowledge Pack through natural-language requests during a session — for example, "add a runbook," "update services.md," or "record this incident pattern." It will read, edit, and save within the current session's scope directly, without you leaving the conversation. Structured onboarding (initial setup) is handled by a dedicated guided flow rather than the inline editor.
</Note>

## How the Agent Uses Knowledge

---

Knowledge is not bulk-loaded into the prompt all at once — it follows a **catalog-first, expand-on-demand** model:

<Steps>
  <Step title="Session start: load the catalog">
    When a session starts, the system inlines the `DUTY.md` for the current scope into the `<available_knowledge>` block of the prompt (no separate file list is attached). Sessions bound to a team load both the account-level and the team's `DUTY.md`; sessions with no team binding load only the account-level one.
  </Step>
  <Step title="Follow references to read files">
    After reading `DUTY.md`, the agent decides which `@references` to expand based on the current incident and uses the `read` tool to fetch `knowledge/<scope>/<filename>` for specific content. Files are pulled from storage on demand and placed in the environment's working directory.
  </Step>
  <Step title="Mount other teams' knowledge on demand">
    When cross-team troubleshooting is needed, the agent reads `knowledge/team_<id>/DUTY.md` — the system then mounts that team's full knowledge bundle (DUTY.md, runbooks) along with its Skills and MCP into the current session, and they remain available for the rest of the session. Each team is mounted at most once per session.
  </Step>
</Steps>

<Tip>
  Cross-team mounting is triggered only when the agent **explicitly reads** a team's `knowledge/team_<id>/DUTY.md` — it cannot be accidentally triggered by vague file traversal. Once mounted, that team's knowledge, Skills, and MCP remain available for the entire session.
</Tip>

## Scope and Visibility

---

Every Knowledge Pack carries a scope identifier `team_id`: `0` means account-level (visible account-wide), and a value greater than `0` means team-level (visible only to members of that team).

| Dimension | Account-level (`team_id = 0`) | Team-level (`team_id > 0`) |
| --- | --- | --- |
| Visibility | All agents / sessions within the account | Only sessions and members of that team |
| Edit permission | Account Owner or account admin | Members of that team, or account Owner / admin |
| Shown in prompt | All sessions | Only sessions bound to that team |
| Readable at runtime | Entire account | Entire account (mounting triggered by read) |

**Edit permissions**: the account Owner or account admin can edit any Knowledge Pack; team members can edit their team's team-level Pack. There is no "creator retains extra rights" rule. The console grays out rows the current user cannot edit and disables toggles and action buttons when `can_edit` is false.

**Runtime visibility**: at session start, the prompt exposes only **account-level** resources plus resources belonging to **the team bound to the current session**. The bound team comes from an explicitly specified team or from the team associated with the war-room incident. Other teams' knowledge is mounted on demand mid-session, when the agent reads that team's `DUTY.md`.

<Warning>
  The account is the only security boundary at runtime; the team is an "editing / ownership" tag — it is **not** a "readable at runtime" boundary. This means any session within the account can read and mount knowledge from any other team in the same account — this is what enables cross-team collaborative troubleshooting. If certain knowledge is sensitive to other teams within your account, consider carefully whether it belongs in a Knowledge Pack.
</Warning>

This two-level scope model applies consistently to all custom resources within the account (Skills, MCP, A2A Agents, Environments). See [Custom Resources & Scope](/en/ai-sre/customize) for the full rules.

## Best Practices

---

<AccordionGroup>
  <Accordion title="Use DUTY.md as a table of contents, not a content document" icon="book">
    Keep `DUTY.md` to link lists and one-line summaries; move all substantive content into sibling files referenced via `@`. This keeps the catalog concise and readable, and lets the agent expand only the branches relevant to the current incident without loading unrelated content into context.
  </Accordion>
  <Accordion title="One topic per file" icon="wrench">
    Focus each runbook on a single incident type or service (e.g., `runbook-api-5xx.md`, `runbook-db-pool.md`), and use clear, descriptive filenames as semantic indexes. Since Packs use flat naming (no subdirectories), your filename prefixes are your directory structure.
  </Accordion>
  <Accordion title="Use structured file types for structured data" icon="code">
    Service catalogs, cluster topology, and threshold configurations are well-suited to `.yaml` / `.json` (e.g., `services.md`, `cluster.yaml`), so the agent can both read and parse them directly. Script snippets work well as `.sh`.
  </Accordion>
  <Accordion title="Keep references consistent" icon="bug">
    Whenever you add or rename a file, update the `@references` in `DUTY.md` and any other files that point to it. The `unresolved_reference` warning on save and the `still_referenced_by` prompt on delete help you catch broken links promptly.
  </Accordion>
  <Accordion title="Account-level for shared conventions, team-level for team-specific content" icon="users">
    Put cross-team conventions in the account-level Pack (naming standards, general troubleshooting methods, platform access); put team-specific service catalogs, on-call runbooks, and upstream/downstream details in each team's Pack. Sessions bound to a team receive both.
  </Accordion>
  <Accordion title="Let the agent help you maintain it" icon="comments">
    When an incident surfaces a new handling approach, ask the agent directly to "add a runbook" or "record this incident pattern." It will read → edit → save within the current scope, writing the new knowledge back into the Pack and creating a continuous accumulation loop.
  </Accordion>
</AccordionGroup>
