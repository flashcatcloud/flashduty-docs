> AI SRE must be activated in the console, is available on On-call Pro or higher, and is billed on actual usage. See [Activation and billing](/en/ai-sre/overview#activation-and-billing).

## Overview

**MCP** (Model Context Protocol) lets AI SRE agents connect to external tools and data sources. Each **MCP server** is a standardized endpoint that exposes a set of tools (functions). Examples include querying GitHub issues, sending Slack messages, reading Kubernetes resources, and retrieving metrics from an observability platform.

After you configure and enable an MCP server in the console, agents **decide on their own** when an investigation needs an external capability. They call the tool directly, so you don't have to copy data back and forth.

<Warning>
This page covers the **"MCP" section inside the AI SRE console** — that is, **third-party MCP servers that agents call** (you bring external tools in for agents to use).

This is **different** from the [Flashduty MCP Server](/en/developer/mcp-server) in the developer docs: that is **Flashduty's own outbound MCP service**. It connects **Flashduty's capabilities to third-party AI clients** such as Claude or Cursor. One direction is "agents calling external services"; the other is "external clients calling Flashduty" — they are opposite flows, not the same thing.
</Warning>

## What is MCP

**MCP** (Model Context Protocol) is an open protocol. It describes, in one uniform format, which tools a server exposes, what parameters each tool accepts, and what each returns. Think of it as the "USB port" of the AI agent world. An agent can discover and call any MCP-compliant server without per-system adapter code.

In AI SRE, MCP extends an agent's capability from "built-in tools" to "any external system":

- You add an MCP server in the console (declaring its endpoint, transport, and authentication).
- At session start, enabled servers visible in the current scope become available to the agent.
- When needed, the agent discovers the tools that server provides and calls them directly.

<Tip>
**MCP versus Skills**: MCP provides **the ability to connect external tools**; a Skill provides **the methodology for orchestrating those tools to accomplish a class of tasks**. A Skill can declare which MCP server tool it needs inside `SKILL.md` using `mcp:server/tool` notation. See [Skills](/en/ai-sre/skills) for details.
</Tip>

## Installing MCP servers from the marketplace

Go to **Customize → Plugins → Overview** to see Flashduty's curated catalog of third-party MCP templates. Category tabs group the catalog: All / Observability / Cloud & Infrastructure / Database & Middleware / Code & Collaboration / Skill. Use the search box in the top-right corner to filter by name or description.

The **Recommended** block above the catalog suggests up to 3 templates based on the alert integrations configured in your account (ranked by alert volume over the last 30 days). Templates that are already installed, need a Runner, or that you cannot install are not recommended.

<Steps>
  <Step title="Find the template to connect">
    Click a template row or its **+** to open the **Connect** dialog. Templates that need a self-hosted Runner when the account has none are marked **Requires self-hosted Runner**; templates you are not allowed to install cannot be clicked.
  </Step>
  <Step title="Review the template and fill in the connection parameters">
    The dialog shows the template's vendor, official docs, description and example questions, followed by the connection parameters. **Shared** fields are used by the whole account; templates in member authorization (key) mode also ask for **your own API token**, which other members enter separately on first use.
  </Step>
  <Step title="Pick an execution environment and submit">
    Choose the **execution environment** to connect from (defaults to the session's environment). For systems reachable only from an internal network, choose a self-hosted Runner on that network. For templates in member authorization (OAuth) mode, click the **Authorize** button and finish authorization in the browser; see [Authentication](#authentication).
  </Step>
  <Step title="Confirm the result">
    The system creates the connector and tests the connection. On success, you can click an example question to start a chat prefilled with it. On failure, the error is shown and you can **Retry**. Templates that need a Runner can also have AI SRE install missing command-line tools on the Runner (such as Node.js for `npx` or uv for `uvx`).
  </Step>
</Steps>

<Note>
Connection parameters are fixed at the first submit; to change them later, edit the server under **Plugins → MCP**. If a connector with the same name already exists in the account, use it, or have an account owner or admin rename or delete it before connecting again.
</Note>

MCP servers installed from the marketplace record their source template and are **always Shared scope** (available to all members of the account). Each template can be installed only once per account.

<Warning>
Templates that **require a Runner** work only on a BYOC Runner you deploy; cloud Sandboxes do not support them. Of the 50 templates in the marketplace today, 23 are **HTTP Streaming** and need no Runner. 27 are **stdio** and need one. They include Alibaba Cloud OpenAPI, Alibaba Cloud Observability, Nightingale (n9e), Gitee, GreptimeDB, Prometheus, Grafana (Self-Hosted), Kafka (Confluent), AWS, ClickHouse, MySQL, PostgreSQL, Alibaba Cloud RDS, Redis, and MongoDB. They start locally through `uvx` / `npx`, so make sure the account has a working BYOC Runner before installing. See [Environments (BYOC)](/en/ai-sre/environments).
</Warning>

### Systems only Monitors can query

The catalog also lists **systems queried through Monitors** (currently Loki, VictoriaLogs and Oracle). They cannot be connected from the marketplace: once you add such a data source in Monitors, AI SRE can query it directly, without an address, token or Runner. Clicking one of these rows shows the account's data sources of that type. Click **Try it in chat** if some exist, or **Add more in Monitors →** if none do (requires permission to add data sources).

Some templates (such as Prometheus, MySQL, PostgreSQL, ClickHouse, Elasticsearch and SLS) support both a direct MCP connection and querying through Monitors. They are labeled `MCP · Monitors`, and you choose the access method when connecting.

<Note>
Row names share a namespace with template names: if a system already has a template of the same name, only the template row is shown. On a private deployment **without the Monitors module**, these rows and the Monitors access method are not shown.
</Note>

## Adding an MCP server

Go to **Customize → Plugins → MCP**. The list page has two entries in the top-right corner:

- **Add MCP**: opens a form for defining an MCP server by hand (its fields are listed under "Basic Fields" below).
- **Add in chat**: opens a session with a prefilled prompt. The agent asks whether you want to connect your own service or install an existing one, checks the plugin catalog first, and searches the web for candidates if nothing matches. The button appears only when the target scope is unambiguous (you have account-level permission, or exactly one of your teams is selected).

### Basic fields

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| Name | string | Yes | The server name, used as the identifier when agents call it (for example, `sqlite-explorer` in `mcp:sqlite-explorer/query`). Must start with a letter; may only contain letters, digits, `-`, and `_`; length 1–255. **Case-insensitive and unique** within an account; cannot duplicate a built-in server name. |
| Transport | enum | Yes | How the agent communicates with the server. See "Transport" below. |
| Scope | Shared / Team | Yes | The scope of this MCP server: **Shared** (visible account-wide) or a specific **Team** (visible only to members of that team). See "Scope" below. |
| Execution Environment | Cloud / BYOC Runners (multiple) | No | Where this server is available; if none are selected, it is available everywhere. Calls are always made from the session's own environment, so for services reachable only from an internal network select only Runners that can reach them. If the session's environment is not listed, see [Cross-environment connectors](#cross-environment-connectors). See [Environments (BYOC)](/en/ai-sre/environments). |
| Description | string | Yes | Describes what this server does, for identification in the list. |

<Note>
After an agent first lists a server's tools, the system generates an **AI description** shown in the list, and keeps it updated as the tools change.
</Note>

### Transport

| Transport | Use Case | Required Fields |
| --- | --- | --- |
| HTTP Streaming (recommended) | Remote MCP server accessed through an HTTP endpoint | URL (endpoint), optional Headers (JSON); HTTPS endpoints can optionally skip TLS certificate verification |
| SSE (standalone, legacy) | Legacy remote servers that only support Server-Sent Events | URL (endpoint), optional Headers (JSON); HTTPS endpoints can optionally skip TLS certificate verification |
| stdio (local command) | MCP server launched as a local subprocess on the machine where the Runner runs | Command, arguments (one per line), environment variables (JSON) |

<Warning>
**stdio is only available for BYOC environments** (Runner deployed on your own machine). Cloud Sandboxes cannot launch local subprocesses. If you are using a cloud environment, use **HTTP Streaming** or **SSE** instead, and ensure the MCP server is reachable from the Sandbox network. For differences between environments, see [Environments (BYOC)](/en/ai-sre/environments).
</Warning>

<Note>
stdio commands run on the **machine where the Runner is deployed**, not on your computer. Avoid personal paths such as `/Users/<name>/...`. Make sure the Runner has the required runtime installed, such as `uv` / `uvx` / `node` / `npx`, or the connection fails.
</Note>

There is a default timeout for both connection and tool calls: 10 seconds for connection, 60 seconds for tool invocation.

<Warning>
Enable "Skip TLS certificate verification" only when the HTTPS server uses a self-signed certificate and the network is controlled. Never enable it for untrusted public endpoints.
</Warning>

### Authentication

MCP servers support three **authorization modes** that determine how credentials are provided to the server:

<Tabs>
  <Tab title="Service authorization (default)">
    All sessions call with the same service identity. You write credentials directly into the server configuration. For HTTP/SSE transport, put them in the **Headers** (JSON), for example `{ "Authorization": "Bearer xxx" }`. For stdio transport, put them in the **environment variables** (JSON), for example `{ "API_KEY": "xxx" }`. Suitable for internal systems accessed with account-level service tokens.

    Values under the following key names (case-insensitive) are **encrypted at rest** and shown masked. All other entries are stored as-is, so put credentials under such key names (for example `Authorization`, `X-API-Key`, `GITHUB_TOKEN`):

    - names containing `KEY`, `SECRET`, `TOKEN`, `PASSWORD`, `PASSWD`, `CREDENTIAL` or `AUTHORIZATION`;
    - names with a segment (split on non-alphanumeric characters) that is exactly `PWD` or `PASS` (such as `REDIS_PWD`, `db-pass`; `BYPASS` and `COMPASS` do not count).

    Any session in the account can call the system with this identity. For personal data or high-risk write operations, use member authorization instead.
  </Tab>
  <Tab title="Member authorization (key)">
    Each member provides their own key on **first use**. Keys are encrypted and isolated per member.

    Selecting this mode requires filling in a **Key Schema**:

    | Field | Required | Description |
    | --- | --- | --- |
    | Header Name | Yes | The HTTP header into which the credential is injected in MCP requests (for example, `X-Api-Key`) |
    | Help Link | No | Link to documentation explaining how to obtain the key |

    Suitable for third-party SaaS where each engineer uses their own API key (for example, a personal GitHub token).
  </Tab>
  <Tab title="Member authorization (OAuth)">
    Each member authorizes individually through **OAuth 2.1**; an authorization window pops up on first use. Dynamic Client Registration (DCR) is supported; authorization servers that support Client ID Metadata Documents instead of DCR also work without extra configuration. Tokens are stored per member and refreshed automatically before they expire. Suitable for services that support OAuth.
  </Tab>
</Tabs>

<Note>
In member authorization modes, a tool call with missing credentials pauses and prompts the current member to enter a key or authorize, then continues.
</Note>

### MCP server authorization (settings)

Member authorization credentials (key or OAuth) are isolated per member. Besides authorizing when prompted in a chat, you can manage your own authorization from the MCP list; both paths save the same credential.

**Authorization status**: the **Member authorization** column of the MCP list shows your own status:

- **Member authorization (OAuth)**: **● Connected** / **○ Disconnected**.
- **Member authorization (key)**: **● Saved** / **○ Not set**. The key is not checked for validity.
- Both modes: **⚠ Expired** (the OAuth token has expired and needs reauthorization).

Service authorization shows a dash ("—"). Click the authorization entry to open the **Credential** dialog; it manages only your own credential and does not change the server's configuration.

**Actions in the Credential dialog**:

- **Member authorization (OAuth)**: choose an **execution environment** (the cloud Sandbox or an online BYOC Runner. "Auto" is not available), then click **Authorize** or **Reauthorize** and finish in the browser window, with no tokens to copy. For OAuth services reachable only from an internal network, choose a Runner that can reach them. The last environment that authorized successfully and is still online is preselected.
- **Member authorization (key)**: click **Enter Key** or **Update Key**.
- **Revoke**: deletes your saved credential.

## Management & inspection

The MCP list shows each server you added with its name and description, scope (Shared or team), transport and enabled state. You can filter by All / Shared / Team and search by name, description, transport or URL. The built-in Flashduty MCP server is not listed.

<AccordionGroup>
  <Accordion title="Enable / Disable" icon="toggle-on">
    Toggle the switch in the list. Only **enabled** servers are available to the agent; disabled servers are invisible to agents and cannot be called.

    A disabled connector cannot be used from the **Connect** entry and does not appear in the enabled section of **Plugins → Overview**. An account owner or admin must re-enable it under **Plugins → MCP**.
  </Accordion>
  <Accordion title="Edit" icon="pen-to-square">
    Click the edit button (or click the row) to open the form. You can modify the name, transport, description, endpoint/command, authorization mode, and scope. If you do not have edit permission, the form opens in **read-only** mode with an explanation.
  </Accordion>
  <Accordion title="Delete" icon="trash">
    Removes the MCP server from the current scope. **Agents that depend on it will no longer be able to access its tools**, and active sessions currently using it will fail. A confirmation prompt is shown before deletion.
  </Accordion>
</AccordionGroup>

### Inspection: Viewing the tools a server exposes

The console does not list the tools an MCP server exposes, because the same server may be reachable with different tools in different environments.

<Tip>
To confirm which tools an MCP server exposes in a given environment, ask the agent in **Chat** to list that server's tools. It shows the tools and how to use each one. See [Conversations](/en/ai-sre/sessions).
</Tip>

<Note>
Reading Flashduty incidents, alerts and other data is a **built-in** agent capability (the Flashduty MCP server). It is available by default and is not configured here.
</Note>

### Cross-environment connectors

An MCP server may be bound to execution environments **other than the current session's**. Because environments do not share a network, the session cannot call it directly, but the agent knows it exists:

- The agent sees the connector's name, purpose and available environments, and asking for it by name gets an explanation rather than "not found".
- The agent dispatches a subagent into the target environment to call it (see [Agents](/en/ai-sre/agents)) and brings the result back to the conversation.
- Only **online** account-level Runners, Runners of the team bound to the session, and the bound cloud environment are valid targets. For others the agent explains it cannot use them right now.
- Only the main session can dispatch this way; subagents cannot dispatch further.

Conversely, to make a connector directly usable **here**, add the current environment to that server's Execution Environment list (provided the server is reachable from this session). See [Environments (BYOC)](/en/ai-sre/environments) for how the environments themselves differ.

## Scope

MCP shares the same **two-level scope** model as other resources (Skills, Knowledge, Agents, Environments), divided into Shared scope and team scope:

| Scope | Visibility |
| --- | --- |
| Shared | Visible to all members of the account |
| Team-level | Visible only to members of that team |

**Edit permissions**: team-level MCP servers can be edited only by members of that team (organization admins must join the team first); Shared-scope servers only by account owners or admins.

**Create and reassign**:

- Creating a team-level server requires membership in that team; creating a Shared-scope server is limited to account owners or admins.
- Marketplace installs are always Shared scope and any member can install them. Exception: only account owners or admins can install templates that use member authorization and also take a free-form address. This keeps other members' credentials from going to an address the installer chose.
- Account owners or admins can move a server to any team (for taking over resources of empty teams or departed members). Regular members can move it only to teams they belong to.
- Marketplace-installed servers cannot be moved to a team; a few early team-level installs can be changed back to Shared scope by an account owner or admin.

**Runtime visibility**: at session start, the agent can use only Shared-scope MCP servers and those of the team bound to the session. Servers and Skills of another team are loaded on demand after the agent reads that team's knowledge. **The account is the only security boundary at runtime; teams only determine ownership and edit permissions.**
