> AI SRE must be activated in the console, is available on On-call Pro or higher, and is billed on actual usage. See [Activation and billing](/en/ai-sre/overview#activation-and-billing).

## Overview

A session is one complete conversation between you and AI SRE. It holds every message you send, the agent's streaming replies, tool calls made along the way, and any artifacts the agent produces (such as code, reports, charts, or Skill archives).

Each session is isolated, with its own context, bound team, and environment. You switch between sessions in the left sidebar, and exchange messages, read replies, and view artifacts in the central chat area. Switching sessions does not interrupt a running turn; when you come back, the streaming output is still there.

## Creating and Managing Sessions

Click **New Chat** in the left sidebar to start a session. The list is sorted by recent activity; click **Show more** for older sessions.

A new session shows four suggestion cards above the input: **Investigate an incident**, **Query data with natural language**, **Reduce alert noise** and **Schedule an automated inspection**. Clicking a card fills in a prompt you can edit before sending.

### Search and Filter

The search box filters by session name. Click the **Filter** icon at the top right of the list to combine these filters (a dot on the icon means filters are active):

| Filter | Options |
|---|---|
| Scope | All / Personal / Team (for Team, **My teams** or specific teams you belong to) |
| Source | All / Started by me / Selected members (hidden when Scope is Personal) |
| Status | Active (default) / Archived / All |
| Recent activity | All / 24 hours / 7 days / 30 days |

### Session Visibility and Permissions

Sessions are never accessible across accounts. Within an account:

| Session type | Can read / continue | Can rename, archive, delete or link to an incident |
|---|---|---|
| Personal session (no team) | Creator only | Creator only |
| Team session (bound to a team) | Members of the account who have the session link | Session creator, account Owner / admins, or team members |

Pinning affects only your own list. Account Owners and admins can manage team sessions but cannot read other members' personal sessions.

### Sharing a Session

If you can manage a session, click **Copy share link** in the chat header.

- Only members signed in to the **same account** can open the link; anonymous access is not supported. The link stays the same while sharing is on.
- People with the link see the whole session **read-only** (including subagent details) and cannot continue it; they can click **Fork into a new session** to continue in their own session.
- Click **Remove share** to invalidate the link immediately; sharing again creates a new link.
- Personal sessions are visible only to their creator by default, so a share link is how other members of the account can view one.

<Note>
Incognito sessions cannot be shared. Sharing is enabled on the root session only; subagent (Subagent / A2A) sessions cannot be shared on their own.
</Note>

### Per-Session Actions

| Action | Where | Notes |
|---|---|---|
| Pin / unpin | Hover over the session row | Pinned sessions stay at the top |
| Archive / unarchive | Hover over the session row | Find archived sessions by setting Status to **Archived** |
| Rename | Click the chat title | Up to 60 characters |
| Delete | Chat header (requires manage permission) | Cannot be undone; background tasks still running in the session are stopped |

A new session gets an automatic title after its first turn; you can rename it at any time.

### List Status Indicators

| Indicator | Meaning |
|---|---|
| Spinning circle | The agent is running |
| 🔭 + number | Number of background tasks running — see [Task Panel and Background Tasks](#task-panel-and-background-tasks) |
| Blue dot | New content you have not seen; cleared when you open the session |
| Relative time | Last activity (e.g. `5m`, `3h`) |

## Sending Messages and Streaming Responses

Type a message in the input and press Enter. The input supports Markdown; type `/` for the Skill and command menu. When a new console version is released, a notice above the input asks you to refresh.

### Attachments and Context References

<AccordionGroup>
  <Accordion title="Uploading attachments" icon="paperclip">
    Click the plus button at the bottom left of the input, or paste a screenshot.

    - **Supported types**: images, PDF, text / Markdown / CSV / HTML, Office documents, archives (`.zip` / `.rar`), and any UTF-8 text file (such as `.go`, `.py`, `.yaml`). Empty files are rejected.
    - **Size and count**: up to **50 MB** per file; up to **9 attachments** per message, **50 MB** in total.
    - **Folders**: choose **Upload folder** from the plus menu or drag a folder onto the input. A folder can hold up to **50 files** (`node_modules` and dot-files are not counted); a larger folder is rejected as a whole, and individual files that do not qualify are skipped with the reason listed. A folder counts as 1 attachment and keeps its directory structure.
    - **How the agent reads them**: attachments are provided as text; for text over 64 KB only the beginning is provided directly, and the agent reads the full file from the sandbox when needed. Archives and folders are not expanded up front; the agent unpacks and reads them in the sandbox as needed.
  </Accordion>
  <Accordion title="Context references" icon="link">
    When you open AI SRE from an incident, alert, alert rule, monitored object, data source or RUM issue (the **AI fix** button), that object is added to the input as a **reference capsule** and sent to the agent with your message. Click the capsule to open the object, or remove it before sending.

    These entry points usually pre-fill a question as well (for example, asking the agent to separate confirmed facts from inferences); edit it as you like before sending. No question is pre-filled when several references are brought in at once.

    In any session, type `@` to search incidents and insert a reference. Typing an email address does not trigger the search.
  </Accordion>
  <Accordion title="Knowledge and Skills" icon="book">
    When a session starts, knowledge and Skills for the bound team are loaded automatically; see <a href="/en/ai-sre/knowledge">Knowledge</a> and <a href="/en/ai-sre/skills">Skills</a>.
  </Accordion>
</AccordionGroup>

### Real-Time Streaming Output

The agent's reply streams in real time, including text, tool calls and reasoning. The run state is kept if you switch pages and come back.

<Note>
While a turn runs, the Send button becomes a **Stop** button. Stopping interrupts the turn immediately and marks it as interrupted.
</Note>

### Queueing Messages While Running

You can keep sending messages while a turn runs; they queue and run in order after the current turn. Queued messages appear above the input, where you can edit, remove or **Clear all** of them. Once the agent has started on a message it can no longer be withdrawn; use Stop to interrupt.

### Environment Initialization

The first time a session runs, an **environment initialization** card shows the sandbox being prepared and then collapses to one line:

| Message | Meaning |
|---|---|
| Session initialized | A new cloud sandbox was created |
| Session restored | The previous sandbox was reused; files are unchanged |
| Session rebuilt | The previous sandbox had been reclaimed, so a new one was created |

Sessions on a self-hosted [BYOC Runner](/en/ai-sre/environments#byoc-runner) show only the step of connecting to the runner.

<Warning>
When an idle sandbox is reclaimed, its files are reset. Keep anything you need by **saving it as an Artifact or to knowledge**. If initialization fails, click the card for details; starting a new session usually helps, or contact Flashduty support.
</Warning>

## Tool Calls and Artifacts

Tools the agent calls (reading and writing files, querying monitoring, running commands, MCP tools, and so on) are collapsed in the conversation by default; click to see input and output.

### Todo List

For tasks with three or more steps, the agent shows a progress badge (such as "Step X / N"); click it to see the task list with each step's status and priority. If the turn ends with a step unfinished, that step shows as paused and continues only after you send a new message.

Todo lists are available in console and IM sessions only, not in automation, API or subagent sessions.

### Agent Questions

When the agent needs clarification, it adds a question card — single choice, multiple choice or free text. You can use the keyboard (↑↓ to choose, Enter to confirm, Esc to skip); optional questions can be skipped with **✕**.

If you send a new message instead of answering, the question is treated as skipped and your message runs immediately. Answering a question that was already skipped or answered elsewhere sends your answer as a regular message.

### When Authorization Is Required

When a tool or MCP call needs a credential or OAuth authorization, an **"Authorize [resource name] to continue"** card appears:

- **Secret-based**: click the button, paste the API key or token and save; the task continues automatically.
- **OAuth-based**: click **Authorize**, complete the third-party authorization, then click **Continue task**. If the authorization link expires, start the task again.

<Note>
Only the console shows the authorization card. In IM and API sessions the agent posts the OAuth link; finish authorizing in a browser and reply that you have authorized. Secrets must be entered in **this same session in the web console** — **never** paste a secret into the chat. Automation sessions do not wait and list the missing authorization as a blocker. See [IM Platforms](/en/ai-sre/im#connections-and-authorization).
</Note>

### When a Connection Is Required

When you ask the agent to use a vendor that is in the plugin marketplace but not yet connected to your account (for example "connect Datadog for me"), a **"Connect [vendor] to continue"** card appears, so you do not have to look for it in the marketplace first.

1. Click **Connect** and fill in credentials and run the connection test in the dialog.
2. Once connected, the card shows **"[vendor] connected"**; click **Continue task** and the agent resumes the original task.

No card appears — the agent explains instead — when the vendor is already connected (it may need enabling or new credentials), only an Owner or admin can connect it, it needs a self-hosted runner and the session has none, or the marketplace has no connector for it.

<Note>
Only the console shows the connection card. In IM and API sessions the agent posts a link; connect and reply "continue". Automation sessions do not wait and list the missing connection as a blocker. See [IM Platforms](/en/ai-sre/im#connections-and-authorization).
</Note>

### Subagents

When the agent delegates work, a subagent line appears in the conversation with its type (Agent / A2A), name, execution environment, status and duration, and afterwards its tool calls, token usage and any failure reason. Click it to open the subagent session side by side; it can be expanded to full screen.

A subagent may also need you:

- **Awaiting authorization**: click **Authorize**, then **Continue task**; the subagent resumes the original task.
- **Awaiting input**: read and answer the subagent's question in the task panel.

Stop subagents from the task panel. A subagent whose executor was lost shows as **Failed**; one terminated by the platform shows as **Killed**.

### Task Panel and Background Tasks

Besides subagents, the agent can run long commands in the background (builds, bulk data pulls) or start monitors that watch a condition until it is met or a deadline passes.

Click the **Tasks** button in the chat header to see all tasks in the session, grouped as **Needs you / Running / Finished**. The number on the button counts tasks that need you or are running, and turns red when something needs you. You can also click the line in the conversation that started a task to open its details.

- **Subagent** details show the subagent's transcript.
- **Background command and monitor** details show status, run time, deadline, exit code, the full command and an event timeline.
- **Stop task** or **Stop Subagent** in the detail header stops only that task, not the main session.

Each time a monitor's condition fires, a 🔭 line appears in the conversation; click to expand the output. When a task ends, its final status and result summary are shown. A session with only monitors or background commands left counts as idle and shows 🔭 with the task count in the list.

### Artifacts Preview

Click a file the agent produced to preview it on the right:

| Type | Preview |
|---|---|
| Code | Syntax highlighting and line numbers |
| Markdown / HTML | Rendered view, with a **Source** toggle |
| Images, PDF | Shown directly |
| Skill package (`.skill`) | File tree and contents; download it or **Save Skill** to your account |

Previews support **Copy** and **Download**. All artifacts can also be managed on the **Artifacts** page in the left navigation — see <a href="/en/ai-sre/artifacts">Artifacts</a>.

### Status Page Update Drafts

The agent can **draft** an announcement for a public status page: a new incident or maintenance event, or an update to an existing one. Drafts are **never published automatically** — you review and publish them in the console, because publishing notifies subscribers immediately and cannot be undone.

The draft card shows exactly what would be published: title, status or schedule, the Markdown message, affected components and their status, and the target status page and event type. If the message uses formatting the status page does not support (such as headings, code blocks, quotes or images), the card lists it, because it would be lost on publishing.

Click **Review →** to open the status page publishing form in a new tab with the draft filled in. After publishing, the button becomes **Published** and links to the published event; if the draft has expired or is missing, ask the agent to draft it again.

<Note>
IM and API sessions show no card; the agent puts a "Review and publish" link at the **start of the reply** and summarizes the draft. If saving the draft failed, the agent summarizes it in text and asks you to check it in the console.
</Note>

### Message Actions

Hover over a message to:

| Action | Applies to | Notes |
|---|---|---|
| Copy | User messages / artifacts | Copy the content |
| Retry | User messages | Run a new turn with this message |
| Edit | User messages | Change and resend it — see below |
| Fork | Replies of completed turns | Start a new session from here to try another approach |

<Note>
Editing an earlier message **rewinds** the session: everything after it is replaced, and related background tasks and subagents are stopped. You cannot edit while that turn is still running or while the session is busy (for example, compacting); try again shortly.
</Note>

### Forking a session

After a turn completes, click **Fork** next to the reply, choose the new session's scope (personal or a team you can access) and runtime environment, and confirm to create and open it.

- The new session contains the conversation and tool calls up to that turn; from then on the two sessions are independent.
- If the source team or environment is not available to you, the new session uses personal scope or **Auto** instead.
- Completed or failed subagents are copied with their results; subagents still running at fork time show as interrupted and can be started again.
- You can fork only from completed turns of a main session, not from subagent sessions.

### Session Feedback

Use **Helpful** or **Not helpful** in the chat header to rate the whole session. With **Not helpful** you can pick reasons (wrong diagnosis / root cause, did not find the problem, unusable remediation, off-topic) and add a comment.

## Context Compaction

As a conversation grows, AI SRE automatically summarizes older history while keeping recent content and key conclusions, so the conversation carries on. Content folded out of context, such as Skills or MCP tool definitions, is reloaded by the agent when needed.

| Trigger | When |
|---|---|
| Automatic | When context usage passes the threshold (before or during a turn), or when the session reaches about **500 events** |
| Manual | Type `/compact` |

Progress is shown while compacting; afterwards the **Context** percentage in the chat header drops (hover for token usage). If compaction happens while usage is far below the threshold, the event limit was reached.

## Choosing a Runtime Environment

When creating a session, choose the **runtime environment** in the input area to decide where the agent's tools, Skills and MCP run:

| Option | Description |
|---|---|
| Auto (default) | The system picks an available environment, falling back to the cloud sandbox |
| Cloud environment | A Flashduty-hosted cloud sandbox (the default template or one you created) |
| BYOC Runner | An online self-hosted runner, so troubleshooting runs inside your network |

Offline runners cannot be selected, and if the selected runner goes offline you cannot send messages. The environment is fixed once the session is created; to change it, fork a new session (IM sessions can switch in place).

## Binding a Team

When creating a session you can **bind a team**; the session then loads that team's knowledge, Skills and MCP. Your choice is remembered. In a personal session without a team, the agent can load knowledge from your teams when needed; a team session uses only shared content and that team's content.

<Note>
Automatic team binding for incidents and war rooms is still being improved.
</Note>

## Session source

Each session records where it came from, which affects some behavior:

| Source | Notes |
|---|---|
| Console | Runtime environment and team are fixed at creation |
| IM platforms (Feishu / DingTalk / WeCom / Slack) | Switch environment and team in the conversation with `/env` and `/scope` |
| API | Programmatic integrations. When creating a session with `POST /safari/session/create` you can pass `entry_kind` (`web` / `im` / `api` / `automation`, default `web`); it cannot be changed later |
| Automation | Triggered by automation rules |

## Reply language

The **reply language** is set when the session is created and used for the whole session.

| Source | Reply language |
|---|---|
| Console | The console UI language at creation; changing the UI language later does not affect existing sessions |
| IM / API / Automation | The account's default notification language |

## Integrating sessions through the API

This section is for developers integrating AI SRE sessions through the [Open API](/en/api-reference/ai-sre/sessions/session-read-info).

### Withdrawing a queued message

The `pending_messages` field in the `POST /safari/session/get` response lists queued messages the agent has not read yet, in execution order. Before the agent reads one, its author can withdraw it with `POST /safari/session/message/cancel`, passing `session_id` and `invocation_id` (the invocation ID returned when the message was sent). The `result` field means:

| Result | Meaning |
|---|---|
| `removed` | Removed from the queue and will never run; clients receive a `user_message_cancelled` frame |
| `consumed` | The agent already read it, so withdrawing has no effect; use Stop to interrupt |
| `forbidden` | The caller is not the message author |

Only regular human messages can be withdrawn, not question answers or messages produced internally. The caller needs permission to chat in the session.

### Error markers in stream frames

Frames in the session stream may carry `is_error` and `error_code`, marking a runtime error the platform surfaces to the user. A frame without them may still contain diagnostics; they also differ from the `error` line that marks a broken export stream below.

### Session data export

`POST /safari/session/export` streams all events from a session as **NDJSON** (`application/x-ndjson`), one JSON object per line. This is intended for auditing, archiving, offline analysis, or feeding session data into external systems.

#### Request fields

| Field | Type | Required | Description |
|---|---|---|---|
| `session_id` | string | Yes | ID of the session to export |
| `include_subagents` | bool | No | When `true`, recursively includes the event streams of all subagent child sessions; defaults to `false` |

#### Response format

The response `Content-Type` is `application/x-ndjson`. The **first line is always** a `session_meta` envelope containing the session's metadata; subsequent lines are session events. When `include_subagents=true`, each `subagent_dispatch` line is immediately followed by the complete event stream of the child session, which also begins with its own `session_meta` line.

```
{"type":"session_meta","session_id":"s_...","app_name":"ai-sre","entry_kind":"web","started_at":"2026-09-08T08:00:00Z","ended_at":"2026-09-08T08:05:00Z"}   // first line: session metadata (has no seq)
{"type":"user_message","seq":1,"session_id":"s_...","content":"help me investigate this incident","ts":"2026-09-08T08:00:01Z"}   // user message
{"type":"tool_call","seq":2,"session_id":"s_...","name":"bash","input":{"command":"..."},"status":"ok","call_id":"call_abc","ts":"2026-09-08T08:00:02Z"}   // tool call (model request side)
{"type":"tool_call","seq":3,"session_id":"s_...","name":"bash","output":"...","output_bytes":123,"status":"ok","call_id":"call_abc","ts":"2026-09-08T08:00:03Z"}   // tool call (runtime response side)
{"type":"subagent_dispatch","seq":4,"session_id":"s_...","agent_name":"explore","call_id":"call_def","ts":"2026-09-08T08:00:04Z"}   // subagent dispatch
{"type":"session_meta","session_id":"sub-tsk_...","parent_session_id":"s_...","app_name":"ai-sre","entry_kind":"web"}   // child session metadata (inlined when include_subagents=true)
{"type":"user_message","seq":1,"session_id":"sub-tsk_...","content":"...","ts":"..."}   // child session events
{"type":"final_answer","seq":5,"session_id":"s_...","content":"...","usage":{"input_tokens":0,"output_tokens":0,"cache_read":0,"cache_creation":0},"ts":"2026-09-08T08:05:00Z"}   // turn-final answer
```

<AccordionGroup>
<Accordion title="Line types">

The export stream contains only the line types below (the `type` field); no other types occur:

| Line type | When it appears | Key fields |
|---|---|---|
| `session_meta` | **First line of every session** (both the main session and inlined child sessions) | `session_id`, `account_id`, `app_name`, `parent_session_id` (child sessions), `entry_kind` (`web` / `im` / `api` / `automation`; empty normalized to `web`), `started_at` / `ended_at` (session created / updated time) |
| `user_message` | User message events | `content` (extracted text: multiple text parts joined with `\n`; reasoning / thought parts skipped; user rows never carry `usage`) |
| `system_reminder` | User rows whose text starts with `<system-reminder>` | `content` (harness context injected by the system — locale / env / knowledge / memory / channel-guide / mount — not something you typed) |
| `tool_call` | Model tool request (`function_call` part) or runtime response (`function_response` part), **one line per part** | Request side: `name`, `input` (args object), `status` (optimistically `ok`), `call_id`; response side: `name`, `output` (response JSON serialized to a string), `output_bytes`, `status` (`ok` / `error`; a row-level error also carries `error`), `call_id` |
| `subagent_dispatch` | Model initiates an `agent_dispatch` call (one line per call) | `agent_name`, `call_id`; with `include_subagents=true` the child's full event stream is inlined right after this line |
| `final_answer` | Turn-complete assistant event (takes priority over `llm_call`) | `content`, `usage` |
| `llm_call` | Text-only model response that carries token usage | `content`, `usage`, `ended_at` |
| `agent_text` | Assistant prose with no usage and not turn-complete (fallback type) | `content` |
| `session_fork` | The "Forked from conversation" divider row | `content` |
| `error` | Appended at the end of the stream when an error occurs after streaming started, or inlined when a child session is unavailable under `include_subagents` | `content` (error text; consumers must inspect this line to tell whether the stream completed — see the Warning below) |

</Accordion>
<Accordion title="Fields and behavioral conventions">

- **`seq`**: a monotonic counter over **lines emitted**, starting at 1 (reset per child session; never reset across pages). When one DB event yields several lines (see below), the lines are numbered consecutively in part order. `session_meta` lines carry no `seq`.
- **`call_id` (the pairing key)**: the `function_call` / `function_response` id (both sides of a call share the same `id`). A single model response can bundle several tool calls into **one DB event** (e.g. 2 `agent_dispatch` calls + 1 `bash` call in the same event); the export emits one line per part, in the original part order, and `call_id` lets a consumer re-pair a response line with its call line without relying on emission order.
- **`usage` (token counts)**: per-event totals (`input_tokens` / `output_tokens` / `cache_read` / `cache_creation`), emitted as `0` rather than omitted when absent. It is **stamped on the first line of the event only** — the lines of a batched dispatch share one usage figure, so a consumer that sums per line is not over-counted N times.
- **No model identifier**: the export deliberately carries **no serving model identifier** — neither `session_meta` nor `llm_call` lines have a `model` field. The export is a customer-downloadable artifact, and the model identifier combined with the per-call token counts is enough to reconstruct the underlying usage cost, so neither the export nor the query APIs (including `/safari/session/get`) return it.
- **Timing**: `ts` is the event's write time (RFC 3339). `llm_call` and `tool_call` lines use it as an approximation of the **end time** (`ended_at`); start times and durations (`started_at` / `duration_ms`) are not provided (empty / 0).
- **`include_subagents=true`**: each `subagent_dispatch` line is immediately followed by the child session's complete export stream, recursively (every dispatch line of a batch is inlined, not just the first); the child's `seq` restarts at 1 and its `session_meta` carries `parent_session_id`. If a child session is missing or fails to export, the parent stream is not interrupted — an inlined `error` line is emitted and the stream continues.
- Some bookkeeping rows produce no export line (e.g. OAuth-authorized markers), so the line count can be lower than the session's event count.

</Accordion>
</AccordionGroup>

<Warning>
If an error occurs after streaming has already begun, the server cannot switch to a standard JSON error envelope. Instead, a JSON-encoded error object is appended as the final line of the stream. Consumers must inspect this last line to determine whether the stream completed successfully.
</Warning>

**Permissions**: the export endpoint uses the same access gate as sending messages, meaning the caller must have message-send permission on the session — read-only access is not sufficient. Personal sessions can be exported only by their creator; team sessions can be exported by same-account members who can access the session.
